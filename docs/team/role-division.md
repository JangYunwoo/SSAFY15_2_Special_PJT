# 백엔드 역할 분담

## 왜 도메인(기능)별로 나누는가

레이어별 분리(한 명은 컨트롤러만, 한 명은 서비스만, 한 명은 엔티티만)는 세 사람이 항상 같은
파일 근처에서 작업하게 되어 충돌이 잦다. 반대로 도메인(기능) 단위 수직 분리는 각자
컨트롤러→서비스→레포지토리→엔티티를 혼자 끝까지 소유하므로, 겹치는 파일이 거의 없다.
그래서 아래 분담은 결제수단이라는 축에 실제로 이어지는 기능(배송·반품·정산 등)을 함께
묶는 "기능별 수직 분리"를 따른다. 이 구조에서 완전한 독립 작업을 막는 진짜 의존성은
아래 "독립 작업을 막는 진짜 의존성 3가지"뿐이다.

## 원칙

1. **결제수단이 축, 그 결제수단과 실제로 얽히는 인접 도메인을 함께 묶는다.** 결제 승인 API 자체만 보면 카드(1개)·카카오페이(4개)·코인(4개) 엔드포인트 수가 작아 보이지만, 실제 업무량은 승인 이후의 배송·반품·정산·환불까지 이어진다. 그 이어지는 도메인을 결제수단과 무관하게 균등 배분하지 않고, 결제수단 담당자가 실제로 가장 자주 마주치는 흐름 쪽으로 붙였다.
2. **코인 담당은 결제 자체 난이도가 높다(온체인 트랜잭션 폴링, Quote/Buffer 환율 계산, 입금 매칭, 컨펌 대기).** 그래서 코인 담당에게는 결제 주변 업무를 최소로 묶고, 남는 업무는 카드·카카오페이 담당에게 분배했다. 세 사람 모두 "이번 프로젝트에서 내가 설계·구현했다"고 말할 수 있는 분량과 난이도를 갖도록 맞췄다.
3. **기준 문서 우선순위(API 명세서 > DB 스키마 > 요구사항 명세서)는 역할 분담과 무관하게 항상 적용한다.**

## 담당자별 도메인

| 담당자 | 결제수단 | 함께 담당하는 도메인 | `backend/.../domain` 패키지 | 관련 API ID | 엔드포인트 수(대략) |
| --- | --- | --- | --- | --- | --- |
| **카드 담당** | 카드결제 (`CARD-01`) | 계정/인증(공통 기반), 결제 공통 슬롯, 참여·구매확정·이의제기, 배송, 알림 | `account`, `payment.common`, `payment.card`, `participation`, `delivery`, `notification` | AUTH, USR, SEL, PAY, CARD, PAR, CFM, DLV, NOTI | 약 36개 |
| **카카오페이 담당** | 카카오페이 (`KAKA-01~04`) | 상품/카테고리/AI, 공동구매, 반품 | `product`, `groupbuy`, `payment.kakaopay`, `returns` | CAT, PRD, AI, WDR, GRP, KAKA, RTN | 약 35개 |
| **코인 담당** | 디지털 자산 결제+에스크로 (`CRYP-01~04`, `ESC-01~03`) | 환불, 정산, 판매자 제재, 관리자/정책 | `payment.crypto`, `escrow`, `refund`, `settlement`, `penalty`, `admin` | CRYP, ESC, RFD, STL, PEN, ADM | 약 31개 (단, 온체인 폴링·Quote 계산 등 개별 난이도가 가장 높음) |

엔드포인트 수는 `docs/api/공구한_API_명세서_v1.md`의 표 기준 개수다. ADMIN 전용 조회(`RTN-10/11`, `PEN-02~06`, `STL-03~07` 등)는 소속 도메인 패키지에 그대로 두고, `admin` 패키지는 정책(`platform_policies`)·감사로그(`audit_logs`) 같이 특정 도메인에 속하지 않는 기능만 담당한다.

## 독립 작업을 막는 진짜 의존성 3가지와 대응

| 의존성 | 왜 문제인가 | 대응 |
| --- | --- | --- |
| 계정/인증 | 인증이 필요한 모든 API(대부분)가 로그인 사용자를 전제로 함 | 카드 담당이 **최소 기능**(회원가입/로그인/JWT 발급·검증 필터)만 빠르게 만들어 가장 먼저 병합. 그 사이 다른 둘은 인증이 필요 없는 계층(엔티티, 레포지토리, 외부 API 클라이언트 PoC)부터 시작해 놀지 않는다. |
| 결제 전략 인터페이스 | `PaymentGateway`(prepare/approve/cancel 등) 시그니처가 안 맞으면 세 결제수단 구현이 서로 어긋난다 | 코드 작성 전에 30분~1시간 짧은 회의로 메서드 시그니처만 합의. 구현은 각자. |
| DB 스키마 | 이미 고정 소스(`V1__init_schema.sql`)라 걸림돌 아님 | 변경이 필요하면 임의 수정 금지, 합의 후 `V2__...` 마이그레이션 추가 |

## 로드맵

### 0단계 - 착수 준비 (다 같이, 반나절)
- Jira 이슈를 API ID 기준으로 생성한다(`AUTH-01`, `CARD-01`처럼 명세서 ID를 이슈 제목에 그대로 사용하면 추적이 쉽다).
- `PaymentGateway` 인터페이스 시그니처를 합의한다.
- 각자 담당 도메인의 엔티티-스키마 매핑을 리뷰한다(스키마는 고정이므로 매핑 오타·타입만 확인).

### 1단계 - 기반 다지기 (병렬 시작)
- **카드 담당**: `domain/account`(회원가입/로그인) + `global/security`(JWT 발급/검증 필터) 최소 구현 → 가장 먼저 PR, 최우선 리뷰·병합.
- **카카오 담당**: `domain/product`, `domain/groupbuy` 엔티티+레포지토리(인증 불필요 영역)부터 시작.
- **코인 담당**: MetaMask + Polygon Amoy 연동 스파이크(테스트넷 송금 1건 왕복 확인), `crypto_quotes` 환율·Buffer 계산 로직.

인증 PR이 병합되면 세 사람 모두 컨트롤러 계층에 인증을 붙여 이어간다.

### 2단계 - 결제 준비~승인
- 카드: `PAY-01~04`(결제 공통 슬롯) + `CARD-01`
- 카카오: `GRP-01~10`(공동구매 CRUD) + `KAKA-01~04`
- 코인: `CRYP-01~04` + 결제 승인 시 `escrows(HELD)` 생성

### 3단계 - 결제 이후 라이프사이클
- 카드: `PAR/CFM`(참여·구매확정·이의제기) + `DLV`(배송) + `NOTI`(알림)
- 카카오: `RTN-01~11`(반품)
- 코인: `RFD`(환불) + `STL`(정산) + `PEN`(제재)

### 4단계 - 관리자·통합·마감
- 코인: `ADM`(정책·감사로그·배치 재실행)
- 셋이 함께: 도메인 간 연동 지점(반품→환불, 위반 후보→제재, 구매확정→정산자격) 통합 테스트, 예외 케이스 점검, 데모 시나리오 리허설.

### 지금 당장 할 일
1. Jira 이슈 생성 (API ID 기준)
2. `PaymentGateway` 인터페이스 합의 미팅 (30분~1시간)
3. 카드 담당자, `domain/account` + `global/security` 브랜치 착수 (`feature/be/{ISSUE-KEY}-auth-signup-login`)
4. 카카오·코인 담당자는 3번을 기다리지 않고 각자 엔티티/레포지토리부터 착수

## 충돌을 줄이는 실무 규칙

- **패키지 소유권을 존중한다.** 다른 사람의 `domain/*` 패키지를 고쳐야 하면 먼저 논의하거나 이슈로 남긴다.
- **`global/*`(공통 응답 포맷, 예외 처리, 보안 설정)은 세 사람 모두의 코드다.** 구조를 바꾸는 PR은 리뷰 필수이며, 급하지 않으면 Phase 0 이후에는 최소한으로만 변경한다.
- **DB 스키마는 `backend/src/main/resources/db/migration/V1__init_schema.sql`이 고정 소스다.** 컬럼 추가/변경이 필요하면 스키마 담당(전체 합의) 없이 임의로 엔티티만 바꾸지 않는다 - `spring.jpa.hibernate.ddl-auto=validate`라서 엔티티와 실제 스키마가 어긋나면 애플리케이션이 아예 기동하지 않는다. 새 마이그레이션(`V2__...`)으로 추가한다.
- **브랜치명·커밋 컨벤션은 [../../GIT_CONVENTION.md](../../GIT_CONVENTION.md)를 따른다.** `feature/be/{ISSUE-KEY}-{설명}` 형태로 본인 도메인 접두어를 쓰면 리뷰어가 충돌 가능성을 한눈에 파악하기 쉽다 (예: `feature/be/B205-21-card-approve`).
