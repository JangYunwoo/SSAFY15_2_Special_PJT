# Jenkins CI/CD 구축 작업 내역 및 운영 가이드

작성일: 2026-09-23. 관련 이슈: **S15P21B205-234**.

이 문서는 팀원에게 무엇을 구축했고 왜 그렇게 구성했는지 설명하거나, 다음 운영자가 배포를 인수인계받을 때 사용한다. 최초 구축의 시행착오는 [기존 학습 기록](./jenkins-cicd-study.md)에 보존하고, 여기서는 현재 코드와 서버에서 확인한 최종 동작을 함께 정리한다.

코드 확인 기준은 원격 `DevelopV2`의 `81ae098673803073d3496c68945f8b742a0b5d58`이다. 서버 상태와 빌드 번호는 작성 시점의 관측이며 이후 커밋에 따라 바뀐다. 이번 문서 작성에서 서버 설정, 서비스, 운영 데이터, 예약 작업은 변경하지 않았다.

## 1. 팀원에게 먼저 설명할 내용

기존에는 사람이 EC2에 접속해 코드를 가져오고 Docker 이미지를 다시 빌드해 배포했다. 지금은 EC2의 Jenkins가 DevelopV2 변경을 감지하고, 프런트엔드·백엔드·AI 검증을 거친 커밋으로 이미지를 만든 뒤 서비스에 적용한다.

배포 전에 DB 백업과 마이그레이션 승인 여부를 확인하며, 적용 후에는 컨테이너와 공개 서비스 상태까지 확인한다. 실패한 후보를 적용한 경우에는 이전 애플리케이션 이미지로 복구를 시도하고, 실패한 배포를 성공으로 숨기지 않는다. 관리자 화면은 인터넷에 공개하지 않고 SSH 터널로 접속한다.

**“DevelopV2에 반영되면 자동으로 검사하고, 테스트와 배포 안전 조건을 모두 통과한 커밋만 배포한다”**가 정확한 설명이다. 모든 커밋이 무조건 배포된다는 의미는 아니다. DB 변경 승인 누락, 자격 증명 만료, 이미지 식별 불일치, 건강 상태 검사 실패 등이 있으면 배포가 차단된다.

### CI와 CD의 의미

- **CI(지속적 통합)**: 변경된 코드를 합쳤을 때 테스트·정적 검사·빌드가 정상인지 자동으로 확인한다.
- **CD(여기서는 자동 배포)**: 검증한 커밋의 이미지를 운영 서비스에 적용하고 정상 기동까지 확인한다.
- Jenkins 설치 성공, 테스트 성공, 실제 서비스 배포 성공은 서로 다른 단계다. 각각의 증거를 확인해야 한다.

## 2. 무엇을 바꿨고 무엇은 유지했는가

| 항목 | 구축 전 | 구축 후 |
|---|---|---|
| 변경 감지 | 사람이 변경을 확인 | Jenkins가 DevelopV2를 약 2분 간격으로 조회 |
| 검사 | 담당자가 개별 실행 | 파이프라인에서 정해진 검사 순서 실행 |
| 배포 버전 | 서버 체크아웃과 수동 빌드 상태에 의존 | 검사한 전체 커밋 SHA를 이미지 태그·라벨로 사용 |
| 배포 성공 판단 | 명령 종료나 화면 확인에 의존 | 컨테이너 health, Nginx 설정, 공개 HTTPS/health 확인 |
| 실패 복구 | 담당자의 수동 판단과 실행 | 후보 적용 실패 시 직전 실행 이미지 ID로 복구 시도 |
| 관리자 접근 | 신규 구축 | localhost 바인딩과 SSH 터널 |
| 운영 DB·환경변수·인증서 | 기존 서버에서 관리 | 기존 파일·볼륨을 보존하여 사용 |

기존 운영 체크아웃을 강제로 초기화하거나 팀원의 파일을 덮어쓰지 않았다. 배포 후보는 별도의 SHA별 릴리스 디렉터리에서 구성한다. DB를 초기화하거나 테스트 데이터를 운영 DB에 주입하는 파이프라인도 아니다.

## 3. 구성 요소와 선택 이유

| 구성 요소 | 역할 | 선택 이유와 제한 |
|---|---|---|
| Jenkins controller | 잡·자격 증명·실행 이력 관리 | 빌드 실행 슬롯은 0개로 설정 |
| Jenkins agent | 검사·이미지 빌드·배포 실행 | 실행 슬롯 1개로 같은 EC2의 과도한 동시 부하 제한 |
| Docker 테스트 컨테이너 | Node, Java, Python 실행 환경 | PC마다 다른 런타임에 덜 의존하도록 구성 |
| 테스트 전용 Redis·MinIO | 인프라 통합 테스트 | 운영 Redis와 S3 데이터를 사용하지 않음 |
| Docker Compose | 기존 서비스 교체 | 기존 `gongguhan-prod` 프로젝트·볼륨 유지 |
| GitLab Deploy Token | 저장소 읽기 | `read_repository` 범위의 전용 자격 증명 사용 |

Jenkins는 개인 PC가 아니라 EC2에 있으므로 PC를 꺼도 변경 감지와 배포가 진행된다. 단, EC2 장애 시 서비스와 빌드가 함께 영향을 받는다. 별도 빌드 서버를 둔 강한 자원 격리 구성은 아니다.

### 웹훅 대신 polling을 사용한 이유

관리자 화면을 공개하지 않는 요구에 맞춰 외부 웹훅 진입점을 추가하지 않고 Jenkins의 SCM polling을 사용했다. 서버 잡에 설정된 간격은 `H/2 * * * *`이다. 약 2분마다 변경 여부를 확인하되 변경이 없으면 빌드하지 않는다.

이 간격은 배포 완료 시간이 아니다. 변경 감지 대기, 기존 빌드 대기, 검사·빌드·배포 시간이 추가된다. 여러 커밋이 빠르게 들어오면 모든 중간 커밋을 각각 배포한다고 보장하지 않는다.

`disableConcurrentBuilds()`는 이전 실행을 강제 중단하지 않고 다음 실행을 대기시킨다. 배포 중 새 커밋이 들어왔다고 진행 중인 배포를 끊지 않기 위한 선택이다.

## 4. 커밋 하나가 배포되기까지

### 4.1 Checkout: 검사할 코드를 고정

Jenkins 전용 작업 공간만 정리하고 소스를 가져온다. `checkout scm`의 반환값에서 브랜치를 읽고, Git HEAD의 40자리 SHA를 `RELEASE_SHA`에 저장한다.

생산 잡은 `gongguhan-DevelopV2`, 체크아웃 브랜치는 `origin/DevelopV2`여야 한다. 값이 없거나 다른 브랜치면 실패시킨다. 검사 후 원격 최신 코드를 다시 가져와 배포하는 방식이 아니므로, 검사한 코드와 배포하는 코드가 달라지는 것을 방지한다.

### 4.2 Frontend test and build

Node 22 컨테이너에서 다음을 순서대로 실행한다.

1. `npm ci`: lock 파일 기준 의존성 설치.
2. `npm test`: 프런트 단위 테스트.
3. `npm run lint`: ESLint 검사.
4. `npm run build`: 프로젝트의 TypeScript 검사와 Vite 빌드.

하나라도 실패하면 다음 배포 단계로 진행하지 않는다.

### 4.3 Deployment guards

배포 도구 자체도 테스트한다. 정상 적용, 후보 실패 시 복구, 공개 health 실패 시 복구, 복구 실패의 오류 전파, SHA 형식, 이미지 태그, 마이그레이션 승인, 생산 잡·브랜치·SHA 일치 여부를 검사한다.

이 검사는 명령 실행을 모킹하는 Python 단위 테스트다. 운영 서버를 실제로 고장 내는 장애 주입 시험과는 다르다.

### 4.4 Backend regression

Java 21 컨테이너에서 Gradle 전체 테스트와 `bootJar`를 실행한다. 별도의 Redis와 MinIO를 임시로 띄워 Redis 경합과 S3 호환 저장소 통합 테스트도 수행한다.

Redis·MinIO는 공개 포트를 열지 않고 테스트 컨테이너끼리 네트워크를 공유한다. 데이터는 제한된 임시 메모리 파일시스템에 저장하고 해당 빌드 종료 시 정리한다. 운영 DB 접속 정보와 실제 금융망·카카오페이 비밀키를 테스트 컨테이너에 전달하지 않는다.

`verify-results.py`는 Redis 경합 2개와 S3 호환 저장소 1개가 누락·생략되지 않았는지 확인한다. 인프라가 없어서 테스트를 건너뛰었는데 전체 성공처럼 보이는 문제를 방지한다.

**MinIO 통과는 실제 AWS S3 IAM·버킷 정책 검증이 아니다.** 실제 금융 결제 승인·휴대전화 인증·외부 지갑 서명도 이 CI의 자동 검증 범위가 아니다.

### 4.5 AI regression

Python 3.12 기반 테스트 이미지에서 pytest를 실행한다. LightGBM에 필요한 `libgomp1`을 포함한다. AI 테스트 결과는 JUnit XML로 수집한다.

### 4.6 Build release images

동일 SHA로 backend, ai, nginx 이미지를 만든다. nginx 이미지에는 프런트 정적 빌드 결과가 포함된다.

- 태그: `gongguhan-ci/<서비스>:<40자리 SHA>`
- OCI 라벨: `org.opencontainers.image.revision=<같은 SHA>`

배포 도구는 이 라벨을 다시 검사한다. 단순히 `latest`라는 이름만 보고 배포하지 않는다. SHA 태그는 운영 관례상 고정해 사용하지만 기술적으로 태그 재할당이 불가능한 것은 아니므로, 롤백에는 직전 컨테이너의 실제 이미지 ID도 기록한다.

### 4.7 Deploy DevelopV2 및 결과 보관

생산 잡에서만 `deploy.py`를 호출한다. 임시 검증 잡은 검사·이미지 빌드까지만 수행한다. 백엔드와 AI의 JUnit 결과, 비밀값 없는 `deployment.json` 등을 보관한다. 실행이 실패해도 해당 실행 라벨의 테스트 컨테이너를 정리한다.

현재 저장소의 설정에는 문서 변경을 자동으로 건너뛰는 경로 필터가 없다. 문서만 수정한 커밋이라도 DevelopV2에 반영하면 전체 파이프라인 대상이 될 수 있다. 작업 브랜치에 푸시하는 것만으로 이 생산 잡이 배포하지는 않는다.

## 5. 배포 안전장치와 실패 복구

### 5.1 교체 전 확인

`deploy.py`는 다음 조건을 검사한다.

1. 생산 잡 이름, 브랜치, 작업 공간 HEAD가 전달된 SHA와 일치한다.
2. 다른 배포와 겹치지 않도록 배타적 파일 잠금을 확보한다.
3. 기존 배포 SHA에서 후보 SHA로 정방향 진행한다.
4. 변경된 DB 마이그레이션 파일이 정확한 내용으로 승인되어 있다.
5. 이미지 revision 라벨이 검증 대상 SHA와 일치한다.
6. 기존 운영 환경변수 파일이 있으며 Compose 설정이 유효하다.
7. 운영 MySQL 논리 백업이 성공한다.

이 중 실패가 있으면 배포가 차단된다. 앱 테스트 통과만으로 안전장치를 생략하지 않는다.

### 5.2 기존 데이터와 설정 보존

후보 코드는 `/opt/gongguhan-ci/releases/<SHA>`에 구성한다. 기존 `/home/ubuntu/S15P21B205/deploy/env`의 운영 환경변수 파일과 비밀 파일 디렉터리를 연결한다. MySQL·Redis·TLS 인증서 볼륨을 가진 기존 Compose 프로젝트 이름을 유지한다.

서버에 따로 있던 금융 테스트 콘솔 파일은 존재할 경우 읽기 전용 마운트로 보존한다. 이 파일의 내용이나 운영 비밀값을 Git에 추가하지 않는다.

DB 백업은 `/opt/gongguhan-ci/state/db-before-<SHA>.sql`에 권한 600으로 생성한다. Jenkins 공개 산출물로 올리지 않는다. 같은 서버 안의 백업이므로 서버 자체 손실까지 대비한 외부 백업은 아니다.

### 5.3 적용 후 성공 판정

backend와 ai를 먼저 교체해 healthy를 기다린다. 이후 nginx를 재생성하고 다음을 확인한다.

- backend와 ai 컨테이너의 health.
- Nginx 설정 문법.
- 공개 HTTPS 메인 페이지 응답.
- 공개 백엔드 health의 `UP` 상태.

모두 통과해야 `current.json`을 새 후보로 갱신하고 `deployment.json`에 `healthy`를 기록한다. health 통과는 실제 모든 사용자 시나리오의 성공을 의미하지는 않는다.

### 5.4 복구 범위와 한계

후보 서비스 적용 중 오류가 발생하면 직전 실행 이미지 ID로 애플리케이션 복구를 시도한다. 복구가 성공해도 해당 배포 잡은 실패로 남는다. 복구 자체가 실패해도 오류를 숨기지 않는다.

**DB dump는 자동 복원하지 않는다.** 배포 중 새 거래가 들어왔을 수 있어 자동 복원하면 데이터를 잃을 수 있기 때문이다. 따라서 DB 변경은 이전 코드와의 호환성까지 검토해야 한다.

단일 EC2에서 컨테이너를 교체하므로 짧은 응답 중단이 가능하다. 무중단 배포라고 설명하면 안 된다. 프로세스 강제 종료나 EC2 장애는 Python 예외로 처리하는 복구 범위와 다르므로 운영자가 직접 상태를 확인해야 한다.

## 6. DB 마이그레이션을 별도 승인하는 이유

최초 구축 시 운영 DB는 V22, 배포 후보는 V24였다. V23과 V24는 운영 스키마만 별도 MySQL 8에 복제해 DDL 적용을 검증했다. 운영 고객 행과 거래 데이터를 테스트 DB로 복사하지 않았다.

승인 파일 `/opt/gongguhan-ci/state/approved-migrations.json`에는 검토한 SQL의 정확한 SHA-256을 기록한다. 변경·추가·삭제된 마이그레이션이 승인과 맞지 않으면 자동 배포를 차단한다. Jenkins가 자신이 배포하려는 SQL을 자동 승인하지 않는다.

이 검증은 실제 MySQL DDL 호환성을 확인한 것이지 대량 운영 데이터의 락 시간·전체 금융 시나리오까지 검증한 것은 아니다. 이후 버전에는 해당 변경에 맞는 별도 검증과 승인이 필요하다.

## 7. 구축 과정에서 실제로 해결한 문제

### 7.1 전역 테스트 설정이 테스트의 전제를 바꿈

초기 CI에서 `APP_SCHEDULING_ENABLED=false`를 전역 주입해 “설정이 없을 때 스케줄러는 기본 활성화”라는 테스트가 실패했다. 테스트를 지우거나 성공 조건을 낮추지 않고 CI의 전역 강제 설정을 제거했다. 해당 실패 실행에서는 후속 검사와 배포가 차단됐다.

### 7.2 인프라 테스트가 생략됨

초기 실행에서 Redis 2개와 S3 호환 저장소 1개 검사가 skip됐다. 빌드 전용 Redis·MinIO를 추가하고 결과 XML을 검사하도록 해 해당 테스트의 누락·생략을 실패로 처리했다.

### 7.3 SQL 줄바꿈 차이로 승인 해시 불일치

Windows의 CRLF 파일과 Git/Jenkins의 LF 파일은 내용이 비슷해 보여도 바이트 해시가 달랐다. 해시 검사를 해제하지 않고, 실제 배포 후보 파일을 다시 검증해 승인했다. 이후 승인 대상은 개발자 PC 복사본이 아니라 배포할 Git 파일이어야 한다.

### 7.4 빌드는 성공인데 배포 단계가 생략됨

생산 잡 최초 실행에서 명시적 `checkout scm`의 반환값을 저장하지 않아 `GIT_BRANCH`가 비었다. 배포 단계의 조건이 false가 되면서 배포가 생략됐지만 전체 빌드는 녹색으로 끝났다.

해결은 브랜치 제한을 없애는 것이 아니었다. 체크아웃 결과에서 브랜치를 명시적으로 전달하고, 생산 잡의 브랜치가 잘못되거나 누락되면 즉시 실패시키도록 바꿨다. 배포 도구에서도 같은 조건을 다시 검사하며 회귀 테스트를 추가했다.

이 사례 때문에 **Jenkins SUCCESS만 보지 않고 deployment.json, current.json, 실행 이미지 revision까지 대조**하는 운영 기준을 사용한다.

## 9. 관리자 접속과 평소 운영 절차

### 9.1 SSH 터널로 접속

개인 PC에서 EC2 키 파일 경로를 자신의 경로로 바꿔 실행한다.

```sh
ssh -i "<EC2 개인키 파일 경로>" -N -L 8088:127.0.0.1:8088 ubuntu@j15b205.p.ssafy.io
```

터널을 유지한 상태에서 `http://localhost:8088`로 접속한다. EC2 보안 그룹에 8088을 공개할 필요가 없다. 관리자 자격 증명과 개인키는 메신저·문서·Git에 붙이지 않는다.

### 9.2 정상 배포 확인 순서

1. 변경을 검토한 뒤 DevelopV2에 반영한다.
2. Jenkins의 `gongguhan-DevelopV2` 잡에서 대상 커밋과 단계별 결과를 확인한다.
3. 테스트 성공뿐 아니라 배포 단계와 `deployment.json`의 SHA·상태를 확인한다.
4. 서버의 `current.json`과 실제 실행 이미지 revision이 맞는지 확인한다.
5. 변경한 사용자 기능을 별도로 점검한다. 자동 health 검사는 업무 시나리오 테스트를 대체하지 않는다.

서버의 옛 `/home/ubuntu/S15P21B205` 폴더 Git HEAD만 보고 현재 배포 버전을 판단하지 않는다. 실제 서비스는 `/opt/gongguhan-ci/releases/<SHA>`에서 실행될 수 있다.

### 9.3 실패 시 대응

| 증상 | 먼저 확인할 것 | 피해야 할 대응 |
|---|---|---|
| Checkout 실패 | Deploy Token 유효성, 저장소 접근, 브랜치 | 토큰 원문을 로그에 출력 |
| 테스트 실패 | 첫 실패 단계와 테스트 보고서 | 실패 검사를 삭제해 통과 처리 |
| 마이그레이션 승인 실패 | 후보 SQL과 승인 해시, 별도 MySQL 검증 | 승인 검사를 해제 |
| 후보 health 실패 | 후보 로그, 롤백 결과, current.json | DB dump를 즉시 자동 복원 |
| 동일 SHA 릴리스가 이미 존재 | 이전 실패 흔적과 실행 이미지 | 릴리스 폴더를 무조건 삭제·덮어쓰기 |
| 디스크 사용 증가 | 캐시·이미지·백업·릴리스별 사용량 | 전체 Docker 볼륨/이미지 일괄 삭제 |

운영 로그에는 민감정보가 포함될 수 있으므로 팀 공유 전에 비밀값과 개인정보를 제거한다.

## 10. 캐시 및 디스크 관리 후속 작업

Jenkins는 빌드 이력 15개, 산출물 최근 8개를 유지한다. 이것만으로 Docker 캐시·이미지·백업·릴리스 용량이 모두 제한되는 것은 아니다.

추가로 EC2에 **빌드 캐시 전용 정리 스크립트와 systemd timer**가 설치되어 있다. 2026-09-23 읽기 확인에서 timer는 active/enabled였다. 기존 서버 설정은 한국시간 매일 04:00이며, 놓친 실행은 `Persistent=true`에 따라 복구 후 수행할 수 있다. 이번 문서 작업에서 예약을 새로 만들거나 변경하지 않았다.

서버 작업 기록에 따른 정리 조건:

- 최근 168시간 사용하지 않은, 사용 중이 아니고 이미지와 공유하지 않는 BuildKit 캐시만 대상.
- 캐시 10GB는 정리 목표이며 전체 디스크의 강제 상한이 아님.
- 배포 잠금과 Jenkins 빌드·대기열 상태를 확인해 바쁘면 건너뜀.
- MySQL·Redis 데이터, 볼륨, 배포 이미지, 롤백 이미지, 환경변수, 인증서, DB 백업, 릴리스는 삭제하지 않음.
- 최초 실행 회수량은 0B. 이를 용량 절감 성과로 표현하지 않음.

서버 파일은 `/opt/gongguhan-ci/config/cache-maintenance.py`, `test_cache_maintenance.py`, `ec2-cache-maintenance-study.md`와 systemd 단위 파일이다. **이 후속 설정은 현재 저장소의 deploy/jenkins에 포함되지 않은 서버 측 구성**이므로 서버 재구축 시 별도 확보가 필요하다. 이 문서는 해당 구현을 새로 배포하거나 예약 점검 루프를 만드는 작업이 아니다. 과거 문서의 별도 앱 알림 설정은 이번 조사에서 활성 여부를 확인하지 않았다.

## 11. 권한·운영 한계와 다음 운영자가 챙길 것

- **Docker 소켓 권한:** agent는 호스트 Docker 소켓을 사용하므로 사실상 호스트 관리자 수준 접근이 가능하다. 신뢰되지 않은 외부 MR이나 임의 저장소 코드를 이 agent에서 실행하지 않는다.
- **Jenkins 사용자 권한:** 현재 부트스트랩은 로그인 사용자의 전체 제어 방식이다. 외부 공개 가입은 꺼져 있지만 세분화된 역할 기반 권한 체계는 아니다.
- **자격 증명 만료:** 초기 기록의 GitLab 읽기 토큰 만료일은 2026-10-22 09:00 KST다. 이번에는 GitLab에서 만료일을 재조회하지 않았으므로 갱신 여부를 관리자에게 확인하고 관리한다.
- **자원 경쟁:** controller/agent와 운영 서비스가 같은 EC2를 공유한다. 테스트 컨테이너 자원 제한과 실행 슬롯 제한은 있지만 이미지 빌드까지 완전한 격리를 보장하지 않는다.
- **복구 한계:** DB 자동 복원, 호스트 장애 자동 복구, 완전한 무중단 교체, 외부 백업 체계는 구현 범위가 아니다.
- **알림:** 기존 구축 기록상 별도 Slack·이메일 배포 실패 알림은 설정하지 않았다. 이번 문서 작업에서도 추가하지 않았다.
- **재구축:** 저장소 코드뿐 아니라 Jenkins 설정·자격 증명, 승인된 마이그레이션 목록, 운영 환경변수, 볼륨, 서버 전용 관리 설정이 필요하다. Git clone만으로 운영 환경이 완전히 복원되지는 않는다.
