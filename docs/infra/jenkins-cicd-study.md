## 1. 무엇이 불편했고 무엇을 자동화하는가

기존에는 담당자가 EC2에 접속해서 코드를 가져오고 컨테이너를 다시 빌드해야 했다. 사람이 기억한 브랜치, 서버의 Git HEAD, 실제 실행 중인 Docker 이미지가 같다고 보장할 수 없었다. 최초 조사에서도 서버 체크아웃은 `28701b1`이었지만 원격 DevelopV2는 더 앞서 있었다. 서버에는 수정된 환경변수 예제와 Git에 없는 금융 테스트 페이지도 있었다. 따라서 기존 폴더를 강제로 초기화하거나 그 자리에서 덮어쓰는 방식을 선택하지 않았다.

최종 목표는 DevelopV2 변경을 Jenkins가 감지하고, 프런트·백엔드·AI 검사에 모두 통과한 커밋의 이미지를 만들어 기존 EC2 서비스에 적용하는 것이다. 기능 구현용 임시 브랜치와 배포 기준 브랜치를 구분한다. `feature/be/S15P21B205-234-jenkins-cicd`는 이 설정을 검토하고 MR로 제출하는 장소이며, 자동 배포 대상은 DevelopV2뿐이다. DevelopV1에는 반영하지 않는다.

## 2. 구성과 선택 기준

EC2에 Jenkins 컨트롤러와 실행 에이전트를 별도 컨테이너로 설치한다. 컨트롤러는 실행 슬롯이 0개여서 프로젝트 빌드를 직접 하지 않는다. 에이전트 실행 슬롯은 1개이다. 기존 서비스와 빌드가 같은 EC2 자원을 사용하므로 여러 대형 빌드를 동시에 실행하지 않기 위해서다.

컨트롤러는 `127.0.0.1:8088`에만 바인딩한다. EC2의 8088 포트를 인터넷에 개방하지 않는다. 에이전트는 내부 네트워크의 WebSocket으로 접속하므로 별도의 공개 에이전트 포트도 필요 없다. 익명 사용자는 Jenkins 내용을 읽을 수 없고 공개 회원가입도 비활성화한다.

GitLab 웹훅은 Jenkins에 도달하는 외부 진입점을 추가로 설계해야 한다. 이번에는 관리자 화면 비공개 요구와 구성을 단순하게 유지하기 위해 Jenkins의 SCM polling을 선택했다. 생산 잡의 `H/2 * * * *`는 약 2분마다 변경 여부를 확인하며, 변경이 없으면 빌드하지 않는다. 웹훅처럼 즉시 시작한다고 보장하지 않으며, 앞선 빌드가 진행 중이면 대기할 수 있다. 이 일정은 개인 PC나 대화창의 반복 작업이 아니라 EC2 Jenkins 자체 기능이다.

공식 동작 근거: [Jenkins Pipeline syntax](https://www.jenkins.io/doc/book/pipeline/syntax/). 동시 실행 금지는 이전 배포를 강제로 중단하는 방식이 아니라 다음 빌드를 대기시키는 방식으로 사용한다.

## 3. 권한과 비밀값을 어떻게 다루는가

GitLab에는 이 프로젝트의 `read_repository`만 가진 Jenkins 전용 Deploy Token을 발급했다. 개인 계정의 광범위한 인증값은 EC2로 복사하지 않았다. Jenkins 자격 증명 ID는 `gongguhan-gitlab-read`이며, 토큰 원문은 소스·빌드 산출물·이 문서에 넣지 않는다. 최초 토큰 만료는 **2026-10-22 09:00 KST**이다. 만료 전에 프로젝트 Deploy Token을 새로 발급하고 같은 Jenkins 자격 증명 항목을 갱신해야 한다. 이를 방치하면 소스 체크아웃 단계가 실패하고 새 배포는 되지 않는다.

Jenkins 초기 관리자 이름은 `taemin-admin`이다. 무작위 초기 비밀번호는 EC2의 `/opt/gongguhan-ci/secrets/admin-password`에 권한 600으로 보관한다. 부트스트랩은 1회만 실행되어 재시작할 때 관리자가 변경한 비밀번호를 덮어쓰지 않는다. 초기 비밀번호를 변경한 뒤에는 초기 파일의 값이 현재 로그인 비밀번호라고 가정하면 안 된다.

**중요한 보안 한계:** 실행 에이전트는 현재 EC2의 Docker 소켓을 사용한다. Docker 소켓 접근은 사실상 호스트 관리자 수준의 권한이다. 컨테이너 안의 일반 사용자로 실행한다고 이 권한이 사라지지 않는다. 따라서 이 에이전트에서 외부인의 MR, 임의 저장소, 검토하지 않은 코드를 실행하면 안 된다. DevelopV2 변경 승인 권한과 Jenkins 관리 권한을 신뢰할 수 있는 팀원에게만 줘야 한다. 별도 빌드 서버와 제한된 배포 인터페이스는 향후 더 강한 격리가 필요할 때의 개선 방향이다. 이번 구성을 강한 다중 사용자 보안 격리라고 설명하지 않는다. [Docker 공식 권한 안내](https://docs.docker.com/engine/install/linux-postinstall/)

운영 환경변수와 GCP 키는 기존 `/home/ubuntu/S15P21B205/deploy` 아래 파일을 그대로 참조한다. 테스트 컨테이너에는 운영 환경변수를 전달하지 않는다. 다만 신뢰된 에이전트 자체는 배포를 위해 해당 파일과 Docker에 접근할 수 있으므로, 에이전트가 탈취되어도 운영 비밀이 안전하다는 의미는 아니다.

## 4. 한 번의 빌드가 지나가는 경로

1. 전용 Jenkins 작업 공간을 정리하고 대상 브랜치의 소스를 가져온다. 이때 테스트할 40자리 커밋 SHA를 고정한다. 기존 운영 체크아웃이나 개발자의 로컬 수정 파일을 정리하지 않는다.
2. Node 컨테이너에서 `npm ci`, 프런트 단위 테스트, ESLint, TypeScript 검사 및 Vite 빌드를 실행한다. 어느 하나라도 실패하면 후속 배포 단계로 가지 않는다.
3. 배포 스크립트의 방어 규칙과 실패 복구 흐름을 Python 단위 테스트로 검사한다.
4. Java 21 컨테이너에서 백엔드 전체 Gradle 테스트와 bootJar를 실행한다. 전체 회귀용 기존 메모리 설정을 재사용한다. 운영 DB가 아니라 저장소의 테스트 설정을 사용하며 실제 결제 승인을 자동으로 수행하는 단계는 아니다.
5. 별도 Python 테스트 이미지에서 AI pytest를 실행하고 JUnit XML을 보관한다. LightGBM 실행에 필요한 libgomp도 포함한다.
6. 같은 SHA로 backend, ai, nginx 이미지를 만든다. 각 이미지의 태그와 OCI revision label에 SHA를 넣는다. `latest`라는 이름만 보고 배포하지 않는다.
7. 잡 이름이 `gongguhan-DevelopV2`이고 체크아웃 브랜치가 `origin/DevelopV2`일 때만 배포 스크립트를 호출한다. 임시 검증 잡은 테스트·이미지 빌드까지만 수행한다.
8. 테스트 결과 XML과 비밀값이 없는 배포 결과 JSON을 보관한다. 빌드가 중단돼도 해당 빌드 전용 라벨의 테스트 컨테이너만 정리한다. 전체 Docker prune이나 운영 볼륨 삭제는 하지 않는다.

컨트롤러는 1 CPU/2 GB, 에이전트 자체는 1 CPU/1 GB 한도이다. 프런트·AI 테스트 컨테이너는 각각 2 CPU/3 GB, 백엔드는 2 CPU/6 GB 한도를 두었다. 이 수치는 애플리케이션 응답속도 최적화 성과가 아니라 같은 서버의 자원 경쟁을 제한하기 위한 운영 설정이다. Docker 이미지 빌드 단계까지 완전한 자원 격리를 보장하지는 않는다.

## 5. 배포와 실패 시 복구

`deploy.py`는 배포 잠금을 획득하고 현재 배포에서 후보 커밋으로 정방향 진행하는지 확인한다. 검사한 소스의 HEAD와 전달받은 SHA, 생성된 이미지의 revision label도 비교한다. 다른 커밋을 검사하고 더 최신의 미검증 커밋을 배포하는 문제를 막기 위한 절차다.

배포 파일은 `/opt/gongguhan-ci/releases/<SHA>`에 Git archive로 만든다. 환경변수는 기존 운영 파일로 연결한다. 기존 MySQL·Redis·인증서 볼륨을 사용하는 Compose 프로젝트 이름 `gongguhan-prod`도 유지한다. 서버 체크아웃에 있던 `bank-console.html`은 기존 파일을 읽기 전용으로 마운트해 보존한다. 이 파일은 이번 CI 소스에 새로 넣거나 내용을 수집하지 않았다.

서비스 교체 전 MySQL의 일관된 논리 백업을 `/opt/gongguhan-ci/state/db-before-<SHA>.sql`에 만든다. 파일은 600 권한이며 Jenkins 공개 산출물로 올리지 않는다. 백업 실패 시 서비스를 교체하지 않는다. 서버 안의 백업이므로 서버 자체 장애를 대비한 외부 백업은 별도 과제다.

backend와 ai를 먼저 교체하고 건강 상태를 기다린다. 그 후 Nginx를 재생성하여 변경된 컨테이너 주소를 다시 해석하게 한다. Nginx 설정 검사, 공개 HTTPS 메인 페이지 응답, 공개 백엔드 health의 UP 상태까지 확인한 뒤에만 `current.json`을 갱신한다.

후보 실행이 실패하면 배포 직전에 실제 실행되던 이미지 ID로 복구한다. 변경 가능한 이전 태그만 기억하면 팀원이 같은 태그를 다시 빌드했을 때 다른 이미지로 복구할 수 있으므로 실제 이미지 ID를 기록한다. 복구가 성공해도 원래 배포 잡은 실패로 남는다. 복구 자체가 실패해도 성공으로 처리하지 않는다.

**DB는 자동 복구하지 않는다.** 새 서비스가 실행되는 동안 추가 거래가 발생할 수 있어 과거 dump를 자동 복원하면 거래를 잃을 수 있기 때문이다. 이번 V23·V24처럼 이전 코드와 호환되는 변경이어야 이미지 롤백이 안전하다. 단일 인스턴스 교체 방식이므로 짧은 응답 중단이 가능하며 무중단 배포라고 주장하지 않는다.

## 6. V24 기준과 다음 DB 변경의 처리

최초 운영 DB의 Flyway 적용 버전은 V22였다. 최신 코드에는 V23의 `payments.reconcile_state`와 V24의 `refunds.payment_id`, 외래키, 유일키가 추가되어 있다. 두 변경은 nullable 열을 추가하고 기존 열을 제거하지 않는 형태라 이전 코드와 공존 가능하다고 검토했다.

검증에서는 운영 DB에서 **스키마만** 읽어 별도 MySQL 8 컨테이너로 복제했다. 고객 행이나 거래 데이터를 복사하지 않았다. 여기에 V23, V24 SQL을 순서대로 적용하고 새 열을 조회했다. 이는 실제 MySQL DDL 호환성 검증이지, 운영 데이터 규모의 락 시간 측정이나 Flyway 이력 전체 재현, 실제 금융 거래 검증은 아니다.

검토를 마친 정확한 SQL 내용의 SHA-256을 `/opt/gongguhan-ci/state/approved-migrations.json`에 기록한다. 이후 배포 후보에서 마이그레이션이 추가·수정·삭제되면 정확히 승인된 내용인지 검사한다. V25가 새로 생기거나 V24를 다시 편집하면 자동 배포는 멈춘다. 테스트를 통과했다는 이유만으로 DB 변경을 무조건 실행하지 않기 위해서다. 이 승인은 Jenkins 파이프라인에서 자동 생성하지 않는다.

`validate-migrations.py`는 이번 V23·V24용 일회성 검증 도구다. V24가 이미 적용된 DB 스키마에 같은 파일을 재적용하는 도구가 아니며, 향후 버전에는 이전 스키마와 새 변경에 맞춘 검증 계획이 필요하다. 검증용 컨테이너와 내부 네트워크만 종료·삭제했고 운영 컨테이너 및 볼륨은 삭제하지 않았다.

## 7. 운영자가 확인하는 방법

개인 PC에서 다음 SSH 터널을 유지한 뒤 `http://localhost:8088`에 접속한다. 별도로 EC2 보안 그룹의 8088을 열지 않는다.

```powershell
ssh -i "C:\Users\SSAFY\Downloads\J15B205T.pem" -N -L 8088:127.0.0.1:8088 ubuntu@j15b205.p.ssafy.io
```

Jenkins의 `gongguhan-DevelopV2` 잡에서 마지막 빌드의 결과, 커밋, 실패 단계, 테스트 보고서를 본다. 서버에서는 `/opt/gongguhan-ci/state/current.json`의 SHA와 실행 중인 이미지 정보를 비교한다. 기존 `/home/ubuntu/S15P21B205` 폴더의 Git HEAD는 새 릴리스 배포 후에도 그대로일 수 있다. 이것만 보고 배포가 옛날 상태라고 판단하면 안 된다.

이미지 교체 후 실패한 후보의 릴리스 폴더는 증거 보존을 위해 남긴다. 같은 SHA를 재시도하면 이를 감지해 자동으로 덮어쓰지 않는다. 운영자는 Jenkins 로그, 기존 `current.json`, 실패 폴더의 `rollback-images.json`, 컨테이너 건강 상태를 확인한 뒤 복구·재시도 방식을 결정해야 한다. DB dump를 무심코 복원하거나 전체 volumes를 삭제하면 안 된다.

빌드 이력은 15개, 산출물은 최근 8개까지만 유지한다. 그러나 Docker 이미지·릴리스·DB 백업은 자동 삭제하지 않는다. 디스크 용량을 주기적으로 확인하고 현재/이전 복구 이미지를 보호하는 보존 정책을 별도로 수립해야 한다. 디스크 자동 정리는 이번 범위에 넣지 않았다.

자동 배포 실패는 Jenkins의 실패 상태와 로그로 확인한다. 별도 Slack·이메일 통지는 설정하지 않았다. 실행 프로세스 강제 종료나 호스트 장애는 Python 예외 기반 롤백과 다르므로, 이 경우 운영자가 실제 컨테이너와 배포 상태를 비교해 복구해야 한다. 임시 검증 잡은 생산 잡 활성화 시 비활성화한다. 삭제된 작업 브랜치로 다시 배포하거나 검증하지 않도록 하기 위해서다.

## 8. 파일을 읽는 순서와 검증 기록

학습 순서는 `Jenkinsfile` → `deploy/jenkins/ci.sh` → `deploy.py` → `test_deploy.py` → `compose.yml` → `bootstrap.groovy`이다. `enable-production.groovy`는 검증 잡 성공과 MR 병합을 확인한 뒤 관리자가 생산 잡을 활성화할 때 사용한다. 설치 스크립트의 1회 초기화와 매 커밋마다 실행하는 파이프라인을 혼동하지 않는다.

확인된 중간 결과:

- 최신 원격 DevelopV2: `a6cf353`, 마이그레이션 최대 V24.
- 프런트 테스트: 24개 파일, 177개 통과. ESLint·TypeScript/Vite 빌드 통과.
- 배포 스크립트 단위 테스트: 정상 적용, 백엔드 실패, 공개 health 실패, 복구 실패, SHA 형식, 이미지 식별, 마이그레이션 내용 승인 등 7개 로컬 통과.
- V23·V24: 운영 스키마만 복제한 MySQL 8에서 적용 성공. 운영 DB 변경 없이 검증.
- Jenkins 검증 1번 빌드: 소스 브랜치를 원격에 올리기 전에 실행해 체크아웃 실패. 이를 애플리케이션 테스트 실패나 통과로 집계하지 않는다.
- 검증 2번 빌드: 백엔드 918개 중 1개 실패, 3개 건너뜀. CI에서 전역으로 넣은 `APP_SCHEDULING_ENABLED=false`가 “설정하지 않았을 때 스케줄러가 기본 활성화된다”는 테스트의 조건을 바꾼 것이 원인이다. 테스트를 삭제하거나 성공 조건을 약화하지 않고 CI의 전역 강제값을 제거했다. 테스트별 명시 설정과 운영 비밀값 미주입은 유지한다. 이 실패 때 AI 검사와 배포가 실제로 차단됐다.
- 전체 회귀 및 실제 배포 결과는 진행 중이며 완료 시 별도 실행 기록으로 추가한다. 앞의 중간 결과만으로 자동 배포가 완성됐다고 판단하지 않는다.

추가 보강: 최초 생략된 3개는 실제 Redis 경합 2개와 MinIO 저장소 1개였다. 최종 CI는 빌드 전용 Redis와 MinIO를 일시적으로 기동한다. localhost를 사용하는 기존 테스트를 수정하지 않도록 Java 테스트 컨테이너와 네트워크 네임스페이스를 공유하되, 포트를 공개하거나 운영 Redis·S3·볼륨을 사용하지 않는다. MinIO는 저장소의 기존 로컬 환경과 같은 고정 이미지와 가짜 자격 증명을 사용하고 메모리 파일시스템에만 저장한다. 테스트 종료 후 전용 컨테이너만 정리하며 이 세 검사가 skip되면 CI를 실패시킨다. MinIO 성공을 AWS IAM·실제 S3 버킷 정책의 검증으로 확대 해석하지 않는다.

검증 4번 빌드는 SUCCESS(479.862초)였다. 프런트 177개, 백엔드 918개, AI 17개, 배포 방어 7개가 통과했다. Jenkins JUnit으로 수집한 백엔드+AI 935개는 실패와 생략 모두 0이었다. 이 실행 시간은 CI 전체 소요시간이지 서비스 처리속도 개선 수치가 아니다.

배포 직전 해시를 대조하니 Windows 작업 파일은 CRLF, Git/Jenkins 파일은 LF여서 서로 SHA-256이 달랐다. SQL 의미가 같더라도 실제 승인 대상은 배포할 파일이어야 하므로, 해시 검사를 제거하거나 줄바꿈을 무시하도록 바꾸지 않았다. Jenkins 체크아웃의 정확한 V23·V24 파일을 별도 MySQL에서 다시 검증해 승인하며 최초 CRLF 검증 기록도 서버에 별도로 보존했다. 이후 같은 절차를 재실행할 때는 Windows 복사본 대신 배포 후보 Git 파일을 사용해야 한다.

최신 `7a71e19`를 합친 `27d301c`의 검증 5번 실행에서는 백엔드 923개(새 정산 보호 5개 추가), AI 17개가 실패·생략 없이 통과했다. 프런트 177개와 배포 방어 7개도 통과했다. 총 1,124개이며, 별도 MySQL DDL 검증은 이 단위·통합 테스트 개수에 억지로 합산하지 않았다. MR 제출 전 추가되는 기록 문서와 관리용 잡 활성화 스크립트는 별도 검토하고, 실제 운영 배포에서는 병합된 SHA 전체를 다시 테스트한다.

## 9. 최초 자동 실행에서 발견한 배포 생략 문제

MR !196 병합 뒤 생산 잡 #1은 SCM 변경을 자동 감지해 `8e8f809`를 검사했고 애플리케이션 테스트·이미지 빌드가 모두 성공했다. 그러나 배포는 완료되지 않았다. 명시적인 `checkout scm`의 반환값을 저장하지 않아, `skipDefaultCheckout`을 사용하는 파이프라인에서 `env.GIT_BRANCH`가 비어 있었다. 관리자 읽기 점검에서도 잡 이름은 생산 잡이었지만 GIT_BRANCH가 null이고 RELEASE_SHA만 존재하는 것을 확인했다.

이 때문에 `when`에 넣어 둔 브랜치 조건이 false가 되어 배포가 생략됐고 전체 잡은 녹색으로 끝났다. 이는 운영에서는 실패로 보여야 할 상태를 성공으로 오인하게 만드는 CI 버그다. 아직 서비스가 교체되지 않았으므로 이 실행을 배포 성공으로 기록하지 않았다.

수정은 checkout의 반환 맵에서 GIT_BRANCH를 명시적으로 전달하고, 생산 잡의 체크아웃이 정확히 origin/DevelopV2가 아니면 즉시 실패시키는 것이다. 배포 단계의 when은 검증 잡을 제외하는 용도로만 사용한다. 실제 배포 스크립트의 잡 이름·브랜치·SHA 방어 조건은 그대로 유지하고 순수 함수로 분리해 누락된 브랜치, DevelopV1, 검증 잡, 다른 SHA를 모두 거부하는 회귀 검사를 추가했다. 브랜치 제한을 없애서 억지로 배포하는 해결책은 선택하지 않았다.
