# 공구한 서버 아키텍처 설계서 (EC2 배포)

> 대상 서버: `j15b205.p.ssafy.io` (SSAFY 제공 AWS EC2, 단일 인스턴스)
> 작성일: 2026-09-18 · 브랜치: `feature/infra/ec2-deployment`
> 이 문서는 **왜 이렇게 배포하는가**를 팀이 공부할 수 있게 기본 개념부터 판단 근거까지 담았습니다.
> 실제 실행 절차만 필요하면 [`../../deploy/README.md`](../../deploy/README.md) 를 보세요.

## 1. 문서의 목적

우리는 지금까지 각자 노트북(localhost)에서 백엔드·프론트·AI를 따로 띄워 개발했습니다.
이제 **하나의 EC2 서버에 전체를 올려서, 팀·평가자가 인터넷 주소로 접속해 테스트**할 수 있어야 합니다.

이 문서는 다음을 설명합니다.
- 우리가 실제로 배포해야 하는 것이 무엇인지 (코드 기준 사실 확인)
- 배포에 필요한 기본 개념 (리버스 프록시, 컨테이너, 오리진, TLS, 방화벽 계층)
- 어떤 구조로 배치했고 **각 결정을 왜 그렇게 내렸는지** (대안과 함께)
- 방화벽·보안·CI/CD·테스트를 어떻게 다루는지

## 2. 무엇을 배포하는가 — 코드 기준 사실 정리

리포지토리를 실제로 조사한 결과, 배포 대상은 **애플리케이션 프로세스 3개 + 인프라 2개**입니다.

| # | 구성요소 | 정체 | 기술 | 내부 포트 | 바깥 의존성 |
|---|---|---|---|---|---|
| 1 | **백엔드** | 단일 Spring Boot 모놀리스 (`com.gongguhan`) | Spring Boot 4.1.1 / Java 21 | 8080, context-path `/api/v1` | MySQL, Redis, AWS S3, SSAFY 금융망, 카카오페이, Polygon Amoy RPC, Upbit 시세 |
| 2 | **프론트엔드** | React SPA (정적 번들) | Vite 8 + React 19 + TS | 정적 파일 | 백엔드 `/api` (상대경로) |
| 3 | **AI 서비스** | 상품 이미지 분석 API | Python FastAPI (uvicorn) | 8000 | Google Vertex AI(Gemini) |
| — | MySQL | 관계형 DB | mysql:8.0 | 3306 | — |
| — | Redis | 캐시·슬롯 게이트·토큰 denylist | redis:7 | 6379 | — |

### 자주 오해하는 두 가지 (직접 확인함)

- **"코인은 별도 지갑 서버가 필요하다"** → 아닙니다.
  코인 결제는 백엔드 안의 한 패키지(`domain/payment/crypto`)이고, `web3j` 로 Polygon Amoy 테스트넷 RPC를
  **읽기만** 합니다(입금 트랜잭션 검증·컨펌 수 확인). `crypto_wallets` 는 **수신 전용 주소만** 저장하고
  **개인키를 서버에 두지 않으며 서버가 서명하지도 않습니다.** 따라서 별도 프로세스도, 지갑 서명 서버도 필요 없습니다.
  (코인 *환불 송금*은 아직 미구현 과제 `S15P21B205-80` 입니다. 이게 구현되면 그때 "핫월렛 개인키"라는
  민감 비밀이 처음 생기며, 그건 5.7절에서 별도로 다룹니다.)
- **AI는 왜 별도 프로세스인가** → 파이썬(FastAPI)이고 Gemini SDK를 쓰므로 Java 백엔드에 합칠 수 없습니다.
  백엔드는 상품 등록 시 `AI_EXTRACTION_BASE_URL` 로 AI 서비스를 **HTTP 호출**합니다(코드로 확인:
  `application.yml` 의 `app.ai-extraction.base-url`). 그래서 AI는 독립 컨테이너로 띄웁니다.

> 결론: **쪼갤 것은 이미 쪼개져 있고(파이썬 AI), 합쳐도 되는 것은 합쳐져 있습니다(코인=백엔드 패키지).**
> 우리는 새 서버를 늘리지 않고, 있는 3개 프로세스를 한 EC2에 잘 배치하기만 하면 됩니다.

## 3. 먼저 알아야 할 기본 개념

배포 설계를 이해하려면 아래 5개 개념이면 충분합니다.

1. **컨테이너 / 이미지 (Docker)**
   - *이미지* = 실행에 필요한 모든 것(런타임+코드)을 담은 스냅샷. *컨테이너* = 이미지를 실행한 인스턴스.
   - 왜 쓰나: "내 노트북에선 되는데 서버에선 안 돼"를 없앤다. 자바 21, 파이썬 3.12, Node 22를 서버에 일일이
     설치·버전 관리하지 않고, 이미지 안에 고정해서 가져간다.

2. **리버스 프록시 (Nginx)**
   - 클라이언트의 요청을 대신 받아 뒤쪽 서버로 넘겨주는 문지기.
   - 왜 쓰나: ① HTTPS(암호화)를 여기서 한 번에 처리(TLS 종료) ② 정적 파일(SPA)은 직접 주고,
     `/api` 요청만 백엔드로 넘김 ③ 내부 서버들을 인터넷에 직접 노출하지 않게 함.

3. **오리진(Origin)과 CORS**
   - 오리진 = `scheme + host + port` (예: `https://j15b205.p.ssafy.io`).
   - 브라우저는 "다른 오리진"으로의 요청을 기본 차단하고, 서버가 CORS 헤더로 허용해야 통과시킨다.
   - 핵심: **프론트와 API를 같은 오리진으로 서빙하면 CORS 자체가 필요 없어진다.** (5.6절에서 이 이점을 활용)

4. **TLS/HTTPS 와 인증서**
   - HTTPS = 통신 암호화 + 서버 신원 증명. 이를 위해 도메인 소유를 증명한 **인증서**가 필요.
   - Let's Encrypt(certbot)로 무료 발급하며, 발급 시 "이 도메인이 이 서버를 가리킨다"를 HTTP-01 챌린지로 증명.

5. **방화벽의 두 계층**
   - **클라우드 보안그룹(SG)**: AWS 레벨. SSAFY가 22/80/443/tcp1024~65535/udp1024~65535 를 이미 열어둠(넓음).
   - **호스트 방화벽(UFW)**: 우분투 안. SG가 넓게 열려 있어도 UFW로 **실제 노출을 좁힌다.** 우리의 방어선.

## 4. 목표와 제약

### 목표
- 인터넷 주소 하나(`https://j15b205.p.ssafy.io`)로 전체 서비스 접속·테스트 가능.
- 재현 가능·재배포 쉬움(한 명령으로 올리고 내리기).
- 팀이 이해·유지보수 가능(과하지 않게).

### 제약 (SSAFY 안내 기준)
- **서버 1대.** 로드밸런서·다중 인스턴스·매니지드 DB 없음 → 모든 것을 한 EC2에.
- **웹 콘솔 없음, SSH만.** 원격 터미널로만 관리.
- **SG는 넓게 열려 있음** → UFW로 반드시 좁혀야 함. "UFW는 항상 enable 유지".
- "**기본 포트를 바꿔 쓰라**"는 권고 (8080 등). → 5.3절에서 우리 방식으로 더 강하게 해결.
- 제공 기간: 프로젝트 종료 후 7일 내 삭제 → **영구 데이터가 아님**(백업/이관 부담 낮음).

## 5. 아키텍처 설계와 판단 근거

### 5.0 전체 그림

```
                    인터넷
                      │  (443/TLS, 80→443 리다이렉트)
              ┌───────▼────────┐
              │     Nginx      │  ← 유일한 공개 진입점 (컨테이너, 80/443 만 publish)
              │  TLS 종료      │
              │  SPA 정적 서빙 │
              │  /api → 프록시 │
              └───┬───────┬────┘
      /api/*      │       │   /  (SPA)
           ┌──────▼──┐    └────────► (정적 파일 직접 응답)
           │ backend │  :8080  (호스트 미노출)
           │ (crypto │
           │ 포함)   │
           └─┬──┬──┬─┘
     ┌───────┘  │  └─────────┐
 ┌───▼──┐   ┌───▼──┐    ┌────▼────┐
 │mysql │   │redis │    │   ai    │ :8000 (호스트 미노출)
 │:3306 │   │:6379 │    │ FastAPI │
 └──────┘   └──────┘    └────┬────┘
  (내부 전용 도커 네트워크)   │
                        Google Vertex AI(Gemini)

바깥으로 나가는 호출(outbound): 백엔드 → S3 / SSAFY / 카카오페이 / Polygon RPC / Upbit,  AI → Gemini
호스트에 열리는 포트: 22(SSH), 80, 443  ← 오직 이 3개
```

### 5.1 결정: Docker Compose 로 오케스트레이션
- **판단**: 5개 컨테이너를 `docker compose` 파일 하나로 정의·기동한다.
- **근거**: 서버가 1대뿐이라 Kubernetes 는 과함(운영 복잡도·학습비용 > 이득). Compose 는 단일 호스트
  다중 컨테이너에 딱 맞고, 서비스 간 내부 네트워크·의존 순서(`depends_on`)·헬스체크를 선언적으로 표현한다.
- **대안과 비교**:
  - *맨몸 설치(자바/파이썬/nginx 직접)*: 버전 충돌·환경 오염. 재현성 낮음 → 기각.
  - *Kubernetes*: 단일 노드에 오버킬 → 기각.
  - *Compose* ✅ : 규모에 적정.

### 5.2 결정: Nginx 를 유일한 공개 진입점으로
- **판단**: 외부에 노출되는 프로세스는 Nginx 뿐. 그것이 TLS 종료 + SPA 서빙 + `/api` 프록시를 모두 담당.
- **근거**: ① 인증서·HTTPS 설정을 한 곳으로 모음 ② 백엔드·AI·DB를 인터넷에서 직접 못 만지게 함
  ③ 프론트와 API가 같은 오리진이 되어 CORS 문제 소멸(5.6).
- **대안**: 백엔드가 직접 443을 서비스(내장 톰캣+TLS). → 인증서 관리가 앱에 섞이고 정적 서빙이 비효율,
  포트 노출이 늘어남 → 기각.

### 5.3 결정(가장 중요): 내부 서비스는 호스트 포트를 열지 않는다 — "포트 변경" 권고에 대한 답
- **SSAFY 권고**: "기본 포트(8080 등)를 바꿔 쓰라."
- **우리 판단**: 포트를 *바꾸는* 대신 **아예 노출하지 않는다.** backend(8080)/ai(8000)/mysql(3306)/redis(6379)
  는 `docker-compose.prod.yml` 에서 `ports:` 를 쓰지 않아 **호스트에 바인딩되지 않고**, 도커 내부 네트워크에서
  서비스명(`backend`, `mysql` …)으로만 통신한다.
- **근거**:
  - 포트를 8080→9000 으로 바꾸는 건 **보안이 아니라 은닉(security by obscurity)** 일 뿐, 스캐너는 금방 찾는다.
  - 노출을 0으로 만들면 애초에 공격 표면이 없다(**security by non-exposure**). 이게 더 강하다.
  - 결과적으로 공개 포트는 80/443/22 뿐이라 SSAFY 권고의 목적("기본 포트로 방치하지 말 것")을 초과 달성한다.
- ⚠️ **반드시 알아야 할 도커-UFW 함정**:
  도커가 `ports:` 로 포트를 publish 하면 **iptables 를 직접 조작해 UFW 규칙을 우회**한다.
  즉 `ports: "8080:8080"` 을 실수로 추가하면, UFW로 8080을 막고 있어도 **인터넷에 그대로 열린다.**
  그래서 내부 서비스엔 절대 `ports:` 를 붙이지 않는다. 디버깅이 필요하면 `127.0.0.1:8080:8080` 처럼
  **루프백에만** 바인딩하고 SSH 터널로 접근한다. (이 규칙을 `scripts/ufw-setup.sh` 주석에도 명시함.)

### 5.4 결정: 백엔드는 모놀리스 그대로 (코인·카드·은행조회를 쪼개지 않음)
- **판단**: 코인/카드/정산/알림 등은 모두 한 Spring Boot 프로세스로 배포.
- **근거**: 이들은 이미 한 Gradle 프로젝트의 도메인 패키지다(별도 빌드·포트·main 없음). 마이크로서비스로
  쪼개면 네트워크 경계·분산 트랜잭션·배포 복잡도만 늘고, 우리 규모·기간엔 이득이 없다. **현업에서도
  "모듈러 모놀리스"가 이 규모의 정답**이다. 코인은 outbound 의존성(Polygon RPC, Upbit) 2개를 더할 뿐이다.

### 5.5 결정: TLS 는 Let's Encrypt(certbot) 자동 발급·갱신
- **판단**: `certbot` 컨테이너가 HTTP-01 챌린지로 `j15b205.p.ssafy.io` 인증서를 발급하고, 12시간마다 갱신 시도.
- **근거**: 무료·자동·표준. 도메인이 이미 EC2를 가리키고 SG/UFW가 80을 열어 챌린지가 통과된다.
- **절차 요지**: ① 80만 여는 임시 nginx 로 챌린지 통과 → ② `certbot certonly --webroot` 발급 →
  ③ 발급된 `fullchain.pem/privkey.pem` 을 nginx 가 볼륨으로 읽어 443 서비스 → ④ certbot 컨테이너가 자동 갱신.
  (인증서 발급 전에는 자체서명으로 임시 기동 가능. 상세는 `deploy/README.md` 4단계.)

### 5.6 결정: 프론트·API 동일 오리진 → CORS 제거
- **판단**: 프론트(`/`)와 API(`/api/`)를 같은 도메인에서 서빙.
- **근거(코드 확인)**: 프론트 API base 는 상대경로 `'/api/v1'`(`shared/config/env.ts`). 프로덕션 빌드에선
  Vite 프록시가 없고, 브라우저가 자기 오리진의 `/api/v1/...` 로 요청 → Nginx가 백엔드로 프록시.
  같은 오리진이므로 **브라우저가 CORS 프리플라이트를 보내지 않는다.** 설정 실수로 인한 배포 장애를 원천 제거.
  (방어적으로 백엔드 `CORS_ALLOWED_ORIGINS=https://j15b205.p.ssafy.io` 도 함께 설정.)

### 5.7 결정: 비밀값 관리
- **원칙**: 어떤 비밀값도 이미지·git 에 넣지 않는다. 런타임에 `env_file`(서비스별 `.env`)·볼륨 마운트로 주입.
- **대상**: DB 비밀번호, `JWT_SECRET`, AWS 키, SSAFY apiKey, 카카오페이 시크릿, (미래) 코인 핫월렛 개인키.
- **Gemini(중요)**: AI는 Vertex AI **Enterprise** 모드라 API 키가 아니라 **Google ADC(서비스계정)** 로 인증한다
  (`gemini_analyze.py` 의 `genai.Client(enterprise=True, project=…)`). 로컬에선 `gcloud auth
  application-default login` 이면 되지만, **헤드리스 EC2에선 대화형 로그인이 불가**하므로
  **서비스계정 키(JSON)를 발급**(Vertex AI User 권한)해 `deploy/secrets/gcp-sa.json` 으로 올리고
  `GOOGLE_APPLICATION_CREDENTIALS` 로 주입한다. → 이 부분은 팀이 GCP 콘솔에서 발급해야 하는 **선행 작업**.
- **코인 핫월렛(미래)**: `S15P21B205-80`(코인 환불 송금) 구현 시 개인키가 처음 생긴다. 절대 코드/DB 평문 저장
  금지, 최소 잔액만 유지, `.env`(또는 별도 시크릿 스토어) 주입. 지금은 해당 없음(수신 전용).

### 5.8 결정: Spring 프로파일은 `prod`
- **판단**: `SPRING_PROFILES_ACTIVE=prod` 로 기동.
- **근거(코드 확인)**: `application-local.yml` 에만 있는 것들 — Swagger UI 활성화, 가상은행 콘솔 CORS 허용,
  **슬롯게이트 로컬 폴백**(`local-fallback-enabled: true`) — 은 `local` 프로파일에서만 로딩된다.
  prod 로 띄우면 이들이 빠지고, 슬롯게이트가 **Redis Lua 원자성**을 사용한다(동시 결제 정합성). 별도
  `application-prod.yml` 없이도 모든 설정이 환경변수로 주입되므로 문제없다.

## 6. 방화벽(UFW) 설계

- 최종 상태: `22/tcp`, `80/tcp`, `443/tcp` **만** ALLOW, 나머지 incoming 전부 DENY.
- 순서(잠김 방지): `allow 22` → `allow 80/443` → `enable`. SSH 세션 2개 이상 열어둔 채 실행.
- 스크립트: [`../../deploy/scripts/ufw-setup.sh`](../../deploy/scripts/ufw-setup.sh) (멱등).
- 검증 포인트: `sudo ufw status` 에 8080/8000/3306/6379 가 **없어야** 정상(내부 전용이므로).
- 앞서 5.3의 도커-UFW 함정을 반드시 기억: 내부 컨테이너에 `ports:` 금지.

## 7. 배포 파이프라인 / CI·CD

- **현재(수동)**: 서버에서 `git pull` → `docker compose -f docker-compose.prod.yml up -d --build`.
  프로젝트 기간·규모에선 이 수동 배포로 충분하다.
- **자동화(선택)**: SSAFY가 Jenkins 가이드를 제공(`project.ssafy.com > Help`). GitLab `DevelopV1` 병합 시
  Jenkins 가 SSH로 서버에 접속해 위 명령을 실행하게 하면 CI/CD가 된다. 도입 시:
  - 빌드는 이미지 빌드까지 CI에서, 배포는 서버에서 pull&up.
  - Jenkins 자체 포트(8080 등)도 UFW·리버스프록시 뒤에 두거나 SSH 터널로만 접근(공개 금지).

## 8. 서버에서의 테스트 전략

배포가 "된다"의 기준을 아래로 정의한다.

1. **헬스체크**: `curl -k https://j15b205.p.ssafy.io/api/v1/actuator/health` → `{"status":"UP"}`.
   컨테이너 헬스체크(`docker compose ps` 의 healthy)도 함께 확인.
2. **프론트 로딩**: 브라우저로 `https://j15b205.p.ssafy.io` 접속, 새로고침(SPA 폴백 동작 확인).
3. **핵심 플로우 E2E**(로컬에서 검증된 시나리오를 서버에서 재현):
   - 회원가입 → 로그인 → 상품 등록(AI 자동 채움) → 공구 생성 → 결제(카드/카카오) → 참여취소·환불.
   - 카드 해피패스는 플랫폼계좌 불필요. 계좌이체 폴백/모집실패 환불은 `SSAFY_PLATFORM_ACCOUNT_NO`(platform_policies)
     설정이 있어야 통과.
4. **AI 단독 점검**: 백엔드 컨테이너에서 `curl http://ai:8000/health` → `{"status":"UP"}`,
   상품 등록 시 AI 추출이 채워지는지.
5. **로그**: `docker compose logs -f backend|ai|nginx` 로 오류 추적.

> 부하 테스트는 `loadtest/`(k6) 를 활용하되, SSAFY 공용망에 과부하를 주지 않도록 소규모로.
