# 반품 목록 N+1 최적화 성능 테스트

## 1. 왜 이 성능 테스트를 기획했는가

구매자·판매자·관리자 반품 목록은 한 행에 반품 자체의 값뿐 아니라 공동구매 번호, 상품명, 구매자 닉네임을 함께 보여 준다. 기존 구현은 먼저 `return_requests` 페이지를 조회한 다음 각 행을 DTO로 바꾸면서 다음 저장소를 차례로 호출했다.

1. `GroupBuyRepository.findById`
2. `ProductRepository.findById`
3. `UserRepository.findById`

페이지 데이터 조회와 전체 개수 조회를 합친 기본 2회에 행마다 최대 3회의 조회가 추가되므로, 모든 행의 공동구매·상품·구매자가 다르면 조회 횟수는 `2 + 3N`이다. 20건만 조회해도 최대 62회이고 1,000건이면 3,002회다. 응답 데이터의 양보다 DB 왕복 횟수가 더 빠르게 커지는 전형적인 N+1 문제다.

이 문제는 단순히 코드가 길다는 이유로 리팩터링한 것이 아니다. 일반 목록·상세 응답을 2초 안에 제공해야 한다는 비기능 요구사항과, 관리자 심사 목록 RTN-10을 추가할 때 같은 문제가 한 번 더 복제되는 것을 막기 위해 먼저 측정 가능한 목표를 세웠다.

목표는 다음과 같다.

- 페이지 크기와 무관하게 목록 SQL을 데이터 1회와 count 1회, 총 2회로 고정한다.
- 기존 응답 필드와 필터 의미를 바꾸지 않는다.
- 쓰기 상태 전이는 계속 JPA 엔티티가 담당하게 한다.
- 시간 수치는 환경 의존성을 분리한 통제 모델로 비교하고, 실제 JPA 쿼리 수는 통합 테스트로 별도 증명한다.

## 2. 변경 전 설계와 병목

변경 전 흐름은 다음과 같았다.

```text
반품 페이지 조회 + count                         2회
  └─ 각 반품 행 N개
       ├─ 공동구매 findById                     N회
       ├─ 상품 findById                         N회
       └─ 구매자 findById                       N회
합계                                         2 + 3N회
```

같은 영속성 컨텍스트 안에서 같은 ID가 반복되면 1차 캐시가 일부 조회를 줄일 수 있다. 그러나 서로 다른 공동구매·상품·구매자가 섞인 정상적인 목록에서는 캐시 적중을 보장할 수 없다. 또한 `hibernate.default_batch_fetch_size`는 지연 연관을 한꺼번에 초기화할 때 도움을 주는 설정이지, 반복문 안에서 서로 다른 Repository의 `findById`를 명시적으로 호출하는 구조를 근본적으로 합치지 못한다.

## 3. 선택지와 결정

### 선택지 A: 모든 도메인을 JPA 연관관계로 추가하고 EntityGraph로 읽기

반품에서 공동구매, 상품, 사용자를 모두 객체 연관으로 연결하면 한 번의 fetch join을 만들 수 있다. 하지만 현재 `Participation`은 다른 도메인과의 결합을 줄이기 위해 공동구매와 사용자 ID를 값으로 보관한다. 조회 한 건 때문에 쓰기 모델에 광범위한 연관관계를 추가하면 자동 생성 FK, cascade, fixture 의존성이 다른 도메인의 독립 테스트까지 흔들 수 있다.

### 선택지 B: JDBC 또는 native SQL 읽기 모델

한 쿼리로 가장 직접적으로 만들 수 있지만, 이 조회에는 MySQL 전용 전문검색이나 복잡한 동적 정렬이 없다. 사용자가 요청한 JPA 중심 원칙을 지키면서도 충분히 표현할 수 있으므로 native SQL을 새로 넣을 이유가 약하다.

### 선택지 C: JPQL 인터페이스 프로젝션

`ReturnSummaryView`에 화면에 필요한 scalar 값만 선언하고, JPQL이 `ReturnRequest`, `Participation`, `GroupBuy`, `Product`, `User`를 ID 조건으로 조인해 한 행으로 반환하도록 했다. 상태 변경은 기존 엔티티와 변경 감지를 그대로 사용하고, 목록 조회만 읽기 전용 모양으로 분리된다.

이 테스트에서는 선택지 C를 채택했다. JPA 방식을 유지하면서 조회 횟수와 불필요한 엔티티 로딩을 동시에 줄이고, 구매자·판매자·관리자 목록이 같은 projection 계약을 재사용할 수 있기 때문이다.

## 4. 테스트 설계

### 4.1 실제 JPA 통합 검증

`ReturnRequestRepositoryTest.listProjectionKeepsQueryCountConstant`는 H2를 MySQL 호환 모드로 실행하고 실제 Spring Data JPA Repository를 호출한다.

1. 사용자, 상품, 공동구매, 참여 데이터와 반품 25건을 만든다.
2. 영속성 컨텍스트를 비워 1차 캐시의 도움을 제거한다.
3. Hibernate `Statistics`를 초기화한다.
4. 첫 페이지 20건과 전체 개수를 조회한다.
5. 상품명·구매자명이 정확한지와 prepared statement 수가 정확히 2인지 단언한다.

이 테스트는 최적화 구현이 실제 JPQL에서 2회로 끝난다는 회귀 방지 장치다. 단순 계산식이나 mock 호출 횟수만으로 성공을 주장하지 않는다.

### 4.2 지연 비교 모델

운영 MySQL의 절대 응답시간은 서버 사양, 데이터 분포, 인덱스 통계, 네트워크에 따라 달라진다. 로컬 H2 시간을 운영 성능처럼 제시하면 오해가 생기므로 `ReturnListPerformanceTest`는 DB 왕복 한 번의 지연을 2ms로 통제한 비교 모델을 사용한다.

- 페이지 크기: 20, 100, 1,000
- 표본 수: 각 경로 5회
- 워밍업: 20건 경로 1회
- 변경 전 조회 횟수: `2 + 3N`
- 변경 후 조회 횟수: `2`
- 대표값: 중앙값과 P95
- 두 경로 모두 같은 수의 결과 행 소비 작업 수행

Windows의 짧은 대기 호출은 타이머 해상도 때문에 2ms 요청이 약 15ms까지 반올림될 수 있다. 따라서 여러 왕복의 총 지연을 한 번에 적용했다. 변경 후 4ms 구간은 여전히 OS 타이머 바닥값의 영향을 받아 약 15ms로 측정된다. 아래 수치는 운영 SLA가 아니라 **동일 환경에서 조회 횟수 증가가 만드는 상대적 차이**다.

재현 명령:

```powershell
cd backend
.\gradlew.bat test --tests "com.gongguhan.domain.returnrequest.repository.ReturnRequestRepositoryTest"
.\gradlew.bat performanceTest --tests "com.gongguhan.domain.returnrequest.ReturnListPerformanceTest" --info
```

| 페이지 행 수 | 변경 전 조회 수 | 변경 후 조회 수 | 변경 전 중앙값 | 변경 후 중앙값 | 중앙값 개선 | 변경 전 P95 | 변경 후 P95 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 20 | 62 | 2 | 129.006ms | 15.648ms | 87.87% | 138.907ms | 16.014ms |
| 100 | 302 | 2 | 608.496ms | 15.679ms | 97.42% | 618.649ms | 16.374ms |
| 1,000 | 3,002 | 2 | 6,014.375ms | 15.504ms | 99.74% | 6,017.932ms | 15.665ms |

핵심 결과는 절대 ms보다 조회 횟수다. 변경 전에는 페이지 크기가 5배, 10배로 늘 때 DB 왕복도 선형으로 늘지만, 변경 후에는 항상 2회다. 실제 JPA 통합 테스트에서도 20건 페이지에 정확히 2회가 기록됐다.

## 6. 기능 정합성 검증

최적화와 함께 다음 기능을 검증했다.

- 구매자 목록의 사용자 소유권·상태·공동구매 필터 유지
- 판매자 목록의 판매자 소유권·상태·공동구매 필터 유지
- 관리자 검토 목록은 `admin_review_required=true`인 신청과 이의제기만 반환
- 판매자 거부 뒤 이의제기 시 구매확정 보류를 다시 설정
- 관리자 승인 시 반품 `APPROVED`, 승인 유형 `ADMIN`, `forced_by/forced_at` 기록, 참여 `RETURNING`
- 관리자 기각 시 반품 `REJECTED`, 기각 사유와 강제 처리자 기록, 구매확정 보류 해제
- 이미 끝난 검토의 중복 처리는 상태 전이 오류로 거부

## 7. 해석 범위와 다음 측정

이번 결과로 증명할 수 있는 것은 “반품 목록의 DB 접근 복잡도가 최대 `2 + 3N`에서 2로 줄었다”는 사실과, 통제된 왕복 지연에서 그 차이가 페이지가 커질수록 확대된다는 점이다.

아직 증명하지 않은 것은 운영 MySQL에서의 2초 SLA다. 이를 최종 판정하려면 운영과 비슷한 데이터 분포, 인덱스 통계, 네트워크를 갖춘 환경에서 다음을 추가해야 한다.

1. 최소 수만 건의 반품·참여·상품 데이터 적재
2. 구매자·판매자·관리자별 실제 필터 비율 구성
3. `EXPLAIN ANALYZE`로 `idx_returns_review`, 참여·공동구매 PK 조인 확인
4. 동시 사용자 부하에서 P50/P95/P99와 오류율 측정
5. 응답 직렬화와 네트워크 시간을 포함한 HTTP 종단 측정

따라서 이 문서의 수치는 최적화 설계의 재현 가능한 비교 근거이며, 운영 용량 산정 자료로 직접 사용해서는 안 된다.
