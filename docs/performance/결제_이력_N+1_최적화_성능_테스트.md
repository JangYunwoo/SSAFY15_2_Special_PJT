# 결제 이력 N+1 조회 최적화와 성능 테스트 설계

## 1. 문서 목적

이 문서는 `GET /api/v1/payments` 결제 이력 조회에서 발견한 N+1 형태의 조회를 왜
최적화 대상으로 골랐는지, 어떤 설계로 수정했는지, 성능 비교를 어떤 가정과 통제 아래
수행했는지를 처음 코드를 보는 사람도 재현하고 검토할 수 있도록 기록한다.

단순히 “몇 ms 빨라졌다”는 결론만 남기지 않는다. 성능 수치는 실행 환경과 데이터에
따라 바뀐다. 따라서 이 문서에서는 다음 네 가지를 구분한다.

1. 코드 구조로 확정할 수 있는 사실: 페이지 한 번을 조회할 때의 저장소 접근 형태
2. 통제된 실험으로 비교한 사실: 같은 데이터와 변환 과정에서 왕복 횟수만 바꾼 실행 시간
3. 실험 결과로 합리적으로 추론할 수 있는 효과: 페이지 크기가 커질수록 제거되는 지연 증폭
4. 이 실험으로는 말할 수 없는 것: 운영 서버의 실제 응답 시간, TPS, 동시 사용자 한계

측정일은 2026-09-11이며, Java 21·Gradle 9.7.1·Windows 개발 환경에서 실행했다.

## 2. 왜 이 기능을 먼저 측정했는가

결제 이력은 사용자가 자신의 결제 상태를 확인하는 읽기 API다. 한 번의 요청이 여러 결제
행을 반환하는 페이지 API이므로, 행마다 추가 조회가 발생하면 데이터가 늘수록 비용이
선형으로 커진다. 특히 결제 준비·승인 같은 쓰기 기능보다 호출 빈도가 높아질 수 있고,
느려졌을 때 사용자가 곧바로 체감하는 화면이다.

변경 전 `PaymentService.listHistory`의 흐름은 다음과 같았다.

```text
결제 이력 요청
  └─ PaymentRepository.findByUserId(...)       1회
       └─ 결제 1건마다 GroupBuySlotPort.get(...) N회
            └─ GroupBuyRepository.findById(...) N회
```

결제 응답에는 분담금과 배송비가 필요하다. 이 값은 공동구매 도메인의 값이므로 결제 행만
조회해서는 응답을 완성할 수 없다. 변경 전 구현은 이 값을 결제 한 건씩 가져왔다. 페이지에
결제가 `N`건 있으면 논리적인 DB 조회 횟수는 다음과 같다.

```text
변경 전 조회 수 = 결제 페이지 1회 + 공동구매 단건 N회 = 1 + N
```

이 구조가 N+1 문제다. 개별 쿼리 자체가 빨라도 애플리케이션과 DB 사이의 왕복, 커넥션
대여, SQL 파싱과 실행 비용이 N번 반복된다. 동시 요청이 늘면 한 요청의 지연뿐 아니라 DB
커넥션 풀 점유와 DB 부하도 함께 증가할 수 있다.

## 3. 최적화 목표와 완료 조건

이번 작업의 목표는 응답 계약이나 정렬 순서를 바꾸지 않고 공동구매 조회 횟수를 페이지당
한 번으로 고정하는 것이다.

```text
변경 후 조회 수 = 결제 페이지 1회 + 공동구매 일괄 조회 1회 = 2
```

완료 조건은 다음과 같이 정했다.

- 반환되는 결제 수, 순서, 페이지 메타데이터와 `PaymentResponse` 값이 바뀌지 않는다.
- 페이지 안의 서로 다른 공동구매 ID를 한 번에 조회한다.
- 결제 건별 `GroupBuySlotPort.get` 호출은 0회여야 한다.
- `GroupBuySlotPort.getAll` 호출은 빈 페이지가 아닌 경우 1회여야 한다.
- 중복 공동구매 ID는 조회 전에 제거한다.
- 요청한 공동구매가 하나라도 없으면 기존 단건 조회처럼 `RESOURCE_NOT_FOUND`로 실패한다.
- 일반 단위 테스트에는 시간 임계값을 넣지 않는다. 시간 기반 비교는 별도 태스크로 분리한다.

페이지 크기에 따른 논리적 조회 감소율은 아래 공식으로 미리 계산할 수 있다.

```text
조회 감소율 = ((1 + N) - 2) / (1 + N) × 100
```

| 결제 행 수 N | 변경 전 | 변경 후 | 논리적 조회 감소율 |
| ---: | ---: | ---: | ---: |
| 20 | 21회 | 2회 | 90.48% |
| 100 | 101회 | 2회 | 98.02% |
| 1,000 | 1,001회 | 2회 | 99.80% |

이 표는 시간 측정치가 아니라 코드 경로에서 결정되는 조회 횟수 비교다. 실행 장비의 잡음과
무관하므로 이번 최적화의 가장 강한 성능 지표로 본다.

## 4. 구현 설계와 판단 과정

### 4.1 선택한 설계: 도메인 포트에 일괄 조회 추가

결제 공통 계층은 공동구매 엔티티나 저장소를 직접 참조하지 않고 `GroupBuySlotPort`라는
경계 계약을 사용한다. 기존 경계를 유지하면서 다음 메서드를 추가했다.

```java
Map<Long, GroupBuySlot> getAll(Collection<Long> groupBuyIds);
```

실제 구현 흐름은 다음과 같다.

```text
PaymentService.listHistory
  1. 결제 페이지 조회
  2. 결제들의 groupBuyId를 불변 Set으로 수집하여 중복 제거
  3. GroupBuySlotPort.getAll(ids)를 한 번 호출
  4. GroupBuySlotService가 JpaRepository.findAllById(ids)를 실행
  5. 조회 결과를 groupBuyId -> snapshot Map으로 변환
  6. Map에서 값을 꺼내 기존 PaymentResponse.from으로 응답 조립
```

JPA의 `findAllById`를 사용했기 때문에 애플리케이션 코드에 네이티브 SQL을 추가하지 않았다.
일반적으로 Hibernate는 전달된 ID들을 `WHERE ... IN (...)` 형태의 SQL로 변환한다. 즉,
JPA 방식과 도메인 경계를 유지하면서도 공동구매 행을 한 번의 저장소 호출로 읽는다.

응답 변환 시각도 결제마다 `LocalDateTime.now(clock)`를 호출하지 않고 페이지당 한 번만
구한다. 이 변경의 주목적은 미세한 시간 호출 절약이 아니라, 같은 페이지의
`remainingSeconds`가 변환 도중 초 경계를 지나 결제마다 다르게 계산되는 일을 막는 것이다.

### 4.2 누락 데이터 정책

결제 행이 가리키는 공동구매는 정상 데이터라면 반드시 존재해야 한다. 일괄 조회 결과 수가
중복 제거한 요청 ID 수보다 작으면 데이터 불변식이 깨진 상태다. 누락된 값을 `null`로
넘겨 뒤에서 `NullPointerException`이 나게 두지 않고, 기존 단건 조회와 같은
`RESOURCE_NOT_FOUND` 예외로 즉시 실패시킨다.

### 4.3 검토했지만 선택하지 않은 방법

#### 결제 서비스에서 공동구매 저장소를 직접 호출

구현량은 적지만 결제 계층이 공동구매의 영속성 세부사항에 직접 결합된다. 이후 공동구매
저장 방식이 바뀔 때 결제 코드까지 수정해야 하고, 이미 만들어 둔 포트 경계를 무너뜨리므로
선택하지 않았다.

#### 도메인을 가로지르는 fetch join 또는 전용 결합 쿼리

한 번의 쿼리로 줄일 수 있지만 결제 저장소가 공동구매 테이블과 응답 모양까지 알게 된다.
현재 목표인 두 번의 고정 조회만으로도 N+1은 제거된다. 조인 한 번과 일괄 조회 두 번의
차이는 실제 DB 데이터로 측정한 뒤 필요할 때 판단하는 편이 결합도를 낮게 유지한다.

#### 캐시 추가

캐시는 반복 조회에는 도움이 될 수 있지만 캐시 미스와 첫 요청에서는 N+1이 그대로다.
금액·모집 상태처럼 변경 가능한 값을 캐시하면 무효화 정책도 필요하다. 잘못된 조회 형태를
먼저 고치지 않은 채 캐시로 가리는 것은 근본 해결이 아니므로 이번 범위에서 제외했다.

#### 단건 조회를 병렬 실행

한 요청의 벽시계 시간은 일부 줄 수 있어도 DB에는 여전히 N번 요청한다. 오히려 한 요청이
여러 커넥션을 동시에 점유해 전체 처리량과 다른 사용자의 지연을 악화시킬 수 있어
선택하지 않았다.

## 5. 성능 테스트를 이렇게 설계한 이유

### 5.1 별도 `performanceTest` 소스셋

성능 비교는 `backend/src/performanceTest`에 두고 Gradle의 일반 `test`와 분리했다.
개발 장비의 스케줄러, JIT, GC 상태 때문에 실행 시간은 흔들릴 수 있다. 일반 CI에서
“20ms 이하여야 한다” 같은 조건을 걸면 기능이 정상인데도 간헐적으로 실패하는 테스트가
된다. 따라서 일반 테스트는 호출 횟수와 결과 같은 결정적인 회귀를 검증하고, 별도 성능
태스크는 사람이 요청할 때 동일 시나리오를 재측정하고 비교표를 갱신하는 용도로 사용한다.

### 5.2 비교 변수와 통제 변수

비교하는 유일한 핵심 변수는 공동구매 정보를 가져오는 방식이다.

| 구분 | 변경 전 모델 | 최적화 모델 |
| --- | --- | --- |
| 결제 데이터 | 동일한 `Payment` 목록 | 동일한 `Payment` 목록 |
| 응답 변환 | `PaymentResponse.from` | `PaymentResponse.from` |
| 시각 | 같은 고정 `Clock` | 같은 고정 `Clock` |
| 공동구매 조회 | ID마다 `get` | ID 집합으로 `getAll` |
| 왕복 지연 모델 | 호출 1회마다 2ms | 호출 1회마다 2ms |

실제 외부 DB를 사용하지 않은 이유는 네트워크 혼잡이나 다른 프로세스 부하를 제거하고,
N번의 왕복과 한 번의 왕복이라는 구조 차이만 반복해서 관찰하기 위해서다. 2ms는 운영값을
주장하기 위한 숫자가 아니라, 호출 횟수에 따라 누적되는 비용을 눈에 보이게 만드는 통제값이다.

### 5.3 데이터 크기 선택

- 20건: 현재 일반적인 기본 페이지를 대표하는 크기
- 100건: 관리자 화면이나 큰 페이지 요청을 가정한 크기
- 1,000건: 조회 횟수가 데이터 크기에 따라 어떻게 증가하는지 확인하는 스트레스 크기

모든 결제가 서로 다른 공동구매를 참조하도록 만들었다. 같은 공동구매가 반복되면 중복 제거로
조회 수가 줄어들기 때문에, 이 데이터는 N+1 비용이 가장 분명하게 드러나는 고유 ID 비율
100% 시나리오다.

### 5.4 워밍업, 표본과 통계량

측정 전에 20건 시나리오를 두 구현으로 한 번씩 실행하여 클래스 로딩, Mockito 준비와 JIT의
첫 실행 비용을 일부 제외했다. 각 데이터 크기는 5회 반복했고 중앙값과 P95를 기록했다.

- 중앙값: 일시적인 느린 표본 하나가 평균을 크게 왜곡하는 문제를 줄인다.
- P95: 표본을 정렬했을 때 느린 쪽 꼬리 지연을 확인한다.

다만 표본이 5개뿐이므로 여기의 P95는 사실상 5개 중 최댓값이다. 정밀한 백분위 추정값이
아니며, 짧은 개발 단계 비교에서 최악 표본도 함께 공개하기 위한 보조 지표다.

## 6. 측정 결과

최종 기록은 호출 횟수 검증을 추가한 뒤 같은 프로세스 안에서 변경 전 모델과 최적화 모델을
교대로 실행한 결과다.

| 행 수 | 변경 전 조회 | 변경 후 조회 | 변경 전 중앙값 | 변경 후 중앙값 | 중앙값 감소 | 변경 전 P95 | 변경 후 P95 | P95 감소 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 20 | 21회 | 2회 | 307.940ms | 18.133ms | 94.11% | 311.184ms | 20.858ms | 93.30% |
| 100 | 101회 | 2회 | 1,552.994ms | 21.781ms | 98.60% | 1,565.760ms | 28.730ms | 98.17% |
| 1,000 | 1,001회 | 2회 | 15,542.438ms | 58.790ms | 99.62% | 15,641.496ms | 64.687ms | 99.59% |

중앙값 기준 변경 전 대비 배수는 약 20건 16.98배, 100건 71.30배, 1,000건 264.37배다.
행이 많을수록 기존 구현은 2ms 왕복을 반복하지만 최적화 구현은 왕복 수가 두 번으로 고정되고,
추가 증가는 주로 ID 수집·Map 생성·DTO 변환 같은 메모리 내 작업에서 발생한다.

최적화 전 코드를 처음 확인할 때 100건·호출당 2ms의 임시 단일 실행에서는 347ms가
관찰되었다. 그 값은 `Thread.sleep` 기반 1회 측정이고, 위 최종 표는 `LockSupport.parkNanos`,
워밍업과 5회 표본을 사용하므로 서로 직접 비교해서는 안 된다. 최종 결론은 반드시 같은
실행에서 같은 지연 모델로 비교한 위 표를 기준으로 한다. 이 차이를 기록하는 이유는 유리한
숫자 하나만 골라 성능 개선을 과장하지 않기 위해서다.

## 7. 결과 해석과 한계

이번 측정으로 확정할 수 있는 것은 다음과 같다.

- 결제 이력 한 페이지의 논리적 저장소 조회 형태가 `1+N`에서 `2`로 바뀌었다.
- 성능 테스트는 최적화 경로가 단건 포트를 0회, 일괄 포트를 1회 호출하는지 직접 검증한다.
- 왕복 비용이 있는 통제 환경에서 페이지 크기가 커질수록 제거되는 누적 지연이 커졌다.
- 응답 조립 로직을 양쪽 모두 동일하게 실행했으므로 비교값에는 DTO 변환 비용도 포함된다.

반대로 다음 내용은 이 결과만으로 주장할 수 없다.

- 운영 환경에서 실제 API가 표의 ms와 동일하게 응답한다.
- TPS가 표의 배수만큼 증가한다.
- 동시 사용자 50명에서도 같은 감소율이 나온다.
- MySQL 실행 계획, 디스크 I/O, 커넥션 풀 대기까지 최적화되었다.

테스트의 절대 시간이 설정한 2ms의 단순 배수보다 큰 이유에는 Windows 타이머 스케줄링,
Mockito 프록시 호출, JVM JIT·GC, Gradle 테스트 프로세스 부하가 함께 들어간다. 그러므로
표의 절대 시간은 SLA로 사용하지 않고, 동일 실행 내 상대 비교와 고정된 호출 횟수를 본다.

`IN` 절도 무한히 크게 만들 수는 없다. 현재 API는 페이지 단위라 ID 개수가 페이지 크기로
제한된다. 향후 허용 페이지 크기를 수천~수만 건으로 늘린다면 최대 페이지 크기를 제한하거나
ID를 청크로 나누는 정책을 별도로 검토해야 한다.

## 8. 기능 회귀 검증

시간 비교와 별도로 아래 단위 테스트를 둔다.

- `PaymentServiceTest`: 중복 ID를 제거해 `getAll`을 정확히 한 번 부르고 `get`은 부르지 않는지 검증
- `GroupBuySlotServiceTest`: 중복 ID를 한 번만 조회하고 하나의 Map으로 반환하는지 검증
- `GroupBuySlotAdapterTest`: 결제 포트의 일괄 계약과 공동구매 서비스 사이 매핑 검증
- `PaymentHistoryPerformanceTest`: 각 행 수에서 결과 건수, 단건/일괄 포트 호출 횟수와 비교 수치 출력

성능 테스트가 빠르다는 이유만으로 기능 완료로 판단하지 않는다. 단위 테스트와 전체 회귀
테스트를 함께 통과해야 하고, 외부 의존성(Redis 등)으로 실패한 테스트는 코드 실패와 환경
실패를 구분해 기록한다.

최신 `origin/DevelopV1`을 반영한 뒤 실제 실행한 결과는 다음과 같다.

- 관련 단위 테스트 3개 클래스: 전부 통과
- 독립 성능 비교 테스트: 통과, 20·100·1,000건 결과를 이 문서 6장에 기록
- 전체 백엔드 회귀: 337개 중 334개 통과, 3개 실패
- 실패한 테스트: `GroupBuySlotGateIntegrationTest` 2개와
  `PaymentServiceConcurrencyTest` 1개
- 공통 원인: 로컬 `localhost:6379`에 Redis가 없고 Docker/Redis 실행 파일도 없어 발생한
  `RedisConnectionFailureException`

실패한 세 테스트는 이번 변경 경로가 아니라 기존 Redis 슬롯 게이트의 동시성 시험이다.
환경 의존 테스트를 임의로 제외하거나 성공으로 바꾸지 않았고, 관련 단위 테스트와 성능
테스트를 별도로 통과시켜 코드 회귀와 로컬 인프라 부재를 구분했다. Redis가 제공되는 CI나
개발 환경에서는 전체 명령을 다시 실행해 세 동시성 시험까지 확인해야 한다.

## 9. 재현 방법

프로젝트의 `backend` 디렉터리에서 실행한다.

```powershell
.\gradlew.bat test --tests "com.gongguhan.domain.payment.common.service.PaymentServiceTest" --tests "com.gongguhan.domain.groupbuy.service.GroupBuySlotServiceTest" --tests "com.gongguhan.domain.groupbuy.adapter.GroupBuySlotAdapterTest"
.\gradlew.bat performanceTest --tests "com.gongguhan.domain.payment.common.service.PaymentHistoryPerformanceTest" --info
```

두 번째 명령의 `PAYMENT_HISTORY` 행이 원시 측정 결과다. 다른 장비에서 문서를 갱신할 때는
기존 숫자를 지우기 전에 실행 날짜, Java 버전, OS, 표본 수와 지연 모델이 같은지 확인한다.
조건을 바꾸었다면 같은 표에 섞지 말고 별도 표로 기록한다.

## 10. 운영에 가까운 후속 성능 시험 계획

이번 테스트는 코드 구조 비교다. 운영 배포 전에는 MySQL과 실제 HTTP 계층을 포함한 다음
시험을 별도로 수행한다.

1. 동일한 스키마와 인덱스를 가진 시험 DB에 사용자별 결제 20·100·1,000건을 준비한다.
2. 각 크기에서 공동구매 ID 중복률 0%, 50%, 90% 데이터를 나눈다.
3. 애플리케이션과 DB를 재시작한 cold 조건, 충분히 예열한 warm 조건을 분리한다.
4. 30초 이상 예열한 뒤 5~10분 동안 동시 사용자 1·10·50으로 요청한다.
5. HTTP p50·p95·p99, 오류율, 초당 처리량을 측정한다.
6. HikariCP 활성/대기 커넥션, MySQL 쿼리 수·실행 시간·CPU를 함께 수집한다.
7. Hibernate 통계 또는 datasource 프록시로 한 요청의 실제 SQL 수가 2회인지 확인한다.
8. `findAllById` SQL에 `EXPLAIN ANALYZE`를 수행해 기본키 `IN` 조회 계획을 확인한다.

운영형 시험에서는 “응답 시간이 빨라졌다”와 “DB 부하가 줄었다”를 따로 판정한다. HTTP
지연만 줄고 DB 쿼리 수가 유지된다면 다른 캐시나 환경 영향일 수 있고, 쿼리 수만 줄었지만
지연이 그대로라면 직렬화·네트워크·다른 외부 API가 병목일 수 있기 때문이다.

## 12. 앞으로 이 코드를 수정할 때 지켜야 할 점

- `listHistory` 안에서 다시 결제별 `groupBuySlotPort.get`을 호출하지 않는다.
- 응답 필드가 추가되어 다른 도메인 정보가 필요해져도 먼저 일괄 계약을 설계한다.
- 실제 수치를 다시 기록할 때 전·후 구현을 같은 프로세스와 같은 데이터로 측정한다.
- 표본이 적은 개발 측정을 운영 성능이나 보장 수치로 표현하지 않는다.
- 캐시나 병렬화를 도입하기 전에 SQL 수, 실행 계획과 병목 위치를 먼저 확인한다.
- 성능 개선 커밋에는 최적화 사유, 변경한 경계, 검증한 테스트, 비교 수치와 한계를 함께 남긴다.
