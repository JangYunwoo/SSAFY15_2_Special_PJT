# 전체 설계 문서 대비 구현 완성도 감사

> 감사 기준일: 2026-09-11
>
> 기준 브랜치: 최신 `DevelopV1`에서 시작한 RTN-10/11 구현 브랜치
>
> 목적: “Controller가 존재한다”가 아니라 요구사항, API 계약, ERD·DB, 외부 연동, 보안·성능·운영 조건이 실제로 이어지는지 판단한다.

## 1. 결론부터 읽기

현재 프로젝트를 “전체 MVP가 완성됐다”고 판정하면 안 된다.

- API 명세의 102개 엔드포인트 중 계약과 URL이 일치하는 구현은 65개, 부분 구현은 1개다. 표면 커버리지는 `65 / 102 = 63.7%`이며, 전용 공동구매 배치 실행 API까지 부분 구현으로 포함하면 `66 / 102 = 64.7%`다.
- 김태민 담당 범위인 카테고리·상품·AI·청약철회 제한·공동구매·카카오페이·반품은 35개 중 34개가 구현되어 엔드포인트 기준 `97.1%`다. 남은 1개 GRP-10은 모든 결제수단 환불과 제재를 동시에 요구하므로 타 담당 도메인의 공통 환불 계약이 선행되어야 한다.
- 사용자가 미리 심어진 계정으로 정상 경로만 확인한다면 상품 등록 → 공동구매 → 결제 → 배송 → 구매확정/반품 일부는 동작한다.
- 그러나 신규 사용자가 스스로 판매자가 되는 흐름, 참여 취소, 공통 환불 이력, 판매자 정산, 제재 운영, 알림, 관리자 로그인·정책·감사로그가 비어 있다. 따라서 실제 서비스의 처음부터 끝까지 이어지는 종단 MVP는 미완성이다.
- 프론트에는 정산·알림 화면과 API 호출 코드가 있지만 백엔드가 없고, 개발 mock이 응답을 대신한다. 화면이 보인다는 사실을 서버 기능 완성으로 계산하면 안 된다.
- 보안 요구사항에서 정산 계좌번호 암호화·마스킹이 지켜지지 않는다. 현재 DB에 평문으로 저장하고 API 응답에도 원문을 반환하므로 출시 전 차단 수준의 문제다.
- 백엔드 테스트는 폭넓지만 Redis가 실행되지 않아 전체 회귀 3건을 통과시킬 수 없다. 프론트는 typecheck·lint·build는 가능하지만 자동화된 단위/E2E 테스트 파일이 0개다.

### 2.2 문서 충돌 처리 기준

프로젝트의 기존 합의대로 API 명세를 요청·응답 계약의 최우선으로, canonical schema와 Flyway를 DB 실행 기준으로 사용했다. 요구사항 PDF는 업무 목적과 비기능 판단에 사용했다.

예를 들어 요구사항 PDF의 초기 문구에는 구매자·판매자 분리 계정, 목표 인원 1명 이상, 플랫폼 고정 배송비가 보이지만 최신 API·DB·코드는 통합 `users + seller_profiles`, 목표 인원 2명 이상, 판매자 입력 배송비를 사용한다. 오래된 문구를 되살려 두 방식을 코드에 함께 넣으면 모델이 이중화되므로 최신 API·DB 결정을 유지한다. 대신 이런 불일치는 문서 개정 항목으로 남겨야 한다.

## 3. API 명세 대비 엔드포인트 커버리지

“구현”은 명세와 같은 URL·HTTP method를 가진 Controller가 있고 서비스 경로가 연결된 경우다. Entity나 프론트 mock만 존재하는 경우는 구현으로 세지 않았다.

| 인증·사용자·판매자 | 18 | 10 | 0 | 8 | refresh/logout/admin login, 판매자 인증·전환 전체 누락 |

### 3.1 인증·계정

완료된 것은 회원가입, 로그인, 사용자 프로필, 배송지 CRUD, 판매자 프로필 조회·수정이다. 회원가입과 로그인 뒤 SSAFY member 생성/조회로 `userKey`를 백필하려는 코드도 있다.

다음은 비어 있다.

- AUTH-03 Access Token refresh
- AUTH-04 refresh token 폐기를 포함한 logout
- AUTH-05 별도 `admins` 테이블 기반 관리자 로그인
- SEL-01/02 휴대폰 인증 요청·확인
- SEL-03/04 SSAFY 1원 송금 기반 정산계좌 인증 요청·확인
- SEL-05 검증 완료 후 `seller_profiles` 생성과 판매자 전환

이 누락은 단순 관리 기능이 아니다. 신규 사용자가 판매자 권한을 얻지 못하므로 상품·공동구매 기능이 구현되어 있어도 정상 UI 흐름으로 진입할 수 없다.

### 3.2 상품·공동구매·카카오페이·반품: 김태민 담당 범위

카테고리 20종 seed, 상품 CRUD·이미지, AI 추출 실패 격리, 청약철회 제한 검토, 공동구매 생성·조회·운영 수정·무참여 취소·모집 판정, 카카오페이 ready/approve/cancel/fail, 반품 미리보기·신청·판매자 처리·이의·자동 승인·수거 후 환불·관리자 심사는 구현되어 있다.

이번 감사에서 RTN-10/11을 추가하며 다음도 함께 고쳤다.

- 관리자 검토 목록은 `admin_review_required=true`인 구매확정 후 신청과 이의제기를 조회한다.
- 관리자는 `REQUESTED` 또는 `DISPUTED`만 승인·기각할 수 있다.
- 승인 시 `approve_type=ADMIN`, `forced_by`, `forced_at`을 기록하고 참여를 `RETURNING`으로 옮긴다.
- 기각 시 사유와 강제 처리자를 기록하고 구매확정 보류를 해제한다.
- 판매자 거부 뒤 구매자가 이의제기하면 `confirm_hold`를 다시 설정한다. 이 조치가 없으면 관리자 심사 중 자동 구매확정이 실행될 수 있었다.

GRP-10은 아직 완료라고 할 수 없다. 판매자 귀책 철회는 참여자 전원 환불, 정산 제외, 위반 후보 생성을 하나의 업무로 묶는다. 현재 반품 `RefundPort` 구현은 카카오페이만 연결되고 카드 취소는 별도 `CardRefundPort`, 코인 공통 환불 adapter와 `refunds` 도메인은 없다. 그룹바이 서비스가 타 결제수단 내부 구현을 직접 참조하게 만들면 담당자 독립성이 다시 깨진다.

### 3.3 프론트와 백엔드의 거짓 양성

다음 프론트 기능은 화면과 API client가 있지만 실제 백엔드가 없다.

- 판매자 정산 목록·상세: `/sellers/settlements`, `/sellers/settlements/{id}`
- 판매자 제재 이력: `/sellers/me/penalties`
- 알림 목록·미읽음 수·읽음 처리: `/notifications/**`
- 판매자 귀책 철회 버튼이 호출하는 `/sellers/group-buys/{id}/withdrawal`

MSW handler가 이 경로를 성공시켜 개발 화면에서는 정상처럼 보일 수 있다. 실서버 모드에서는 404가 발생한다.

## 4. ERD·canonical schema·Flyway·JPA 비교

### 4.1 canonical schema의 32개 테이블

JPA Entity가 있는 핵심 테이블은 사용자, 주소, 판매자 프로필, 카테고리, 제한 사유, 상품·이미지, 정책, 공동구매, 참여, 결제 및 카드·카카오·코인 하위 테이블, SSAFY 로그, 에스크로, 배송, 반품, 판매자 제재다.

Entity 또는 실질 구현이 없는 canonical 테이블은 다음과 같다.

| 테이블 | 상태 | 연결되는 미구현 기능 |
| --- | --- | --- |
| `seller_verifications` | Entity/Service/Controller 없음 | SEL-01~04 |
| `admins` | Entity/Auth 없음 | AUTH-05와 모든 실제 관리자 로그인 |
| `chain_scan_cursors` | Entity 없음 | 다중 인스턴스에서 체인 스캔 위치 영속화 |
| `settlements` | 구현 없음 | STL-01~07 |
| `settlement_items` | 구현 없음 | 정산 포함·제외·상계 근거 |
| `refunds` | 구현 없음 | RFD-01~04와 결제수단 공통 환불 이력 |
| `notifications` | 구현 없음 | NOTI-01~03 |
| `audit_logs` | 구현 없음 | ADM-07, 정책·강제 처리 감사 |

`ReturnRequestHistory`와 `kakaopay_cancellations`처럼 canonical schema v2 이후 Flyway에서 추가된 구조도 있다. 이는 기능 확장 자체는 타당하지만, schema 문서와 ERD를 Flyway 최종 상태로 다시 생성하지 않으면 새 개발자가 서로 다른 DB 모양을 보게 된다.

### 4.2 ERD 이미지의 오래된 명칭

ERD 이미지에는 판매자 관계가 `sellers` 중심으로 보이는 부분이 있지만 canonical schema와 코드는 `users`의 PK를 공유하는 `seller_profiles`를 사용한다. 요구사항 PDF의 분리 계정 서술과도 이어지는 오래된 흔적이다. 실행 기준을 `seller_profiles`로 유지하고 ERD를 최신화해야 한다.

### 4.3 Flyway 버전 정합성

최신 `DevelopV1`을 실제 MySQL에 기동했을 때 V8이 두 개여서 시작 자체가 실패하던 문제가 있었다. 이미 적용된 카테고리 V8의 이름과 checksum을 보존하고 뒤늦게 합쳐진 주소 변경을 V10으로 이동했다.

- 기존 DB: V8 checksum 유지, V9·V10 순차 적용 확인
- 새 빈 DB: V1부터 V10까지 적용 후 JPA validation과 Spring Boot 시작 확인
- `FlywayMigrationVersionTest`: 같은 버전 번호 재사용을 회귀 테스트로 차단

이 사례가 보여 주는 원칙은 “파일 내용이 둘 다 필요하면 둘 다 살린다”가 아니라, 원격에 이미 적용된 이력을 보존한 채 충돌한 새 변경을 다음 버전으로 재작성하는 것이다.

### 4.4 JPA 프로젝트에 SQL이 남아 있는 이유

직접 SQL의 존재만으로 JPA 원칙 위반이라고 판단하지 않았다. 코드를 용도별로 나눴다.

| 용도 | 현재 방식 | 판단 |
| --- | --- | --- |
| 상품·공동구매·반품 상태 변경 | JPA Entity + 변경 감지 | 유지. 상태 전이와 잠금이 객체 한 곳에 모임 |
| 반품 목록 | JPQL scalar projection | 이번에 개선. JPA를 유지하며 N+1 제거 |
| 공동구매 공개/판매자 읽기 모델 | `NamedParameterJdbcTemplate` SQL | 유지. MySQL fulltext, 동적 정렬, 다중 집계를 화면 한 쿼리로 만드는 CQRS 경계 |
| 참여 화면 읽기 모델 | JDBC projection | 타 담당 영역. 실행계획과 통합 테스트 근거를 유지해야 함 |
| Flyway migration | SQL | 당연히 유지. 배포 DB 구조 이력 자체임 |
| 테스트 fixture | SQL insert/update | 허용. 실제 스키마 계약을 빠르게 구성하는 테스트 도구이며 운영 Repository가 아님 |

즉 쓰기 도메인 규칙을 SQL 문자열에 흩뿌리는 것은 피해야 하지만, MySQL 고유 검색과 복잡한 화면 projection까지 억지로 Entity 그래프로 만들면 객체 로딩·N+1·동적 쿼리 복잡도가 더 커질 수 있다. 남겨 둔 SQL에는 반드시 목적 주석, parameter binding, 실제 DB 통합 테스트와 실행계획 검증이 따라야 한다.

## 5. 외부 SSAFY 금융망·카카오페이 설계 비교

### 5.1 SSAFY 금융망

외부 플로우와 XLSX를 대조하면 카드 결제의 선행 순서는 API key → member 생성/조회 → userKey 저장 → 카드 승인이다. 현재 구현은 다음 계약을 사용한다.

- member 생성/조회로 `userKey` 연결
- `createCreditCardTransaction`에 Header, cardNo, cvc, merchantId, paymentBalance 전달
- 거래 고유번호와 승인 결과 저장
- `deleteTransaction`은 금액 필드가 없어 원거래 전액 취소만 가능
- 카드번호는 마지막 4자리만 남기고 CVC는 저장하지 않음
- 외부 호출 timeout과 응답 로그 기록

SSAFY API key는 로컬 `.env`에 존재하는 것만 확인했으며 원문은 읽기 결과, 문서, 로그, 커밋에 남기지 않았다. 다만 실제 결제 E2E에는 SSAFY에 생성된 테스트 사용자·카드·가맹점의 유효성이 필요하다.

### 5.2 카카오페이

개발용 secret key는 로컬 `.env`에 존재하는 것만 확인했다. `TC0ONETIME` CID를 사용하는 개발 테스트는 별도의 운영 가맹점 계약 없이 개발자 센터 키로 연동할 수 있다. ready와 approve 사이에는 DB에 redirect state를 저장하고 사용자·결제·state를 다시 검증하며, 취소는 별도 멱등 기록으로 이중 취소를 막는다.

실제 외부 API 성공까지 자동으로 보장된 것은 아니다. 네트워크가 필요한 provider sandbox E2E와 사용자가 결제창에서 승인하는 수동 단계가 남아 있다.

## 6. 비기능 요구사항 감사

### 6.1 보안

| 요구 | 상태 | 근거와 문제 |
| --- | --- | --- |
| HTTPS | 미검증 | 배포·reverse proxy·CI 설정이 저장소에 없음 |
| 비밀번호 단방향 hash | 구현 | BCrypt 사용 |
| 정산계좌 암호화·화면 마스킹 | **미구현/중대** | 사용자·판매자 계좌를 평문 컬럼에 저장하고 profile 응답에 원문 반환 |
| 역할별 API 분리 | 부분 구현 | `/admin/**`, `/sellers/**` role 보호. 통합 사용자 모델은 최신 API 결정이나 세부 소유권은 기능별 테스트 필요 |
| 타인 거래·배송 접근 차단 | 주요 경로 구현 | 결제·참여·배송·반품에서 user/seller 조건 사용 |
| 결제·정산·환불·반품·제재 권한 | 부분 | 구현된 영역은 검사하지만 미구현 도메인은 판단 불가 |
| 카드 인증정보 비저장 | 구현 | 카드번호 mask만 저장, CVC 미저장, 로그 snapshot에도 제외 |

정산계좌 문제는 후순위 리팩터링이 아니라 데이터 보안 설계 작업이다. 암호화 key 관리, JPA converter 또는 암호화 서비스, 기존 데이터 migration, 마지막 4자리 기반 mask DTO, 키 회전 방침을 함께 설계해야 한다.

### 6.2 데이터 정합성

슬롯은 Redis Lua로 원자 선점하고 DB `@Version`과 결합한다. 금액은 long 원 단위, 공동구매 생성 시 snapshot, 반품 환불액도 신청 시 snapshot이다. 반품 신청과 구매확정은 participation lock과 `confirm_hold`로 경쟁을 막는다.

반면 전체 요구사항의 정산·공통 환불·상계가 미구현이므로 다음을 아직 증명할 수 없다.

- 에스크로 총액과 미해제 결제 합계의 지속적 reconciliation
- 정산 공식과 실제 지급액 일치
- 하나의 참여가 두 번 환불·상계되지 않는 전역 멱등성
- 구매확정 후 선환불과 다음 정산 상계

### 6.3 성능

- 결제 이력 N+1: `1 + N`에서 2회로 개선하고 별도 성능 문서 작성
- 반품 목록 N+1: 최대 `2 + 3N`에서 2회로 개선. 1,000행 통제 모델 중앙값 6,014.375ms → 15.504ms, 99.74% 감소
- 공개 공동구매: fulltext index와 전용 projection 사용
- AI timeout: 기본 10초
- 슬롯 만료 scheduler: 매분

이 결과는 로컬 회귀와 통제 모델이지 정상 부하 2초 SLA 인증이 아니다. 운영 유사 MySQL 데이터, `EXPLAIN ANALYZE`, HTTP 부하 테스트의 P95/P99가 추가로 필요하다.

### 6.4 운영·가용성

timeout은 SSAFY, 카카오, AI, 시세, blockchain RPC에 설정되어 있다. 그러나 일관된 retry/backoff/circuit breaker 정책은 없다. 외부 결제에서 무조건 자동 retry하면 이중 승인 위험이 있으므로 조회·멱등 키·provider 거래 상태 확인과 함께 설계해야 한다.

슬롯 만료, 모집 종료, 배송 기한, 자동 구매확정, 반품 자동 승인·환불 scheduler는 존재한다. 다중 인스턴스 분산 lock과 공통 job 실행 이력은 없다. 현재 `@Scheduled`는 인스턴스마다 실행되므로 멱등한 상태 전이가 일부 중복을 흡수하더라도 모든 배치가 운영 요구를 충족한다고 볼 수 없다.

저장소에서 CI/CD 설정을 찾지 못했다. NFR-OP-04는 미구현이다.

## 7. 테스트와 코드 검토 결과

### 7.1 자동화 현황

- 백엔드: 테스트 클래스 68개, `@Test` 메서드 348개
- 반품 변경: service 단위, repository/JPA 통합, HTTP 권한·상태 전이, 성능 비교 추가
- 프론트: typecheck, ESLint, production build script 존재
- 프론트 자동 테스트: `*.test.*`, `*.spec.*` 파일 0개
- CI/CD pipeline: 없음

전체 백엔드 회귀 348건 중 345건은 통과했고, 3건은 Redis가 `localhost:6379`에 없어 실패한다.

- `GroupBuySlotGateIntegrationTest` 2건
- `PaymentServiceConcurrencyTest` 1건

실패 원인은 `RedisConnectionFailureException`이며 테스트를 skip하거나 mock으로 약화하지 않았다. Redis가 준비된 환경에서 다시 실행해야 최종 녹색 판정이 가능하다.

### 7.2 이번 코드 리뷰에서 발견·수정한 항목

1. 중복 Flyway V8 때문에 애플리케이션이 시작되지 않던 문제
2. 공동구매 운영 상세를 목록 100건 조회 후 프론트에서 찾던 불필요한 조회
3. 반품 목록의 최대 `2 + 3N` 조회
4. 이의제기 후 구매확정 보류가 복구되지 않던 상태 전이 경쟁
5. ERD에 이미 있는 관리자 심사 상태와 `forced_by`가 API에 연결되지 않던 누락

### 7.3 확인했지만 아직 남긴 항목

- crypto scheduler에서 설정값 0을 “비활성”으로 설명하지만 `@Scheduled(fixedDelayString=0)`은 시작 오류가 된다. `@ConditionalOnProperty`로 활성 여부를 분리해야 한다.
- 관리자 강제 반품 처리는 `forced_by`를 기록하지만 `audit_logs` 자체가 없어 NFR-ADM 감사 추적을 완전히 충족하지 못한다.
- 상세 DTO에는 강제 처리자·처리시각이 노출되지 않는다. 관리자 종합 화면 계약 확정 뒤 추가할 수 있다.
- 외부 API retry는 timeout만 있고 체계적 backoff/조회 보정이 없다.

## 8. 남은 작업의 의존성 우선순위

다른 팀원이 독립적으로 작업하려면 화면 순서가 아니라 공통 계약과 데이터 경계를 먼저 고정해야 한다.

| 우선순위 | 선행 작업 | 이유 | 이후 독립 가능한 작업 |
| ---: | --- | --- | --- |
| P0 | `RefundPort` 공통화, `refunds` Entity/Repository, 결제수단 adapter 계약 | GRP-10, PAR-03, 모집 실패, 반품 환불이 모두 의존 | 그룹바이 철회·참여 취소·관리자 재시도·각 결제 담당 adapter |
| P0 | seller verification + seller conversion 계약 | 실제 판매자 진입이 막힘 | 상품/공구 UI 실제 E2E |
| P0 | 계좌 암호화·마스킹 설계와 migration | 민감정보 평문 노출 | 판매자 인증·정산 개발 |
| P0 | `admins` 인증과 audit actor 계약 | RTN/PEN/STL/ADM UI를 실제 로그인으로 시험 불가 | 각 관리자 도메인 독립 구현 |
| P1 | 정산 aggregate와 `settlement_items` 포함/제외 계약 | 에스크로 해제, 반품, 상계의 종착점 | seller/admin 정산 API와 계좌이체 adapter |
| P1 | 판매자 귀책 이벤트/제재 후보 계약 | GRP-10과 배송 위반이 공유 | penalty review API 독립 구현 |

| P2 | MySQL 부하·실행계획, frontend E2E, CI | 현재 수동 검증 의존 | 성능·회귀 품질 gate |

충돌이 발생하면 최신 `DevelopV1` 구현을 기준으로 보존하고, 담당 브랜치에서 필요한 부분을 새 계약 위에 다시 적용한다. 두 버전을 조건문이나 중복 서비스로 모두 살려 코드 길이를 늘리지 않는다.

## 9. 완료를 위해 사용자·팀에 필요한 것

### 지금 바로 필요한 환경

1. Redis: Docker Desktop에서 프로젝트 Redis를 실행하거나 접근 가능한 `REDIS_HOST`, `REDIS_PORT` 제공
2. S3: 상품 이미지 실제 업로드를 위한 bucket, region, access key, secret key. 채팅에 붙이지 말고 `backend/.env`에 직접 저장
3. AI: 실행 가능한 추출 서버 주소 또는 로컬 8000 서버
4. SSAFY E2E: 금융망에 등록된 테스트 사용자 이메일, 결제 가능한 테스트 카드와 CVC, V7의 가맹점 ID가 현재 계정에서 유효한지 확인
5. Kakao E2E: 현재 dev key와 TC0ONETIME 사용 권한, 브라우저 redirect가 가능한 frontend/backend 동시 실행

### 팀 결정이 필요한 계약

1. 카드·코인·카카오를 하나로 묶는 환불 요청/결과 DTO와 멱등 키 규칙
2. 카드 전체 취소가 불가능한 경우 SSAFY 계좌이체로 보상 환불할지에 대한 정책
3. 코인 환불을 원화 계좌이체로 할지 같은 자산으로 보낼지, gas와 환율 차이를 누가 부담하는지
4. 관리자 ID와 일반 user ID의 namespace, `forced_by`/`audit_logs` actor 연결 방식
5. 정산계좌 암호화 key 보관 위치와 운영 키 회전 방식
6. 최신 API·DB와 충돌하는 요구사항 PDF의 계정 분리/목표 인원/배송비 문구를 개정할 문서 담당자

이 입력과 계약이 없으면 임의 구현은 가능하지만 팀원 코드와 충돌하거나 금액 정책을 다시 뜯어고칠 가능성이 높다.

## 10. 최종 판정 기준

다음 조건이 모두 만족되어야 “전체 MVP 완료”로 상태를 바꿀 수 있다.

1. API 명세의 Must 경로가 실제 Controller부터 DB·외부 adapter까지 연결된다.
2. 신규 사용자 가입부터 판매자 전환, 상품·공동구매, 모든 결제수단, 배송, 구매확정/반품/취소, 환불, 정산까지 한 데이터로 종단 통과한다.
3. 실패·timeout·중복 callback·scheduler 재실행에서도 금액과 상태가 중복 변경되지 않는다.
4. ERD/canonical schema/Flyway/JPA의 이름·컬럼·상태가 일치하고 문서가 최종 migration을 반영한다.
5. 민감정보 암호화·마스킹, role·소유권, 카드정보 비저장 요구를 통과한다.
6. Redis 포함 전체 backend 회귀, frontend 자동 테스트, 외부 sandbox E2E, 운영 유사 성능 테스트가 녹색이다.
7. CI/CD가 같은 검증을 병합 gate로 실행한다.

현재는 김태민 담당 구현은 거의 끝났지만, 플랫폼 전체로는 위 조건을 충족하지 못한다. 가장 정확한 표현은 **“상품·공동구매·카카오페이·반품 핵심 구현 완료, 공통 환불 의존 1건과 전체 플랫폼의 계정 전환·정산·제재·알림·관리 운영 미완료”**다.
