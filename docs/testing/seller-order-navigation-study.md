# B06 주문 관리 진입의 공동구매 선택 보존

이슈: S15P21B205-192. 기준 aa19698. DevelopV2 전용이며 배포 서버·주문 상태 변경은 없다.

## 재현과 원인

공동구매 101 상세에서 주문 관리로 이동했는데 최신 공동구매 281이 보였다. 상세 링크가 /seller/orders로만 이동했고 주문 페이지는 useState(null)에서 목록 첫 항목을 골랐다. 주문 관리 화면은 송장과 배송 상태를 바꾸는 화면이므로 선택 유실은 단순 편의 문제가 아니다. 사용자가 상품명을 놓치면 다른 주문에 작업할 수 있다.

## 선택 기준

전역 상태에 마지막 공구를 저장하면 새로고침·뒤로가기·직접 링크에서 의미가 불명확해진다. URL에 groupBuyId를 넣으면 현재 작업 대상을 다시 열고 공유할 수 있다. 이것은 조회 식별자이며 인증정보를 URL로 보내는 변경이 아니다. 서버 권한 검증은 여전히 필수다.

목록 첫 100개에 없다는 이유만으로 첫 항목으로 돌아가는 방식도 제외했다. 오래된 정상 공동구매가 첫 페이지 밖에 있을 수 있기 때문이다. 명시된 ID는 유지하고 목록 밖이면 판매자 상세 API로 소유권 확인이 완료된 후 주문 보드를 연다. 존재하지 않거나 다른 판매자 공구면 기존 오류 경계가 서버 거절을 표시하고 임의의 다른 주문을 대신 열지 않는다. 숫자 ID 형식이 아닌 입력은 명확한 오류로 표시한다.

## 실제 변경

orderSelection.ts는 링크 생성 및 명시적 선택 해석을 담당한다. SellerGroupBuyDetailPage의 링크가 현재 item.id를 전달한다. SellerOrdersPage는 useSearchParams로 읽고 셀렉트 변경도 URL에 반영한다. 따라서 뒤로가기/앞으로가기는 해당 URL의 선택으로 돌아온다. 보드의 key는 공구 ID를 유지하여 다른 공구의 송장 편집 상태가 넘어가지 않게 한다. 스타일은 변경하지 않았다.

## 시험과 검토

순수 계약 9개는 링크의 ID, 목록 밖 명시적 선택 유지, 파라미터 없는 기본 진입, 빈 값·0·음수·문자·슬래시·소수 입력을 검사한다. 실제 페이지 SSR 3개는 query cache와 MemoryRouter를 사용해 URL101 진입 시 281이 선택되지 않음, 권한 상세 조회가 있는 경우 상품명 반영, 잘못된 ID의 보드 미표시를 검사한다. 브라우저 클릭 E2E나 실제 타인 계정 API 호출을 이 결과로 대체하지 않는다.

전체 프런트 124개 통과, 타입 검사 포함 production build, ESLint 및 diff 검사를 수행했다. 초기 SSR 검사는 페이지 안내 문구에도 같은 단어가 있어 한 번 실패했으며 검사 대상을 보드 제목으로 좁혔다. 잘못된 ID일 때 브라우저가 첫 옵션을 시각적으로 선택하지 않도록 빈 안내 옵션도 추가했다. 기능 정합성 수정이므로 응답시간 개선 수치를 주장하지 않는다. 서버의 상세/배송 API 소유권 검사는 기존 계약을 사용하며 이 MR에서 권한 정책을 완화하지 않았다.

학습 순서: 기존 두 페이지 링크와 초기값 문제 → orderSelection 테스트 → URL 기반 상태 → 목록 밖 상세 경계 → DeliveryBoardView의 key를 읽는다. 재실행은 frontend의 npm test, npm run lint, npm run build이다.
