# FR-PAY-26 미매칭 코인 입금 환불 실행권 학습 기록

이슈 S15P21B205-213. DevelopV2 de1d116을 기준으로 분리한 버그 수정이다. 외부 체인 송금은 모두 모킹했고 실제 지갑, EC2 데이터, DevelopV1은 변경하지 않았다.

## 1. 증상과 수정 전 재현

공통 참여/반품 환불은 실행권 보호를 사용하지만 CryptoDepositRefundService는 별도 경로였다. 입금 원장을 생성한 후 바로 refundAsReceived를 호출하고, 응답 불명 예외를 받으면 ledger.fail만 호출했다. 코드에 “체인 확인 후 재처리”라는 문구는 있었지만 DB에서 재송금을 금지하는 상태는 남지 않았다.

Refund.markFailed는 executionClaimed가 true이면 활성 마커를 보존한다. 그런데 이 경로는 실행권을 한 번도 획득하지 않으므로 false였다. FAILED가 되고 마커가 해제되면 같은 입금의 다음 관리자 요청은 새 환불 원장을 만들고 토큰을 다시 전송했다. 메시지에 경고를 적는 것과 실제 동작을 금지하는 것은 다르다.

수정 전 실제 Spring/JPA/H2에 UNMATCHED 입금 한 건을 만들었다. 외부 반환 어댑터만 EXTERNAL_SERVICE_UNAVAILABLE를 던지도록 모킹하고 같은 관리자 환불 메서드를 두 번 호출했다. 첫 refundId=1, 두 번째 refundId=2가 반환되어 “같은 원장이어야 한다” 단언이 실패했다. 실패 결과는 crypto-deposit-refund-before.json에 별도로 보존했다. 운영 거래의 ID가 아니라 격리된 H2 행이다.

실제 체인 송신 성공을 재현한 것이 아니다. 응답을 잃었을 때 이미 전송했는지 모른다는 조건에서, 코드가 두 번째 전송 시도를 허용한다는 것을 재현한 것이다. 이 불확실성에서 다시 보내지 않는 것이 이번 안전 조건이다.

## 2. 구현 대안과 선택

한 방법은 입금 테이블에 전용 REFUNDING/UNKNOWN 상태와 새 실행권 테이블을 추가하는 것이다. 하지만 공통 refunds 원장에는 이미 execution_claimed와 활성 유일 마커, 잠금 기반 tryClaimExecution이 있다. 같은 금융 실행 조건을 또 만들면 두 도메인의 재시도 규칙이 달라질 수 있어 기존 원장을 재사용했다.

DB 트랜잭션을 체인 응답까지 길게 유지하는 방법도 쓰지 않았다. 외부 송신은 되돌릴 수 없으므로 DB 롤백만으로 돈이 돌아오지 않고, 지연 시간 동안 DB 연결과 잠금을 점유한다. 짧은 원장 실행권 트랜잭션을 먼저 커밋한 뒤 외부를 호출한다. 공개 환불 메서드에는 트랜잭션 NEVER를 붙여 상위 트랜잭션 안에서 잘못 호출하는 경우도 차단한다.

같은 원장이 PROCESSING이지만 execution_claimed=false라면 아직 송신을 시작하지 않았다는 영속 증거가 있다. 관리자의 재요청은 이 원장을 그대로 사용해 실행권을 얻을 수 있다. 시간을 기준으로 true를 false로 돌리거나 UNKNOWN을 자동 재시도하는 기능은 추가하지 않았다.

## 3. 실제 코드 흐름

1. 입금이 존재하는지 읽고 공통 원장의 활성/완료/결과 불명 환불을 먼저 찾는다.
2. 이미 COMPLETED이면 환율·지갑 상태·체인 호출 없이 입금 상태 종결만 재시도한다.
3. 결과 불명 FAILED+claimed 또는 진행 중 claimed이면 기존 원장을 반환한다.
4. 새 환불은 기존 정책대로 자산을 확인하고 당시 원화 참고액을 기록한다. 실제 반환 수량은 rawAmount 원본 그대로다.
5. 기존 미송신 원장 또는 새 원장에 대해 공통 tryClaimExecution을 호출한다. 패자는 현재 원장만 읽어 반환한다.
6. 지갑 비활성처럼 송신하지 않았음이 확실한 준비 실패는 failRejected로 실행권 해제와 실패를 함께 커밋한다.
7. 실행권 소유자만 refundAsReceived를 호출한다. 완료 원장에 해시/수량을 남긴 뒤 별도 입금 종결을 수행한다.

ChainTransferClient는 송신 전 조회 실패, 노드 거부, 전송 후 영수증 대기 시간 초과를 충분히 다른 타입으로 구분하지 않는다. 따라서 어댑터 호출에 들어간 뒤의 예외를 “확실한 미송신”이라고 추정하지 않는다. BusinessException뿐 아니라 예기치 않은 RuntimeException에도 실행권을 유지한 FAILED 원장을 남긴다. 관리자 공통 retry도 이 실행권을 보고 거절한다.

## 4. 외부 성공 뒤 입금 상태 저장만 실패한다면

기존 코드는 completeByCrypto와 markDepositRefunded를 같은 try/catch에 두었다. 앞의 원장은 이미 COMPLETED로 커밋됐는데 뒤의 입금 저장이 실패하면 catch가 완료 원장을 FAILED로 바꾸려 했다. 엔티티가 이를 거절하더라도 요청은 실패하고, 다음 요청은 기존 원장을 반환하기만 해서 입금 상태 복구가 안 됐다.

이번에는 송신/원장 완료와 입금 종결을 분리했다. 완료 원장은 그대로 보존하고 입금 종결 실패를 명확하게 기록한다. 다음 관리자 요청은 완료 원장을 먼저 찾아 markDepositRefunded만 다시 수행한다. 환율 서비스가 장애여도 이미 완료된 환불의 내부 상태 복구를 막지 않는다.

원장 완료 응답 처리에서 예외가 났더라도 다시 읽은 원장이 이미 COMPLETED이면 실패로 덮지 않는다. DB 자체를 읽을 수 없는 장애에서는 요청이 실패할 수 있으나, 미리 커밋한 실행권은 해제하지 않아 다음 전송을 막는다. 자동 체인 대조나 관리자 강제 실행권 해제는 구현하지 않았다.

## 5. 테스트 설계와 관측 지표

새 CryptoDepositRefundSafetyIntegrationTest는 실제 JPA 트랜잭션과 원장을 사용한다. CryptoRefundService와 시세만 모킹하고, 종결 장애는 실제 CryptoTxRecordService의 한 호출에만 예외를 주입한다.

| 시험 | 합격 조건 |
|---|---|
| 응답 불명 후 같은 입금 재요청 | 동일 원장 1건, 외부 반환 호출 1회, 실행권 유지, 공통 retry 거절 |
| 예기치 않은 RuntimeException | 두 번째 송신 0회, 실행권 유지 |
| 지갑 비활성 | 외부 호출 0회, 실행권 해제; 설정 보완 후 정상 실행 가능 |
| 송금 완료 후 입금 상태 저장 실패 | 원장 COMPLETED 유지; 재요청에서 입금만 REFUNDED, 외부 호출 합계 1회 |
| 원장 예약 직후 프로세스 중단에 해당하는 상태 | 미송신 기존 원장으로 실행, 새 원장 생성 없음 |
| 첫 외부 호출 응답 대기 중 두 번째 요청 | 원장 PROCESSING 보존, 전송 1회, 승자 정상 완료 |
| 종결 복구 시 가격 서비스 장애 | 시세 조회 없이 복구, 이미 환불 완료 입금도 동일 응답 |

수정 전 핵심 시험은 환불 원장 ID가 1에서 2로 바뀌어 실패했다. 수정 후에는 같은 원장 ID를 유지하고 송신 호출 수를 1회로 검증한다. 이는 정합성 지표이며 성능 최적화가 아니다. 전체 테스트 실행시간으로 거래 처리 속도 개선율을 만들지 않는다.

## 6. 남아 있는 경계

이 변경은 이미 기록된 미매칭/금액 오류 입금의 반환 실행 안전성을 수정한다. 종료된 결제의 늦은 영수증/컨펌 추적 누락, 미달·초과 입금의 확정 컨펌 추적과 결제 재매칭 경계는 별도 후속 점검이다. 입금 감지 자체가 없으면 이 서비스가 환불할 대상을 만들 수 없다.

과거 원장과 실제 체인이 일치하지 않는 내역을 자동으로 수정하거나 송금하지 않았다. 이미 배포된 데이터가 있다면 제공사/체인 대조로 송신 여부를 확인해야 한다. 임의의 기다린 시간만으로 실행권을 해제해서는 안 된다. 이번에는 새로운 스키마 변경 없이 기존 V18 실행권을 사용한다.

실제 MySQL 다중 노드, 체인 재구성, nonce 경쟁, 실제 지갑 잔액/가스 문제를 H2·모킹 시험으로 완료 처리하지 않는다. 로컬 검증, DevelopV2 병합, 운영 배포는 별개 단계다.

## 7. 실행 기록

재현 명령은 backend의 Java 21 `./gradlew.bat test --tests '*CryptoDepositRefundSafetyIntegrationTest' --console=plain`이다. 수정 전 1개 시험이 실패했고, 수정 후 기존 단위 9개와 신규 통합 6개(총 15개)가 모두 통과했다. 위 표의 7개 검증 조건 중 종결 실패 복구와 가격 서비스 장애는 한 통합 테스트에서 함께 확인한다. 최초 보고에서 조건 수를 테스트 메서드 수로 잘못 셌으며 XML의 tests=6에 맞게 정정했다. 이어서 `./gradlew.bat test --console=plain` 전체 회귀에서 118개 클래스 / 763개 중 760개 통과 / 실패·오류 0 / 환경 제외 3개(Redis 2, S3 1)를 확인했다. 전체 실행 3분 28초는 이 로컬 검증의 소요시간일 뿐 금융 처리 응답 시간 지표가 아니다.
