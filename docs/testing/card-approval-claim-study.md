# 카드 승인 실행권과 결과 불명 처리 학습 기록

이슈 S15P21B205-194. B15 중복 승인, B24 승인 중 취소/만료, B26 응답 유실 후 재승인은 모두 외부 승인 실행권이 없다는 같은 원인에 속한다. DevelopV2 a9fa9c1 기준 전용 브랜치이며 실제 금융망 거래와 DevelopV1 배포본을 변경하지 않는다.

## 1. 재현한 문제

기존 CardPaymentService는 진행 중인 결제를 읽고 금융망을 호출했다. 결제 상태가 PAID로 바뀌는 시점은 외부 응답 뒤였다. 따라서 요청 두 개가 동시에 진행 중 상태를 읽거나 첫 금융망 응답을 잃으면 같은 paymentId로 금융망을 다시 호출할 수 있었다. 프런트 버튼 비활성화만으로는 재전송, 다른 탭, 서버 동시 요청을 막지 못한다.

새 테스트는 은행이 첫 요청에서 응답 유실 예외를 던지고 다음 요청에서 성공하도록 설정한다. 수정 전 관측은 은행 호출 2회, 첫 결과 EXTERNAL_SERVICE_UNAVAILABLE, 두 번째 성공, 최종 PAID였다. 첫 호출이 실제로 결제되지 않았다는 증거는 없으므로 이 재시도는 이중 청구 위험이다. `expected 1 but was 2`로 집중 테스트가 실패한 뒤 수정했다.

공통 결제 행 잠금(B16)은 내부 상태 전이를 직렬화하지만 금융망 호출 이전의 중복 실행은 막지 못한다. 또한 카드 응답을 기다리는 동안 슬롯 만료나 취소가 성공하면 외부에서는 돈이 나갔는데 참여를 확정하지 못한다. 외부 요청 전부터 승인 실행 중임을 다른 트랜잭션이 볼 수 있어야 한다.

## 2. 대안과 선택 기준

금융망 호출 전체에 DB 잠금을 걸면 코드상 직렬화는 쉽지만 느린 응답 동안 연결과 행 잠금을 점유한다. 금융망 성공 후 DB 롤백이 발생해도 외부 청구는 취소되지 않는다. 서버 메모리 락은 여러 서버나 재시작 후에는 사라진다. 프런트 요청 키만 신뢰하면 외부 호출 자체의 결과 불명 문제를 해결하지 못한다.

따라서 별도 짧은 트랜잭션으로 실행권을 먼저 커밋하고 외부 호출을 수행한다. CardApprovalRecordService가 이 트랜잭션 경계를 담당한다. 오케스트레이션인 CardPaymentService.approve는 Propagation.NEVER로 기존 트랜잭션에 포함되는 호출을 금지한다. claim의 커밋이 외부 호출 이후로 미뤄지는 잘못된 재사용을 방지하기 위해서다.

## 3. 상태와 흐름

payments.card_approval_status가 NULL이면 아직 실행권이 없다. claim은 결제 행을 잠그고 소유자, CARD 수단, PROCESSING 상태, 미만료, 기존 실행권 없음 조건을 확인한다. 통과하면 PROCESSING과 기관거래고유번호를 기록하고 커밋한다. 여기서 PROCESSING은 결제 전체 상태와 별도의 카드 실행 상태다.

이후 금융망 호출에는 DB 트랜잭션을 유지하지 않는다. 성공 응답의 카드 상세 증거를 저장하고 공통 참여·에스크로 확정을 호출한다. markPaid는 승인 실행 상태를 COMPLETED로 바꾼다. 명시적인 거절 응답이면 카드 실행 상태 FAILED를 먼저 기록하고 결제 실패 처리가 슬롯을 반환한다. 응답 유실, 상세 저장 오류, 내부 확정 오류처럼 성공 여부가 불명확하면 UNKNOWN을 기록한다. UNKNOWN 기록마저 실패하면 먼저 커밋한 PROCESSING이 남아 재승인을 막는다.

recordOutcome은 실행 상태가 아직 PROCESSING인 경우에만 변경한다. 이미 확정된 결제를 후속 예외 때문에 UNKNOWN으로 되돌리거나 명시적인 거절을 UNKNOWN으로 덮어쓰지 않는다. 카드 실행 PROCESSING/UNKNOWN이면 일반 취소와 실패/만료 배치가 슬롯을 해제하지 못한다. 승인 요청이 유효시간 안에 실행권을 얻었다면 응답이 슬롯 만료 후 와도 그 승인 자체를 확정할 수 있다. UNKNOWN은 자동 확정하지 않고 거래 대조 대상으로 남긴다.

## 4. 데이터 변경과 배포 주의

V17__claim_card_approval.sql은 실행 상태와 기관거래고유번호 두 nullable 열을 추가한다. 카드 상세가 이미 있는 기존 행은 PAID이면 COMPLETED, 그 외이면 UNKNOWN으로 보수적으로 표시한다. 과거 코드가 외부 호출 증거를 저장하지 못한 거래는 이 backfill만으로 알아낼 수 없다. 기관 내역 대조가 별도로 필요하며 임의로 실패 거래를 다시 승인하지 않는다.

기관거래고유번호는 이후 대조에 필요한 업무 식별자다. 카드번호나 CVC를 새 열에 저장하지 않는다. 기존 로그도 카드번호/CVC 없는 요청 스냅샷을 유지한다. 마이그레이션은 새 버전 배포 전에 적용해야 하며 이 작업에서는 운영 DB에 실행하지 않았다. H2 ORM 테스트 통과를 실제 MySQL migration 실행 증거로 표시하지 않는다.

## 5. 검증 설계

CardLifecycleSafetyAuditTest는 Spring/JPA/H2에서 실제 사용자·배송지·공구·결제·참여·카드 상세 행을 생성한다. 금융망과 정책, API 로그, Redis 게이트는 mock이다. 외부 은행 호출 횟수, 결제 상태, 참여와 카드 상세 행 수, 다른 사람 슬롯의 보존을 함께 확인한다. 실제 돈이나 토큰은 사용하지 않는다.

검증하는 경계는 정상 승인, 승인 중 사용자 취소, 승인 중 슬롯 만료, 응답 유실 후 재승인, 동시 승인, 원 호출이 없어도 커밋된 실행권 유지, 명시적 거절, 승인 전 취소, 동시 취소가 다른 사람의 예약을 감소시키지 않음, 기존 트랜잭션 안에서 외부 승인 호출 금지다. latch로 은행 응답을 지연하여 타이밍 우연에 의존하지 않는다.

수정 전 집중 시험은 은행 호출 2회로 실패했다. 수정 후에는 같은 결제에 은행 호출 1회, UNKNOWN 유지, 취소/만료를 통한 슬롯 반환 없음이다. 정상 및 늦은 성공은 PAID와 참여 1건으로 종결한다. 첫 전체 회귀는 650개 중 647개 통과, 실패/오류 0, Redis/S3 환경 제외 3개였다. 이후 트랜잭션 금지 회귀 1개를 추가한 최종 전체 결과는 101 suites, 651개 중 648개 통과, 실패/오류 0, 환경 제외 3개다. 코드·상태 전이·잠금 순서·비밀정보 비저장 검토 및 diff 검사도 수행했다. CI 파이프라인 결과가 아니라 로컬 실행 결과다.

이 수정은 금융 정합성 수정이지 성능 최적화가 아니다. 실행권 저장 트랜잭션 비용이 추가된다. Gradle 테스트 시간은 API 지연/처리량의 성능 개선 지표로 사용하지 않는다.

## 6. 한계와 별도 수정

외부 금융기관과 DB 사이의 완전한 분산 원자성을 보장하지 않는다. UNKNOWN 또는 실행권만 남은 거래는 자동 재승인하지 않는 안전 정지 상태이며 운영 대조/복구 도구는 별도 구현 대상이다. 실행권 직후 프로세스 종료 시 실제 호출 전이어도 자동 해제하지 않는다. 잘못 재청구하는 것보다 거래 대조가 필요한 상태를 명시적으로 남기는 선택이다.

주소 삭제 후 외부 승인 문제(B25)는 이 MR과 별도로 사전 검증/스냅샷 수명으로 수정한다. 코인·카카오 외부 실행권을 이 카드 전용 변경이 보장하지 않는다. Redis/DB 부수 효과의 롤백 일치 역시 별도 항목이다. Docker 보류로 Redis 2개와 S3 1개 실환경 시험은 실행하지 않았다. 실제 카드 API를 호출하거나 과거 실패 거래를 재처리하지 않았다.

읽는 순서: 실패 재현 테스트 → CardApprovalRecordService.claim → CardPaymentService의 외부 호출 경계 → PaymentService의 종료 가드 → 엔티티 상태 → migration. backend에서 Java 21로 `./gradlew.bat test --tests '*CardLifecycleSafetyAuditTest' --console=plain`, 전체는 `./gradlew.bat test --console=plain`으로 실행한다.
