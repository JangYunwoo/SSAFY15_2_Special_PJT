# 추천 후보의 모집 기간 검증

이슈 S15P21B205-191. 기준 DevelopV2 aa19698. 대상은 AI에 전달하는 후보 조회이며 배포본과 슬롯 발급 코드는 변경하지 않는다.

## 증상과 원인

RecommendationRepository.findCandidates는 상태가 RECRUITING인 공동구매, ACTIVE 상품, 정지되지 않은 판매자만 조회했다. RECRUITING이라는 문자열이 '지금 참여 가능한 모집 기간'을 보장하지 않는다. 판매자가 내일 시작하도록 생성한 공구도 해당 상태일 수 있고, 마감 시각을 지났지만 스케줄러가 아직 상태 전이를 하지 않은 행도 있다. AI는 받은 후보를 점수화할 뿐 모집 기간을 전달받아 재검증하는 계약이 아니므로 이들이 홈페이지 추천으로 나올 수 있었다.

기간은 UTC 시작 시각 포함, 종료 시각 제외인 `[recruit_start_at, recruit_end_at)`로 판단한다. 마감과 같은 시각은 이미 종료다. 기간 판단이 없던 기존 상태 필터만 유지하면 스케줄러 실행 주기 사이에 결과가 일관되지 않는다.

## 대안과 결정

프런트에서 제거하면 이미 서버가 후보 제한을 적용한 뒤이므로 잘못된 후보들이 결과를 차지하고 정상 상품이 누락된다. AI에서 제거하려면 별도 기간 계약이 필요하며 AI가 실패하는 백엔드 fallback에는 적용되지 않는다. 스케줄러만 빠르게 실행하는 것은 짧은 틈을 줄일 뿐 제거하지 못한다. 따라서 후보를 선택하는 SQL의 WHERE에 시간 조건을 넣어 ORDER BY와 LIMIT보다 먼저 거르는 방법을 선택했다.

DB의 로컬 시간 설정에 의존하는 NOW() 대신 애플리케이션에서 UTC 시각을 한 번 정하고 기존 timestamp 변환으로 바인딩한다. SQL 문자열에 사용자 값을 이어 붙이지 않는다. 공개 findCandidates(int)는 기존 호출 계약을 유지하고, 같은 패키지의 시각 인자 오버로드로 고정 시각 경계를 결정적으로 시험한다.

## 구현과 의도적으로 유지한 부분

조회 조건에 `gb.recruit_start_at <= :now`와 `gb.recruit_end_at > :now`를 추가했다. 상품/판매자 상태 조건과 최근 생성 순서, 최대 후보 수, 썸네일 선택은 유지했다. findCandidateSnapshots는 이벤트 기록에서 과거에 조회했던 공동구매의 특징을 얻는 경로이므로 모집 기간 필터를 붙이지 않았다. 이미 마감한 항목의 행동 로그까지 저장 불가로 만들면 후보 노출과 이력 기록이라는 서로 다른 목적이 섞인다.

기존 JDBC 읽기 모델을 JPA로 전면 교체하지 않았다. 이 쿼리는 여러 테이블의 조회 결과를 추천 전용 DTO로 투영하며, 이번 버그는 그 조회 조건 누락이다. 전면 교체는 독립 회귀 범위를 늘리고 기간 오류 해결에 필요하지 않다. JPA 엔티티의 쓰기 경로는 변경하지 않는다.

## 재현 및 전후 결과

RecommendationCandidateWindowTest는 실제 Repository SQL과 ResultSet 매퍼를 H2 MySQL 모드의 격리 DB에서 실행한다. SQL 문자열 포함 여부만 검사하지 않는다. 카테고리, 판매자, 상품, 이미지, 공동구매 테이블의 쿼리 필수 열을 만든 후 고정 시각 2026-09-21T06:00:00Z를 사용한다.

1. 모집 중, 정확한 시작, 시작 1초 전, 정확한 마감, 마감 1초 후를 같은 데이터셋에 넣어 모집 중과 정확한 시작만 반환하는지 본다.
2. 미래 공구가 정렬상 앞에 있고 limit=1일 때도 정상 모집 공구가 반환되는지 본다. 이는 사후 메모리 필터로는 놓칠 회귀다.
3. 마감 후보는 제외하되 동일 ID의 스냅샷 조회는 유지되는지 본다.
4. 기존 상품 비활성, 판매자 정지, RECRUITING 외 상태 제외 규칙이 유지되는지 본다.

수정 전 4개 중 기간 관련 3개가 실패하고 기존 상태 조건 테스트만 통과했다. 수정 후 전체 백엔드 테스트 640개 중 637개 통과, 3개 건너뜀, 실패 0이었다. 테스트는 Windows와 Java 21, 프로젝트 Gradle Wrapper로 실행했다. 이 수치는 기능 정합성 결과이며 처리 속도 개선 수치가 아니다.

## 재실행, 한계, 학습 순서

backend에서 `./gradlew.bat test --tests '*RecommendationCandidateWindowTest' --console=plain`, 전체는 `./gradlew.bat test --console=plain`을 실행한다. 결과 XML은 build/test-results/test에 생성된다. H2는 SQL과 경계를 빠르게 검증하지만 운영 MySQL의 실행 계획이나 인덱스 비용을 대신하지 않는다. 대량 데이터 성능 최적화는 하지 않았으므로 성능 개선 주장은 없다. Redis/S3 3개 테스트는 Docker를 나중에 진행한다는 사용자 요청에 따라 미실행이다.

이 조회가 통과해도 이후 사용자가 결제할 때 마감될 수 있다. 결제 준비 트랜잭션에서의 기간 검증은 반드시 별도 안전망이며 별도 이슈에서 수정한다. 예약 슬롯까지 모두 찬 경우는 결제 시점의 일시적 점유일 수 있으므로 이번 모집 기간 오류와 섞어 노출 정책을 바꾸지 않았다.

학습할 때 후보 조회 → AI rank 또는 fallback → 후보 제한 적용 위치 → 테스트 limit=1 사례 순서로 읽으면 필터 위치가 기능 정확성에 미치는 영향을 볼 수 있다.
