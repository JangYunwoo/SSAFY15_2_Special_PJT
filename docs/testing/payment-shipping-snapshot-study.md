# 결제 중 주소 변경과 배송 요청 유실 수정 학습 기록

관련 이슈: S15P21B205-211. 결제/배송 분류 B25·C05와 일회성 배송 요청 B04를 하나의 데이터 전달 문제로 다룬다. 작업 대상은 DevelopV2이며 DevelopV1, EC2, 배포 DB, 실제 금융 거래는 변경하지 않았다.

## 1. 어떤 문제가 있었는가

사용자는 배송 화면에서 수령인 주소를 고른 다음 결제수단을 선택한다. 화면에서 선택한 주소가 결제 완료 때까지 그대로 쓰일 것이라고 기대하는 것이 자연스럽다. 그러나 기존 코드는 결제 준비에서 주소 ID만 `payments.address_id`에 저장하고, 승인 후 해당 ID의 주소록 행을 다시 읽었다.

예를 들어 준비 시점의 수령인이 A이고 주소가 X였다고 하자. 다른 탭에서 주소록을 B/Y로 수정한 뒤 결제를 승인하면 참여 주문에는 B/Y가 들어갔다. 화면에서 확인한 주문과 실제 배송 정보가 달라지는 것이다. 카드 승인 서비스는 외부 금융망 성공 응답을 받은 뒤 주소를 읽었기 때문에, 조회 실패가 생기면 외부 승인과 내부 주문 확정 사이에서 실패할 수 있었다. 카카오페이는 공통 `completeOwnedPayment`, 코인은 확인 블록 수 도달 후 `buildSnapshot`에서 같은 의존성을 가지고 있었다.

주소 삭제는 환경에 따라 다른 방식으로 문제를 드러냈다. V3 운영 마이그레이션에는 `fk_payments_address` 외래키가 있고 삭제 동작을 지정하지 않았다. 따라서 실제 MySQL에서는 사용 중인 주소 삭제 자체가 제약 오류가 날 수 있다. Hibernate가 만든 H2 테스트 스키마에는 이 수동 외래키가 없으므로 삭제는 되지만 이후 결제 완료가 주소 없음으로 실패한다. 두 환경을 동일한 결과로 보고하면 안 된다. 이번 수정에서는 양쪽의 원인인 주소록과 거래 배송 정보의 수명 결합을 해소했다.

별도의 전달 누락도 있었다. 프런트 배송 화면은 `checkoutStore.deliveryRequest`를 저장했지만 결제 준비 요청에는 이 값이 없었다. 참여 테이블과 판매자 배송 응답에도 해당 필드가 없어, 사용자가 이번 주문에서 고른 요청이 판매자에게 전달될 수 없었다.

## 2. 원래 설계가 왜 바뀌어야 했는가

V3 SQL 주석은 당시 `user_addresses`에 수정 메서드/API가 없어 ID 재조회로도 같은 값을 얻는다고 설명한다. 현재는 `UserAddress.update`와 주소 수정·삭제 API가 실제로 존재한다. 과거에 성립하던 불변 가정이 기능 확장 뒤에는 성립하지 않는 것이다. 단순히 잘못된 한 줄이 아니라, 도메인 객체의 변경 가능성이 바뀌었는데 결제 경계가 그 변화를 반영하지 못한 경우다.

주소록은 앞으로 사용할 배송지 목록이다. 거래 스냅샷은 특정 결제에서 합의한 배송 정보다. 사용자가 주소록을 수정했다고 이미 준비한 주문의 수령인이 자동 변경되면 안 된다. 주소록 삭제 역시 과거 거래 기록 삭제와 같지 않다. 이 수정은 개인정보 보관기간이나 삭제 정책을 새로 정하는 작업이 아니라, 주소록 삭제와 거래 기록 보존의 책임을 분리하는 작업이다. 실제 거래 기록의 보존·파기 정책은 별도 운영 정책에 따라야 한다.

## 3. 검토한 대안과 선택 기준

### 승인 직전 주소를 한 번 더 읽기

카드가 외부 승인을 먼저 하고 주소를 읽는 순서만 바꾸면 '청구 후 주소 조회 실패' 일부는 막는다. 하지만 준비 이후 승인 직전까지 바뀐 주소가 주문에 들어가는 문제는 남는다. 코인 폴링처럼 사용자의 요청이 없는 비동기 경로에서도 같은 문제를 반복한다. 모든 신규 결제의 기준으로는 선택하지 않았다.

### 결제가 살아 있는 동안 주소 수정·삭제 금지

주소록 기능을 결제 상태에 강하게 결합한다. 여러 주문이 같은 주소를 사용할 때 오래된 거래 때문에 주소록 관리가 막히고, 주소 외래키가 존재한다는 이유로 UI 동작이 달라진다. 슬롯 기간이 짧더라도 완료 주문은 영구적으로 주소를 참조할 수 있다. 따라서 선택하지 않았다.

### 삭제 시 address_id를 NULL로 변경

`ON DELETE SET NULL`이면 외래키 오류는 사라진다. 그러나 같은 멱등 요청을 재시도할 때 원래 보낸 addressId와 저장된 NULL이 달라져, 같은 요청인데 충돌로 판정된다. 최신 B17의 요청 본문 검증을 훼손하지 않기 위해 선택하지 않았다.

### 준비 시점 값을 복사하고 원본 ID는 이력으로 보존

선택한 방식이다. 준비 트랜잭션에서 본인 주소인지 확인한 뒤 수령인/전화/우편번호/주소1·2/최종 배송 요청을 Payment에 복사한다. 주소 ID는 원본 요청 비교용 숫자로 유지하고, 주소록 삭제를 막는 외래키만 V22에서 해제한다. 신규 스냅샷에는 변경 메서드가 없고 `captureShipping`을 두 번 호출하면 거부한다. 승인·입금 확인은 저장된 스냅샷만 읽는다.

## 4. 요청사항의 null과 빈 문자열을 왜 구분하는가

`deliveryRequest`는 최대 100자이며 기존 클라이언트도 요청할 수 있도록 선택 필드다.

| 준비 요청 값 | 확정하는 주문 요청사항 | 원본 멱등 비교 값 |
| --- | --- | --- |
| 필드 생략 또는 null | 그 시점 주소록의 기본 요청 | null |
| 빈 문자열 | 요청 없음 | 빈 문자열 |
| 실제 문자열 | 이번 주문의 요청 | 전달된 문자열 그대로 |

최종 값만 저장하면 null 요청의 재시도에서 문제가 생긴다. 처음 기본값이 '문 앞'이었는데 주소록을 '경비실'로 변경한 뒤 같은 null 요청을 재시도하면, 최종 값으로 비교할 경우 같은 요청을 다른 것으로 판정할 수 있다. 그래서 `prepare_delivery_request`에는 원본 요청을 저장하고, `shipping_delivery_request`에는 확정된 최종 값을 저장한다. B17의 소유자·공구·수단·주소·코인 자산 검증에 원본 요청사항 비교만 추가했다.

프런트는 배송 화면에서 사용자가 '없음'을 선택했을 때 저장된 null을 결제 요청에서 빈 문자열로 보낸다. 주소록 기본값을 다시 적용하라는 의미가 아니기 때문이다. 슬롯 선택 키에도 요청사항을 포함하여, 요청을 바꾸면 기존 슬롯 해제 완료 후 새 키로 준비한다. 통신 실패로 같은 시도를 재전송할 때는 본문과 키를 그대로 유지한다. 주소록의 기본 요청을 PATCH하는 방식은 사용하지 않았다.

## 5. 구현을 따라 읽는 순서

1. `payment/common/entity/PaymentShippingSnapshot.java`: JPA `@Embeddable` 값 객체다. 별도 배송지 테이블 조회 없이 Payment 행의 컬럼으로 저장된다. 필수 수령 정보는 생성 시 null을 거부하고 외부 setter를 제공하지 않는다.
2. `Payment.captureShipping`: 불변 스냅샷을 한 번만 기록하고 원본 요청사항을 함께 보관한다. 기존 `prepareCryptoAssetId`는 그대로 보존한다.
3. `PaymentSlotReservationTransaction.execute`: 소유자 주소 조회와 슬롯 예약의 같은 트랜잭션에서 스냅샷을 만든다. 결제 저장이 실패하면 슬롯 증가와 스냅샷도 함께 롤백된다.
4. `PaymentService.reusePreparedPayment`: 최신 원본 요청 검증에 요청사항 비교를 더한다. 주소록이 사라져도 저장된 원본 ID와 요청이 같으면 같은 진행 중 결제를 재사용할 수 있다.
5. `PaymentService.getApprovalContext`: 결제 행을 잠근 뒤 소유자/수단/진행 상태/만료를 검증하고 레거시 스냅샷을 확정한다. 짧은 별도 트랜잭션에서 완료하므로 금융 승인 네트워크 대기 동안 주소 보정 잠금을 잡지 않는다.
6. `CardPaymentService`, `KakaoPayService`, `CryptoQuoteService`, `CryptoWalletProofService`: 외부 승인 또는 송금에 필요한 견적/증명 제공 전에 공통 검증 경계를 지난다. 카드 실행권 claim보다도 먼저 주소를 확인한다. quote/proof의 발급 메서드는 `NOT_SUPPORTED`로 오케스트레이션하여 바깥 트랜잭션이 커넥션을 보유한 채 `REQUIRES_NEW`용 추가 커넥션을 기다리는 상황을 피한다. 스냅샷 확정과 최종 quote/challenge 저장은 각각 짧은 트랜잭션이다. 시세 조회도 DB 트랜잭션 밖으로 나온다. 이는 조회와 단건 저장의 경계 조정이며 `recordVerified`의 nonce 소비·입금 기록 원자적 트랜잭션은 그대로다. 발급 전체가 원자적이지 않으므로 발급 사이 종료/만료된 결제가 견적을 잠시 받을 수는 있고, 후속 proof/승인/record 경계에서 진행 상태·만료·원본 자산을 다시 확인하는 방어가 필요하다. 발급됐다는 사실만으로 송금 승인이 보장되는 것은 아니다.
7. `PaymentService.completePayment(paymentId)`: 더 이상 호출자가 주소 스냅샷을 인자로 넘기지 않는다. 승인 후 저장된 Payment 스냅샷을 참여 생성 명령으로 전달한다. 누락 시 주소록을 사후 조회하거나 다른 주소로 대체하지 않는다.
8. `ParticipationWriterPort`와 `ParticipationWriterAdapter`: 요청사항을 참여 엔티티로 옮긴다. 최근 B14에서 정리한 UTC Clock 시각 생성은 그대로 유지했다.
9. `ParticipationQueryRepository`와 참여 상세 DTO, `SellerDeliveryItemResponse`: 저장된 요청사항을 구매자 상세와 판매자 배송 목록으로 전달한다. 기존 JDBC 조회에 필요한 한 필드만 추가했으며 이 이슈와 무관한 전체 저장소 재작성은 하지 않았다.
10. 프런트 `PaymentPage → usePaymentSlot → PaymentSlotController → paymentApi`: 일회성 요청을 전달한다. 판매자 배송 API 매핑이 새 필드를 버리지 않도록 하고, 기존 배송 주소 칸에 기존 텍스트 스타일로 요청을 표시한다. CSS/디자인 개편은 없다.

## 6. 레거시 결제의 처리 원칙

V22 이전 행에는 스냅샷이 없다. 과거 값을 현재 주소로 일괄 UPDATE하면 '당시 배송지'라고 보장할 수 없는 데이터를 생성하게 된다. 그래서 마이그레이션은 컬럼만 추가하고 과거 주문의 값을 추측하여 채우지 않는다.

진행 중인 레거시 결제가 외부 호출로 넘어가려 할 때만, 원본 addressId가 현재도 해당 사용자 소유인지 확인하고 한 번 고정한다. 소유자 주소가 없으면 `VALIDATION_ERROR`로 중단한다. 카드/카카오페이 외부 승인 또는 코인 새 견적을 내보내기 전에 실패하므로 이 실패 때문에 새 청구가 발생하지 않는다.

이미 코인을 보낸 과거 거래나 이미 외부 승인이 난 레거시 거래까지 '무청구'라고 부를 수는 없다. 스냅샷 없이 완료 경계에 바로 도달하면 `INVALID_STATE_TRANSITION`으로 안전하게 중단하고 거래 대조가 필요하다고 알린다. 임의 새 주소 선택, 자동 재승인, 자동 재송금은 하지 않았다. 이런 데이터는 실제 배포 전 잔여 진행 결제와 외부 거래를 대조해야 한다.

## 7. 테스트 기획과 관측 결과

이 변경은 응답 속도가 아니라 결제 정합성을 검증하는 작업이다. 동일 요청의 재시도, 주소 변경 시점, 외부 승인 전후 경계를 나누어 검사했다. 금융망과 카카오페이 gateway는 대역을 사용하여 실제 청구 없이 내부 트랜잭션을 실행한다. 데이터 보존과 경합은 실제 JPA/H2와 별도 스레드로 확인한다.

수정 이전 기준은 `85e9199`이다. 별도 `shipping-before` worktree에서 신규 `PaymentShippingAddressRegressionTest`만 같은 내용으로 실행했다. 이 테스트는 기존 API만 사용하므로 없는 새 컬럼이나 새 메서드 때문에 실패하는 테스트가 아니다.

| 비교 시나리오 | 수정 전 | 수정 후 |
| --- | --- | --- |
| CARD/KAKAOPAY/CRYPTO 각각 준비 후 주소 수정, 최초 수령인 유지 | 3개 모두 실패: 수정된 수령인 저장 | 3개 통과 |
| CARD/KAKAOPAY/CRYPTO 각각 준비 후 주소 삭제, 같은 키 재시도와 완료 | 3개 모두 실패: 완료 시 주소 조회 실패 | 3개 통과 |

추가 통합 시험은 요청사항 null/빈 값/명시 값의 참여 및 배송 응답 보존, 같은/새 키로 바뀐 요청 재사용 거절, 세 수단 레거시 한 번 확정, 카드/카카오 ready/코인 quote/proof의 누락 주소 무외부호출, 카카오 approve의 누락 주소 무청구, 타인 주소 거부, 스냅샷 없는 사후 확정 거절, 동시 레거시 확정과 중복 완료의 단일 참여 생성까지 다룬다. 실제 카드/카카오 서비스의 gateway 대역 안에서 주소를 삭제한 뒤 성공 응답을 돌려주는 시나리오도 포함한다. 카카오는 같은 승인 재시도가 추가 gateway 승인 없이 같은 참여를 반환하는지 확인한다.

최종 검증 기준은 최신 `8902037` 통합 후 이 변경을 적용한 코드이며, 2026-09-21 17:42 KST에 백엔드 전체 실행이 종료됐다. **백엔드 전체 798개 중 795개 통과, 실패/오류 0, 건너뜀 3개**다. 건너뛴 항목은 `GroupBuySlotGateIntegrationTest` 2개와 `S3ProductImageStorageIntegrationTest` 1개이며 통과로 계산하지 않았다. 주소 재현 6개와 추가 스냅샷 통합 18개는 모두 통과했다. 시세 조회 대역에서는 실제 트랜잭션이 비활성인지 확인하고, 그 사이 결제를 종료한 뒤 proof 발급이 거절되는 것도 검증했다. **프런트 전체 177개 통과, 타입 검사·ESLint·프로덕션 빌드 통과**이며 배송 요청 변경/동일 통신 재시도/배송 응답 매핑 시험을 포함한다. `git diff --check`도 통과했다.

최초 회귀 중 발견된 기존 테스트 픽스처의 누락도 숨기지 않는다. 모집 기간 단위 시험은 주소 mock에 ID만 넣어 수령 정보가 null이었고, 카카오 원자성 시험은 준비 단계를 건너뛴 결제를 직접 완료했다. 전자는 실제 수령 값을 가진 주소 fixture로, 후자는 승인 전 준비 스냅샷을 명시하는 fixture로 고쳤다. 카카오 서명 시험은 외부 키를 쓰지 않고 테스트 전용 공개 문자열을 설정해야 했다. 실제 비밀키를 테스트에 복사하지 않았다.

## 8. 성능에 대해 말할 수 있는 범위

승인 완료 경로의 살아 있는 주소록 조회는 기존 1회에서 신규 스냅샷 결제 0회로 사라진다. 이는 코드 경로상 접근 횟수 변화이지 응답시간 벤치마크 결과가 아니다. 반대로 준비 시 Payment 행에 배송 컬럼을 더 저장하고 외부 호출 전 짧은 검증 경계를 거치므로 비용도 있다. 전체 테스트 소요 시간이나 번들 빌드 시간을 처리 성능 향상 수치로 사용하지 않았다. 실제 MySQL/Redis와 동시 승인 부하에서 지연·락 대기·커넥션 사용량을 측정하지 않았으므로 성능이 향상됐다는 결론은 내리지 않는다.

## 9. 배포·검증 한계 및 재실행

V22는 `fk_payments_address`를 제거하고 스냅샷 컬럼 6개, 원본 요청 컬럼 1개, 참여 요청 컬럼 1개를 추가한다. V3에 기록된 실제 제약 이름을 사용했다. H2 시험은 Hibernate DDL로 만들므로 MySQL의 Flyway V22 실행 자체를 검증한 것은 아니다. 실제 적용 전 별도 MySQL에서 기존 V21 데이터에 V22를 적용하고 주소 삭제/보존/동일 키를 재확인해야 한다. Redis/S3 Docker 시험은 사용자가 보류한 상태를 유지했다.

로컬 재실행:

```powershell
$env:JAVA_HOME='C:/Program Files/Java/jdk-21.0.12.1'
cd backend
./gradlew.bat test --tests com.gongguhan.audit.PaymentShippingAddressRegressionTest --tests com.gongguhan.audit.PaymentShippingSnapshotIntegrationTest
./gradlew.bat test
cd ../frontend
npm run test
npm run typecheck
npm run lint
npm run build
```

학습할 때는 테스트의 '준비 → 주소록 변경 → 승인' 순서를 먼저 읽고, 그다음 스냅샷의 저장 시점과 사용 시점을 찾아보면 된다. `addressId`를 저장했다는 사실과 '그때 주소값'을 저장했다는 사실은 다르다. 이 차이가 이번 수정의 핵심이다.
