# B17 결제 준비 요청 키의 소유권과 본문 계약

이슈: S15P21B205-207. DevelopV2 통합용 수정이며 DevelopV1·배포 DB·외부 결제는 변경하지 않는다.

## 1. 재현한 문제와 보안 경계

기존 prepare는 idempotencyKey로 결제를 찾으면 요청자의 사용자 ID나 공동구매 ID를 비교하지 않고 그 결제 응답을 반환했다. 요청 키는 통신 재시도의 중복 방지 수단이지 인증 수단이 아니다. 키를 알고 있다는 이유만으로 남의 결제를 읽게 해서는 안 된다. 또한 본인이더라도 같은 키에 다른 결제수단·배송지·코인 자산을 넣으면 최초 요청과 달라진 상태다. 기존 응답을 조용히 돌려주면 화면 선택과 서버의 실제 결제 계약이 달라진다.

실제 Spring/JPA/H2 트랜잭션으로 결제 준비 후 다른 사용자 ID와 동일 키로 호출한 시험은 수정 전 실패했다. 기대는 RESOURCE_ACCESS_DENIED였지만 기존 구현은 응답을 반환했다. 이는 외부 금융 서비스 장애와 무관하게 로컬에서 재현할 수 있는 서버 검증 누락이다.

## 2. 허용하는 재시도와 거부하는 재사용

동일 사용자·동일 공구·동일 수단·동일 배송지·동일 자산이며 진행 중이고 미만료인 결제만 다시 반환한다. 같은 요청을 다시 보낸다고 새 슬롯이나 결제 행을 만들지 않는다. 다른 사용자는 소유권 오류, 본문 변경은 PAYMENT_REQUEST_CONFLICT, 종료 결제는 PAYMENT_ALREADY_PROCESSED, 만료 결제는 PAYMENT_SLOT_EXPIRED로 구분한다. 만료 시각과 정확히 같은 순간도 준비 완료로 취급하지 않는다.

새로고침으로 키만 달라져도 동일한 진행 중 슬롯을 찾는 기존 동작은 유지한다. 다만 이 경로도 같은 검증 함수를 통과해야 한다. 한 경로만 보호하면 다른 키를 보내는 방식으로 본문 검증을 우회할 수 있기 때문이다. 종료 후 새로운 구매 시도에는 새 키를 보내고, 이전 슬롯을 먼저 해제하는 프런트 수명주기와 결합한다.

요청 키는 비어 있지 않은 64자 이하여야 한다. 수단과 배송지 ID도 서비스 경계에서 검증한다. 코인은 양수 자산 ID가 필수이고 카드·카카오에는 코인 자산 ID를 허용하지 않는다. 컨트롤러의 Bean Validation만 신뢰하지 않는 이유는 내부 호출·테스트·후속 진입점에서도 동일한 업무 전제조건이 필요하기 때문이다.

## 3. 왜 최초 코인 자산을 DB에 저장하는가

기존 payments에는 method는 있지만 최초 prepare에서 고른 cryptoAssetId는 없었다. 승인 단계의 견적을 역으로 읽으면 아직 견적이 없거나 나중에 발급된 견적의 자산을 최초 선택이라고 오인할 수 있다. V21은 nullable prepare_crypto_asset_id를 추가하고 최초 슬롯 저장과 같은 트랜잭션에 원요청 자산을 기록한다. 나중 견적으로 덮어쓰지 않는다.

과거 코인 결제의 NULL은 알 수 없음이며 현재 견적을 보고 임의로 보정하지 않는다. 따라서 원자산을 확인할 수 없는 진행 중 레거시 코인 결제는 prepare 재사용을 거부한다. 기존 행을 삭제하거나 이미 완료된 결제·입금을 새 결제로 바꾸지 않는다. 운영 적용 시 이런 슬롯은 상태와 체인 입금을 확인한 뒤 별도 종료/복구 절차가 필요하다.

## 4. 동시에 같은 키로 들어오는 경우

처음 조회에서 두 요청 모두 결제가 없다고 볼 수 있다. DB의 유일성 제약과 기존 슬롯/정원 트랜잭션이 최종 중복 생성을 막는다. 패자는 롤백된 트랜잭션 안에서 재조회하지 않는다. 외부 prepare 경계로 돌아온 뒤 Redis의 임시 예약을 반환하고, 동일 키의 승자 행이 존재하면 소유권·본문·상태를 다시 검증하여 그 응답을 돌려준다.

반드시 기존 DUPLICATE_PARTICIPATION 오류일 때만 이 복구를 시도한다. 모든 오류를 성공으로 바꾸면 주소 검증 오류나 실제 저장 장애가 숨겨진다. 승자 행이 없거나 다른 요청이면 원래 오류를 보존한다. Redis가 먼저 정원 초과로 거절한 순간에는 아직 승자 행이 커밋되지 않았을 수 있으므로 모든 동시 요청이 무조건 즉시 같은 성공 응답을 받는다는 보장은 하지 않는다. 같은 키로 안전하게 다시 조회할 수 있다는 계약이다.

## 5. 테스트 설계와 전후 관찰

새 통합 시험은 최초 코인 자산의 DB 재조회 보존, 다른 자산/새 키 충돌, 레거시 원자산 불명, 타인 키 사용, 공구·수단·배송지 변경, 종료 키와 새 키 구별, 만료 키, 잘못된 키·수단·자산, 모집 마감 시 신규 발급 거부, 기존 슬롯의 마감 후 재조회, 동일 키 동시 요청을 검사한다. 두 동시 요청은 실제 JPA 저장 경합을 만들고 결제 행 1개·예약 슬롯 1개를 확인한다. 외부 금융 호출은 없다. Redis 게이트는 모킹하므로 Redis 다중 서버 경쟁의 실측이라고 주장하지 않는다.

기존 PaymentServiceTest의 정상 재시도 mock에는 새로 검증하는 소유자·주소·NULL 자산을 명시해야 했다. 특히 Mockito의 Long 기본값은 0일 수 있어 카드 자산 없음은 명시적으로 null을 지정했다. 이 fixture 보강은 검증을 삭제하거나 기대 결과를 완화한 것이 아니다. 수정 도중 중복 factory 선언으로 컴파일 실패한 것도 제거 후 재검증했다. 최종 전체 회귀 결과는 아래에 별도 기록한다.

이 수정의 지표는 무단 응답 0건, 변조된 본문의 재사용 0건, 정상 동일 요청의 저장 행/예약 수 1개다. 테스트 실행 시간을 사용자 응답 속도 개선으로 해석하지 않는다. 성능 최적화를 수행한 MR이 아니다.

## 6. 학습 순서와 남은 경계

PaymentPrepareRequest → PaymentService.prepare → reusePreparedPayment → Payment.prepare 자산 저장 → PaymentSlotReservationTransaction 저장/롤백 → 통합 테스트 순서로 읽는다. 요청 키를 인증 정보와 구분하고, 원요청 본문을 복원할 수 있는 데이터를 저장하며, 롤백된 세션 밖에서 승자의 결과를 읽는 세 가지가 핵심이다.

주소 내용 자체와 일회성 배송 요청사항의 불변 스냅샷은 별도 B25/C05·B04 작업이다. 이 MR에서 비교하는 것은 주소 ID이며 주소록 수정/삭제 후 승인 안전성까지 완료한 것으로 보지 않는다. 코인 지갑 소유권과 선택 자산을 견적에 바인딩하는 후속 통합 검증도 별도 기록한다. 실제 MySQL 마이그레이션·배포·Redis/S3 시험을 H2 시험으로 대체하지 않는다.

재실행: backend에서 Java 21로 `./gradlew.bat test --console=plain`. 집중 실행은 `--tests '*PaymentPrepareBoundaryIntegrationTest' --tests '*PaymentServiceTest'`를 사용한다.
