# 반환 대상 코인 입금을 새 결제에 재사용하던 문제 — S15P21B205-221

## 1. 문제가 되는 실제 상태 조합

코인 입금은 `crypto_payments`와 `crypto_deposits`에 서로 다른 의미로 남는다. 전자는 유효한 결제 시도에 연결된 상세 정보이고 후자는 우리 지갑에 도착한 Transfer 로그의 사실 기록이다. 견적과 금액이 맞지 않으면 결제는 거절돼야 하지만 받은 돈의 기록까지 사라지면 안 된다. 그래서 기존 `CryptoDepositRecorder`는 `REQUIRES_NEW`로 미달·초과 입금을 따로 커밋한다. 이 분리는 필요한 설계이며 이번 수정에서 없애지 않았다.

문제는 그 이후다. 첫 시도에서 견적이 7토큰인데 5토큰을 보내면 UNDERPAID 입금이 남고 바깥 결제 상세는 롤백된다. 구매자가 새 5토큰 견적과 결제를 만든 뒤 같은 해시를 다시 제출하면, 상세 테이블에는 그 해시가 없으므로 사전 중복 검사에 걸리지 않는다. 영수증의 금액도 새 견적과 일치한다. 기존 `recordDeposit`은 해당 해시·로그 인덱스의 입금 행이 있다는 이유만으로 반환하고, 호출자는 그것을 정상 매칭으로 간주해 참여·에스크로를 만든다.

따라서 동일한 5토큰이 미달 입금 반환 원장에서는 돌려줘야 할 돈이고, 새 결제에서는 상품 구매에 사용된 돈이 된다. 이미 REFUNDED인 경우에도 같은 문제가 생긴다. 이는 단순 화면 표기 문제가 아니라 한 입금의 자금 용도가 두 번 인정되는 P1 정합성 결함이다. 초과 입금도 현재 구현은 전액 반환 대상이며, 초과분만 돌려주고 결제는 인정한다는 오래된 엔티티 주석은 실제 동작과 달라 함께 바로잡았다. 반환 금액 정책 자체를 바꾼 것은 아니다.

## 2. 의심과 확정 증거를 구분한 재현

기준 DevelopV2는 `301eef91c031775d47d27f5f3fff62ffc933d9ce`였다. 먼저 별도 detached 진단 worktree에서 제품 코드를 바꾸지 않고 실제 Spring/JPA/H2 저장 경로를 시험했다. UNDERPAID, OVERPAID, REFUNDED 세 상태 모두 두 번째 결제가 예외 없이 PAID가 돼, 거절을 요구한 세 검증이 실패했다. 해당 시각은 2026-09-22 09:01:05 KST이고 원본 관측은 `crypto-deposit-reuse-before.json`에 보존했다. 실제 버그를 확인한 다음 Jira221와 전용 수정 브랜치를 만들었다.

직접 기록 서비스 시험만으로는 상위 서명 검증이나 DB 제약이 막는지 설명이 부족하다. 그래서 추가로 지갑 challenge 발급, 무자금 시험 키의 EIP-191 서명 생성, 서명 검증, `submitTransaction`, 실제 JPA 저장까지 이어지는 경로로 재현을 강화했다. H2의 Hibernate create-drop은 Flyway UNIQUE를 자동 복제하지 않으므로 운영과 같은 `crypto_payments(tx_hash)` 및 `crypto_deposits(tx_hash,log_index)` UNIQUE 인덱스를 시험 시작 시 명시적으로 만들었다.

강화 시험의 초기 fixture는 quoteId와 assetId를 혼동하고 최초 선택 자산 값을 누락해 입금 검증 전에 거절됐다. 이 실패는 제품 버그 증거로 세지 않았다. DTO의 quoteId와 준비 자산 계약을 맞추고, 첫 오류가 반드시 CRYPTO_AMOUNT_MISMATCH인지 검증해 재현 단계가 정확히 도달했음을 확인했다. 그 뒤 수정 전 저장 로직으로 다시 실행한 09:08:57 KST 결과에서도 세 상태 모두 새 결제가 PAID가 됐다. 유효한 서명과 UNIQUE 제약이 있어도 막히지 않는다는 추가 증거다.

REFUNDED fixture는 실제 송금을 하지 않고 입금 종결 메서드로 반환 완료 상태를 만든다. 그래서 이 시험이 실제 지갑에서 반환 송금까지 수행한 end-to-end 테스트라는 뜻은 아니다. 반환 상태에 도달한 원장이 재사용될 수 있는지를 검증한 것이다.

## 3. UNIQUE와 지갑 서명이 왜 해결책이 아니었나

UNIQUE는 같은 키를 가진 행을 두 번 삽입할 때 적용된다. 기존 로직은 이미 존재하는 입금 행을 발견하면 삽입 자체를 건너뛰었다. 따라서 입금의 UNIQUE가 발동할 기회가 없었다. 상세 테이블의 UNIQUE도 최초 실패로 해당 행이 롤백된 상태라 막을 수 없었다. 제약을 추가하거나 중복 오류만 잡는 방식은 이 분기에 대한 해결책이 아니다.

서명은 신고한 송신 지갑을 현재 요청자가 통제한다는 사실을 증명한다. 그 지갑이 보낸 입금을 이미 반환했는지, 다른 결제에 사용했는지를 증명하지는 않는다. 본인이 보낸 오래된 거래라도 두 번 사용할 수 없도록 원장 소유권을 별도로 확인해야 한다. 서명 검증을 완화하거나 없애지 않고 그 뒤의 DB 매칭 경계를 강화한 이유다.

실제 V1 제약은 체인을 포함한 복합 키가 아니라 tx_hash, 그리고 tx_hash+log_index다. 이번 수정은 이 전역 유일성 정책을 변경하지 않는다. 다른 체인에서 우연히 같은 해시가 나타나면 현재 저장 구조에서는 충돌할 수 있으므로 다중 체인 확장 시에는 별도 스키마·조회·환불 계약 검토가 필요하다. 지금은 서로 다른 체인의 입금을 같은 것으로 허용하지 않는 안전한 방향으로 검증한다.

## 4. 선택한 수정과 대안

### 4.1 같은 원장을 읽었다면 같은 사실인지 검사한다

`CryptoDepositRepository.findForUpdateByTxHashAndLogIndex`는 기존 행을 비관적 쓰기 잠금으로 읽는다. `CryptoTxRecordService.recordDeposit`은 기존 입금이 있을 때 다음 조건을 모두 요구한다.

- 상태가 MATCHED다.
- 입금의 paymentId가 현재 결제 ID와 같다.
- 입금의 체인이 현재 결제 체인과 같다.
- 토큰, 송신자, 수신자, 원시 정수 수량이 지금 검증한 Transfer와 같다.

하나라도 다르면 CRYPTO_AMOUNT_MISMATCH로 거절한다. 특히 DETECTED는 아직 수락한 입금이 아니므로 MATCHED처럼 취급하지 않는다. UNMATCHED, UNDERPAID, OVERPAID, REFUNDED를 새 결제에 자동 연결하지 않는다. 이는 환불 실행권의 PROCESSING/UNKNOWN/COMPLETED 세부 상태와 관계없이 안전하다. 반환용 입금 상태에 있는 한 새 구매 자금으로 사용할 수 없기 때문이다.

반대로 같은 결제에 정상 MATCHED로 저장된 동일 Transfer를 다시 확인하는 경우는 허용한다. 이 경우 새 입금 행을 만들지 않는다. 무조건 모든 기존 행을 거절하는 대안은 정상적인 원래 기록의 재확인까지 깨뜨릴 수 있어 제외했다. 기존 상태를 새 결제의 MATCHED로 덮어쓰는 대안도 이미 예약·송신된 반환과 경합할 수 있어 제외했다. 기존 입금을 다른 결제의 잔액으로 재사용하는 상품 정책이 필요하다면, 반환 실행권과 자금 배분을 묶는 별도 설계가 선행돼야 한다.

### 4.2 잠금·롤백·외부 호출 경계

기존 결제 처리 순서인 Payment 잠금 → 견적 claim → CryptoPayment 저장 → 입금 잠금/검증을 유지한다. 입금을 잠근 뒤 다른 Payment를 잠그는 역순은 추가하지 않았다. 수정은 외부 RPC를 트랜잭션 안으로 옮기지 않는다. 이미 외부에서 얻은 영수증을 짧은 DB 트랜잭션으로 반영하는 구조 그대로다.

검증 실패 시 새 상세 결제, 견적 claim, 지갑 증명 소비, 참여/에스크로 생성은 같은 바깥 트랜잭션에서 롤백된다. 기존 입금 원장의 상태와 소유권은 바꾸지 않는다. 이미 존재하는 행의 상태가 동시 처리 중 변하는 것을 피하려고 입금 행 잠금을 사용한다. 아직 행이 없는 두 요청의 동시 삽입은 기존 운영 UNIQUE가 마지막 방어선이며 이번에 새 인덱스나 마이그레이션을 만들지 않았다. 미달 원장을 지키는 REQUIRES_NEW 분리 또한 유지한다.

## 5. 테스트에서 확인하는 것

`CryptoDepositReuseIntegrationTest`는 실제 JPA 저장소와 트랜잭션을 사용하고 RPC·Redis 게이트만 대체한다. 최초 세 상태 재현은 모두 유효한 서명부터 제출 서비스까지 거친다. 추가 매개변수 시험은 DETECTED, UNMATCHED, 다른 결제 MATCHED, 체인/토큰/송신자/수신자/수량 불일치를 각각 거절하는지 확인한다. 같은 결제의 동일 MATCHED 사실은 성공시키고 입금은 1건만 유지하는 대조군도 있다.

경합 시험은 두 개의 별도 결제가 한 UNDERPAID 입금에 동시에 접근하도록 시작 신호를 맞춘다. 두 새 결제가 모두 거절되고, CryptoPayment 0건·새 참여 0건·기존 UNDERPAID 1건이 유지되는지 확인한다. 이 시험은 서명부터의 정상 검증과 분리해 DB 쓰기 경계 자체의 경합을 집중 검사한다. 기존 `CryptoSignedSubmissionIntegrationTest`는 정상 신규 서명 거래와 동일 요청 복구가 계속 동작하는 회귀 대조군이다.

| 정확성 지표 | 수정 전 | 수정 후 |
| --- | --- | --- |
| UNDERPAID 입금의 새 결제 수락 | PAID 1건 | 새 참여 0건, 원장 상태 보존 |
| OVERPAID 입금의 새 결제 수락 | PAID 1건 | 새 참여 0건, 원장 상태 보존 |
| REFUNDED 입금의 새 결제 수락 | PAID 1건 | 새 참여 0건, 원장 상태 보존 |
| 유효한 서명 + 운영 동일 UNIQUE 적용 | 세 시나리오 모두 통과시켜 버그 재현 | 원장 매칭 검사에서 거절 |
| 정상 동일 결제·동일 MATCHED 입금 | 정상 흐름 유지 필요 | PAID, 입금 1건 |
| 두 새 결제가 반환 대상 하나에 동시 접근 | 행 존재만으로 수락하는 위험 | 양쪽 거절, 기존 자금 배분 유지 |

최초 전체 실행은 최신 DevelopV2 `635a787b821c3096ab15a3f17d88329bcd1c91b7`을 통합한 `06e02691e1aaf132c073500c9cd5c9249ac4ec5f`에서 수행했다. 2026-09-22 09:16:56 KST 종료, 129스위트 884개 중 29개 실패·오류 0·기존 환경 제외 3개였다. 원인은 테스트 JVM의 OutOfMemoryError로 반품 정산 컨텍스트 13개와 권한 경계 컨텍스트 16개가 실행되지 못한 것이다. 이를 통과로 세지 않고 `crypto-deposit-reuse-runtime-failure.json`에 별도 보존했다. 앱 JVM이나 배포 설정을 바꾸지 않고 선택형 Gradle init-script로 테스트 프로세스에 2GB 힙과 제한된 Spring 컨텍스트 캐시를 지정해 처음부터 재실행한다.

두 번째 실행은 힙 2GB/캐시 8로 수행했으나, 09:19:36 KST 종료 시 884개 중 20개 실패·오류 0·환경 제외 3개였다. `ReturnRequestRepositoryTest` 8개와 `SettlementBatchIntegrationTest` 12개가 빈 DB의 users 테이블을 찾지 못했다. 여러 Spring 컨텍스트가 같은 H2 메모리 DB를 공유하면서 create-drop을 사용하는 기존 시험 구조에서, 작은 캐시가 오래된 컨텍스트를 퇴출하면 그 컨텍스트가 테이블을 삭제해 아직 사용 중인 다른 컨텍스트에 영향을 준 것이다. 제품 SQL 오류로 오인해 쿼리를 바꾸지 않았다. 이 결과도 같은 환경 실패 JSON에 추가 보존했다.

세 번째 실행은 힙 2GB를 유지하고 캐시를 64로 높여 공유 DB 컨텍스트가 실행 도중 퇴출되지 않게 했다. 09:22:59 KST에 2분 36초로 종료했으며 129스위트 884개 중 879개 통과, 2개 실패, 오류 0, 기존 환경 제외 3개였다. 신규 입금 재사용 13개는 모두 통과했고 해당 클래스 XML 합계는 2.347초였다. 테스트 힙은 앱 런타임과 무관하다.

남은 2개는 기존 `SellerGroupBuyIntegrationTest`의 공통 DB 간섭이었다. 전체 DB의 공구가 반드시 하나라는 `findAll().hasSize(1)`에서 실제 두 건을 읽었고, `findAll().getFirst()`로 잡은 다른 fixture의 공구 ID를 조회해 404가 났다. 같은 코드와 2GB/cache64 설정에서 이 클래스만 단독 실행하자 09:24:52 KST에 성공했다(Gradle 17초). 제품 로직을 바꾸지 않은 대조 시험이다. 이 문제는 Jira220 통합 검증 작업에서 판매자 테스트의 H2 URL을 별도로 분리한다. 장기적으로 각 테스트 컨텍스트의 DB와 스키마 수명을 일관되게 격리하는 것이 필요하다.

따라서 이 개별 MR의 전체 실행을 무조건 성공이라고 기록하지 않는다. 제품 수정의 신규 13개와 기존 기록·서명 선택 회귀는 통과했으며, 전체는 위 환경 및 fixture 실패를 그대로 보존했다. 부모 통합 작업이 Jira217/221 제품 소스와 Jira220 시험 격리를 함께 전체 검증하고, 검증한 제품 코드 트리를 확인한 뒤 MR을 순서대로 병합한다. 그 최종 통합 결과는 Jira220 문서에 남긴다. 제외 3개는 Redis 슬롯 게이트 2개와 S3 이미지 저장 1개다.

이 수치는 정합성 검증이지 TPS나 API 지연시간이 아니다. SELECT 존재 검사 대신 잠금 SELECT로 바뀌므로 동시 같은 입금 접근은 직렬화된다. 운영 DB에서의 잠금 대기 분포나 처리량을 측정하지 않았고 성능 향상을 주장하지 않는다.

## 6. 한계와 운영 후속

이미 과거에 이 버그로 이중 사용된 거래가 있는지 자동 수정하지 않았다. 그러한 거래는 입금·반환 원장·참여·에스크로·체인 송신 결과를 함께 대조해야 하며, UNKNOWN 반환을 재송금하거나 과거 PAID를 임의 취소해서는 안 된다. 이번 MR은 앞으로 같은 입금을 새로 수락하는 경계만 막는다.

H2에 관련 UNIQUE 제약을 추가해 시험했지만 전체 MySQL DDL·격리 수준·교착 탐지·Flyway 마이그레이션을 실행한 것은 아니다. 실제 RPC, 서명용 개인 지갑, 가스비, 토큰 반환, Docker Redis/S3, EC2 배포는 사용하지 않았다. 고정 시험 키는 실제 자금이 없는 암호 알고리즘 fixture이며 운영 자격증명이 아니다.

이 수정으로 프런트 스타일·결제 계약·배포본 DevelopV1을 바꾸지 않았다. 원래 실패한 새 제출은 오류로 종료되며 기존 반환 내역을 확인해야 한다. 실패한 제출 뒤 새 금액을 실제로 보내려면 별개의 온체인 거래 해시를 사용해야 한다. 이전 입금이 없어졌다는 이유로 재송금을 자동 요청하거나 수행하지 않는다.

## 7. 재실행과 학습 순서

Java 21로 backend에서 `./gradlew.bat test --tests '*CryptoDepositReuseIntegrationTest' --tests '*CryptoTxRecordServiceTest' --tests '*CryptoSignedSubmissionIntegrationTest' --console=plain`을 실행한다. 전체는 `./gradlew.bat test --console=plain`이다.

현재 전체 모음에는 테스트 전용 힙 설정이 필요하다. Jira220의 `docs/testing/full-regression-runtime.gradle`을 사용할 때는 backend에서 `./gradlew.bat -I ../docs/testing/full-regression-runtime.gradle test --rerun-tasks --console=plain`로 실행한다. 이 MR 검증 시에는 통합 worktree에 있던 같은 파일의 절대경로를 사용했다. 스크립트의 `maxHeapSize='2g'`, `spring.test.context.cache.maxSize=64`는 테스트 태스크에만 적용하며 배포 JVM 설정이 아니다.

처음 읽을 때는 `CryptoDepositRecorder.recordMismatched`의 REQUIRES_NEW 이유부터 확인한다. 다음 `CryptoTxVerificationService`의 해시 사전 중복 검사와 `CryptoTxRecordService.recordDeposit`의 기존 행 분기를 비교한다. UNIQUE가 검사하는 대상이 행 삽입이지 금융적 의미의 재사용 전체가 아니라는 점이 핵심이다. 마지막으로 새 테스트의 수정 전 3건과 SAME_MATCH 대조군, 동시 요청 시험을 함께 읽으면 정상 멱등 재시도와 잘못된 입금 재사용을 왜 구분해야 하는지 이해할 수 있다.

관련 Jira: S15P21B205-221. DevelopV2에만 MR로 전달하며 상세 검토와 필수 조건을 통과한 뒤 병합한다.
