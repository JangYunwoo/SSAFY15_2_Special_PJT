# 판매 정지 이후 기존 공동구매의 신규 결제 차단 — S15P21B205-245

## 1. 요구사항을 확정한 배경

2026-09-23 사용자가 “판매 정지된 판매자의 기존 공구에서 신규 결제를 허용할지”에 대해 **비허용**이라고 결정했다. 이전 코드의 제재 주석은 신규 상품 등록과 공동구매 생성만 막는다고 설명하고 있었다. 따라서 이전 동작을 처음부터 명백한 구현 오류였다고 단정하지 않고, 보류했던 정책을 확정해 결제 경계에도 적용하는 수정으로 기록한다.

판매 정지와 기존 거래 전체 취소는 다르다. 이번 정책은 새로운 결제 시작을 막는 것이지, 이미 결제한 구매자의 조회·배송·반품·환불·정산 권리를 없애는 것이 아니다. 정지 전에 발급한 미완료 결제도 정지 후 새 승인 요청에 사용할 수 없어야 한다. 그렇지 않으면 정책 적용 전에 슬롯을 확보해 놓는 것만으로 제한을 우회할 수 있다.

프런트는 다른 팀원이 작업 중이므로 수정하지 않는다. 백엔드 계약을 유지하고 기존 `SELLER_SUSPENDED` 오류 코드(HTTP 403)를 사용한다. 결제 요청에는 “판매 정지된 판매자의 공동구매에는 새 결제를 진행할 수 없습니다.”라는 설명을 별도로 제공한다.

## 2. 코드에서 확인한 원인과 우회 경로

공개 공동구매 목록은 정지된 판매자를 걸러낸다. 하지만 목록에서 숨기는 것만으로 쓰기 요청을 막을 수는 없다. 사용자가 이전에 열었던 화면, 저장한 공동구매 ID, 직접 API 요청을 사용할 수 있기 때문이다.

결제 준비에는 세 가지 반환 경로가 있다. 동일한 멱등키의 결제가 있으면 기존 준비를 반환한다. 키가 달라도 같은 사용자의 유효한 동일 수단 슬롯이 있으면 그 슬롯을 재사용한다. 둘 다 없을 때만 실제 슬롯 예약 트랜잭션을 수행한다. 신규 예약만 검사하면 앞의 두 경로는 정지 여부를 확인하지 않는다.

또한 준비 API를 다시 호출하지 않고 paymentId로 승인 요청을 보낼 수 있다. 카드의 승인, 카카오페이의 ready/approve, 코인의 견적·지갑 증명 발급은 `PaymentService.getApprovalContext`를 사용한다. 이 공통 경계를 검사하면 어댑터마다 정책을 중복해서 구현하지 않아도 된다.

## 3. 선택한 구현과 대안 비교

`GroupBuyRepository.hasSuspendedSeller(groupBuyId)`를 JPQL로 추가했다. 공동구매의 sellerId를 통해 `SellerProfile.status = SUSPENDED`인 행이 있는지 조회한다. 서비스에 원시 SQL을 넣지 않았고, 공개 상세 응답 전체를 불러오지도 않는다. 기존 외래키가 참조 무결성을 보장하는 운영 구조에서 판매 정지 상태만 판단한다. 판매자 미존재를 새 정책으로 해석해 기존 테스트나 오류 의미를 바꾸지 않는다.

다음 세 위치에 검사를 적용했다.

1. `PaymentSlotReservationTransaction.execute`: 공동구매와 삭제 상품 검증 직후, DB 슬롯 증가·결제 저장 전 검사한다. 정지이면 트랜잭션이 실패하므로 DB 결제나 예약 수가 남지 않는다. 먼저 얻은 Redis 잠정 예약은 기존 `PaymentService.prepare`의 실패 보상 경로에서 반환한다.
2. `PaymentService.reusePreparedPayment`: 소유자, 요청 내용, PROCESSING 상태, TTL 검증 후 검사한다. 동일 멱등키와 다른 키의 활성 슬롯 재사용에 모두 적용된다. 소유권 검증을 앞에 유지하므로 타인의 키로 판매자 상태를 탐색하는 경로를 추가하지 않는다.
3. `PaymentService.getApprovalContext`: 본인 결제와 수단·유효 상태 확인 후, 외부 승인 또는 견적에 필요한 정보를 반환하기 전 검사한다. 카드 금융망 호출·카카오페이 ready/approve 호출·코인 시세 요청 전에 거부한다.

기존 삭제 상품 검사 메서드는 이제 두 정책을 검사하므로 `ensureProductNotDeleted`에서 `ensureNewPaymentAllowed`로 이름을 바꿨다. 삭제 상품 오류의 기존 우선순위를 유지하고 이후 판매 정지를 검사한다. 예약 트랜잭션은 별도 빈으로 분리된 기존 경계를 유지한다. 소량의 검사를 줄이기 위해 두 빈의 트랜잭션 구조나 생성자 계약을 광범위하게 바꾸지는 않았다.

판매 정지 시 모든 결제 행을 삭제하거나 공구를 자동 무산시키는 방식은 선택하지 않았다. 이미 진행 중인 외부 승인과 경합하며 원장·환불·슬롯을 함께 훼손할 수 있고, 이번 사용자 결정은 거래 전체 취소를 지시한 것이 아니기 때문이다. 화면의 버튼만 비활성화하는 방식도 직접 API 호출을 막지 못하며 FE 수정 금지 범위에 어긋난다.

## 4. 기존 거래와 진행 중 금융 요청을 보존하는 이유

`getPayment`, `getCompletedPayment`, `abort`와 환불·정산 서비스는 이 정책 검사로 감싸지 않는다. 완료된 결제를 조회할 수 있고, 승인 전 슬롯은 사용자가 중단하거나 TTL 만료로 반환할 수 있다. 정지 여부를 읽었다고 이미 확보한 슬롯을 즉시 삭제하지 않는다. 정지 중 미완료 슬롯이 TTL까지 남을 수 있는 것은 원장을 보존하는 기존 처리 방식이다.

카드·카카오페이의 외부 승인이 이미 시작된 후 판매 정지가 확정될 수 있다. 외부에서 청구가 성공했는데 내부 결과 기록만 거절하면 실제 출금과 내부 원장이 달라진다. 따라서 이번 검사는 새 승인 **진입**을 차단하며, 이미 진행한 금융 호출의 결과 기록과 기존 정합성 처리는 유지한다. 검증부터 외부 호출 종료까지 판매자 행 잠금을 유지하지 않는다. 정지와 외부 금융망을 하나의 원자적 트랜잭션으로 만든 수정은 아니다.

코인도 서버가 사용자의 지갑 송금을 직접 중단시킬 수는 없다. 신규 견적과 증명 발급은 차단하지만 정지 전에 시작한 온체인 송금의 접수·컨펌·결과 분류를 임의로 삭제하지 않는다. 이미 발급된 정보로 사용자가 직접 송금하는 행위까지 네트워크 차원에서 차단한다고 주장하지 않는다. 이 수정은 정지 이후 모든 외부 금융 결과를 자동 취소·환불하는 기능을 추가한 것이 아니다.

정지가 해제되어 다시 ACTIVE가 되면 DB의 현재 상태를 읽으므로 정상적인 신규 준비가 가능하다. 별도 캐시 무효화나 결제 데이터 일괄 복원은 필요하지 않다.

## 5. 테스트 기획과 수정 전 증거

운영 DB의 판매자 상태를 바꾸거나 실제 금융 거래를 만들지 않고, 전용 H2 메모리 DB에서 검증한다. 판매자·상품·카테고리·공동구매·배송지 행을 생성하고 테스트마다 다른 ID를 쓴다. 스케줄러와 코인 폴링은 끄며 Redis 슬롯 게이트와 외부 금융/시세 클라이언트는 모킹한다. 따라서 외부 호출이 없음을 검증할 수 있으며 API 키나 실제 카드 정보는 필요 없다.

최초 12개 테스트를 기존 코드로 실행했을 때 9개 실패, 3개 통과했다. 정지 판매자의 신규 준비, 준비 후 정지한 경우의 재사용, 정지 해제 대조 시나리오의 최초 거부 검증이 각각 세 수단에서 실패했다. 실패 이유는 기대한 예외가 발생하지 않은 것이었다. 이미 완료된 결제를 읽는 대조군 3개는 통과했다. 원본 XML은 작업 공간 `output/bug-audit-20260923/suspended-245-before.xml`에 보존했다. 수정 후 결과로 덮어쓰지 않는다.

이후 실제 어댑터 경로 다섯 개도 추가했다. 카드 승인·카카오 ready·카카오 approve가 외부 클라이언트를 호출하지 않는지, 코인 견적이 시세 클라이언트를 호출하지 않는지, 코인 증명 발급이 정지 오류로 거절되는지를 확인한다. 카카오 승인 테스트는 테스트 전용 값으로 유효한 상태 서명을 만들어 인증 오류 대신 판매 정지 오류에 도달함을 검증한다.

대조군과 검증 대상은 다음과 같다.

- CARD/KAKAOPAY/CRYPTO 각각 신규 준비 거절, DB 결제 0건·예약 0개, Redis 잠정 예약 반환.
- 정상 준비 후 정지하면 동일 키/다른 키 재사용과 승인 진입 모두 거절. 기존 결제 조회와 abort는 성공하고 예약은 0개로 복귀.
- 정지 해제 후 신규 준비·멱등 재사용·승인 컨텍스트 조회 복구.
- 이미 PAID인 결제는 판매 정지 후에도 조회 가능. 이 대조군은 조회 계약을 검증하는 fixture이며 실제 출금 성공을 의미하지 않는다.
- 다섯 어댑터 경로의 외부 호출 이전 거절.

전체 결제·제재 회귀에 이어 백엔드 전체 테스트도 수행한다. 결제 준비만 통과했다고 기존 환불·정산이 검증됐다고 표현하지 않는다. 로컬에서 Redis·S3 통합 검사가 환경 때문에 건너뛰어지면 그 수를 명시하고, Jenkins의 격리 Redis/MinIO 테스트 결과와 구분한다.

## 6. 재실행과 결과 기록

Java 21에서 backend 디렉터리의 Gradle Wrapper를 사용한다.

```text
gradlew.bat --init-script ../docs/testing/full-regression-runtime.gradle test --tests com.gongguhan.audit.SuspendedSellerPaymentIntegrationTest --console=plain
gradlew.bat --init-script ../docs/testing/full-regression-runtime.gradle test --console=plain
```

수정 후 최초 공통 정책 12개를 포함한 결제·제재 회귀 346개가 모두 통과했다. 다섯 어댑터 검사 추가 후 최종 신규 테스트 17개도 모두 통과했다. 최종 로컬 백엔드 전체는 951개 중 948개 통과, 실패·오류 0, Redis 2개와 S3 1개 건너뜀이다. `suspended-245-core-after.xml`과 `suspended-245-after.xml`을 각각 보존했다. 전체 회귀에는 기존 환불·정산·제재·카드·카카오페이·코인 검사가 포함된다.

직접 코드 검토에서 신규/멱등/활성 슬롯 경로, 소유권 검증 순서, Redis 실패 보상, 어댑터의 외부 호출 순서, 기존 금융 결과 기록의 보존을 확인했다. FE 변경은 없으며 `git diff --check`도 통과했다. 운영 배포 성공과 CI의 실제 Redis/S3 테스트 결과는 로컬 통과와 별도로 MR/Jira 및 완료 기록에 남긴다. 이번 수정은 성능 최적화가 아니며 DB 조회가 추가된다. 테스트 개수나 실행 시간을 처리 성능 개선 수치로 포장하지 않는다.

## 7. 학습 순서와 검토 기준

먼저 `PaymentService.prepare`에서 멱등키·활성 슬롯·새 예약 세 경로를 따라간다. 다음으로 예약 빈의 트랜잭션과 실패 시 Redis 게이트 반환을 확인한다. 이후 세 수단 어댑터에서 `getApprovalContext`가 외부 호출 앞에 있는지 살펴본다. 마지막으로 완료 처리와 환불 경로에는 왜 같은 검사를 넣지 않았는지, 실제 자금 이동과 내부 결과 기록을 구분해서 읽는다.

검토 시 “정지 계정은 전부 막는다”보다 “어떤 새 행위를 막고 어떤 기존 의무를 보존하는가”를 기준으로 삼는다. 주석·API 문서도 이제 신규 결제 차단을 포함하도록 함께 갱신했다. FE 파일·화면 스타일·DB 스키마·비밀값·운영 데이터는 변경하지 않는다.
