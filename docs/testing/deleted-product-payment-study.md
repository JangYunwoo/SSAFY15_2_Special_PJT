# 삭제 상품의 결제 진입 방어 — S15P21B205-238

## 1. 문제를 어느 수준으로 볼 것인가

공개 목록과 상세 API는 ACTIVE 상품만 보여 준다. 사용자가 지적했듯 일반 화면에서는 삭제 상품에 접근할 수 없다. 따라서 이 문제를 누구나 정상 화면에서 결제하는 긴급 P1 장애로 분류한 것은 과했고, 기존 공동구매 ID를 알고 있는 인증된 클라이언트의 직접 API 호출을 막는 P2 방어 보완으로 재분류했다.

또한 일반 상품 삭제 API는 활성 공동구매가 있으면 삭제를 거부한다. 이번 운영 테스트 상품 정리는 사용자 요청에 따라 금융 이력을 보존하면서 상품 상태만 DELETED로 바꾼 경우다. 이런 유지보수 상태에서 공동구매가 RECRUITING으로 남을 수 있다. 정상 상품 삭제 API가 이 조합을 만든다고 설명해서는 안 된다.

로컬에서 공개 상세 결과가 없음을 먼저 확인했지만 PaymentService.prepare는 성공했다. 결제 준비와 실제 승인·출금은 다르다. 이번 재현은 준비·슬롯 확보이며 운영 금융 거래를 생성한 것이 아니다.

## 2. 원인과 호출 경로

PaymentSlotReservationTransaction은 공동구매 기간·상태·정원, 중복 참여, 배송지 소유권, 결제수단을 검사한 후 Payment를 저장했다. 공개 조회가 삭제 상품을 걸러준다는 사실은 이 쓰기 API에 자동으로 적용되지 않는다. prepare는 상세 조회를 거치지 않고 직접 호출할 수 있기 때문이다.

prepare의 멱등키/기존 활성 슬롯 재사용은 예약 트랜잭션을 건너뛴다. 신규 예약 경로만 수정하면 이미 확보한 슬롯이 그대로 반환된다. 외부 결제 어댑터도 paymentId로 getApprovalContext를 호출하므로, 삭제 후 prepare를 다시 하지 않는 클라이언트까지 고려해야 한다.

## 3. 수정한 경계

GroupBuyRepository에 hasDeletedProduct(groupBuyId)를 추가했다. JPQL로 공동구매의 productId와 Product의 삭제 상태만 확인한다. 직접 SQL을 서비스에 넣거나 공개 상세 전체를 불러오지 않았다. 운영 스키마 V1의 fk_group_buys_product가 상품 참조 존재를 보장하고 Product의 현재 상태는 ACTIVE/DELETED다. 이 수정은 DELETED 차단에 한정되며 미존재 공동구매의 기존 오류 경로를 바꾸지 않는다. 일부 기존 단위/통합 fixture는 상품 없는 공동구매를 사용하지만, 새 회귀 테스트는 실제 상품·카테고리·판매자 행까지 만든다.

검사 위치는 세 군데다.

1. 예약 트랜잭션에서 실제 결제/슬롯 저장 전 검사한다. 삭제된 경우 RESOURCE_NOT_FOUND로 거부한다. 잠정 Redis 게이트 획득 뒤 거부되면 기존 prepare의 실패 경로가 게이트를 반환한다.
2. 기존 준비 재사용에서 소유자·요청 일치·상태·TTL 검사가 끝난 뒤 검사한다. 같은 멱등키뿐 아니라 새 키로 같은 활성 슬롯을 찾는 경로에도 적용된다. 타인의 요청 키로 상품 상태를 탐색하지 않도록 소유권 검증보다 앞에 두지 않는다.
3. getApprovalContext에서 소유권·수단·유효 상태를 검증한 뒤 검사한다. 카드 외부 승인, 카카오 ready/approve, 코인 견적/지갑 증명 진입 전에 삭제 상태를 확인한다.

응답 구조와 프런트 파일은 변경하지 않는다. 삭제 상태의 공개 상세와 같은 RESOURCE_NOT_FOUND를 사용해 기존 오류 처리 계약을 유지한다. 판매 정지 상태는 정책상 범위가 불명확하므로 건드리지 않는다.

## 4. 왜 모든 결제 메서드를 막지 않았는가

이미 낸 돈에 대한 조회·환불을 상품 숨김 때문에 막으면 사용자가 거래를 정리할 수 없게 된다. 따라서 getPayment, getCompletedPayment, abort, 기존 취소·환불 경로에는 삭제 검사를 추가하지 않았다. 삭제 전에 시작한 외부 승인 응답을 수신한 뒤 내부 원장에 기록하는 완료 경로에도 새 삭제 예외를 넣지 않았다. 외부 청구가 성공했는데 내부 기록만 롤백되는 문제를 만들지 않기 위해서다.

진행 중 슬롯은 삭제 감지 시 일괄 삭제하지 않는다. 새 외부 승인 진입만 거부하고 사용자의 중단 또는 기존 TTL 만료 처리로 반환한다. 원장·슬롯·Redis 카운터를 임의의 관리용 SQL로 함께 지우는 접근은 제외했다.

## 5. 경합과 범위의 한계

검사는 각 요청의 DB 조회 시점에 적용된다. 외부 금융 HTTP 호출 내내 상품 행 잠금을 잡아 두지 않는다. 삭제가 검증 이후 이미 진행 중인 외부 호출과 겹치면, 기존 완료·환불 정합성 흐름으로 실제 금융 결과를 기록해야 한다. 이 수정이 상품 숨김 시 진행 중 외부 결제를 원자적으로 전부 취소하는 기능은 아니다.

일반 삭제 API는 활성 공구를 삭제하지 못하게 막으므로 이 경합은 주로 직접 운영 유지보수에서 고려할 사항이다. 운영자가 진행 중 거래 전체를 종료하려면 단순 화면 숨김과 별도의 공구 종료·환불 절차가 필요하다. 이번 사용자의 요청은 그런 전체 취소가 아니므로 확대하지 않았다.

## 6. 테스트 설계와 증거

별도 test 프로필 H2 메모리 DB에 상품·판매자·카테고리·공동구매·배송지를 구성하고 Redis 게이트만 모킹했다. 스케줄러는 비활성화했다. 운영 환경변수·DB·금융 API는 사용하지 않았다.

DeletedProductPaymentIntegrationTest는 세 수단 각각 신규 삭제 상품 준비 거부와 준비 후 삭제한 상품의 재사용/승인 진입 차단을 확인한다. 결제 행과 예약 수가 추가로 증가하지 않는지, 기존 결제 조회가 가능한지, abort가 자리를 반환하는지를 같은 시나리오에서 확인한다. 완료된 결제 조회 보존은 별도 대조군이다.

수정 전 7개 중 6개 실패했다. 세 수단의 신규 준비와 재사용이 거부되지 않았다. 이미 완료된 결제 조회 대조군 1개는 통과했다. 실패 원본 XML은 output/bug-audit-20260923/deleted-238-before.xml에 보존했다. 수정 후 신규 7개 모두 통과했고, 기존 준비 경계 및 결제 도메인을 합한 306개가 실패·건너뜀 없이 통과했다. 성공 원본은 deleted-238-after.xml로 분리했다. 전체 회귀/배포 결과는 MR과 완료 기록에 별도로 남긴다. 테스트 시간이나 추가 검증 수를 성능 개선 수치로 바꾸어 표현하지 않는다.

재실행: Java 21 환경에서 backend/gradlew.bat --init-script ../docs/testing/full-regression-runtime.gradle test --tests com.gongguhan.audit.DeletedProductPaymentIntegrationTest --tests com.gongguhan.audit.PaymentPrepareBoundaryIntegrationTest --tests "com.gongguhan.domain.payment.*" --console=plain.

후속 로컬 전체 회귀는 934개 중 931개 통과, 실패·오류 0, Redis 2개 및 S3 1개는 환경 조건으로 건너뛰었다. 첫 검색 수정의 Jenkins에서는 별도 Redis/MinIO 컨테이너로 해당 3개를 실제 실행해 통과했지만, 이 브랜치의 배포 CI 결과를 그 결과로 대체하지 않는다. 이번 변경의 CI·배포 결과는 실제 실행 후 별도 기록한다.

## 7. 검토 체크리스트

- 조회 경로에서만 숨긴다고 쓰기 경로를 신뢰하지 않는다.
- 신규 예약과 멱등/활성 슬롯 재사용 양쪽을 막는다.
- 이미 가진 paymentId로 외부 승인에 진입하는 경로도 검사한다.
- 본인 확인을 삭제 검사보다 먼저 적용할 수 있는 곳에서는 그 순서를 유지한다.
- 거부 시 Redis 잠정 예약을 반환하고 DB 결제 행을 남기지 않는다.
- 완료 거래 조회·미완료 슬롯 중단·환불 및 금융 결과 기록은 보존한다.
- FE와 판매 정지 정책을 수정하지 않는다.
