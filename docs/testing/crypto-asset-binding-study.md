# 최초 코인 자산과 견적·지갑 증명을 끝까지 연결하기

이슈 S15P21B205-212. B17(V21 최초 자산 저장)과 C03(V20 지갑 증명)이 통합된 DevelopV2 85e9199에서 시작했다. 추가 스키마 변경은 없다. 실제 지갑 송금과 배포를 하지 않는다.

## 1. 기능을 합친 뒤 발견한 연결 누락

B17은 같은 prepare 요청 키로 자산을 바꾸지 못하게 했다. C03은 사용자가 송신 지갑을 소유하는지 서명으로 확인했다. 그러나 둘만으로는 최초에 USDT를 고른 사용자가 이후 견적 발급에서 다른 자산 ID를 보내는 일을 막지 못했다. 지갑 소유권 증명은 원선택 자산을 결정하는 규칙이 아니기 때문이다. 기존 견적 서비스는 요청받은 자산의 활성 여부와 결제 원화 금액만 보고 발급했다.

수정 전 집중 시험 두 개는 모두 실패했다. 최초 자산과 다른 요청, 최초 자산이 NULL인 과거 결제에 견적을 요청했는데 거부되지 않고 시세를 조회하고 견적을 만들었다. 기대한 PAYMENT_REQUEST_CONFLICT가 발생하지 않은 것이다. 이 실패는 외부 체인이나 개인키 없이 실제 서비스와 도메인 객체를 사용해 재현했다.

## 2. 정책의 위치와 적용 단계

CryptoPreparedAssetPolicy에 한 가지 규칙을 모았다. 결제 수단이 CRYPTO이고 최초 자산이 양수로 존재하며 이후 사용할 자산과 같아야 한다. 같은 조건을 여러 서비스가 조금씩 다르게 구현하면 어느 경로에서는 NULL을 허용하는 식의 차이가 생기므로 공통 검사로 묶었다. 금융 호출이나 저장을 수행하지 않는 순수 검증이다.

CryptoQuoteService는 활성 자산·수취 지갑·외부 시세 조회 전에 이 검사를 한다. 따라서 잘못된 요청으로 불필요한 외부 시세 호출이나 견적 행이 발생하지 않는다. CryptoWalletProofService.issue도 견적의 자산을 최초 선택과 대조하여 다른 자산 견적에 지갑 증명을 발급하지 않는다.

CryptoTxVerificationService는 증명 검증 이후 RPC를 호출하기 전 다시 견적 자산을 확인한다. 마지막 CryptoWalletProofService.recordVerified에서는 결제 행 잠금 아래 최초 자산, 견적 자산, 실제 기록에 넘길 자산과 결제 원화 금액을 재검증한다. 증명 발급 후 RPC를 기다리는 사이 상태가 바뀌어도 이전에 읽은 정보만 믿고 기록하지 않기 위한 경계다. 실제 원선택을 바꾸는 정상 수정 API는 없지만, 단계 사이 불변조건을 한 곳의 가정에 의존하지 않도록 했다.

## 3. 레거시와 재시도 선택 기준

최초 자산이 NULL인 과거 결제는 새 견적/새 증명/새 거래 등록에 사용할 수 없다. 나중 요청 자산을 최초 값으로 채우면 검증을 통과시키기 위해 증거를 새로 만드는 셈이므로 하지 않는다. 과거 입금이 있으면 먼저 체인·원장을 대조하고 기존 환불/수동 조사 절차로 처리해야 한다. 이 MR에서 과거 결제를 삭제하거나 다시 청구하지 않는다.

이미 소비된 증명으로 정확히 같은 거래의 응답만 복구하는 경로는 유지한다. 이 경로는 사용자·서명·기록된 견적/체인/주소/해시를 대조하고 새 견적이나 자금 이동을 만들지 않는다. 새 거래 승인과 성공 응답 유실 복구를 같은 기준으로 막으면 정상 통신 재시도가 불필요하게 실패하므로 구분했다.

## 4. 테스트 기획과 검증 수준

견적 단위 시험 두 개는 잘못된 최초 자산과 NULL 레거시를 거부하고 시세 호출 0회·견적 저장 0회를 확인한다. 기존 정상 견적 fixture는 B17 이후 실제 prepare처럼 최초 자산을 저장하도록 보강했다. 미지원 자산·만료·타인 결제 등 기존 거부 시험도 유지한다.

실제 JPA 지갑 증명 통합 시험에는 다른/불명 자산의 challenge 발급 차단 두 경우와, RPC 구간 중 자산/원화 금액이 바뀐 두 경우를 추가했다. 실패 시 nonce 미소비와 하위 기록 호출 0회를 검사한다. 테스트 DB를 바꾸는 장애 주입은 운영 DB를 임의 수정하라는 절차가 아니다.

실제 서명→거래 기록 연결 시험에서도 증명 발급 후 자산 불일치를 주입하면 RPC가 호출되지 않는지 먼저 확인한 뒤 원상태에서 정상 등록·동일 응답 복구를 확인한다. 기존 서명 변조·만료·취소·동시 nonce 사용 시험 전체를 유지했다. 암호 서명은 공개된 테스트 전용 고정 키이며 운영 키가 아니다.

이번 변경의 지표는 원선택 불일치 견적/증명/거래 생성 0건, 거부 시 외부 호출 0회, 정상 동일 요청의 거래 1건이다. 속도 최적화가 아니므로 회귀 테스트 실행 시간을 결제 성능 개선율로 제시하지 않는다. 실제 MySQL·체인·MetaMask·Redis·S3 환경을 모킹/H2로 완료 처리하지 않는다.

## 5. 재실행과 학습 순서

Java 21에서 backend의 `./gradlew.bat test --console=plain`으로 전체를 실행한다. 집중 확인은 CryptoQuoteServiceTest, CryptoWalletProofIntegrationTest, CryptoSignedSubmissionIntegrationTest 세 클래스를 실행한다. 학습 순서는 원요청 영속값 → 견적 발급 전 검증 → 서명 발급 → RPC 전 재검증 → 잠금 아래 최종 검증 → 동일 응답 복구다.

배송지 불변 스냅샷은 별도 Jira211에서 진행한다. 동일 서비스에 후속 변경이 들어가므로 최종 통합 후 전체 회귀를 다시 확인한다. 이 문서의 결과는 대상 소스와 실행 범위를 명시한 후 하단에 기록한다.

## 6. 실제 검증 결과

수정 전 견적 경계 2개는 예상한 거부가 없어 모두 실패했다. 수정 후 85e9199 기반 전체 백엔드 회귀는 115개 스위트, 748개 중 745개 통과, 실패/오류 0, Redis 2·S3 1개 환경 제외다. 전체 실행 후 실제 서명 연결 시험에 RPC 미호출 단언을 추가했고 해당 통합 시험을 다시 실행해 통과했다. 기능 소스는 전체 회귀 이후 변경하지 않았다. 새 소스와 후속 배송지/환불 변경을 모두 합친 최종 전체 회귀는 통합 현황에서 별도로 기록한다.
