# 종료된 공동구매의 새 결제 진입 차단 — 학습 기록

관련 이슈: S15P21B205-219. 수정 기준은 DevelopV2 `301eef91c031775d47d27f5f3fff62ffc933d9ce`다. 2026-09-21에 제품 코드를 바꾸지 않은 상태에서 재현 시험을 실행했고, 사용자 요청으로 중단한 뒤 2026-09-22에 원본 실패 결과를 보존하고 수정을 이어갔다. 이 문서는 배포 완료나 실제 금융망 결제 성공을 의미하지 않는다.

## 1. 어떤 오류를 막으려는가

공동구매와 결제는 서로 다른 상태를 가진다. 공동구매의 `group_buys.status`는 모집이 계속 가능한지를 나타내고, `payments.status`와 `slot_expires_at`은 개별 결제가 진행 중인지, 확보한 자리의 시간이 남았는지를 나타낸다. 두 값은 매 순간 같이 바뀌는 하나의 행이 아니다.

예를 들어 구매자가 모집 중인 공구에서 카카오페이를 선택하여 결제를 준비하면 결제는 PROCESSING이 되고 만료 시각이 정해진다. 그 직후 판매 철회나 모집 실패 처리가 먼저 공구를 CANCELED 또는 FAILED로 바꿀 수 있다. 아직 개별 결제 정리가 끝나지 않았다면 결제 행에는 PROCESSING과 미래 만료 시각이 남는다. 기존 코드는 이 결제 행만 보고 카카오페이 준비 또는 승인을 계속 시작할 수 있었다.

카드 승인에서도 같은 문제가 있었다. 이미 판매할 수 없는 공구인데 금융망 승인 호출부터 시작하면, 뒤의 참여 확정이 실패하더라도 외부 청구와 내부 주문이 어긋날 수 있다. 코인에서는 새 견적과 지갑 소유권 증명 요청이 계속 발급되어 사용자를 불가능한 결제로 유도할 수 있었다. 소유권 증명 발급 자체가 코인 송금은 아니지만, 종료 공구에 새 결제 절차를 제시해서는 안 된다.

이번 수정이 보장하려는 조건은 다음과 같다. **진입 검사 시 이미 종료된 공구라면, TTL이 남은 PROCESSING 결제라도 새 외부 승인·준비·견적 및 새 소유권 증명 발급을 시작하지 않는다.** 이미 외부 승인에 들어간 뒤 공구가 바뀌는 경우는 별도의 경합·보상 문제이며 이번 조건과 구분한다.

## 2. 재현 시험을 이렇게 설계한 이유

컨트롤러를 모두 가짜로 바꾼 시험은 실제 서비스가 어디서 상태를 검사하는지 입증하기 어렵다. 그래서 `TerminalGroupBuyPaymentBoundaryIntegrationTest`는 Spring Boot의 실제 PaymentService, 카드·카카오 서비스, 코인 견적·소유권 증명 서비스를 사용하고, H2에 실제 결제와 공구를 저장한다. 카드 금융망 클라이언트, 카카오 게이트웨이, 환율 제공자만 네트워크를 사용하지 않는 대역으로 교체한다. Redis 슬롯 게이트도 대역을 사용하지만 DB 슬롯 준비는 실제 공통 서비스를 통과한다.

시험은 처음부터 깨진 결제 행만 넣지 않는다. 먼저 정상 RECRUITING 공구와 구매자·배송지를 만든 뒤 실제 prepare를 호출한다. 카카오 승인 경로는 정상 HMAC state와 준비 기록까지 만든다. 그 후 공구 상태만 종료로 바꾼다. 이 순서로 '예전에 정상 발급한 슬롯이 이제는 종료 공구를 가리키는 상황'을 재현한다.

종료 상태 세 가지 FAILED, CANCELED, FULFILLED를 각각 다섯 진입점 CARD, KAKAO_READY, KAKAO_APPROVE, CRYPTO_QUOTE, CRYPTO_PROOF와 조합했다. 모두 15개 음성 사례다. FULFILLED도 모집 가능한 상태가 아니므로 제외하면 안 된다. 외부 대역을 호출하면 `MOCK_EXTERNAL_BOUNDARY_REACHED` 예외를 던지도록 하여 잘못된 외부 진입을 명확히 드러낸다. 실제 금융망, 카카오페이, 체인 RPC에는 연결하지 않는다.

동시에 정상 사례도 필요하다. 세 결제수단에서 공구가 RECRUITING이고 슬롯 TTL이 유효하면 공통 승인 문맥 조회가 성공해야 한다. 모집 종료 시각만 지난 경우에도 상태가 아직 RECRUITING인 동안에는 이미 확보한 유효 슬롯을 사용하는 기존 정책을 보존한다. 이 시험을 같이 두면 상태 차단을 구현하면서 임의로 시간 정책까지 바꾸는 실수를 잡을 수 있다.

## 3. 수정 전에 실제로 확인한 결과

제품 코드 변경 전 18개 시험 중 15개가 실패하고 3개가 통과했다. 실패는 애플리케이션 기동 실패가 아니라 예상한 업무 오류를 내지 않은 검증 실패였다.

| 사례 | 수정 전 관측 |
|---|---|
| 카드 승인 × 종료 상태 3종 | 금융망 승인 대역까지 도달: 3건 |
| 카카오 준비 × 종료 상태 3종 | 카카오 준비 대역까지 도달: 3건 |
| 카카오 승인 × 종료 상태 3종 | 카카오 승인 대역까지 도달: 3건 |
| 코인 견적 × 종료 상태 3종 | 환율 조회 대역까지 도달: 3건 |
| 코인 소유권 증명 × 종료 상태 3종 | 예외 없이 증명 발급: 3건 |
| 정상 RECRUITING·유효 TTL × 수단 3종 | 통과: 3건 |

실패 XML은 수정 후 재실행 전에 `backend/build/terminal-boundary-before.xml`로 복사했다. 원본 SHA-256은 `A09237475F7601970755044AE63BC101D7846DA52A7BA778604F046218602893`이다. build 디렉터리는 Git 추적 대상이 아니므로 다른 작업자가 내려받을 수 있도록 관측값과 해시를 `payment-terminal-boundary-before.json`에도 남겼다. JSON은 원본 XML 전체의 대체물이 아니라 재현 결과 요약이다. 원본 XML은 이 작업의 로컬 worktree에 보존되어 있다.

## 4. 코드 원인과 대안 선택

`PaymentService.getApprovalContext`는 소유자가 맞는 결제 행을 잠그고, 요청 수단과 실제 수단이 같은지, PROCESSING인지, 슬롯이 만료되지 않았는지 검사했다. 이어서 배송지 스냅샷을 보장한 뒤 외부 승인에 필요한 값만 반환했다. 그런데 이 과정에서 공구 상태를 한 번도 보지 않았다.

검토한 첫 번째 대안은 카드·카카오·코인 서비스마다 공구를 조회하는 것이다. 작동은 하지만 공통 규칙을 여러 서비스에 복제하게 되고 새 수단이나 새로운 준비 진입점을 추가할 때 빠뜨리기 쉽다. 이미 배송지 스냅샷 수정으로 다섯 진입점 모두 getApprovalContext를 사용하므로 그 공통 경계에 배치하는 편이 변경 범위와 정책 중복을 줄인다.

두 번째 대안은 슬롯 만료 처리 배치를 더 빠르게 실행하는 것이다. 정리 지연을 줄일 수는 있어도 배치가 실행되기 전의 틈을 없애지 못한다. 외부 호출 직전의 검사를 대체할 수 없으므로 이번 해결책으로 선택하지 않았다.

세 번째 대안은 공구의 모집 종료 시각을 다시 검사하는 것이다. 하지만 현재 결제 정책은 기존 슬롯의 유효 시간을 별도로 관리한다. 시간만으로 거절하면 이미 확보한 유효 슬롯까지 임의로 취소하는 정책 변경이 된다. 이번 문제는 '이미 종료 상태인데도 승인 가능'이므로 RECRUITING 상태인지 확인하는 것만 선택했다.

네 번째 대안은 공구 잠금을 외부 HTTP 호출 내내 유지하는 것이다. 긴 네트워크 지연 동안 DB 잠금과 연결을 점유하게 되며, 외부 결제와 DB를 진정한 하나의 원자적 거래로 만드는 것도 아니다. 기존의 짧은 DB 트랜잭션 원칙을 유지하고, 진행 중 종료 경합의 보상 설계는 별도 과제로 남긴다.

## 5. 실제 구현 흐름

수정한 제품 코드는 `backend/src/main/java/com/gongguhan/domain/payment/common/service/PaymentService.java`의 getApprovalContext다. 기존 소유권·수단·결제 상태·만료 검사를 그대로 수행한 다음, `GroupBuySlotPort.get(payment.getGroupBuyId()).status()`가 RECRUITING인지 확인한다. 아니면 기존 `GROUP_BUY_NOT_RECRUITING` 업무 오류를 던진다. 배송지 스냅샷 저장보다 앞에 있으므로 종료 공구의 새 외부 준비를 위해 레거시 주소를 확정할 이유도 없다.

기존 포트를 사용하여 공통 결제 서비스가 GroupBuyRepository 또는 새 SQL에 직접 의존하지 않게 했다. DB 스키마, HTTP 요청/응답, 오류 코드, 프런트 스타일은 변경하지 않았다. 결제 행 잠금과 REQUIRES_NEW 전파도 그대로 유지한다. 새 검사는 공구를 읽는 검사이며 외부 호출 동안 공구 잠금을 유지하지 않는다.

카드는 이 공통 검사를 통과해야 승인 실행권을 잡고 금융망을 호출한다. 따라서 차단된 요청은 `card_approval_status`도 만들지 않는다. 카카오 준비는 최초 외부 호출 전과 외부 준비 응답 후에 공통 검사를 수행하므로 이 규칙이 두 지점에 모두 적용된다. 카카오 승인은 새 승인 호출 전 검사에 적용된다. 코인 견적은 환율 호출 전, 소유권 증명은 nonce 저장 전에 이 검사에 도달한다.

기존 `getCompletedPayment`에는 이 상태 검사를 추가하지 않았다. 이미 성공한 카카오 결제의 응답이 통신 문제로 유실되었다면, 뒤에 공구가 종료되어도 기존 완료 응답을 다시 읽을 수 있어야 하기 때문이다. 이 경로는 새 외부 승인을 하는 경로가 아니다. 이를 지키는 PAID 결과 회복 회귀 시험도 종료 상태별로 3개 추가했다. 시험에서 PAID는 DB fixture로 만든 상태이며 실제 청구 성공을 검증한 것은 아니다.

기존 CryptoWalletProofIntegrationTest와 CryptoSignedSubmissionIntegrationTest는 결제 행만 있고 연결 공구 행이 없는 축약 fixture를 사용했다. 실제 공구 상태가 이제 승인 전제이므로 해당 fixture에 정상 모집 중인 공구를 추가했다. 공통 서비스를 mock하여 검사를 우회하거나 제품 코드에 '공구가 없으면 허용' 예외를 넣지 않았다.

## 6. 수정 후 검증과 성능 해석

최초 집중 회귀는 종료 공구 시험과 두 코인 서명 통합시험을 함께 실행하여 성공했다. 신규 종료 공구 시험은 기존 18개에 완료 응답 회복 3개를 더한 21개다. 종료 공구 15개는 전부 지정 오류로 차단되고, 외부 금융·환율 대역 호출 0회, 새 증명 0개, 카드 승인 실행권 없음, 기존 결제 PROCESSING 보존을 확인한다. 결제 종료·슬롯 반환은 기존 정리 책임이며 이 진입 검사에 섞지 않았다.

2026-09-22 09:04 KST에 완료한 전체 백엔드 회귀는 126개 시험 클래스, 총 840개 중 837개 통과, 실패 0, 오류 0, 환경 제외 3개였다. Gradle 실행 시간은 1분 50초였다. 제외는 Redis 슬롯 게이트 통합시험 2개와 S3 이미지 저장 통합시험 1개다. 현재 worktree의 전체 XML 집계를 사용했으며 이전 문서의 오래된 시험 수를 그대로 옮기지 않았다. 집중 시험의 실행 시간 43초 및 전체 실행 시간은 애플리케이션 초기화와 시험 비용을 포함하므로 결제 API 성능 개선 수치로 해석해서는 안 된다. 프런트 파일 변경은 없으며 이번 수정의 신규 브라우저 E2E는 실행하지 않았다.

이번 수정은 정합성 개선이며 성능 최적화가 아니다. 종료 상태 15건의 잘못된 신규 진행이 15건에서 0건으로 바뀐 것은 기능 안전성 지표다. 정상 경로에는 공구 상태를 조회하는 읽기가 추가되므로 오히려 DB 접근 비용이 늘 수 있다. 실제 MySQL 부하에서 지연시간·처리량을 측정하지 않았고 p95나 TPS가 개선되었다고 주장하지 않는다. 외부 호출을 막은 12건 역시 이번 대역 시험에서 관측한 경계 호출 수이지 실서비스 비용 절감량 측정치가 아니다.

## 7. 해결하지 않은 경계와 배포 시 확인 사항

첫째, 공통 검사 순간에는 RECRUITING이었으나 그 직후 외부 승인이 진행되는 동안 공구가 종료될 수 있다. 이를 TOCTOU, 즉 검사와 사용 사이 상태가 바뀌는 문제라고 한다. 이번 수정은 이미 종료된 공구의 새 진입을 막지, 진행 중 금융 거래를 자동 취소하거나 환불하지 않는다. 후속 참여 확정의 종료 상태 검사는 Jira218과 연결되지만 그것만으로 이미 발생한 외부 청구의 보상이 완성되는 것은 아니다. 외부 승인 결과·내부 실행권·기존 환불 원장을 대조하고 별도 설계된 보상 절차가 필요하다.

둘째, 이미 코인이 송금된 뒤의 영수증 수집과 반환은 별도 책임이다. 이번 변경은 새 견적·새 소유권 증명 발급을 막을 뿐, 과거 입금 증거를 버리거나 체인 송금을 되돌리지 않는다. 종료 결제의 늦은 입금 추적은 Jira216에서 다룬다.

셋째, 전체 회귀는 로컬 H2와 외부 대역을 사용한다. 실제 MySQL 잠금·Redis·S3·실 금융 승인·실체인 송금·EC2 배포 확인과 같지 않다. Docker 관련 제외 항목은 통과로 기록하지 않는다. 이 수정은 마이그레이션이 없지만 기존 버전의 마이그레이션 적용 검증까지 대신하지 않는다.

## 8. 재실행과 학습 순서

Windows PowerShell에서 backend 디렉터리로 이동하여 Java 21을 선택하고 실행한다. 실제 키나 계좌는 필요하지 않다.

```powershell
$env:JAVA_HOME='C:/Program Files/Java/jdk-21.0.12.1'
./gradlew.bat test --tests com.gongguhan.audit.TerminalGroupBuyPaymentBoundaryIntegrationTest --console=plain
./gradlew.bat test --console=plain
```

수정 전을 직접 재현하려면 별도 worktree에서 위 기준 커밋을 사용하고 이 변경의 신규 테스트만 가져온다. 기존 18개 시험 중 15개가 실패하는 것이 원래 증거다. 이후 추가된 완료 응답 회복 3개까지 함께 가져오면 총 21개 중 15개 실패가 되므로 두 실행의 시험 수를 혼동하지 않는다. 원본 실패 XML을 보존하려면 다음 시험 전에 build 외부 또는 다른 파일명으로 복사한다.

학습할 때는 신규 통합시험의 prepare → 공구 상태 변경 → 수단별 진입 순서를 먼저 읽는 것이 좋다. 그 다음 PaymentService의 validateApprovalCandidate와 getApprovalContext를 비교하면 결제 상태와 공구 상태가 왜 별도 전제인지 알 수 있다. 이어서 CardPaymentService.approve, KakaoPayService.ready/approve, CryptoQuoteService.issueQuote, CryptoWalletProofService.issue를 읽으면 작은 공통 검사 하나가 여러 외부 진입을 어떻게 보호하는지 확인할 수 있다. 마지막으로 getCompletedPayment를 읽어 '새 작업 허가'와 '이미 끝난 작업 결과 회복'을 분리한 이유를 확인한다.
