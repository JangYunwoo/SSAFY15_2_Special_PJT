# B09 원승인 이력과 참여 환불 상태를 함께 보여주기

이슈: S15P21B205-206. DevelopV2 전용. 기존 승인·환불 원장이나 외부 금융 거래를 수정하지 않는 조회/UI 변경이다.

## 1. 재현과 도메인 판단

카드 결제 68의 참여를 취소했을 때 참여 화면은 환불 완료였지만 결제 내역은 결제 완료만 표시했다. Payment.status=PAID는 원승인이 발생했다는 이력이므로 이를 FAILED로 바꾸면 승인 이력을 훼손한다. 문제는 승인 상태와 환불 상태가 별개인데 조회 API와 UI가 후자를 생략한 데 있다.

참여 취소는 반품 신청이 아니므로 반품 목록을 조회해 환불 여부를 추측하면 정상 취소 환불을 놓친다. 결제별 환불 원장을 기준으로 연결해야 한다. 이번 연결은 payment.participationId→refund.participationId이며 참여 취소와 반품 환불을 모두 포함한다. 참여가 생성되지 않은 미매칭 코인 입금의 환불은 depositId 경로이며 이 요약의 대상이 아니다.

## 2. 대안과 구조

PaymentResponse에 필드를 강제로 추가하면 prepare·승인·상세 모든 응답과 생성자가 영향을 받는다. 본 문제는 결제 이력 화면이므로 별도 PaymentHistoryResponse와 PaymentHistoryService를 두고 GET /users/me/payments만 확장했다. PaymentService의 기존 사용자 필터·페이지 조회는 그대로 사용한다. 다른 사용자의 임의 참여 ID를 입력받는 새 API는 만들지 않았다.

각 결제마다 RefundRepository를 호출하는 N+1은 피한다. 본인 결제 한 페이지에서 null이 아닌 참여 ID를 모아 findByParticipationIdIn으로 일괄 조회한다. 이 메서드는 Spring Data JPA 파생 쿼리이며 직접 SQL은 없다. 참여 없는 페이지는 조회를 생략한다. 이것은 신규 기능의 쿼리 수 제한 설계이고 기존 버전 대비 처리속도 개선 실측이라고 주장하지 않는다.

## 3. 환불 상태와 금액의 의미

refund.completedAmount는 COMPLETED 원장의 금액만 합산한다. 실패했던 1,000원과 이후 완료된 700원이 있으면 1,700원이 아니라 700원이다. 상태 우선순위는 FAILED+executionClaimed 결과 불명→PROCESSING→완료 금액 존재→FAILED→NONE이다. 처리 중 실행권을 잡은 것만으로 결과 불명이라고 판단하지 않는다. 정상 PROCESSING+claimed는 처리 중이다.

프런트는 승인 상태 chip을 그대로 두고 환불 요약을 아래에 표시한다. 완료 금액이 원승인보다 작으면 부분 환불 완료로 구분한다. UNKNOWN은 환불 결과 확인 필요이며 돈이 반환됐다고 단정하지 않는다. 실패/처리 중도 완료 금액이 실제로 있는 경우에만 해당 금액을 별도로 표시한다. 구 배포 서버가 refund 필드를 보내지 않으면 환불 없음이라고 추정하지 않고 정보 미제공이라고 표시한다.

## 4. 테스트 설계와 결과

백엔드 신규 7개는 원승인 PAID 보존+환불 요약 JSON, 페이지 ID 집합의 단일 batch 호출, 참여 없음의 조회 생략, 결과 불명과 처리 중 구별, 실패 이력 합산 제외, 단독 실패 및 빈 원장을 검사한다. 실제 PaymentHistoryService·Refund 엔티티·JSON 직렬화를 쓰며 결제 조회와 Repository만 모킹했다. DB 쿼리 시간이나 실제 금융 완료를 재측정한 것이 아니다.

프런트 신규 SSR 7개는 전액·부분 환불, 처리 중·실패·불명, 환불 없음, 구 서버 필드 누락을 검사한다. 총 프런트 152개와 ESLint/TypeScript 포함 빌드 통과. 백엔드 전체 108개 클래스, 693개 중 690개 통과·실패/오류 0·환경 제외 3개. Redis/S3 실제 환경 검증은 사용자 요청대로 보류다.

## 5. 한계와 학습 순서

이 MR은 배포 서버의 과거 환불을 재실행하거나 복구하지 않는다. 표시 개선이 외부 금융 환불 성공을 보장하지 않으며 원장 상태의 신뢰성은 환불 실행 도메인의 검증을 따른다. 미매칭 코인 입금 환불은 입금/환불 관리 화면에서 확인해야 한다. 상세 종료 사유와 상품명·승인시각 추가는 별도 문제다.

학습 순서: PaymentResponse와 원승인 의미 → PaymentHistoryService 페이지 참여 ID 수집 → RefundSummary 우선순위 → PaymentHistoryResponse → 프런트 schema/model → PaymentRefundSummary SSR. 재실행: backend gradlew.bat test, frontend npm test/npm run lint/npm run build. 성능 테스트를 새로 주장하지 않으며 단일 batch 호출 검사는 쿼리 구조의 회귀 방어다.
# 리뷰 보강: 공제 후 0원 완료

최종 통합 검증: DevelopV2 b365dda에 rebase하면서 Refund의 실행권 getter는 이미 병합된 구현을 보존했다. 0원 보강까지 포함한 최종 소스에서 백엔드 115개 스위트 741개(738개 통과, 3개 스킵, 실패·오류 0), 프런트 172개, lint·타입 검사·빌드를 다시 통과했다. 백엔드 전체 실행 시간 3분 11초는 회귀 검사 시간이며 처리속도 성능지표가 아니다.

완료 금액이 양수인지로 완료 상태를 판단하면 배송비 공제 후 반환액이 0원인 정상 완료 원장이 NONE으로 사라진다. 상태는 `isCompleted` 원장 존재 여부로 판단하고 금액은 그 완료 원장들의 합계로 별도 계산하도록 분리했다. 화면은 이 경우 `환불 처리 완료(반환액 0원)`으로 표시해 송금이 있었다고 오해시키지 않는다. 백엔드 집계 경계와 프런트 SSR 테스트를 각각 추가했다. 백엔드 테스트는 0원 원장을 mock으로 주어 집계 계약을 독립 검증하며, 0원 반품 원장을 생성하는 업무 로직은 별도 반품 수정 범위다.

보강 후 PaymentHistoryServiceTest 8개, 프런트 전체 153개와 lint·타입 검사·빌드가 통과했다. 아래의 백엔드 전체 회귀 693개 결과는 이 보강 직전 실행이며, 보강 후에는 관련 백엔드 8개를 다시 실행했다.
