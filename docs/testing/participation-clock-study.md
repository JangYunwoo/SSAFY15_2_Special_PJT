# B14 참여 생성 시각의 UTC 일관성

이슈: S15P21B205-209. 병합 대상은 DevelopV2이며 배포 DB와 DevelopV1은 변경하지 않는다.

## 증상과 코드상 원인

참여 생성자가 `LocalDateTime.now()`를 직접 사용했다. 이 타입은 시간대 정보가 없으므로 JVM이 한국 시각인 경우 12시를 저장하고, UTC 서버에서는 동일한 순간에 3시를 저장한다. 다른 결제·배송 시각이 UTC 기준인 시스템에서 이 값에 다시 한국 시간 표시 변환을 적용하면 참여 시간만 9시간 어긋날 수 있다. 서버 설정이 우연히 UTC라고 해도 로컬 테스트와 배포 환경이 달라질 때 재발한다.

2026-09-21 03:04:05Z를 기준으로 한국 시간은 12:04:05다. 저장할 값은 호스트 시간대와 관계없이 03:04:05여야 한다. 단순히 서버 시간을 바꾸는 방법은 개별 개발 환경과 테스트에서 보장되지 않아 제외했다. 프런트에서 9시간을 빼는 방법도 이미 UTC인 데이터까지 잘못 바꾸므로 제외했다.

## 구현과 선택 기준

`ParticipationWriterAdapter`가 애플리케이션의 `Clock`을 주입받고 그 `instant()`를 UTC의 LocalDateTime으로 변환한다. Clock 자체가 Asia/Seoul이어도 변환 목표는 명시적인 ZoneOffset.UTC다. 생성한 참여를 저장하는 원래 트랜잭션과 저장 횟수는 그대로다.

`Participation.create`에는 확정한 생성 시각을 인자로 받는 오버로드를 추가했다. 엔티티는 전달된 값을 그대로 보관하고 null은 거절한다. 기존 호출과 테스트의 호환성을 위한 기존 오버로드는 명시적 UTC now를 사용한다. 실제 결제 승인 후 참여 생성 경로는 주입 Clock을 거치는 새 오버로드를 사용한다. DB 스키마, API 필드 이름, 정렬 규칙은 변경하지 않는다.

Clock 주입의 목적은 단지 테스트 편의가 아니다. 업무 시간을 결정하는 지점을 서비스 경계에 두어 호스트 설정에 숨은 의존성을 제거하는 것이다. 엔티티 생성 시마다 임의로 현재 시간을 다시 읽지 않으므로 하나의 업무 시각을 테스트에서 재현할 수 있다.

## 검증 설계와 결과

기존 어댑터 테스트에 2026-09-21T03:04:05Z, Asia/Seoul인 고정 Clock을 넣었다. 저장 인자를 캡처해 joinedAt이 03:04:05인지 확인한다. 12:04:05라면 실패하므로 UTC Clock만 넣고 통과시키는 약한 검증과 다르다. 별도 테스트는 2020년의 명시 시각을 넘겨 엔티티가 현재 시각으로 덮어쓰지 않는지 확인한다.

수정 전 코드는 Clock 주입을 받지 않고 생성자가 직접 시스템 시간을 읽었으므로 고정 Clock 계약을 만족하지 않는다. 수정 후 어댑터 및 참여 전이 집중 테스트가 통과했다. 전체 백엔드 회귀는 Java 21, H2 테스트 프로필에서 109개 스위트 697개 중 694개 통과, 3개 스킵, 실패·오류 0개였다. 전체 실행은 1분 57초였으며 이는 테스트 수행 시간이지 서비스 성능 향상 지표가 아니다. 추가 쿼리나 외부 호출은 없다.

재실행은 backend에서 `./gradlew.bat test --tests '*ParticipationWriterAdapterTest' --tests '*ParticipationTransitionTest'` 후 `./gradlew.bat test` 순서다. 테스트 XML의 skipped도 함께 확인해야 하며 스킵을 성공으로 집계하면 안 된다.

## 한계와 학습 순서

과거 DB에 이미 저장된 값은 변환하지 않는다. 기존 행이 UTC인지 한국 시각인지 값만 보고 판단할 수 없으므로 일괄 9시간 차감은 위험하다. 복구가 필요하면 배포 시기, JVM 설정, 결제 원장 시각 등 별도 증거로 구간을 확인해야 한다. 이번 변경은 신규 참여 joinedAt 경로만 다루며 다른 엔티티의 모든 시간 필드를 점검 완료했다는 의미가 아니다.

학습 시 먼저 Instant와 LocalDateTime의 차이를 보고, 어댑터에서 instant를 UTC로 바꾸는 지점, 엔티티가 받은 값을 보존하는 지점, 저장 인자를 캡처하는 테스트를 차례로 읽으면 된다. 배포 환경의 실제 응답 확인은 DevelopV2 통합 및 배포 후 별도 수행해야 한다.
