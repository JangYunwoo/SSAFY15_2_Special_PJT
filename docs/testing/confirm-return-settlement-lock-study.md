# C04 반품·구매확정·정산 경합 경계

이슈 S15P21B205-198. DevelopV2 전용 수정이며 배포 DB/DevelopV1/실제 정산 이체는 변경하지 않는다.

## 1. 순차 테스트가 통과해도 버그인 이유

반품 신청은 이미 참여 행을 잠갔지만 수동·자동 구매확정은 일반 findById로 조회했다. 어느 한쪽만 잠금을 쓰면 다른 쪽의 오래된 읽기까지 금지되는 것은 아니다. 반품 트랜잭션이 confirm_hold=true를 저장하기 전, 확정 요청이 DELIVERED/hold=false를 읽으면 두 요청이 각자의 조건 검사를 통과할 수 있다. 마지막 저장이 앞선 상태를 덮어쓰는 lost update가 가능하다.

정산도 같은 종류의 문제가 있었다. 후보 목록은 트랜잭션 밖에서 읽었으며, 실제 지급 명세 생성에서는 후보의 현재 confirm_hold와 정산 가능 시각을 다시 검증하지 않았다. 특히 후보 SQL에도 confirm_hold=false가 없어 구매확정 후 반품이 접수된 참여가 정산에 들어갈 수 있었다. 정산은 아직 은행 송금 전이어도 에스크로를 RELEASED로 바꾸므로 반품 환불과 충돌한다.

## 2. 선택한 방법과 제외한 방법

서비스 메서드에 synchronized를 붙이는 방법은 같은 JVM 안에서만 동작한다. 서버가 두 대가 되면 공유되지 않으므로 선택하지 않았다. 화면의 버튼을 비활성화하는 방법도 이미 발송된 요청이나 배치와의 경쟁을 막지 못한다.

엔티티 전체에 새 version 컬럼을 추가하는 낙관적 잠금도 가능하다. 하지만 기존 반품 신청이 이미 비관적 잠금을 사용하고, 이번 업무는 동일 주문의 상태 변경을 서로 직렬화해야 하므로 기존 participation 행 잠금 계약을 통일했다. 스키마를 추가하지 않고 구매확정·이의제기·반품·정산 기록이 같은 행을 기준으로 순서를 정하도록 했다.

모든 주문을 하나의 전역 잠금으로 묶지는 않는다. 관련 참여 행만 잠그며, 정산은 여러 참여를 잠글 때 ID 오름차순을 사용한다. 금액을 계산한 뒤 뒤늦게 잠그는 대신 실제 기록 전에 검증하는 것이 핵심이다.

## 3. 변경한 경계

PurchaseConfirmService의 confirmManually와 autoConfirmIfDue는 findWithLockByParticipationId로 현재 상태를 읽는다. 반품이 먼저 커밋하면 수동 확정은 충돌로 거절하고, 자동 확정은 hold를 보고 건너뛴다. 자동 배치 전체를 실패시키지 않는 기존 계약은 유지했다.

ParticipationDisputeService도 같은 참여 잠금을 사용한다. 이의 제기가 confirm_hold를 설정하는 다른 진입점이기 때문이다. 반품 화면만 잠가서는 이의 제기와 확정의 경쟁이 남는다.

ReturnRequestRepository의 반품 상태 변경 경로는 참여 ID만 먼저 조회한 뒤 참여 → 반품 순으로 잠근다. 이때 ID projection을 사용하므로 잠금 대기 전에 반품 엔티티의 오래된 상태를 영속성 컨텍스트에 넣지 않는다. 단순히 findById로 엔티티를 먼저 읽고 나중에 잠금 쿼리를 날리면 같은 트랜잭션의 1차 캐시 때문에 오래된 상태를 다시 사용할 수 있다는 점도 고려했다.

SettlementTargetRepository는 confirm_hold=false를 조회 조건에 추가한다. 다만 조회 조건만 추가해도 조회 직후 새로운 반품/이의가 들어올 수 있으므로 SettlementRecordService.settle에서 참여를 잠근 뒤 상태, hold, 정산자격시각, 공구 귀속, 분담금/배송비, 실제 에스크로 잔액을 다시 비교한다. 하나라도 달라지면 해당 공구 정산 생성 전체를 롤백한다. 같은 요청에서 일부 항목만 먼저 에스크로를 해제하지 않는다.

## 4. 실제 교차 순서를 만든 시험

테스트는 실제 Spring 트랜잭션과 H2 JPA를 사용한다. 원격 서버나 실제 주문은 사용하지 않는다. CountDownLatch로 첫 트랜잭션이 상태를 바꾼 후 커밋 직전에 정지하게 하고, 두 번째 스레드의 요청을 그 사이에 시작한다.

| 선행/후행 | 검증 결과 |
|---|---|
| 반품 신청 쓰기 후 커밋 대기 / 수동 확정 | 후행 요청 대기 후 충돌 거절, DELIVERED + hold=true 유지 |
| 반품 신청 쓰기 후 커밋 대기 / 자동 확정 | 후행 요청 대기 후 건너뜀, hold 유실 없음 |
| 수동 확정 쓰기 후 커밋 대기 / 반품 신청 | 확정 후 상태를 읽어 postConfirm/adminReviewRequired=true로 접수 |
| hold=true인 CONFIRMED 참여 / 정산 후보 조회 | 후보에서 제외 |
| 후보 조회 후 hold 변경 / 실제 정산 기록 | 거절, settlements 0건, escrow HELD 유지 |
| 후보 조회 후 환불누계 변경 / 실제 정산 기록 | 오래된 원금 지급 거절, 참여 CONFIRMED 유지 |

대기 확인에 사용한 200ms는 성능 목표나 응답시간 벤치마크가 아니다. 테스트가 한 요청을 의도적으로 붙잡아 둔 동안 두 번째 요청이 완료되지 않는지 확인하는 관측 구간이다. 그 이후 최종 상태를 반드시 검증하므로 단순히 느려서 대기한 것만으로 성공 판정을 내리지 않는다. 각 Future에는 10초 제한을 두어 교착이 발생하면 테스트가 실패하도록 했다.

기존 구매확정·이의제기·반품 저장소·정산 배치 시험도 함께 실행했다. 이 수정의 핵심 지표는 외부 성능 개선이 아니라 유실된 hold 0건, 잘못 생성된 정산 0건, 올바른 관리자 검토 분기다. 기존 일반 조회를 잠금 조회로 바꾸므로 같은 참여의 경쟁 요청은 의도적으로 대기한다. 관련 없는 참여의 처리량이 향상됐다고 주장하지 않는다.

## 5. 범위와 남은 조건

H2의 실제 잠금 시험은 모킹보다 강하지만 MySQL/InnoDB 격리 수준·다중 서버·장애조치의 완전한 대체물이 아니다. Docker 실환경은 사용자 요청으로 보류했다. 원격 정산 실행과 기존 배포 거래 복구도 하지 않았다.

부분 환불 잔액은 별도 정책 MR로 처리한다. 이 MR에서는 기존의 부분환불 자동정산 제외 정책을 유지하며, 잔액을 임의로 상품 분담금으로 바꾸어 플랫폼 수수료를 부과하지 않는다. 후속 사용자 선택에 따라 배송비임을 증명한 잔액만 판매자 정산 대상으로 포함하는 규칙을 별도로 구현·검증한다.

배송 상태 변경도 참여를 갱신하므로 전체 업무 경합의 추가 점검 대상이다. 이 문서는 확정·반품·이의·정산 후보 기록의 검증을 뜻하며 모든 배송/금융 경합이 해결됐다는 의미가 아니다.

학습 순서는 PurchaseConfirmService의 조회 변경 → ReturnRequestRepository.findLockedReturn의 잠금 순서 → SettlementRecordService.settle의 재검증 → ConfirmReturnConcurrencyIntegrationTest의 두 스레드 순서다. 잠금은 현재 값으로 판단할 기회를 보장하는 도구이고, 상태/금액 검증 자체를 대신하지 않는다는 점을 함께 읽으면 좋다.

최종 로컬 전체 회귀: 102개 테스트 클래스, 총 651개 중 648개 통과, 실패/오류 0개, 환경 제외 3개(Redis 2/S3 1). 신규 교차 순서·stale 후보 통합 6개를 포함한다. 실행은 Java 21 환경의 backend에서 `./gradlew.bat test --console=plain`로 수행했다. 이 수치는 이 MR의 소스 기준이며 병합 대상의 다른 병렬 수정까지 자동으로 검증했다는 뜻은 아니다. GitLab 파이프라인과 로컬 회귀도 구분한다.
