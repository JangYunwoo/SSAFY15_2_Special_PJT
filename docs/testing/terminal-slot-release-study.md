# 종료된 공동구매의 남은 결제 슬롯 정리

이슈 S15P21B205-218. 기준 DevelopV2 `462ca8f`. 판매 철회 후 환불 원장 예약 문제(Jira217)와 구분해, 아직 결제하지 않은 슬롯의 종료만 다룬다.

## 1. 사용자가 보던 현상과 코드상 원인

결제를 시작한 뒤 판매자가 공구를 철회하거나 모집 실패 판정이 발생하면 공구의 reserved_slots는 0으로 정리된다. 하지만 각 payments 행은 여전히 PROCESSING일 수 있다. 이후 사용자가 취소하거나 결제 실패 콜백이 도착하거나 만료 배치가 실행되면 PaymentService는 개별 결제를 종료하기 전에 GroupBuySlotService.release를 호출한다.

기존 releaseSlot은 공구가 어떤 상태인지와 관계없이 예약 수가 양수일 것을 요구했다. 종료 과정에서 이미 0이 된 합계를 다시 감소시키려다가 IllegalStateException이 발생하고 결제 상태 변경도 롤백된다. 배치가 다음에 실행되어도 조건은 같으므로 시간이 더 지난다고 해결되지 않는다. '공구 예약 합계 정리'와 '각 결제의 종료'가 다른 시점에 일어난다는 사실을 반영해야 한다.

반대로 confirmParticipant는 예약 수만 양수이면 공구가 종료됐어도 참여를 늘릴 수 있었다. 정상 신규 흐름에서는 합계가 0이라 우연히 실패했지만, 오래된 데이터나 불일치한 양수 카운터가 있다면 종료된 공구를 확정할 수 있는 상태 검사 누락이다.

## 2. 수정 전 재현 설계

실제 JPA/H2 서비스 통합 테스트에서 PROCESSING 결제와 예약 1개를 만든다. CANCELED는 GroupBuy.withdrawBySeller, FAILED는 실제 judgeRecruitment로 전환해 합계가 0이 되는 과정을 거친다. FULFILLED는 방어적 레거시 조합을 fixture로 구성한다. 각 상태에서 abort, expireSlotIfDue, failPayment를 호출해 결제 종결과 합계 0 유지를 확인한다.

추가 3개는 종료 상태에 오래된 예약 1개를 주입한 뒤 공통 confirm을 호출한다. 마지막 1개는 모집 중 예약 0이라는 진짜 불일치를 계속 거절하는지 검사한다. 따라서 무조건 예외를 무시하는 수정은 이 테스트를 통과할 수 없다.

기준 코드에 같은 테스트만 추가한 결과 총 13개 중 12개가 실패했다. 종료 후 취소/만료/실패 9개는 슬롯 없음 예외로 종료하지 못했고, 종료 후 확정 3개는 거절되어야 하는데 성공했다. 모집 중 0 검사 1개만 통과했다. `terminal-slot-before.json`은 이 수정 전 증거다.

## 3. 선택한 구현과 제외한 대안

공구 종료 트랜잭션 안에서 모든 Payment 행을 잠그고 일괄 종료하는 방법은 기존 payment → group 잠금 순서와 반대가 되기 쉽다. 카드 외부 승인 중이거나 결과 불명인 건까지 일괄 종료하는 것도 안전하지 않다. 공구 종료가 외부 승인 결과를 모르는 상황에서 금융 상태까지 추정하면 안 된다.

예약 수가 0이면 언제나 성공으로 처리하는 방법도 사용하지 않았다. 모집 중 0은 중복 해제나 데이터 불일치를 드러내는 중요한 오류다. 이를 숨기면 정상 모집의 슬롯 수 계산이 잘못돼도 발견하지 못한다.

선택한 조건은 정확하다. reservedSlots가 0이고 상태가 CANCELED, FAILED, FULFILLED 중 하나이면 공구 합계 해제는 이미 끝난 작업으로 본다. 별도 감소 없이 반환하여 호출자가 자기 Payment를 종료할 수 있게 한다. 그 외에는 기존 양수 검사와 감소를 그대로 수행한다. 알 수 없는 상태, 음수, 모집 중 0을 허용하지 않는다.

confirmParticipant에는 RECRUITING 상태 검사를 추가했다. 종료 상태에서 양수 카운터가 있어도 GROUP_BUY_NOT_RECRUITING으로 거절하며 참여를 늘리지 않는다. 외부 승인 전의 상태 확인과 이미 진행 중인 외부 승인의 보상 정책은 이 내부 슬롯 정리와 별도 경계다.

## 4. 중복과 금융 실행권에 미치는 영향

공통 PaymentService는 이미 Payment 행을 잠그고 PROCESSING 여부를 재검증한다. 첫 만료/실패가 성공하면 뒤 반복 호출은 공구 해제까지 가지 않는다. 즉 그룹 합계의 제한적 멱등 처리가 개별 결제 상태 검사를 대체하지 않는다. 카드 승인 실행 중/UNKNOWN 해제 금지 역시 수정하지 않았다.

Redis 게이트 호출 위치와 정책도 바꾸지 않았다. 테스트는 명시적으로 로컬 게이트 대체 구현을 선택한다. 실제 Redis 장애/재동기화 검증은 사용자 요청으로 보류된 별도 항목이다. 종료 공구에 새 예약을 허용하지 않으며 DB가 최종 상태 판단을 한다.

이 수정은 기존 결제에 실제 환불하거나 재승인하지 않는다. 남아 있는 PROCESSING을 신규 정상 실행 경로로 종료할 수 있게 하는 코드 변경이다. 과거 외부 승인이 실제로 존재하는지는 원장·제공사 대조가 필요하고, 시간 경과만으로 카드 UNKNOWN 실행권을 해제하지 않는다.

## 5. 비용, 성능과 검증 범위

추가 DB 조회나 외부 호출은 0이다. 이미 잠근 GroupBuy 객체에서 상태 조건만 판단한다. 이는 코드상 호출 수 비교이며 지연시간이나 처리량이 개선됐다는 측정은 아니다. 기능 정합성 작업으로서 테스트 실행 시간을 서비스 성능으로 해석하지 않는다.

실제 JPA/H2에서 세 종료 상태 × 세 종결 경로 9개, 양수 불일치 확정 거절 3개, 모집 중 0 오류 유지 1개를 검증한다. 만료와 실패는 같은 요청을 두 번 호출해 두 번째 감소가 없는지도 확인한다. 실제 MySQL 잠금 특성, Redis, 외부 금융 승인과 공구 철회의 교차 경합을 모두 완료했다고 주장하지 않는다.

재실행은 backend Java 21에서 `./gradlew.bat test --tests '*TerminalGroupSlotIntegrationTest' --console=plain`, 이후 전체 `./gradlew.bat test --console=plain`이다. 학습할 때는 GroupBuy의 종료 시점, PaymentService의 개별 종결 시점, 트랜잭션 롤백으로 PROCESSING이 남는 이유, 제한된 멱등 조건 순서로 읽는다.
