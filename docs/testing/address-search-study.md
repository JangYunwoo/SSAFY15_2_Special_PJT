# 주소 검색 팝업 학습 기록

관련 이슈: S15P21B205-182. 기준 브랜치: DevelopV2(e3cb004). 작성일: 2026-09-21.

## 1. 기존 흐름과 변경 목적

기존 회원가입, 배송지 등록·수정, 판매자 반품주소 등록 화면은 우편번호와 기본주소를 직접 입력하도록 되어 있었다. 사용자가 실제 도로명주소를 검색하고 그 주소에 해당하는 우편번호를 함께 선택하는 일반적인 주소 입력 흐름이 없었다. 우편번호와 기본주소를 따로 입력하면 서로 다른 주소를 조합하는 실수도 가능했다.

이번 변경은 주소 검색이라는 기능을 추가하되 기존 폼의 TextField, Button, 색상·간격 토큰을 재사용한다. 주소 자체를 DB에 저장하는 API나 기존 DTO 계약은 변경하지 않는다. 기존 주소를 수정 화면에 불러오는 기능도 유지한다.

## 2. 검토한 방법과 선택 기준

별도 브라우저 창을 여는 방식은 브라우저의 팝업 차단과 창 전환의 영향을 받는다. 앱 안의 모달에 공식 우편번호 서비스를 embed하는 방식을 선택했다. 브라우저 기본 dialog의 showModal을 사용하여 배경 입력을 막고 검색 창에 제목을 연결했다. 외부 검색 UI를 복제하거나 자체 주소 DB를 만들지 않는다.

공식 서비스는 별도 API 키 없이 사용할 수 있다. 카카오페이 Secret Key와는 무관하며 해당 키를 프런트에 넣지 않는다. 공식 가이드의 현재 kakao.Postcode와 기존 daum.Postcode 이름을 모두 수용한다. 외부 서비스의 로고와 안내 링크는 가리지 않는다.

참조: [카카오 우편번호 서비스 공식 가이드](https://postcode.map.kakao.com/guide).

## 3. 코드의 책임과 처리 순서

`frontend/src/features/address/postcode.ts`는 외부 SDK 로드와 결과 변환을 담당한다. 버튼을 처음 누를 때만 공식 스크립트를 추가하므로 주소 검색을 사용하지 않는 방문에는 SDK를 미리 요청하지 않는다. 동시에 두 호출이 발생해도 같은 Promise를 공유한다. 15초 동안 로드되지 않거나 로드 오류가 발생하면 Promise를 초기화하고 자신이 추가한 script만 제거하여 다시 시도할 수 있게 한다. 성공 시 외부 생성자가 실제로 존재하는지도 확인한다.

검색 결과의 zonecode는 정확히 숫자 5자리여야 한다. 사용자가 도로명을 선택했으면 roadAddress, 지번을 선택했으면 jibunAddress를 사용하고 해당 값이 비어 있으면 address로 보완한다. 기본주소가 공백이면 오류로 처리한다. 이 검사는 잘못된 응답의 입력을 방어하는 것이며 해당 사용자의 거주 여부를 인증하는 기능은 아니다.

`AddressFields.tsx`는 우편번호·기본주소·상세주소와 검색 팝업을 묶는다. 검색 결과를 선택하면 우편번호와 기본주소를 하나의 onChange로 전달한다. 이전 주소와 달라졌다면 이전 건물의 동·호수가 남지 않도록 상세주소를 비운다. 같은 주소를 다시 선택했다면 상세주소를 유지한다. 검색을 취소하거나 닫으면 입력값은 바뀌지 않는다.

팝업은 언마운트 시 iframe과 dialog를 정리하고 active 플래그를 내려서 늦게 돌아오는 SDK 응답이 닫힌 팝업을 다시 채우지 않게 한다. 로드 실패는 오류 메시지와 다시 시도 버튼으로 노출한다. 서비스가 로드된 뒤 서비스 내부 검색 요청이 실패하는 경우는 외부 SDK의 안내를 따르므로 별도 장애 통계까지 구현한 것은 아니다.

회원가입 SignupPage, 배송지 공통 AddressForm, 판매자 SellerVerifyPage에서 같은 컴포넌트를 사용한다. 저장 시 전송하는 zipcode/address1/address2 필드명은 그대로다. 기본주소와 우편번호는 검색 결과의 짝이 깨지지 않도록 읽기 전용이고 상세주소는 직접 입력한다.

## 4. 직접 테스트하면서 수정한 포커스 문제

처음에는 주소 선택 직후 requestAnimationFrame에서 상세주소 input에 focus를 주었다. 실제 브라우저에서 주소 값은 들어갔지만 바로 타이핑한 상세주소가 들어가지 않았다. dialog를 정리하는 effect가 이후에 실행되면서 브라우저 기본 포커스 복귀가 개입할 수 있었다.

선택 시 포커스 이동 의도를 ref에 기록하고 open=false 렌더링 후 effect에서 이동하도록 변경했다. 삭제된 팝업의 정리가 끝난 뒤 상세주소에 포커스를 주는 순서다. 변경 후 실제 활성 요소가 data-address-detail인 INPUT인지 읽어서 확인했고, 칸을 따로 클릭하지 않고 `테스트 상세주소`를 입력하여 화면에 들어가는 것까지 검증했다. 단순히 값 변경만 성공했다고 사용성까지 성공으로 판단하지 않은 이유다.

## 5. 검증 설계와 결과

기준 프런트 테스트는 86개였다. 주소 결과 변환 8개와 SDK 로더 3개를 추가하여 97개가 통과했다. 도로명·지번·대체 주소, 잘못된 우편번호와 빈 주소, 동시 로드 공유, 로드 실패 후 재시도, 무응답 15초 제한을 검증한다. 로더 테스트는 가짜 document/window와 가상 시간을 사용하며 실제 외부 CDN 장애를 일으킨 테스트는 아니다.

타입 검사, ESLint, 프로덕션 빌드도 수행한다. 기능 수정이며 응답 속도 최적화 전후 수치는 측정하지 않았다. 테스트 실행 시간을 서비스 성능 향상 수치로 표현하지 않는다.

로컬 회원가입 화면(127.0.0.1:5188/signup)에서 실제 공식 SDK로 공개 장소인 `서울 중구 세종대로 110`을 검색했다. 도로명 검색 결과 선택 후 우편번호 `04524`와 기본주소 `서울 중구 세종대로 110`이 표시되었다. 상세주소 자동 포커스와 타이핑을 확인했고 재검색 창을 열었다가 닫기 버튼으로 닫아 세 필드가 유지되는 것을 확인했다. 회원가입 제출이나 DB 저장은 이 브라우저 테스트에서 실행하지 않았다.

브라우저 자동화의 iframe 좌표 검증 때문에 결과 버튼 클릭이 도구에서 거부되는 경우가 있어 결과 버튼에 키보드 Enter를 사용했다. 주소 선택 자체는 정상 완료했다. iframe 내부에 포커스가 있을 때 Escape는 외부 SDK가 키 입력을 받으므로 닫기 버튼을 항상 제공한다. 모든 모바일 브라우저와 보조공학 환경을 검증했다는 뜻은 아니다.

## 6. 한계와 재실행 방법

외부 CDN 또는 주소 검색 서비스 장애 시 신규 주소 선택은 불가능하다. 이때 임의의 값을 조합하여 저장시키는 우회는 넣지 않았다. 상세주소는 검색 서비스가 보증하지 않으므로 사용자 확인이 필요하다. 구매자 소유 주소의 권한 검사는 기존 백엔드가 계속 담당한다.

재실행은 frontend에서 `npm test`, `npm run typecheck`, `npm run lint`, `npm run build` 순서다. `npm run dev` 후 회원가입 화면의 주소 검색에서 실제 주소를 선택하고 상세주소 입력, 재열기와 닫기, 네트워크 차단 시 재시도를 확인한다. 배송지와 판매자 화면은 같은 공통 컴포넌트를 사용하지만 로그인·저장까지의 전체 E2E를 이번 검사로 대체하지 않는다.

Docker 엔진 장애로 Redis/S3 실환경 테스트는 수행하지 않았으며 사용자가 이 작업을 나중으로 미뤘다. 본 변경은 DevelopV2 MR 대상으로만 반영하고 DevelopV1 또는 배포 서버를 변경하지 않는다.
