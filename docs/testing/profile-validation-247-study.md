# 프로필 입력 검증 수정 학습 기록 — S15P21B205-247

## 증상과 재현

2026-09-23 실서비스 QA에서 `PATCH /api/v1/users/me`에 빈 nickname과 `phone: "abc"`를 보내면 HTTP 200으로 저장됐다. GET으로 다시 조회해 빈 닉네임을 확인했다. 실제 QA 계정은 점검 후 정리했으며 이 문서에 비밀번호·회원 키·카드 정보를 남기지 않는다.

수정 시작 기준은 `origin/DevelopV2`의 `469b0c9`다. 이전 점검 이후 팀원이 홈·목록 화면을 변경했으므로 최신 버전을 가져와 격리된 작업 폴더에서 시작했다. 기존 작업 폴더의 미커밋 변경과 프런트는 수정하지 않았다.

## 원인: 최대 길이 검사는 필수값·형식 검사가 아니다

`UserController.updateMe()`에는 이미 `@Valid`가 있어 요청 DTO의 제약을 실행한다. 그러나 `UserUpdateRequest`의 nickname과 phone에는 `@Size(max=...)`만 있었다. 빈 문자열은 길이가 0이므로 최대 길이 검사를 통과하고, `abc`도 20자보다 짧아 통과한다. 서비스는 전달된 값을 엔티티에 그대로 반영하므로 잘못된 값이 DB에 저장된다.

검증 위치가 없는 것이 아니라 검증 규칙이 부족한 문제다. 전역 예외 처리기나 저장 로직을 다시 만드는 대신 기존 HTTP 입력 검증 경계의 제약을 보완했다.

## 선택 기준과 적용한 규칙

### PATCH의 null·미전달 의미를 보존

`User.updateProfile()`은 null 필드를 변경하지 않는다. 따라서 `@NotBlank`를 무조건 붙이면 nickname만 수정하는 요청에서 phone이 없다는 이유로 정상 요청까지 거절하게 된다. null을 허용하는 `@Pattern`과 기존 `@Size`를 함께 사용했다. nickname은 값이 전달되었을 때 공백 이외의 문자가 하나 이상 있어야 한다. 일반 공백, 탭·개행, 전각 공백과 NBSP만으로 만든 이름을 거절한다.

닉네임을 자동으로 잘라내거나 다른 문자열로 변환하지 않는다. 기존 사용자의 표시 이름을 뜻하지 않게 변경하지 않기 위해서다. 최대 50자 계약은 유지한다. 필드 생략과 명시적 null은 모두 기존 값을 유지한다.

### 전화번호는 기존 숫자 전용 계약에 맞춘다

프런트의 `PhoneField`는 화면에서는 하이픈을 보여주고 API에는 숫자를 보낸다. `MyPage`의 프로필 저장도 숫자만 보낸다. 백엔드는 이 계약에 맞춰 0으로 시작하는 ASCII 숫자 9~11자만 받는다. 02 일반전화의 9자리, 일반 지역 전화의 10자리, 010·070 등의 11자리 형식을 허용한다.

국가별 전화번호 라이브러리나 번호 발급 대역 전체를 새로 도입하지 않았다. 이번 수정은 국내 서비스의 명백한 잘못된 입력을 차단하는 형식 검사다. 실제 존재하는 번호인지, 입력자가 그 번호를 소유하는지 확인하는 인증을 대신하지 않는다. +82, 하이픈 포함 원문, 공백, 영문 혼합, 전각 숫자는 거절한다. 외부 클라이언트가 있다면 기존 숫자 전용 계약에 맞춰 전송해야 한다.

회원가입의 선택적 phone도 같은 규칙을 적용했다. 수정 API만 막아도 회원가입을 통해 `abc`를 새로 저장할 수 있기 때문이다. 회원가입에서 전화번호 null은 계속 허용한다. 기본 배송지 연락처 검증은 별도 버그 S15P21B205-248에서 처리한다.

### 변경 위치

- `domain/account/dto/AccountInputPatterns.java`: 공통 입력 패턴·오류 문구. 상태나 I/O가 없는 상수만 둔다.
- `domain/account/dto/UserUpdateRequest.java`: 닉네임 공백과 전화번호 형식 제약.
- `domain/account/dto/SignupRequest.java`: 선택적으로 전달되는 회원 전화번호 형식 제약.
- 기존 `GlobalExceptionHandler`: 수정하지 않았다. `VALIDATION_ERROR`, HTTP 400, fieldErrors 반환을 재사용한다.

DB 스키마, 기존 저장 데이터, 인증·금융 로직 및 FE에는 변경이 없다. 기존 잘못된 데이터의 일괄 치환은 수행하지 않는다. 데이터 정비는 대상과 소유자의 실제 값을 확인해야 하는 별도 작업이다.

## 검증 설계

1. DTO 단위 검증: 빈 문자열·여러 종류 공백·영문·너무 짧거나 긴 번호·하이픈·전각 숫자·개행을 거절하는지 검사한다. null과 정상 9~11자리 번호를 허용하고 닉네임 길이·계좌번호 기존 제약이 유지되는지도 검사한다.
2. 실제 Spring HTTP 통합 검증: 서명된 테스트 JWT, 보안 필터, JSON 역직렬화, 실제 컨트롤러·서비스·JPA를 거쳐 격리된 H2 DB까지 확인한다. 단순히 응답이 400인지만 보지 않고, 정상 이름과 잘못된 전화번호를 같이 보내도 이름만 일부 저장되지 않는지 DB를 재조회한다.
3. null·필드 생략·닉네임만 변경·전화번호만 변경의 정상 경로를 검증한다.
4. 백엔드 전체 회귀와 bootJar 빌드를 실행한다. 운영 DB와 외부 금융 API는 로컬 테스트에 사용하지 않는다.

관련 테스트는 `UserInputValidationTest`와 `ProfileValidationIntegrationTest`다. 통합 테스트의 요청 본문 자동 출력은 꺼서 JWT가 실패 로그에 출력되지 않게 했다.

## 수정 전·후 결과

수정 전 새 테스트 30개 중 20개가 실패했다. 실패는 검증 오류를 기대한 입력이 허용되거나 HTTP 400 대신 200이 반환되는 재현이다. 나머지 10개는 기존 정상·부분 수정 계약을 검사한다. 수정 전 XML 결과는 로컬 `output/input-validation-20260923/profile-*-before.xml`에 별도 보관해 수정 후 결과로 덮어쓰지 않았다.

전체 회귀 첫 실행은 기본 512MB 테스트 힙으로 진행하다가 `CryptoTerminalDepositIntegrationTest` 컨텍스트 생성에서 메모리 부족이 발생했다. 이 실행은 중단했고 통과로 집계하지 않는다. 저장소와 Jenkins가 이미 사용하는 `full-regression-runtime.gradle`(테스트 힙 2GB, 컨텍스트 캐시 64)을 적용해 다시 실행한다. 운영 JVM 메모리나 배포 설정을 변경하지 않는다. 실패 XML은 별도 보관했다.

수정 후 새 테스트 30개가 모두 통과했다. 로컬 전체 회귀는 981개 중 978개 통과, 실패·오류 0개, 환경 의존 3개 생략(Redis 2개·S3 1개)이었고 bootJar 빌드도 성공했다. 생략 항목은 Jenkins의 임시 Redis·MinIO 환경 결과로 따로 확인한다. 병합·배포 결과는 MR과 Jira에 기록한다.

테스트 실행 시간은 성능 개선 지표로 제시하지 않는다. 이번 변경의 목적은 입력 정합성이고, 부하 테스트나 응답 속도 최적화가 아니다.

## 재실행·검토 포인트

Java 21 환경에서 backend의 `gradlew test --tests '*UserInputValidationTest' --tests '*ProfileValidationIntegrationTest'`로 집중 검증하고, `gradlew --init-script ../docs/testing/full-regression-runtime.gradle test bootJar`로 회귀·빌드를 확인한다.

검토할 때에는 DTO의 null 허용이 서비스의 null=유지와 일치하는지, 영문을 제거해 숫자처럼 꾸미는 임의 정규화를 하지 않는지, 반환되는 오류가 기존 FE가 처리하는 400/VALIDATION_ERROR 계약인지 확인한다. 필수값 검사와 형식 검사, 번호 소유 인증을 서로 혼동하지 않는 것이 학습의 핵심이다.
