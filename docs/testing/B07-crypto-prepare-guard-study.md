## 2. 사용자가 보는 문제와 코드 원인

배포본 조작 점검에서는 결제수단을 코인으로 바꾸는 순간, 자산을 고르기도 전에 ‘cryptoAssetId가 필요하다’는 서버 오류가 표시됐다. 사용자가 필수 정보를 아직 입력하는 중인데 서버에 먼저 제출해 버린 것이다.

`frontend/src/features/checkout/usePaymentSlot.ts`의 useQuery 활성화 조건은 `addressId !== null`이었다. 카드·카카오는 배송지만으로 준비할 수 있지만 코인은 어느 자산으로 결제할지도 필요하다. 자산이 queryKey와 요청 본문에 들어간다는 사실만으로 요청 시작이 지연되는 것은 아니다. enabled 조건에 그 선행 조건을 명시해야 한다.

백엔드에서 cryptoAssetId 검증을 없애면 잘못된 코인 결제가 만들어질 수 있다. 따라서 서버 검증은 그대로 유지하고 프런트가 입력이 준비된 뒤 요청하게 한다.

## 3. 선택한 구현과 다른 대안

`hasRequiredAsset`은 카드·카카오에서는 true이고, 코인에서는 cryptoAssetId가 null·빈 문자열·공백 문자열이 아닐 때만 true다. 실제 UI는 주로 null을 쓰지만 공백까지 거부해 필수 값의 의미를 명확하게 했다. 입력값을 임의로 다른 ID로 변환하지 않으며 자산의 실제 존재 여부는 서버가 판단한다.

동일한 판정은 두 곳에서 사용한다. queryFn 안에서는 queryKey에 이미 들어 있는 method와 cryptoAssetId로 직접 판정하여 요청 의존성이 명시되도록 한다.

1. `enabled`: 배송지와 필요한 자산이 준비되었을 때만 자동 prepare를 허용한다.
2. `queryFn`: 수동 refetch 등으로 enabled 조건 밖에서 실행되더라도 API 호출 전에 설명 가능한 오류로 중단한다.

enabled만 바꾸는 대안은 자동 요청에는 충분해 보이지만 queryFn이 직접 실행되는 경로까지 막지는 못한다. 두 번째 검사를 넣은 이유다. 컴포넌트 구조를 바꾸거나 요청 전체를 재설계하는 대안은 별도의 슬롯 전환 문제와 섞이므로 이 MR에서는 제외했다.

## 4. 재현 테스트 설계

`frontend/src/features/checkout/usePaymentSlot.test.ts`는 실제 usePaymentSlot을 불러오되 React의 수명주기와 useQuery 실행기는 가볍게 대체한다. 훅이 useQuery에 넘긴 enabled와 queryFn을 직접 확인하고 prepare API 호출을 관찰한다.

테스트가 자체 복제한 조건만 검사하는 것이 아니라 실제 훅의 설정과 실행 함수를 검사하게 한 이유는, 올바른 보조 함수만 만들어 놓고 정작 훅에 연결하지 않은 실수를 놓치지 않기 위해서다.

다음 10개 사례를 고정했다.

- 코인 자산 null, 빈 문자열, 공백 문자열에서 자동 준비 금지: 3개.
- 코인 자산 없이 queryFn 직접 실행 시 prepare 호출 금지: 1개.
- 카드·카카오는 자산 없이 준비 허용 및 요청 본문 확인: 2개.
- 카드·카카오·코인 모두 배송지가 없으면 자동/수동 요청 금지: 3개.
- 자산 선택 및 변경 후 현재 선택한 자산 ID를 전달: 1개.

먼저 수정하지 않은 기준 코드에 이 테스트만 넣어 실행했다. 자산 미선택 3개와 수동 실행 차단 1개가 실패하여 4개 실패/6개 통과를 확인했다. 이후 구현을 수정하여 같은 테스트를 다시 실행했다.

## 6. 검토와 한계

변경한 운영 코드에는 CSS·JSX·레이아웃 변경이 없고, 요청 본문 형식과 카드·카카오 활성화 조건도 유지한다. 자산 변경 시 기존 queryKey가 달라지는 동작을 유지한다. API 키나 사용자 데이터를 테스트에 넣지 않았다.

이 테스트는 실제 DOM 조작, React StrictMode의 effect 정리, 외부 지갑 연결, 블록체인 입금 검증을 수행하지 않는다. 특히 B02/B03의 슬롯 경합이 함께 해결되었다고 해석하면 안 된다. 현재 MR의 변경만으로 서버의 금융 상태나 기존 거래를 수정하지 않는다.

최종 배포 후에는 코인 선택 직후 자산을 고르기 전 Network에 prepare 요청이 없는지, 자산 선택 후 올바른 cryptoAssetId로 요청되는지 직접 확인해야 한다. MR 병합과 실제 배포 검증은 별도 단계다.

## 7. 재실행 및 학습 순서

frontend 폴더에서 `npm test -- src/features/checkout/usePaymentSlot.test.ts`, `npm test`, `npm run build`, `npm run lint` 순서로 실행한다.

코드를 읽을 때는 먼저 기존 enabled 조건을 확인하고, 전용 테스트의 자산 미선택 사례를 읽은 뒤 hasRequiredAsset이 enabled와 queryFn에 각각 왜 필요한지 비교한다. 마지막으로 카드·카카오 회귀 사례를 읽으면 다른 결제수단의 계약을 유지했는지 판단할 수 있다.
