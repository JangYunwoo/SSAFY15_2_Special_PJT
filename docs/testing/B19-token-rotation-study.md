# B19: 토큰의 고유성과 한 번만 가능한 갱신

## 1. 기준과 범위

Jira: [S15P21B205-179](https://ssafy.atlassian.net/browse/S15P21B205-179). 브랜치 `fix/be/S15P21B205-179-token-rotation`, 기준 DevelopV2 `a0cc722ff9ecad580fd54437d5232e3fab493e70`. 관리자·구매자 경계 수정 MR !144까지 반영했다. 배포본 DevelopV1과 실제 사용자의 토큰은 변경하지 않는다.

이 수정은 리프레시 토큰 로테이션의 두 가지 보장, 즉 새 토큰은 이전 토큰과 달라야 하고 기존 토큰은 한 번만 사용할 수 있어야 한다는 조건을 함께 다룬다. 두 조건 중 하나만 고치면 로그인 유지가 끊기거나 중복 갱신이 남는다.

## 2. 수정 전에는 왜 문제가 생겼나

### 발급 시각은 고유 식별자가 아니다

JWT에는 subject, role, isSeller, tokenType, issuedAt, expiration이 들어간다. JWT 날짜는 초 단위로 표현되므로 같은 사용자에게 같은 초에 발급하면 모든 값이 같아질 수 있다. 같은 내용과 같은 서명 키로 만든 토큰 문자열도 같아진다.

기존 refresh는 이전 토큰을 Redis 폐기 목록에 넣고 새 토큰을 반환한다. 그런데 새 문자열이 이전 것과 같다면 반환한 직후부터 이미 폐기된 토큰이다. 빠르게 재갱신하면 인증 실패가 난다. 시간 간격을 강제로 늘리거나 테스트에 sleep을 넣는 것은 원인을 해결하지 못한다.

### 확인 후 저장 사이에는 다른 요청이 들어온다

기존 로직은 isRevoked 조회 후 계정 확인을 거쳐 revoke를 저장했다. 요청 A와 B가 동시에 폐기 여부를 읽으면 둘 다 false를 볼 수 있다. 이후 두 요청이 같은 키에 무조건 저장하고 각각 새 토큰을 반환한다. 조회 자체가 정확해도 조회와 저장이 하나의 연산이 아니므로 한 요청만 이긴다는 보장은 없다.

프런트 공통 API 클라이언트에는 이미 같은 화면 내 refresh Promise를 공유하는 로직이 있다. 그러나 다른 탭, 다른 앱 인스턴스, 직접 API 요청까지 직렬화할 수 없으므로 서버에서 해결해야 한다. 이 MR은 프런트에 불필요한 지연이나 중복 로직을 추가하지 않는다.

## 3. 구현 흐름과 선택 이유

JwtTokenProvider의 공통 발급 메서드에 UUID 기반 jti를 넣었다. access와 refresh의 기존 역할·사용자·유효기간·타입 계약은 바꾸지 않는다. 새 claim은 기존 JWT 검증에 필수로 요구하지 않아 아직 유효한 이전 형식 토큰도 갱신할 수 있다. 새로 발급하는 토큰부터 고유 식별자를 가진다.

RefreshTokenDenylist.tryConsume은 기존 폐기 키에 대해 값이 없을 때만 TTL과 함께 저장한다. StringRedisTemplate의 setIfAbsent(key, value, Duration) 하나로 전달한다. 키 존재 확인 뒤 별도 저장하거나, 저장 후 TTL을 따로 설정하는 방식은 사용하지 않는다. 전자는 중복 승자를 만들고 후자는 프로세스 중단 시 만료 없는 키를 남길 수 있다.

TokenService는 기존 isRevoked를 빠른 거절 용도로 유지하지만 그 결과를 실행권으로 믿지 않는다. 유효한 JWT와 현재 계정을 확인한 후 tryConsume이 true일 때만 새 토큰을 만든다. false 또는 null이면 발급하지 않는다. Redis 연결 실패도 성공으로 취급하지 않고 예외를 전달한다. Redis를 우회해 새 토큰을 발급하면 장애 시 중복 소비 방지가 사라지기 때문이다.

기존 logout의 revoke와 새 tryConsume은 동일한 키를 사용한다. logout이 먼저 키를 저장하면 그 뒤 갱신의 조건부 저장이 실패한다. 반대로 갱신이 먼저 성공하여 새 토큰을 발급한 뒤 기존 토큰으로 logout하면, 이미 발급된 자식 토큰까지 전부 폐기하는 기능은 아니다. 그것은 별도의 세션/토큰 계보 설계가 필요한 범위다.

키는 기존 해시 방식을 유지하여 배포 중 이전 폐기 목록과 호환된다. 토큰 원문은 Redis 키에 넣지 않으며 로그나 보고서에도 출력하지 않는다. 해시 알고리즘 변경은 기존 폐기 기록을 읽지 못하게 할 수 있어 이번 동시성 수정에 섞지 않았다.

JVM synchronized만 사용하는 대안은 여러 서버 인스턴스 사이에서 효과가 없어 제외했다. DB 잠금 추가 대신 이미 공유하는 Redis의 조건부 명령을 선택했다. 새 분산 락 키와 해제 절차를 추가할 필요 없이 '이 토큰이 소비되었는가' 자체가 일회성 표시다.

## 4. 테스트 설계와 수정 전 증거

수정 전에는 4개 테스트 중 빠른 연속 갱신과 동시 갱신이 실패하고, 이전 토큰 재사용 거절 및 로그아웃 후 갱신 거절 2개는 통과했다.

TokenRotationRegressionTest는 실제 JWT 발급기·TokenService·RefreshTokenDenylist를 사용한다. Redis 명령 경계만 ConcurrentHashMap의 원자적 집합 연산으로 대체한다. 폐기 어댑터 자체를 가짜 성공 메서드로 바꾸지 않으므로 서비스가 실제로 조건부 Redis 명령을 사용하는지까지 통과한다. 단, Redis 네트워크·서버를 시험하는 것은 아니다.

연속 갱신은 100회 실행하고 매번 이전 토큰은 폐기됐고 새 토큰은 폐기되지 않았는지 확인한다. 동시 갱신은 계정 조회 지점에서 두 요청을 barrier로 만나게 해 둘 다 초기 폐기 확인을 통과하도록 만든다. 시작 시각이 우연히 겹치길 기대하는 테스트보다 check-then-write 경합을 직접 드러낸다. 결과는 성공 하나와 업무 거절 하나여야 한다.

수정 후에는 초기 확인과 소비 사이에 로그아웃이 먼저 완료되는 사례, Redis 소비 실패 시 새 토큰 발급 메서드가 호출되지 않는 사례를 추가했다. 별도 어댑터 테스트는 SET NX와 TTL이 함께 전달되는지, 원문 없는 동일 키인지, 만료된 TTL에는 쓰지 않는지, null/연결 실패가 성공이 되지 않는지 확인한다. JWT 테스트는 100회 발급 시 jti가 모두 다르고 actor 계약은 유지되는지 확인한다.

## 5. 검증 결과와 해석

최초 수정 후에는 로테이션 4개·어댑터 3개·기존 JWT 1개가 모두 통과했다. 보강 후에는 로테이션 6개·어댑터 3개·JWT 2개가 모두 통과했다. 최종 전체 백엔드는 95개 클래스, 609개 중 606 통과/3 제외, 실패·오류 0이다. Gradle BUILD SUCCESSFUL과 XML 집계를 확인했으며 `B19-token-rotation-results.json`에도 기록했다. 추가 경계 사례는 최초 수정 전 통계와 구분한다. 로컬 검증이며 GitLab CI 실행 결과가 아니다.

로컬 환경에서 Docker 실행 파일과 6379 리스너를 확인했으나 사용 가능한 Redis를 찾지 못했다. 이를 이유로 EC2 Redis나 실제 사용자 토큰을 시험 대상으로 바꾸지 않았다. 실제 Redis의 다중 프로세스 동시성, 장애/응답 유실, 복제·장애 조치에 따른 내구성 검증은 남는다. 일반 전체 회귀의 Redis/S3 제외도 별도로 표시한다.

소비 성공 후 새 토큰 응답이 유실되면 사용자는 같은 이전 토큰으로 재시도할 수 없고 다시 로그인해야 할 수 있다. 결과 캐시나 토큰 계보 없이 임의의 재사용 유예를 넣으면 공격자의 재사용도 허용할 수 있으므로 이번에는 추가하지 않았다. '안전하게 거절한다'와 '장애 중에도 사용자가 끊김 없이 계속 사용한다'는 서로 다른 보장이다.

이 변경은 보안·정합성 수정이다. Redis 명령 수나 Gradle 소요 시간으로 TPS 개선률을 주장하지 않으며 성능 최적화 결과로 기록하지 않는다. 테스트 통과는 배포 완료, 실제 Redis 복구 보장, 모든 인증 취약점 해소를 뜻하지 않는다.

## 6. 다시 실행하며 공부하기

JwtTokenProvider.createToken의 jti → TokenService.refresh의 검증/계정 확인 → RefreshTokenDenylist.tryConsume → 새 access/refresh 발급 순서로 읽는다. Redis 조건부 쓰기 이전과 이후 각각 프로세스가 중단되면 무엇이 남는지 생각하면, 왜 응답 유실 복구는 별도 설계인지 이해할 수 있다.

backend에서 `./gradlew.bat test --tests '*TokenRotationRegressionTest' --tests '*RefreshTokenDenylistTest' --tests '*JwtTokenProviderTest'`를 실행하고 `./gradlew.bat test`로 전체 회귀를 확인한다. 사용되는 서명 키는 테스트 전용 문자열이며 운영 키가 필요하지 않다.
