# 김태민 담당 기능 수동 점검 시나리오

## 1. 목적

이 문서는 김태민 담당 범위인 카테고리·상품·AI 추출·청약철회 제한·공동구매·카카오페이·반품을 화면과 Swagger에서 함께 검증하기 위한 절차다. 화면에서는 사용자가 실제 동선을 확인하고, Swagger에서는 같은 시점의 HTTP 상태 코드와 응답 JSON을 확인한다.

Controller가 존재하는지만 보는 검사가 아니다. 정상 경로, 권한 분리, 선행 데이터, 외부 연동, 다른 담당 도메인과의 의존성이 실제로 이어지는지까지 확인한다.

## 2. 실행 주소

- 사용자 화면: `http://127.0.0.1:5175/`
- Swagger UI: `http://127.0.0.1:8082/api/v1/swagger-ui.html`
- 김태민 담당 OpenAPI JSON: `http://127.0.0.1:8082/api/v1/v3/api-docs/kim-taemin`

Swagger는 `local` 프로필에서만 활성화한다. 배포 프로필에서는 API 문서와 UI를 기본적으로 비활성화해 내부 DTO와 운영 API가 불필요하게 노출되지 않게 한다.

## 3. Swagger 사용 방법

1. Swagger 상단의 API 정의가 `김태민 담당 + 테스트 인증`인지 확인한다.
2. `POST /auth/login`을 펼치고 `Try it out`을 누른다.
3. 판매자 또는 구매자 테스트 계정의 이메일과 비밀번호를 입력하고 `Execute`를 누른다.
4. 응답 JSON의 `data.accessToken` 값을 복사한다.
5. 화면 상단 `Authorize`에서 `bearerAuth`에 토큰 원문만 입력한다. `Bearer ` 접두어는 Swagger가 붙인다.
6. 판매자 API는 `data.actor.isSeller=true`인 토큰, 구매자 API는 구매자 토큰으로 각각 다시 인증한다.

판정할 때는 다음 필드를 항상 함께 본다.

- HTTP 상태: 정상 생성은 주로 `201`, 정상 조회·변경은 `200`, 본문 없는 삭제는 `204`
- `success`: 성공이면 `true`, 업무 오류면 `false`
- `data`: 실제 업무 결과
- `meta`: 목록의 `page`, `size`, `totalElements`, `totalPages`
- `error.code`: 실패 원인을 프로그램이 구분할 수 있는 코드
- `traceId`: 서버 로그와 한 요청을 연결하는 식별자

## 4. 시나리오 A — 공개 카테고리와 공동구매 목록

### A-1. CAT-01 카테고리 조회

`GET /categories`를 인증 없이 실행한다.

판정 기준:

- HTTP `200`, `success=true`
- `data`가 20개
- ID가 `10001`부터 `10020`까지이고 기획서 순서와 이름이 일치
- 마지막 항목이 `기타`

### A-2. GRP-01 빈 공동구매 목록

`GET /group-buys`에서 `status=RECRUITING`, `sort=popular`, `page=0`, `size=20`으로 실행한다.

초기 DB 판정 기준:

- HTTP `200`, `success=true`
- `data=[]`
- `meta.totalElements=0`

빈 목록은 정상 결과다. 프론트 개발 콘솔에서 첫 항목 계약 검사 오류가 보인다면 실제 API 실패가 아니라 빈 배열의 `data[0]`을 검사하는 프론트 검증기 문제다.

## 5. 시나리오 B — 판매자 상품과 청약철회 제한

### B-1. PRD-02 판매자 상품 목록

판매자 토큰으로 `GET /sellers/products`를 실행한다.

초기 DB에서는 HTTP `200`, `data=[]`가 정상이다. 구매자 토큰으로 같은 요청을 실행했을 때는 HTTP `403`과 권한 오류 JSON이 나와야 한다.

### B-2. WDR-01 활성 제한 사유

판매자 토큰으로 `GET /withdrawal-restriction-reasons`를 실행한다. 제한 사유 ID·코드·설명이 비어 있지 않은지 확인한다.

### B-3. PRD-01 상품 등록

사용자 화면에서 `판매자센터 → 상품 관리 → 상품 등록`으로 이동한다. JPG 또는 PNG 이미지를 넣고 카테고리, 상품명, 가격, 설명을 입력해 등록한다. 이후 Swagger의 `GET /sellers/products`로 생성된 상품 JSON을 다시 확인한다.

현재 로컬 환경에는 S3 버킷과 AWS 자격 증명이 없다. 따라서 이미지 저장 단계에서 `INTERNAL_SERVER_ERROR`가 반환되는 것은 재현 가능한 환경 차단 사항이다. 상품 API가 완성됐다는 판정을 내리려면 S3 개발 버킷을 제공하거나 `local` 프로필 전용 파일 저장 어댑터가 추가되어야 한다.

### B-4. AI-01 이미지 추출

Swagger의 `POST /sellers/products/ai-extraction` 또는 상품 등록 화면의 AI 추출 버튼에 이미지를 넣는다. 정상이라면 `status=COMPLETED`, 각 필드의 `value`와 `confidence`, `warnings`를 확인한다.

기본 AI 주소는 `localhost:8000`인데 현재 별도 AI 서버가 준비되어 있지 않다. 연결 실패 JSON이 나오면 백엔드의 실패 격리는 확인할 수 있지만 AI 실연동 성공으로 판정할 수는 없다.

## 6. 시나리오 C — 공동구매 생성과 운영

이 시나리오는 B-3에서 생성된 상품 ID가 필요하다.

1. `POST /sellers/group-buys/preview`로 분담금·배송비·수수료를 미리 계산한다.
2. `POST /sellers/group-buys`로 목표 인원 2명 이상, 시작 시각과 종료 시각을 입력해 생성한다.
3. `GET /sellers/group-buys`와 `GET /group-buys/{id}`에서 같은 건이 보이는지 확인한다.
4. 참여자가 없을 때 `PATCH /sellers/group-buys/{id}`로 조건을 변경한다.
5. `GET /sellers/group-buys/{id}/participants`가 빈 목록을 반환하는지 확인한다.
6. 참여자가 없는 별도 건은 `POST /sellers/group-buys/{id}/cancel`로 취소한다.

중요 계산 판정:

- `unitShareAmount = ceil(productPrice / targetCount)`
- 개인 결제 예정액은 확정 분담금과 배송비의 합
- 플랫폼 수수료는 배송비를 제외한 상품 금액을 기준으로 계산
- 생성 이후 참여·반품 때문에 분담금이 다시 계산되면 안 됨

## 7. 시나리오 D — 구매자 결제와 카카오페이

이 시나리오는 모집 중 공동구매, 구매자 배송지, 실행 중인 Redis가 필요하다.

1. 사용자 화면에서 구매자 계정으로 로그인한다.
2. 공동구매 상세에서 참여하기를 눌러 배송지를 선택한다.
3. 결제수단으로 카카오페이를 선택한다.
4. 공통 결제 `PAY-01`이 슬롯과 `PROCESSING` 결제를 만드는지 확인한다.
5. Swagger에서 `POST /payments/{paymentId}/kakaopay/ready`를 실행한다.
6. `next_redirect_pc_url`, `tid`, 결제 ID가 응답에 있는지 확인한다.
7. 카카오페이 테스트 화면에서 승인 후 callback의 `pg_token`으로 approve가 호출되는지 확인한다.
8. 결제·참여·에스크로가 한 흐름에서 생성되는지 조회한다.

카카오페이 개발 키는 로컬 환경에 설정되어 있지만, Redis가 없으면 공통 슬롯 선점 단계에서 진행할 수 없다. 이 경우 김태민의 KAKA API뿐 아니라 윤홍준의 PAY 선행 기능 환경도 함께 확인한다.

## 8. 시나리오 E — 반품 라이프사이클

결제 완료 참여, 배송 완료 또는 구매확정 상태가 선행되어야 한다.

1. 구매자 토큰으로 `POST /users/me/participations/{id}/returns/preview`
2. 예상 환불액과 반품 가능 여부 확인
3. `POST /users/me/participations/{id}/returns`로 신청
4. `GET /users/me/returns`에서 신청 이력 확인
5. 판매자 토큰으로 `GET /sellers/returns` 확인
6. 승인 경로는 `POST /sellers/returns/{id}/approve`
7. 거절 경로는 별도 건에서 `POST /sellers/returns/{id}/reject`
8. 거절된 건을 구매자 토큰으로 `POST /users/me/returns/{id}/disputes`
9. 승인 건은 `POST /sellers/returns/{id}/pickup-complete`로 수거 완료·환불 개시

반품 상태와 `confirmHold`, 환불 금액, 처리자, 처리 시각이 단계마다 일관되게 바뀌는지 JSON으로 확인한다. 현재 실제 환불 어댑터는 카카오페이 중심이며 카드·코인 공통 환불 이력은 타 담당 선행 작업이 필요하다.

## 9. 명확히 실패해야 하는 경계 시나리오

- 구매자 토큰으로 `/sellers/**` 호출: `403`
- 인증 없이 보호 API 호출: `401`
- 목표 인원 1명으로 공동구매 생성: 검증 오류
- 존재하지 않는 상품·공동구매·반품 ID: `404`
- 참여자가 있는 공구에 무참여 취소 API 사용: 상태 오류
- 참여자가 있는 공구에 GRP-10 판매자 귀책 철회: 현재 전용 구현이 없으므로 완료 판정 금지
- 동일 결제 준비 요청의 `Idempotency-Key` 재사용: 같은 업무 결과를 반환하거나 중복 생성을 차단

## 10. 현재 판정에 필요한 외부 준비물

김태민 범위를 코드 존재가 아니라 실제 종단 성공으로 확인하려면 다음이 필요하다.

1. 상품 이미지 저장용 S3 개발 버킷, 리전, 접근 자격 증명
2. AI 추출 서버 주소와 실행 가능한 모델 서버
3. Redis 로컬 또는 개발 인스턴스
4. 카카오페이 개발 애플리케이션과 유효한 테스트 결제 환경
5. 카드·코인까지 포함하는 공통 환불 Port와 어댑터
6. 관리자 검토를 실제 UI로 확인할 관리자 로그인 구현

위 항목이 없으면 해당 단계의 실패 JSON을 기록할 수는 있지만, 성공 시나리오가 통과했다고 판정해서는 안 된다.
