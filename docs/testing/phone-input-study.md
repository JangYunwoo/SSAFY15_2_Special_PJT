# 전화번호 입력 자동 하이픈 — S15P21B205-181

## 원인과 범위

가입(본인·수령인), 배송지 추가/수정, 내 정보, 판매자 연락처는 모두 일반 TextField에 입력 문자열을 그대로 보여주고 있었다. 서버 전송 직전에는 숫자만 남기지만 입력 중 서식은 없었다. 입력창별로 서로 다른 정규식을 추가하면 유지보수와 삭제 동작이 달라질 수 있어 공통 PhoneField를 추가했다. 최신 DevelopV2 `c6c92dfb710787fcbec34240635986876f1a6376`의 추천 기능을 포함한 상태에서 작업했다.

## 선택 기준과 구현

상태에는 숫자만 저장하고 렌더링할 때 하이픈을 추가한다. 기존 서버 DTO가 숫자 문자열을 받는 계약을 바꾸지 않는다. 이미 저장된 숫자·하이픈 포함 값도 표시 단계에서 정규화된다. 내 정보의 변경 여부는 하이픈을 제외한 숫자로 비교하므로 서식만 바뀌었다고 저장 버튼이 켜지는 일을 막는다.

PhoneField는 기존 TextField의 레이블·오류·CSS를 재사용한다. 글로벌 스타일이나 입력창 디자인은 수정하지 않는다. 휴대폰/국내 일반전화 입력을 지원하고 서울 02는 두 자리 지역번호로 구분한다. 국제번호 지원이나 전화번호 실소유 인증 기능은 추가하지 않았다. 최대 11자리 숫자 입력 범위를 사용한다.

하이픈을 상태에 그대로 저장하는 대안은 각 폼의 검증·변경 비교까지 수정해야 하므로 제외했다. 일반 텍스트 서식 함수만 onChange에 넣으면 중간 편집 시 커서가 끝으로 이동하거나 하이픈만 반복 삭제되는 문제가 생길 수 있다. 따라서 커서 앞 숫자 개수를 기억하여 표시 후 위치를 복구하고, 하이픈 경계의 Backspace/Delete는 인접 숫자를 지우도록 처리한다. 범위 선택 삭제는 브라우저 기본 동작을 유지한다.

## 테스트 설계와 결과

기존에는 공통 전화번호 입력 컴포넌트가 없으므로 기존 함수를 고의로 실패시키는 전후 테스트 대신 입력 요구사항 16개를 새로 명시했다. 부분 입력, 완성 휴대폰, 서울·지역·070 번호, 하이픈 포함 붙여넣기, 최대 길이, 숫자 비교, 커서 위치를 검증한다. 전체 프런트 테스트 86개, 타입 검사, ESLint, 프로덕션 빌드 모두 통과했다. 구현 중 발견한 JSX 문법 오류와 테스트의 ESLint 오류는 수정 후 재검사했다.

로컬 5187 가입 화면에서도 직접 숫자 01012345678을 입력해 010-1234-5678 표시를 확인했다. 첫 하이픈 뒤에서 Backspace를 눌렀을 때 하이픈에 갇히지 않고 인접 숫자가 삭제되는 것도 확인했다. 실제 회원가입을 제출하거나 사용자 연락처를 서버에 저장하지 않았다. 다른 폼에는 동일한 공통 컴포넌트를 적용했지만 모든 로그인 후 화면을 각각 실제 DB 저장까지 시험한 것은 아니다.

이 작업은 사용성 수정이며 성능 최적화가 아니다. 단위 테스트 실행 시간을 응답 성능 개선 수치로 기록하지 않는다. Docker Redis·MinIO 환경 검증은 사용자가 보류했으며 이 프런트 변경의 통과와 혼동하지 않는다.

## 학습·재실행

phoneInput.ts의 숫자 정규화/표시/커서 계산 → PhoneField의 입력·키보드 처리 → 각 폼의 숫자 상태 → 기존 API 전송 순서로 읽는다. `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`로 재검증한다. 가입 화면에서 중간 삽입, 범위 선택 삭제, 숫자 붙여넣기, 하이픈 경계 삭제를 함께 확인한다.
