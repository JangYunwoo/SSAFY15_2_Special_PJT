# B12 반품 환불 경로·원장·에스크로 일관성 학습 기록

관련 이슈: S15P21B205-189. 대상 브랜치: DevelopV2. DevelopV1 및 EC2 배포, 기존 QA 실패 거래의 실제 금융 재처리는 이 변경에 포함하지 않는다.

## 1. 무엇이 실제로 고장 났는가

기존 배포 점검에서는 카드로 결제한 상품의 반품 신청과 판매자 승인까지 성공했다. 하지만 판매자가 수거 완료를 누르면 `지원하는 환불 어댑터가 없습니다: CARD`라는 사유로 REFUND_FAILED가 됐다. 이는 금융망 잔액 부족에 도달한 것이 아니다. 반품 서비스가 직접 검색하는 RefundPort 구현에는 카카오페이만 있었고, 카드 계좌이체와 코인 실행기를 이미 보유한 공통 RefundOrchestrationService는 호출되지 않았다.

클래스 이름에 Refund가 붙었다고 같은 계약을 구현하는 것은 아니다. 카드 승인 취소의 CardRefundPort와 반품 RefundPort는 서로 다른 인터페이스다. 구현체 목록에 카드 클래스를 무조건 추가하기보다, 어느 계층이 환불 원장·중복 방지·실제 외부 호출을 책임지는지 먼저 정해야 했다.

코드를 연결하는 과정에서 후속 불일치도 발견했다. 반품 완료는 참여를 REFUNDED로 바꾸지만 escrow.refunded_amount는 바꾸지 않았다. 또한 공통 환불 재시도는 모든 FAILED를 다시 실행할 수 있었다. 응답 유실은 미송금의 증거가 아니므로 이대로 카드 이체를 연결하면 오히려 중복 지급 위험이 열린다.

## 2. 선택한 책임 분리와 대안

대안 A는 카드 반품 전용 RefundPort를 새로 만들어 금융망을 직접 호출하는 것이다. 연결 코드는 짧지만 원장 생성, 수취 계좌 검증, 코인 분기, 재처리 정책을 다시 구현하게 된다. 이미 공통 서비스가 있는 상황에서 두 경로의 동작이 시간이 지나며 달라질 위험이 커 제외했다.

대안 B는 수거 완료부터 금융망 응답까지 하나의 DB 트랜잭션으로 감싸는 것이다. DB 롤백이 외부 은행 송금까지 되돌려 주지는 않는다. 은행이 성공한 직후 DB 커밋이 실패하면 오히려 성공 증거가 사라진다. 장시간 잠금도 필요해 제외했다.

선택한 구조는 짧은 예약 트랜잭션 → 외부 실행 → 짧은 종결 트랜잭션이다. 반품 상태와 공통 원장은 함께 예약하고, 외부 호출 전에 실행권을 별도 커밋하며, 실제 성공 원장이 남은 뒤 반품·참여·에스크로를 함께 종결한다.

자동 카드 환불은 기존 정책대로 ACCOUNT_TRANSFER다. 이 프로젝트 금융망 카드 취소는 카드번호/CVC 재입력이 필요하지만 판매자 수거 완료와 배치는 구매자의 카드 입력을 받을 수 없다. 보안정보를 DB에 저장하는 우회책을 사용하지 않았다. 이것은 카드 승인 취소가 성공했다는 뜻이 아니며, 사용자에게 표시하는 환불 수단도 계좌이체 원장을 따라야 한다. 카드 취소 자체의 별도 사용자 취소 경로는 유지했다.

## 3. 실제 요청이 흘러가는 순서

1. ReturnRefundRecordService.prepareSeller 또는 prepareAutomatic은 반품 행을 잠그고 권한/기한/현재 상태를 검사한다. APPROVED가 아니라 이미 진행·실패·완료한 상태는 외부 실행을 반복하지 않는다.
2. 같은 트랜잭션에서 반품 REFUND_REQUESTED, 참여 REFUNDING, 수거/환불 요청 이력, RefundLedgerService.openForReturn의 PROCESSING 원장을 만든다. 원장 생성이 실패하면 앞의 상태도 롤백된다. 지원하지 않는 수단을 넣는 통합 테스트가 이 경계를 검증한다.
3. 커밋된 Preparation은 새 원장을 이 호출이 만들었는지 나타내는 OpenResult를 포함한다. ReturnRefundService는 executeReservedReturn에 이 예약을 전달한다. 이 메서드의 Propagation.NEVER는 외부 금융 호출이 기존 트랜잭션 안에서 실행되는 실수를 차단한다.
4. 공통 오케스트레이터가 결제수단에 맞는 기존 실행기를 호출한다. 계좌이체는 플랫폼 계좌, 구매자 계좌, 금융망 연결을 먼저 확인한다. 실제 외부 호출 직전 execution_claimed를 저장하고 기관거래고유번호도 원장에 남긴다.
5. 명시적인 금융망 거절은 failRejected가 실행권 해제와 FAILED 전이를 같은 트랜잭션에서 기록한다. 네트워크 예외처럼 결과가 불명확한 실패는 실행권을 유지한다. 실패 상태 이름만 보고 안전한 재송금이라고 판단하지 않는다.
6. 외부 성공은 먼저 refunds에 COMPLETED로 기록한다. 이후 RefundFinalizationService가 반품, 참여, 에스크로 누계, 완료 이력을 함께 반영한다. 반품 상태의 조건부 전이를 이용해 이미 반영한 부분환불을 다시 차감하지 않는다.

## 4. 부분 환불과 전액 환불은 왜 다르게 기록하는가

검증용 원결제는 1,000원이다. 800원 환불이면 escrow.amount는 원래 1,000원으로 유지하고 refunded_amount만 800원이 된다. 남은 200원은 HELD로 남는다. 전액 1,000원을 환불하면 escrow 상태는 REFUNDED가 된다. 원결제액 자체를 200원으로 덮어쓰면 거래 원금 증거가 사라지므로 그렇게 하지 않는다.

이 MR은 잔액을 정확히 보존하는 데까지 책임진다. 잔액을 판매자 정산 대상으로 편입하는 규칙과 반품/구매확정/정산 경합은 C04 후속 점검 대상이다. 단순히 에스크로 HELD 잔액이 있다고 실제 정산까지 끝났다고 해석하면 안 된다.

## 5. 관리자 재처리와 결과 불명 방지

계좌 미등록은 외부 호출 전 실패다. 계좌를 보완한 후 동일 환불 ID를 재처리할 수 있다. 반면 송금 응답 유실은 실행권이 남으므로 관리자도 재처리를 바로 실행할 수 없다. 관리자 버튼을 신뢰하는 것이 아니라 서버에서 검증한다.

FAILED여도 execution_claimed가 true면 활성 환불로 조회하고 새 원장 생성도 억제한다. DB 유일 마커 역시 새 실패에서는 유지한다. 기존 환불 ID 재시도만 막고 새 ID로 다시 송금하는 우회가 생기지 않도록 두 경로를 함께 시험했다.

원장 재처리는 비관적 행 잠금을 사용한다. 두 요청이 같은 FAILED 행을 동시에 읽고 둘 다 PROCESSING으로 바꿀 수 없도록 하기 위해서다. 실제 H2 JPA 트랜잭션 두 개를 동시에 시작하는 테스트에서 실행권 획득 1건/거절 1건을 확인한다.

외부 성공 이후 에스크로 종결이 실패하면 이미 송금한 원장을 FAILED로 되돌리지 않는다. COMPLETED를 유지하고 오류를 기록한다. 같은 원장을 다시 대조하는 내부 호출은 외부 송금을 반복하지 않고 종결만 재시도한다. 통합 테스트에서는 에스크로를 의도적으로 제거한 후 복구하여 이 특성을 확인했다. 이는 운영자가 DB를 임의 수정해 복구하라는 안내가 아니라, 격리된 테스트에서 장애를 주입한 것이다.

## 6. 스키마 변경과 기존 데이터 취급

V18__guard_ambiguous_refund_execution.sql은 refunds.execution_claimed를 기본 false로 추가한다. 신규 예약은 실행권을 얻기 전 false이므로 실제 호출 여부를 구분할 수 있다.

기존 PROCESSING/FAILED는 과거 코드만으로 송금하지 않았다고 증명할 수 없다. migration은 이들을 보수적으로 true로 표시한다. 역사적 FAILED 여러 개가 동일 참여를 가리킬 수 있으므로 기존 NULL 유일 마커를 임의로 Y로 바꾸지 않는다. 중복된 역사 행은 조회가 명확하지 않아 차단될 수 있으며, 제공사 내역 대조 후 별도 복구가 필요하다. 무조건 재시도 가능하게 만드는 데이터 보정은 하지 않는다.

H2 MySQL 모드의 별도 연결에서 실제 migration 리소스를 실행해 같은 참여의 과거 FAILED 두 행이 있어도 컬럼 추가/보수적 표시가 가능하고 새 행 기본값은 false인지 확인한다. MySQL/InnoDB 배포 migration 실행과 동일하다고 주장하지 않는다. V17은 별도 카드 실행권 수정에 예약된 번호이므로 통합/배포 시 migration 순서를 함께 확인해야 한다.

## 7. 테스트 기획 이유와 검증 지표

환불은 HTTP 200만으로 평가할 수 없다. 그래서 테스트 단위는 외부 실행 횟수와 네 개 장부의 최종 상태로 정했다. 은행은 모킹하지만 반품/참여/환불/에스크로와 트랜잭션은 실제 Spring/JPA/H2를 사용한다. 테스트마다 독립 ID를 생성하고 실제 금융망이나 기존 거래는 건드리지 않는다.

| 시나리오 | 기대한 관측값 |
|---|---|
| 800원 부분 반품과 중복 호출 | 은행 1회, 환불 원장 1건, 환불 누계 800원, 잔액 200원 HELD |
| 1,000원 전액 반품 | 은행 1회, 반품/참여/환불/에스크로 종료 |
| 계좌 미등록 후 보완 | 최초 은행 0회, 추적 가능한 FAILED 원장, 재처리 후 반품까지 종료 |
| 응답 유실 | 은행 1회, 관리자 재처리 거절, 새 원장 생성 없음, 기관번호 보존 |
| 명시적 거절 후 재시도 | 거절 1회 + 정상 재시도 1회, 원장 한 건 유지 |
| 첫 외부 응답 대기 중 중복 수거 | 은행 1회, 중복 상태 전이 없음 |
| 미지원 수단 예약 실패 | 상태/원장 모두 롤백, 은행 0회 |
| 송금 성공 후 종결 실패·대조 | 원장 COMPLETED 보존, 종결 재시도 후 누계 1회 반영, 은행 추가 0회 |
| 같은 실패 원장 동시 재처리 | PROCESSING 획득 1건, 경쟁 요청 거절 1건 |

수정 전 배포 증거는 카드 반품 2건 모두 어댑터 누락으로 실패하고 환불 원장이 0건이었다. 이 과거 실제 교육망 증거와 이번 모킹 통합 시험은 환경이 다르므로 성능 전후 비교로 취급하지 않는다. 이번 수정은 정합성 수정이다. Gradle 실행 시간이나 테스트 개수 증가를 처리속도 개선으로 제시하지 않는다.

초기 전체 회귀에서 기존 환불 조회 fixture 13개가 새 필드의 Hibernate DDL 기본값 부재로 실패했다. migration은 DEFAULT FALSE였지만 JPA 테스트 자동생성 스키마가 달랐던 문제다. 엔티티의 columnDefinition도 같은 기본값으로 맞췄으며, 테스트 데이터를 우회해서 새 필드를 강제로 넣는 방식으로 숨기지 않았다. 확실한 거절이 기존 fail 대신 원자적 failRejected로 가는 두 단위 테스트의 기대 호출도 계약에 맞췄다.

최종 로컬 전체 회귀는 총 648개 중 645개 통과, 실패/오류 0개, 환경 조건 제외 3개다. 신규 생명주기 통합 8개, 실행권 통합 3개, migration 리소스 시험 1개를 포함한다. GitLab 파이프라인 결과가 아니라 Java 21/Gradle 로컬 실행 결과다. 실행 명령은 backend에서 `./gradlew.bat test --console=plain`이다. 커밋 SHA는 MR의 소스 커밋으로 추적한다.

## 8. 남은 한계와 공부 순서

Docker가 사용자 요청으로 보류되어 Redis 2개/S3 1개 실환경 시험은 제외한다. 이번 결과는 MySQL 잠금/다중 프로세스 장애조치, 실제 금융망 이체, 실제 체인 송금의 완료 증거가 아니다. 코드 연결로 코인 경로도 공통 서비스에 도달하지만 실제 가스/지갑/체인 검증을 수행한 것은 아니다.

예약 커밋 직후 프로세스가 종료된 미실행 PROCESSING, 외부 성공 후 종결 미반영, 기존 배포 실패 데이터의 자동 대조/복구는 별도 재처리 스캔 설계가 필요하다. 이 MR은 그 상태를 원장에 남기고 위험한 중복 송금을 차단한다. 모집 실패 환불의 영속 후보 스캔은 B13에서 이어서 다룬다.

공부할 때는 먼저 ReturnRefundRecordService.prepare의 같은 트랜잭션 경계를 보고, RefundLedgerService.OpenResult의 created를 따라간다. 다음으로 claimExecution과 failRejected가 왜 서로 다른 트랜잭션에 필요한지 확인한다. 마지막으로 RefundFinalizationService.finalizeReturnRefund와 ReturnRefundLifecycleIntegrationTest의 장애 주입을 비교하면 외부 송금 성공과 내부 장부 완료를 구분하는 이유를 이해하기 쉽다.
