# 배송 완료와 분쟁 접수의 보류 상태 유실 방지

이슈: S15P21B205-210. 수정 대상은 DevelopV2 백엔드이며 배포 데이터와 DevelopV1은 수정하지 않는다.

## 문제가 만들어지는 과정

구매자의 분쟁 접수는 참여 행을 비관적 쓰기 잠금으로 조회한 뒤 `confirm_hold=true`로 바꾼다. 이 값은 자동 구매확정과 정산을 막는 중요한 상태다. 반면 판매자의 배송 상태 변경은 같은 참여를 일반 조회로 읽었다. 두 트랜잭션이 겹치면 배송 처리가 아직 커밋되지 않은 분쟁의 옛 값인 false를 읽고, 나중에 자신의 상태 변경을 저장하면서 true를 false로 덮어쓸 수 있다.

배송 코드에 `confirmHold=false` 대입이 없어도 문제가 생긴다. JPA는 수정된 관리 엔티티를 flush하면서 상태를 UPDATE하는데, 엔티티에 남아 있는 오래된 필드가 함께 쓰일 수 있기 때문이다. 트랜잭션을 각각 붙이는 것만으로는 두 트랜잭션 사이의 실행 순서가 정해지지 않는다. 사용자에게 분쟁 접수 성공을 돌려주고도 정산 보류가 풀리는 것이므로 단순 화면 오류가 아닌 정합성 문제다.

## 대안과 선택 기준

`@DynamicUpdate`로 변경된 컬럼만 UPDATE하도록 할 수 있지만 업무 판단 자체가 오래된 status를 읽는 문제까지 해결하지는 못한다. 낙관적 버전 필드를 추가하면 충돌을 감지할 수 있으나 DB 변경과 재시도 정책이 필요하고 기존 반품·확정 경로는 이미 참여 행 비관적 잠금을 사용한다. 따라서 배송도 같은 참여 행을 잠그는 일관된 실행 순서를 선택했다.

여기서 잠금 호출만 뒤에 추가하면 불충분하다. 잠금 전에 참여 엔티티를 조회했다면 JPA 1차 캐시가 그 오래된 인스턴스를 유지할 수 있다. 그래서 단건 배송은 배송 ID에 대응하는 **참여 ID 값만** 먼저 조회하고, 참여 행을 잠근 다음 배송 엔티티를 읽는다. 일괄 배송도 참여 엔티티 목록 대신 오름차순 ID 목록만 먼저 읽고 각 참여를 잠근 뒤 해당 배송을 읽는다. ID 조회는 JPQL이며 SQL 문자열로 도메인 갱신을 우회하지 않는다.

## 구현 범위

`DeliveryRepository.findParticipationIdByDeliveryId`와 `ParticipationRepository.findIdsByGroupBuyIdOrderByParticipationIdAsc`는 ID만 반환한다. `DeliveryService.findLockedRow`는 참여 잠금 이후 배송 조회라는 순서를 한 곳에 모은다. 송장 등록과 단건 상태 변경이 이 경로를 사용한다. 송장 변경도 배송 상태 변경과 같은 참여 잠금에 들어가야 발송 이후 송장이 오래된 READY 상태로 덮이는 것을 막을 수 있다.

일괄 변경은 참여 ID 오름차순으로 처리한다. 서로 다른 일괄 요청이 동일한 순서로 잠금에 접근하게 하여 역순 잠금의 교착 위험을 줄인다. 배송이 없거나 전이 조건에 맞지 않는 행은 기존과 같이 건너뛴다. 조회 전용 판매자 배송 목록과 구매자 배송 조회에는 불필요한 쓰기 잠금을 추가하지 않는다. 판매자 권한 검증, 허용 상태 전이, 정책에 따른 기한 계산과 응답 형식은 그대로다.

## 테스트를 이렇게 설계한 이유

Mockito로 잠금 메서드 호출만 확인하면 실제 데이터 유실 여부를 알 수 없다. 따라서 H2 DB, 실제 Spring 서비스, 서로 다른 두 스레드의 트랜잭션으로 검증한다. 테스트용 사용자·상품·공구·배송 중 참여·배송과 필요한 정책 행만 별도 테스트 DB에 만든다. 실 금융망이나 배포 서버에는 연결하지 않는다.

첫 트랜잭션에서 실제 분쟁 접수 서비스를 호출하고 커밋 직전에 latch로 대기한다. 두 번째 트랜잭션에서 실제 단건/일괄 배송 완료 서비스를 실행한다. 첫 트랜잭션을 해제한 뒤 DB를 새로 조회하여 배송과 참여는 DELIVERED, confirm_hold는 true, 분쟁 후보는 1건인지 확인한다. 대기 여부만 확인하는 것이 아니라 최종 보류 값이 살아 있는지를 검증하는 이유는 기존 코드도 UPDATE 순간에는 DB 잠금 때문에 잠시 기다릴 수 있기 때문이다.

반대 순서인 배송 완료 선행 후 분쟁 접수도 검증한다. 양방향 순서에서 최종 상태가 배송 완료와 보류를 동시에 보존해야 한다. 기존 단위 테스트는 단건의 ID조회→참여잠금→배송조회→변경 순서 및 일괄 참여 ID 순서를 확인하도록 보강했다.

초기 통합 테스트의 첫 실행은 테스트 DB에 정책 시드가 없어 실패했다. 운영 코드를 기본값으로 우회하지 않고 테스트 fixture에 청약철회·정산기한 정책을 명시해 다시 실행했다. 이 초기 실패는 제품 버그의 재현 증거로 계산하지 않는다.

정책 fixture 보완 후 수정 코드에서 집중 테스트 13개가 통과했다. 이후 배송 서비스의 읽기 순서만 원래 구현으로 되돌리고 동일한 실제 경합 테스트 3개를 재실행했다. 단건/일괄 배송 완료는 모두 최종 confirm_hold가 false가 되어 실패했고, 배송 선행 테스트도 후속 분쟁이 참여 잠금에서 기다려야 한다는 조건을 만족하지 않아 실패했다. 이 수정 전 결과는 테스트 XML 기준 3개 중 3개 실패였다. 원래 구현을 재현한 임시 변경은 즉시 복원했으며 커밋에는 포함하지 않는다.

## 성능과 남은 검증

수정 코드 복원 후 전체 회귀는 Java 21/H2에서 111개 스위트, 708개 중 705개 통과, 3개 스킵, 실패·오류 0개였다. 배송·분쟁 경합 3개도 모두 통과했다. 실행 시간은 3분 5초이며 다른 병렬 테스트와 CPU를 공유한 검사 소요 시간이지 API 지연시간이 아니다. `git diff --check`도 통과했다.

이번 수정은 최적화가 아니라 데이터 유실 방지다. 읽기 목록 API의 배치 조회 구조는 유지한다. 쓰기 일괄 경로는 기존 참여·배송 각 1회 조회에서 ID 1회와 참여 잠금/배송 조회 각 N회로 바뀐다(권한 조회·정책·UPDATE 제외: 2회 → 1+2N회). 예를 들어 25건이면 2회에서 51회로 늘며 이를 성능 향상이라고 표현하지 않는다. 실제 처리량 측정 없이 응답속도 개선 수치를 만들지 않는다. 사용자 제한과 실제 데이터 규모에서 잠금 대기와 처리 시간을 별도 측정해야 한다.

H2 통합 테스트는 애플리케이션 잠금 경로와 상태 보존을 검증하지만 MySQL의 격리 수준·잠금 대기·교착 처리까지 동일하다고 보장하지 않는다. Docker 검증은 사용자 지시로 보류되어 실제 MySQL 동시 요청 재검증은 남아 있다. 배송 서비스 밖에서 같은 엔티티를 갱신하는 새 경로가 추가되면 이 잠금 규칙을 함께 적용해야 한다.

학습 순서는 Participation.holdConfirmForDispute, 기존 배송 전이, 새 ID projection, 잠금 조회, 통합 테스트의 latch와 커밋 경계 순서가 좋다. 재실행 명령은 backend에서 `./gradlew.bat test --tests '*DeliveryServiceTest' --tests '*DeliveryDisputeConcurrencyIntegrationTest'` 후 `./gradlew.bat test`다.
