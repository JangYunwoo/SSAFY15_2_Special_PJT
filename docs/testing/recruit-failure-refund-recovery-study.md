# B13/C06 모집 실패 환불과 영속 복구

이슈 S15P21B205-201. B12 공통 환불 연결과 실행권 가드를 전제로 하는 별도 MR이다. DevelopV1/EC2 배포와 실제 금융 재처리는 하지 않는다. 대상 통합 브랜치는 DevelopV2다.

## 1. 기존 실패의 정확한 위치

기존 교육망 검증에서는 모집 마감 후 공구가 FAILED로 바뀌었지만 참여는 PAID, 에스크로는 HELD였으며 refunds 행 자체가 없었다. GroupBuyFailedEvent는 발행됐지만 실제 환불을 시작하는 연결이 없었다. 따라서 API 키를 넣거나 금융망 잔액을 채워도 이 단계의 문제는 해결되지 않는다. 금융 API 호출까지 도달하지 않기 때문이다.

한 번 이벤트 소비자를 추가하는 것만으로도 정상 서버에서는 시작할 수 있다. 하지만 메모리 이벤트 발행 직후 프로세스가 종료되면 재실행의 근거가 없다. 또한 반품의 수거 완료처럼 예약 트랜잭션과 외부 실행 사이에서 종료되는 상황도 별도로 남는다. 이번 수정은 “어떤 DB 상태가 남으면 다음 실행이 무엇을 해도 안전한가”를 명확하게 구분하는 데 목적이 있다.

## 2. 이벤트 대신 DB 상태 스캔을 기본 경로로 선택한 이유

모집 실패라는 업무 결정은 이미 group_buys.status=FAILED에 영속화된다. 결제 완료 참여와 실제 결제도 DB에 남는다. 이를 다시 읽어 환불 원장을 예약하면 이벤트가 한 번도 발행되지 않은 상황에서도 복구할 수 있다. 별도 메시지 브로커나 새로운 outbox 테이블을 지금 추가하지 않아도 이 업무의 영속 후보를 식별할 수 있다는 점을 이용했다.

스케줄러는 기본 60초 fixed delay로 실행되며 한 종류당 최대 500개 후보를 처리한다. 실제 외부 호출이 길어져도 같은 스케줄러 메서드의 이전 실행이 끝난 뒤 다음 주기가 시작한다. 여러 서버/직접 요청과의 경쟁은 스케줄 주기가 아니라 원장·참여 잠금과 실행권이 막는다.

GroupBuyFailedEvent에 비어 있는 소비자를 만들어 “이벤트 연결 완료”라고 표현하지 않는다. 이 변경의 환불 주 경로는 영속 상태 스캔이다. 기존 이벤트는 다른 소비자의 계약을 위해 그대로 유지하며, 모든 알림 이벤트의 전달 보장까지 해결한 것은 아니다. C06 중 모집 실패 환불 누락과 원장 복구만 이번 범위다.

## 3. 후보 조회부터 환불 예약까지

FailedRecruitmentRefundRepository는 FAILED 공구 + PAID 참여 + PAID 결제 + 지원 수단 + 해당 참여에 환불 원장이 없는 조건으로 ID를 조회한다. 기존 FAILED 원장을 매번 새 원장으로 만들어 재시도하지 않기 위해 상태와 관계없이 이미 있는 원장은 후보에서 제외한다. 금융 실패 해결은 같은 원장의 관리자 재처리 경로를 사용한다.

FailedRecruitmentRefundRecordService.reserve는 후보 ID를 믿고 바로 송금하지 않는다. 참여 행을 잠근 후 현재 상태와 공구 FAILED, 결제 PAID를 다시 확인한다. 같은 트랜잭션에서 RECRUIT_FAILED 원장을 만들고 참여를 REFUNDING으로 바꾼다. 환불 대상 금액은 현재 상품 가격이 아니라 참여에 저장된 원결제 총액이다.

모집 실패 후의 정원 값은 재모집용 슬롯처럼 줄이지 않는다. 이 공구는 이미 실패로 닫혔고, current_participants는 실패 당시 결제 참여 이력을 나타낸다. 구매자 활성 참여 마커는 실제 환불 종결 시 기존 Participation.markRefunded 규칙으로 해제한다.

## 4. 복구할 수 있는 상태와 복구해서는 안 되는 상태

| 영속 상태 | 자동 동작 | 이유 |
|---|---|---|
| FAILED 공구, PAID 참여, 환불 없음 | 원장 예약 후 실행 | 결정은 남았지만 작업이 아직 시작되지 않음 |
| PROCESSING, execution_claimed=false, 예약 30초 경과 | 실행권 획득 후 실행 | 외부 호출 시작 전이라는 영속 증거가 있음 |
| PROCESSING, execution_claimed=true | 송금하지 않음 | 이미 호출했거나 호출 직전 종료됐을 수 있어 결과 대조 필요 |
| FAILED 원장 | 자동 재송금하지 않음 | 계좌/설정/명시거절 등 원인 확인 후 관리자 동일 원장 재처리 |
| COMPLETED 원장, 참여 미종결 | 외부 호출 없이 종결만 | 돈은 이미 나갔으므로 반복 송금 금지 |

30초는 외부 요청을 취소하는 기한이 아니다. 방금 생성된 원장을 최초 요청이 처리할 시간을 주는 복구 지연이다. 30초가 지나도 실행권이 true면 자동으로 해제하지 않는다. 시간이 오래됐다고 미송금으로 추정하지 않는다.

사용자 카드정보가 필요한 CARD_CANCEL 예약은 자동 복구 후보에서 제외한다. 카드번호/CVC를 저장하거나 무조건 계좌이체로 바꿔 보내는 우회는 하지 않는다. 이러한 과거 미실행 예약은 인증/입력과 제공사 대조가 있는 별도 복구 절차가 필요하다.

## 5. 최초 요청과 복구 스캔이 동시에 도착하면

복구 기능이 생기면 최초 요청이 아직 실행 중일 때 스캔이 같은 원장을 읽을 수 있다. execution_claimed를 읽고 false인지 확인하는 것만으로는 부족하다. 두 요청이 동시에 false를 볼 수 있기 때문이다.

RefundLedgerService.tryClaimExecution은 원장 행을 잠그고 상태가 PROCESSING이며 아직 실행권이 없는 경우에만 true를 돌려준다. 패자는 false를 받고 현재 원장을 읽어 반환한다. 중요한 점은 패자를 예외로 처리한 뒤 공통 catch에서 FAILED로 바꾸지 않는 것이다. 그렇게 하면 승자가 은행 응답을 받는 도중 그 원장이 실패로 덮여 정상 완료를 기록하지 못한다.

두 개의 실제 JPA 트랜잭션을 동시에 시작하여 true 1건/false 1건, 원장 PROCESSING 유지인지 시험한다. 별도 생명주기 시험에서는 첫 은행 응답을 보류한 동안 두 번째 resumePersisted를 실행하고 외부 호출이 한 번뿐인지 확인한다.

자체 검토에서 실행권을 외부 호출 바로 앞에만 두면 불충분한 경계를 발견했다. 패자가 그 앞의 계좌/지갑 기록이나 사용자 조회 실패 처리에 들어가 승자의 원장을 FAILED로 만들 수 있었다. 따라서 실행권 획득을 공통 execute의 첫 동작으로 이동했다. 오래된 created=true 결과를 보유한 요청도 실행권이 없으면 목적지 변경, 설정 조회, 실패 기록을 전혀 하지 않는다. 계좌/플랫폼 설정 누락처럼 외부 송신을 하지 않았음이 확실한 실패는 failRejected가 실패와 실행권 해제를 한 트랜잭션으로 처리한다. 송금 상관번호는 실행권을 획득한 뒤 별도 원장 기록 메서드로 남긴다. 이 차이를 단위 테스트로 추가하고 전체 회귀를 다시 실행했다.

## 6. 외부 성공과 내부 종결의 분리

RefundFinalizationService의 참여 전액 환불 종결도 참여 행을 잠그도록 바꿨다. 이미 REFUNDED면 반복 차감하지 않고 종료한다. 외부 COMPLETED 원장은 복구 스캔에서 다시 송금하지 않으며 에스크로/참여 종결만 시도한다.

통합 테스트는 에스크로 행을 테스트 DB에서 제거해 종결 실패를 만들었다. 이때 원장 COMPLETED가 보존되는지 먼저 확인하고, 테스트 fixture를 복구한 후 스캔을 두 번 더 실행한다. 은행 호출은 최초 한 번 그대로이고 참여와 에스크로만 최종 REFUNDED가 되어야 한다. 운영 DB를 임의로 고치라는 뜻이 아니라 회복 경계를 검증하기 위한 장애 주입이다.

## 7. 테스트 설계와 판정 기준

테스트는 실제 Spring/JPA/H2 MySQL 모드의 트랜잭션과 장부를 사용한다. 은행/정책/외부 로그 채번만 모킹한다. 가짜 금융 응답을 쓴 시험이므로 실제 교육망 승인/송금이 성공했다고 표현하지 않는다.

신규 시나리오는 이벤트 없는 FAILED 상태 복구, RECRUITING 제외, 계좌 미등록 한 건과 정상 한 건의 격리, 예약 직후 중단 복구, 실행권이 있는 결과 불명 원장 제외, 외부 성공 후 내부 종결 복구, 최초 요청과 복구 경쟁이다. 추가 실행권 동시 획득 시험을 포함한다.

정량 판정은 정상 환불 원장 1건/외부 호출 1회, 결과 불명 재호출 0회, 기존 실패 원장의 반복 신규 생성 0건, 정상 참여의 REFUNDED 종결이다. 원래 배포 증거는 FAILED인데 원장 0건이었다. 서로 다른 환경의 결과이므로 처리속도 개선율로 계산하지 않는다. 이번 변경은 정합성과 재시작 내성을 보완하는 것이며 성능 최적화가 아니다.

최종 Java 21 로컬 전체 회귀: 105개 클래스, 676개 중 673개 통과, 실패/오류 0개, 환경 제외 3개(Redis 2/S3 1). 신규 복구 생명주기 7개와 실행권 경쟁 1개, 오래된 생성 결과를 가진 패자의 부작용 차단 1개를 포함한다. 실행 명령은 backend의 `./gradlew.bat test --console=plain`이다. 최초 선별 시험에서 미송신 fixture의 createdAt을 Windows 기본 시간대로 만들었기 때문에 UTC 서비스 기준으로 미래가 되어 1개가 실패했다. 해당 테스트 데이터를 명시적 UTC로 수정한 뒤 전체 회귀를 통과했다. 생산 복구 시계는 처음부터 공통 Clock/UTC를 사용했다. 테스트 실패를 숨기거나 서버 시각을 변경하지 않았다.

## 8. 운영 적용 전 확인과 한계

기본 스케줄러는 배포 후 기존 FAILED 공구도 발견한다. 배포 전에는 후보 조회 결과를 확인하고 QA/업무 대상이 의도한 목록인지 점검해야 한다. 이 MR 작성 중에는 배포하지 않았으며 기존 교육망 거래를 자동 재처리하지 않았다.

과거에 환불 원장 없이 이미 외부 송금만 한 데이터는 DB만으로 판단할 수 없다. 이번 후보 스캔의 전제는 결제·환불 원장이 업무 자금 이동의 기준이라는 것이다. 배포 전 제공사 대조가 필요한 역사 데이터는 따로 제외/정리해야 한다. UNKNOWN의 자동 재송금은 어떤 경로에도 추가하지 않았다.

한 번에 500개라는 범위 제한은 과도한 금융 요청을 피하기 위한 운영 상한이다. 반복 실패하는 후보가 상한을 계속 차지하는 대량 장애에서는 운영 점검과 후보 격리가 필요하다. MySQL 다중 인스턴스, 실제 제공사 장애, Redis/S3는 이 H2 검증을 대신 완료 처리하지 않는다.

공부 순서는 영속 후보 JPQL → reserve의 짧은 트랜잭션 → resumePersisted의 상태 분기 → tryClaimExecution의 경쟁 승자 → finalization의 멱등 종결 → 통합 테스트의 장애 주입이다. “반복 실행”과 “돈을 반복 송금”이 같은 의미가 아니도록 경계를 설계한 부분에 집중하면 된다.
