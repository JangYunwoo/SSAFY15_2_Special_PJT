# 정산 중복 이체와 보류 경합 수정

이슈 S15P21B205-202. B22/C01 및 B23은 정산 한 건의 외부 이체 실행권 누락이라는 같은 원인이다. DevelopV2 전용이며 배포/실제 송금/기존 실패 거래 재처리를 하지 않는다.

## 재현과 원인

기존 loadExecutable은 readOnly 트랜잭션에서 상태만 확인했다. 메서드 이름이나 주석에 잠금이라고 적혀 있어도 실제 저장소는 findById였다. 두 요청이 PENDING을 읽으면 둘 다 은행에 송금했다. 송금 응답을 기다리는 동안 관리자가 HOLD로 바꾸면 외부 송금은 이미 진행 중인데 내부 완료 처리만 실패할 수 있었다.

실제 Spring/JPA/H2와 모의 은행을 사용한 수정 전 집중 시험 5개 중 3개가 실패했다. 동시 실행의 은행 호출이 2회였고, 이체 중 보류가 허용됐으며, 실행을 시작한 실패 정산이 자동 재시도 후보에 계속 남았다. 보류 선행 시 송금 거절과 결과 불명 재시도 거절은 기존에도 동작한 정상 대조군이다.

## 선택한 구현과 대안

외부 호출을 전체 DB 트랜잭션에 넣지 않는다. 은행 송금은 DB 롤백으로 취소할 수 없고 느린 호출 동안 연결을 점유하기 때문이다. JVM 잠금도 다중 인스턴스와 재시작을 보호하지 못한다. 따라서 짧은 행 잠금 트랜잭션에서 transfer_claimed=true를 먼저 커밋하고 호출한다. 이 방식은 카드 실행권과 원칙이 같지만 정산의 기존 PENDING/HOLD 및 transferStatus 계약은 유지한다.

SettlementRepository.findForUpdate가 정산 행 잠금을 제공한다. SettlementRecordService의 상태 변경은 이 조회를 사용한다. loadExecutable은 더 이상 단순 읽기가 아니라 실행 자격 재검사와 claimTransfer를 함께 수행한다. 두 번째 실행자는 이미 얻어진 실행권을 보고 거절한다. hold도 실행권 또는 UNKNOWN이면 거절하므로 관리자가 송금 시작 후 돈을 멈췄다고 오해하지 않는다.

기관거래고유번호는 실제 호출 전에 별도 커밋한다. success는 COMPLETED, 명시적인 거절/미실행 검증 오류는 FAILED로 기록하고 실행권을 해제한다. 응답 유실은 UNKNOWN으로 남기며 실행권을 유지한다. 런타임 예외도 응답 불명으로 취급한다. 로그 저장이나 결과 기록이 실패해 UNKNOWN까지 기록하지 못해도 먼저 커밋한 실행권이 재송금을 차단한다. 자동 재시도 조회 역시 transfer_claimed=false만 선택한다.

execute의 사용자/배치 두 진입점은 Propagation.NEVER로 기존 트랜잭션 안에서 호출되는 실수를 막는다. 실행권 커밋이 금융 호출 후로 밀리면 이 설계의 의미가 사라지기 때문이다. 서로 다른 정산 행은 같은 전역 잠금을 공유하지 않는다.

## 마이그레이션과 복구 한계

V19는 transfer_claimed 열을 기본 false로 추가하고 기존 UNKNOWN만 true로 보존한다. 과거 프로세스가 송금 중 죽었지만 PENDING만 남긴 경우를 이 컬럼만으로 복원할 수 없다. 신규 버전 배포 시 작업 중인 이체가 없도록 운영 절차와 금융망 대조가 필요하다. 이 작업에서 운영 DB migration을 실행하지 않았다.

실행권 커밋 후 실제 송금 전에 죽은 경우도 자동 재실행하지 않는다. 이후 기관 내역을 대조할 때까지 안전하게 막는 상태다. 자동 복구가 완성됐다는 뜻은 아니다. 정책 조회나 계정 조회 중 예외가 발생해 실행권이 남을 수도 있으므로 관리 대상의 사유 기록/대조 경로는 후속 운영 보완이다. 이 안전 정지를 단순 실패로 보고 DB 플래그만 지워 재송금하면 안 된다.

## 시험 설계와 결과

SettlementSafetyAuditTest는 실제 사용자·판매자·정산 행을 만들고 은행만 모킹한다. 동시 실행, 이체 중 보류, 보류 후 실행, 결과 불명, 실행 중 자동 재시도 후보 제외를 먼저 확인한다. 추가로 기존 트랜잭션 호출 금지, 일반 런타임 예외, 은행 성공 후 로그 저장 실패, 명시적 거절 후 정상 재시도를 확인한다. 마지막 경우만 두 번의 은행 호출을 허용하는데 첫 호출이 확실히 거절된 경우이기 때문이다.

관찰 기준은 은행 호출 횟수와 최종 상태, 기관거래고유번호 보존, 후보 제외다. 대기 시간을 API 성능 개선 지표로 삼지 않는다. 이번 변경은 정합성 수정이며 실행권 저장 비용이 추가된다. H2는 실제 JPA 경합을 검증하지만 MySQL/InnoDB와 실은행의 부하/장애 특성을 대신하지 않는다. Docker 보류로 Redis 2개/S3 1개 환경 시험은 건너뛴다.

DevelopV2 4f759f2(구매확정/반품/정산 후보 검증 포함)로 통합 기준을 갱신하고 전체 회귀를 다시 실행했다. 최종 109 suites, 701개 중 698개 통과, 실패/오류 0, 환경 제외 3개다. 새 안전 경계 시험은 9개이며 GitLab CI 결과가 아니라 로컬 Java 21/Gradle 실행 결과다. 다른 MR의 참여 정산 후보 검증(settle)은 보존하고 이체 실행권 변경만 추가했다. 코드 검토와 diff 검사도 통과했다.

학습 시 실패 시험 → loadExecutable → 엔티티 claim/hold → 외부 호출 전 기관번호 기록 → UNKNOWN/자동 재시도 필터 순으로 읽으면 된다. backend에서 Java 21로 `./gradlew.bat test --tests '*SettlementSafetyAuditTest' --console=plain`, 전체는 `./gradlew.bat test --console=plain`으로 재실행한다.
