# 추천 세션·캐시의 사용자 경계

이슈 S15P21B205-185. 기준 DevelopV2 03f78eb. 작성일 2026-09-21.

## 1. 같은 브라우저 탭이 같은 사용자는 아니다

기존 tracking.ts는 sessionStorage의 gongguhan.recommendation-session에 UUID 하나만 저장했다. sessionStorage는 탭 단위이므로 A 계정 로그아웃 후 B 계정 로그인에도 같은 값이 남는다. 정상적인 순차 요청에서 백엔드는 세션 소유자가 다른 B의 이벤트를 거절한다. 프런트는 추천 로그 실패를 삼키도록 되어 있어 화면 탐색은 되지만 B의 행동 학습이 조용히 누락될 수 있다.

로그아웃 기능은 React Query 캐시를 비우지만 추천 sessionStorage는 비우지 않았다. 또한 인증이 만료되는 경로까지 모든 캐시가 항상 정리된다고 의존하는 것은 취약하다. 추천 쿼리 키에는 size만 있고 사용자 ID가 없었다. 홈의 추천 결과 계산도 로그인 여부가 아니라 캐시에 남아 있는 items만 보았다. 사용자 경계를 캐시 삭제의 성공 여부에만 의존하지 않도록 고쳤다.

## 2. 대안과 선택

로그아웃 버튼 한 곳에서 키를 지우는 방법은 세션 만료, 다른 계정으로의 직접 전환, 오래된 callback에는 충분하지 않다. 키를 사용자마다 여러 개 만드는 방법은 이전 사용자 세션을 오래 보관한다. 하나의 저장 항목 안에 `{userId, id}`를 저장하고 현재 로그인 사용자와 일치할 때만 재사용하는 방법을 선택했다. 계정 전환이면 새 UUID로 교체한다. 기존 버전의 소유자 없는 단순 UUID와 깨진 JSON은 재사용하지 않는다.

프런트의 userId는 서버 권한을 증명하는 값이 아니다. 서버는 여전히 인증 토큰의 사용자로 권한을 검사한다. 클라이언트의 분리는 잘못된 세션 재사용을 막는 것이며 백엔드 소유권 검사를 대체하지 않는다.

## 3. 구현과 데이터 흐름

recommendationSessionId는 호출 순간의 useSessionStore.getState를 읽는다. actor 또는 accessToken이 없으면 세션을 지우고 null을 반환한다. recordRecommendationEvents는 null일 때 요청을 보내지 않는다. 따라서 로그아웃 직후 이미 예약된 노출 callback이 불필요한 인증 요청을 만들지 않는다. 스토리지가 차단돼 예외가 발생해도 기존 원칙대로 상품 탐색을 막지 않는다.

useRecommendationSessionLifecycle의 effect 의존성을 로그인 boolean에서 실제 userId로 변경했다. 새 로그인 사용자는 새 세션을 사용하고 비로그인 전환 때 키를 정리한다. pagehide callback은 현재 토큰의 사용자가 자신을 등록한 사용자와 같은지 다시 확인한다. 계정 전환 전에 등록된 callback이 새 계정 토큰으로 옛 세션 종료를 요청하지 않게 한다. BFCache의 persisted=true 이동에는 종료하지 않는 기존 정책을 유지한다. 로그아웃 시 옛 토큰으로 종료 API를 억지로 재시도하지 않으며 서버의 기존 무활동 종료 기준에 맡긴다.

추천 목록 쿼리 키에는 userId를 넣었다. HomePage는 비로그인 상태에서 캐시 데이터가 있더라도 추천 목록을 만들지 않으며, 사용자별로 추천 Carousel을 다시 마운트하여 이전 노출 중복 방지 Set이 새 사용자의 노출을 누락시키지 않게 한다. 일반 인기 목록과 UI 스타일은 변경하지 않았다.

## 4. 수정 전·후 검증과 범위

세션 관련 6개 재현 테스트를 먼저 기존 코드에 실행했다. 4개 실패·2개 통과였다. 계정 전환의 동일 UUID 재사용, 로그아웃 상태의 세션 생성, 소유자 없는 예전 UUID 재사용, 로그아웃 후 이벤트 전송이 실패 항목이다. 동일 계정의 세션 유지와 저장소 예외 격리는 기존에도 통과했다.

수정 후 사용자별 쿼리 키, 정상 pagehide 종료, BFCache 유지, 오래된 계정 종료 callback 차단 4개를 더해 총 10개를 검사했다. 프런트 전체 112개 테스트가 통과했다(기준 102개 + 10개). 타입 검사와 프로덕션 빌드도 수행했다. 테스트의 effect는 함수를 직접 실행하는 대역이며 실제 브라우저의 전체 React 렌더링·탭 종료 E2E를 시뮬레이션했다는 뜻은 아니다. 최종 lint도 확인한다.

이 수정은 로컬 단위 테스트와 코드 검토로 사용자 경계 계약을 확인한 것이다. 운영 계정을 실제로 교대로 로그인하거나 배포 로그를 분석한 결과는 아니다. 브라우저 저장소 자체가 사용자에 의해 변경될 수 있으므로 서버에서 권한 검사를 유지해야 한다. 백엔드의 동시에 처음 생성된 같은 세션 ID 소유권 경합은 별도 버그로 다룬다.

## 5. 재실행·학습 안내

frontend에서 `npm test -- tracking.test.ts`, 전체는 `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`를 실행한다. 읽는 순서는 tracking.ts의 savedSession → recommendationSessionId → recordRecommendationEvents → lifecycle, 이어서 queryKeys.ts와 HomePage다. 테스트에서 auth.userId를 101에서 202로 바꾸는 부분이 같은 탭의 계정 전환을 나타낸다. 테스트 토큰은 실제 비밀값이 아닌 상수 대역이다.

성능 개선 목적이 아니라 계정별 정합성 수정이므로 속도 향상 수치를 주장하지 않는다. 추천 endpoint·DB 스키마·배포 서버·DevelopV1은 변경하지 않으며 DevelopV2에 독립 MR로 전달한다.
