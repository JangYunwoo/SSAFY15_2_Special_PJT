# 판매자명 검색 누락 수정 — S15P21B205-237

## 사용자가 겪는 문제

2026-09-23 배포본 0d05049에서 공동구매 5번 락앤락 텀블러의 판매자는 키친앤라이프였다. 그러나 상품명·판매자 검색 입력창에 키친앤라이프를 검색하면 해당 상품이 빠졌다. 검색 결과 14건이 보인다고 판매자 검색이 정상인 것은 아니었다. 상품명 n-gram 부분 일치로 다른 상품이 반환되었기 때문이다.

## 원인을 찾은 기준

프런트 안내와 공개 API의 실제 WHERE 절을 비교했다. GroupBuyQueryRepository는 응답의 sellerName에 business_name을 채우지만 검색은 p.name만 사용했다. MySQL에서는 두 글자 이상에 MATCH AGAINST, 그 외 경로에서는 LIKE를 사용한다. 양쪽 모두 판매자명이 조건에서 빠져 있었다.

최신 사용자 지시에 따라 FE는 팀원이 수정 중이므로 전혀 변경하지 않았다. 기존 화면이 이미 판매자 검색을 안내하므로 백엔드 조건을 계약에 맞추는 것으로 해결할 수 있다. FE 검색창 상태 초기화나 거래 100건 제한은 별도 보류 항목이다.

## 구현과 선택 이유

기존 상품명 검색 조건을 그대로 두고, LOWER(sp.business_name)의 부분 일치를 OR로 추가했다. 두 조건 전체를 괄호로 묶어 AND로 연결된 공개 상태·삭제 제외·정지 판매자 제외·카테고리가 유지되도록 했다. 괄호 없이 OR를 붙이면 판매자명만 맞는 삭제 상품까지 노출될 수 있으므로 필수적인 경계다.

판매자 검색어는 별도 바인딩 파라미터 sellerKeyword에 넣는다. !를 escape 문자로 정하고 !, %, _를 순서대로 이스케이프한다. 실제 이름에 포함된 특수문자가 SQL 와일드카드로 해석되어 범위를 넓히지 않게 하기 위해서다. 기존 상품명 검색 의미는 이번 작업에서 바꾸지 않았다. 따라서 기존 상품명 검색 자체의 와일드카드/자연어 매칭 정책을 통일한 작업은 아니다.

목록 쿼리와 COUNT 쿼리는 같은 publicWhere와 publicParameters를 사용하므로 항목 수와 페이지 수에 동일한 조건이 적용된다. 별도 UNION이나 두 번의 검색 결과 병합을 하지 않아 상품명과 판매자명이 동시에 일치하는 행도 중복되지 않는다. SQL은 기존 읽기 전용 조회 계층의 구조를 유지했으며 엔티티 쓰기 경로를 JDBC로 옮긴 것이 아니다.

새 FULLTEXT 색인을 판매자 테이블에 추가하는 방법은 마이그레이션과 검색 의미 변경을 동반한다. 이번 누락 수정에는 필요하지 않아 제외했다. LIKE는 선행 % 때문에 일반 B-tree 색인 최적화를 보장하지 않는다. 큰 데이터셋에서의 성능 향상을 주장하지 않으며, 검색 요구와 부하가 커지면 별도로 실행 계획·부하를 측정해야 한다.

## 검증 설계와 전후 결과

기존 통합 테스트에 네 가지 조건을 추가했다. 판매자명에만 일치하는 상품의 페이지 0/1 및 총건수, 카테고리/삭제/종료 필터, 정지 판매자 제외, 대소문자·한 글자·특수문자 검색이다. 기존 상품명 검색과 정렬 테스트도 함께 실행했다.

수정 전 GroupBuyQueryIntegrationTest 11개 중 3개 실패: 판매자 전용 이름 검색, 필터 조합 검색, 특수문자 이름 검색이 기대한 결과를 주지 못했다. 정지 판매자 테스트는 수정 전에도 검색 결과가 없었으므로 그것만으로 올바른 검색을 증명하지 않았다.

수정 후 공동구매 패키지 전체 60개 중 58개 통과, 2개는 Redis 통합 환경 조건 때문에 건너뜀, 실패 0. GroupBuyQueryIntegrationTest 11개는 모두 통과했다. Redis 테스트가 실제 수행됐다고 표현하지 않는다.

H2만으로 MySQL MATCH 문법이 검증되지는 않는다. 운영 MySQL에서는 SET SESSION TRANSACTION READ ONLY와 일관된 스냅샷을 사용해 이전/수정 WHERE의 결과만 비교했다. 변경·금융 호출은 하지 않았다. 동일 공개 조건에서 키친앤라이프의 검색 결과는 14건→20건, 5번 상품 포함 여부는 0→1이었다. 이는 검색 완전성 수치이며 지연시간·처리량 개선 수치가 아니다.

원본 실패 XML은 output/bug-audit-20260923/search-237-before.xml, MySQL 조회문은 search-237-mysql-readonly.sql에 별도로 보존했다. 재실행은 Java 21에서 backend/gradlew.bat test --tests "com.gongguhan.domain.groupbuy.*" --console=plain으로 가능하다.

## 검토 및 남은 범위

운영 데이터, API 요청/응답 형식, 정렬 순서, FE, 판매 정지 정책은 변경하지 않았다. 사용자 입력은 바인딩하므로 SQL 문자열에 직접 삽입하지 않는다. 판매자 결과를 포함하는 OR가 공개 범위를 넓히지 않는지, 목록과 COUNT가 같은 조건인지 검토했다. 전체 백엔드 회귀와 실제 배포 여부는 MR/배포 기록과 구분해서 확인한다.
