# B02·B03 결제 슬롯 수명과 수단 전환 학습 기록

이슈: S15P21B205-187. 기준: DevelopV2 aa19698. DevelopV1 및 배포 DB는 변경하지 않는다.

## 1. 왜 고쳤는가

배포 점검에서 카드에서 카카오로 바꿀 때 이전 abort와 다음 prepare가 동시에 실행됐다. 서버는 아직 카드 슬롯을 잡은 같은 사용자를 중복 참여로 판단할 수 있었다. 카드→카카오→카드로 돌아오면 조합별로 보관한 멱등키가 과거 FAILED 결제를 다시 가리켰다. useQuery는 HTTP 성공을 데이터 성공으로 보았고 버튼은 데이터가 null이 아닌지만 보았기 때문에 종료된 결제로 승인 버튼이 켜졌다. 카드가 기본 선택이므로 사용자가 카카오를 처음 선택하기 전부터 카드 슬롯이 만들어지는 문제도 있었다.

이것은 상품 정원을 수단마다 늘려야 하는 문제가 아니다. 현재 서버는 PROCESSING payment가 자리를 점유하는 계약이다. 이번 수정은 이 계약을 유지하며 프런트가 자원 생성과 해제를 순서대로 수행하도록 한다. 수단과 독립적인 별도 reservation 도메인 도입은 DB·모든 승인 경로를 함께 바꾸는 별도 설계다.

## 2. 대안과 선택 기준

query invalidation만 추가하면 해제와 준비의 순서가 보장되지 않는다. 요청을 AbortController로 취소해도 서버가 이미 만든 결제는 취소되지 않으므로 누수 가능성이 남는다. 매번 새 키를 쓰면 응답을 잃은 재시도가 중복 생성을 유발한다. 반대로 조합별 키를 무한 보존하면 종료 거래를 재사용한다.

따라서 React와 분리한 PaymentSlotController가 단일 비동기 실행 경로를 소유한다. desired는 마지막 사용자 선택, attempt는 결과가 확인되지 않은 prepare와 그 키, held는 서버에서 생성된 슬롯이다. revision은 같은 수단으로 돌아와도 이전 생명주기와 현재 시도를 구별한다. 이 구조는 타이밍을 제어하는 Promise 테스트로 경합 순서를 직접 증명할 수 있다.

## 3. 구현을 따라 읽는 순서

1. PaymentMethodPicker와 PaymentPage는 최초 null 선택을 사용한다. 선택 전에는 카드 슬롯도 만들지 않는다. B07의 코인 자산 null·빈 문자열·공백 차단은 그대로 유지한다.
2. usePaymentSlot은 선택을 controller로 전달하고 외부 스토어를 구독한다. 화면에 보여줄 payment는 수단·공구 일치, PROCESSING, 미래 만료시각, busy 아님을 모두 만족해야 한다.
3. controller는 held가 현재 revision과 일치하면 사용한다. 선택이 달라졌으면 abort 성공을 기다리고 나서만 새 prepare를 호출한다. 해제가 실패하면 held를 보존하고 오류를 보여준다. 새 자리 확보를 강행하지 않는다.
4. prepare 중 사용자가 여러 번 전환해도 응답은 버리지 않는다. 응답으로 받은 과거 슬롯을 먼저 해제한 다음 최종 선택만 준비한다. 화면을 떠난 경우도 같은 정리를 한다.
5. 통신 실패·5xx·408·429처럼 결과가 불명확하면 attempt와 키를 보존한다. 재시도 또는 다음 선택에서 동일 요청을 먼저 확인한다. 명확한 4xx 거절 또는 종료 상태 응답은 그 시도를 끝내므로 다음 시도는 새 키다.
6. 외부 카카오 창이나 코인 입금 확인으로 소유권을 넘길 때 handoff한다. 정상 승인 후 cleanup이 방금 결제한 자리를 취소하지 않도록 한다. 코인 실패 후 돌아올 때는 수단을 다시 고르게 하여 새 준비가 가능하게 한다.
7. 코인 견적은 결제 ID·자산 ID별 query에 보관한다. 이전 선택의 늦은 견적이 새 결제에 붙지 않으며, 만료 견적은 제출하지 않는다. 견적 실패/만료 및 슬롯 실패에 명시적인 재시도를 제공한다.
8. 승인 중 수단 선택을 잠그고 같은 렌더 사이 중복 클릭도 ref로 차단한다. 카드·카카오 승인 준비 재시도 키는 payment별로 유지한다. 서버의 중복 승인 방어를 대체하는 것은 아니다.

## 4. 검토 중 발견한 추가 경계

완료 snapshot을 구독자에게 통지한 직후, 실행 Promise의 finally 이전에 구독자가 선택을 변경할 수 있다. running=true라는 이유로 start가 건너뛰어지면 busy가 영원히 남는다. finally에서 남은 busy를 다시 실행하도록 고쳤고 구독 콜백에서 수단을 바꾸는 테스트를 추가했다. StrictMode의 setup→cleanup→setup도 이전 revision의 늦은 슬롯을 정리하는지 검증한다.

## 5. 검증 설계와 결과

기존 112개에 controller 경합 16개를 추가했다. 기존 B07 10개는 useQuery 내부 옵션에 결합된 테스트여서 새 구현에서 9개가 실패했다. 기능 요구사항을 삭제하지 않고 훅→controller 선택 연결 계약으로 옮겼다. 자산 미선택·공백·배송지 없음·수단 없음·자산 변경을 계속 검증한다.

전체 프런트 128개 통과. TypeScript 검사, ESLint, production build, git diff --check를 수행한다. controller 테스트는 해제 지연/실패, 준비 응답 유실, 늦은 응답, StrictMode, 종료 응답, 만료 응답, 새 키/동일 키, handoff를 독립적으로 다룬다. 가짜 시각과 제어 가능한 Promise를 사용하므로 실제 결제나 송금은 발생하지 않는다.

이 작업은 정합성 수정이며 성능 최적화가 아니다. 테스트 실행 시간을 사용자 응답속도 개선 지표로 표현하지 않는다. 새 브라우저 승인·실제 금융 API·체인 송금 E2E는 이 MR에서 수행하지 않았다. 기존 영상은 수정 전 증거로 보존하며 새 결과로 덮어쓰지 않는다.

## 6. 한계와 후속 확인

전체 새로고침·탭 강제 종료에서는 브라우저가 네트워크 정리를 완료할 수 없다. 서버 슬롯 TTL과 승인/만료 경합 방어는 여전히 필수다. 다중 탭의 같은 사용자 충돌도 서버가 최종 방어해야 한다. 승인 결과가 불명확한 거래는 무조건 새 결제를 만들지 말고 결제 내역을 확인해야 한다. 배포 후에는 카카오 휴대전화 인증, 코인 지갑 서명이 필요한 실제 승인 시나리오를 별도로 확인해야 한다.

재실행: frontend에서 npm test, npm run typecheck, npm run lint, npm run build. 학습 시 controller의 select→reconcile→publish를 먼저 읽고 테스트의 deferred 응답 순서를 따라간 뒤 React 훅과 PaymentPage를 읽으면 된다.
