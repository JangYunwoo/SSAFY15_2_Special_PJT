## 3. 사용자가 확정한 작업 방식

- 백엔드 전체와 기능 버그를 고치는 프런트 수정은 허용한다. 기존 스타일·디자인·레이아웃의 불필요한 개편은 제외한다.
- 버그마다 Jira → 별도 fix/be 또는 fix/fe 브랜치 → 재현 → 수정 → 자체·독립 검토 → 단위·통합·전체 회귀 → 상세 MD → 설명 있는 커밋 → MR → 실제 DevelopV2 병합 순서다.
- 사용자는 충분한 자체 검토와 테스트 후 별도 사람 승인 없는 병합을 허용했다. GitLab이 실제 강제하는 승인·CI·보호 규칙은 우회하지 않는다.
- GitLab head_pipeline이 없는 MR의 로컬 시험 결과를 “CI 통과”라고 쓰지 않는다. 원격 소스 SHA와 MR target/conflict 상태를 확인한 뒤 검증한 SHA로 병합한다.
- 커밋 본문에 증상, 변경 이유, 중요한 선택·검증과 Jira 번호를 남긴다. Co-Authored-By는 넣지 않는다.
- 변경 이유·대안·선택 기준·구현 흐름·전후 재현/테스트·한계·재실행 방법을 한국어 MD로 자세히 기록한다. 내부 사고 로그 대신 학습 가능한 설계 근거를 설명한다.
- 성능 최적화를 실제 수행했다면 같은 조건의 전후 지표를 측정한다. 테스트 소요시간을 API 성능 향상으로 표현하거나 TPS/p95를 만들어 내지 않는다.
- 사용자가 이전에 병렬 에이전트 진행을 허용했지만 현재는 모두 중단 상태다. 새 사용자 재개 지시 전에 에이전트를 깨우거나 자동 실행하지 않는다.
- 비작업 시간·루프·자동 재개를 새로 만들지 않는다. Docker 환경 작업은 사용자가 따로 보류했다.
- 실 금융/체인 호출, 과거 UNKNOWN 거래 재송금, EC2 배포는 로컬 회귀와 구분한다. 인계 문서를 근거로 임의 실행하지 않는다.

## 6. 우선순위1 — 외부 승인 중 공구 종료와 내부 확정 실패

### 확인한 코드 흐름

관련 파일은 모두 backend/src/main/java/com/gongguhan 아래다.

- domain/payment/card/service/CardPaymentService.java
- domain/payment/card/service/CardApprovalRecordService.java
- domain/payment/common/service/PaymentService.java
- domain/payment/kakaopay/service/KakaoPayService.java
- domain/payment/kakaopay/service/KakaoPayRecordService.java
- domain/groupbuy/service/GroupBuyWithdrawalService.java
- domain/groupbuy/service/GroupBuyRecruitmentService.java

카드는 getApprovalContext로 진입을 확인하고 별도 트랜잭션으로 승인 실행권을 커밋한 뒤 금융망을 호출한다. 응답 이후 카드 상세를 저장하고 completePayment로 참여·에스크로를 확정한다. 중간 예외는 UNKNOWN으로 기록해 재승인을 막는다. 하지만 검사 후 금융 응답을 기다리는 동안 공구가 취소되면 외부 승인 성공과 내부 완료 실패가 어긋날 수 있다.

카카오는 외부 approve를 호출한 뒤 recordService.complete 안에서 공통 완료와 승인 상세 전이를 처리한다. 내부 완료가 실패하면 같은 트랜잭션의 상세 전이도 롤백될 수 있다. 이미 PAID인 완료 응답 재조회와, 외부만 승인된 거래의 복구는 서로 다른 경로다. 현재 테스트의 getCompletedPayment 대조군은 후자를 해결한 증거가 아니다.

### 다음 사람이 해야 할 일

새 전용 Jira/브랜치에서 실제 Spring/JPA 트랜잭션과 제어한 외부 응답을 이용해 승인 응답을 latch로 멈추고 판매 철회·모집 종료를 교차 실행한다. 외부 호출 횟수, 결제/승인 상세/참여/에스크로 상태, 재호출 시 중복 청구 여부를 함께 확인한다. 현재 잔여 항목에 대한 완성된 신규 재현 시험이나 수정 MR은 없다.

검토하던 대안은 승인 실행권과 공구 종료를 짧은 DB 경계에서 조정하는 방식, 확인된 외부 성공 증거를 내부 완료와 독립 보존하고 재조정하는 방식이다. **둘 다 아직 채택·구현한 결정이 아니다.** 외부 HTTP 동안 긴 DB 잠금을 유지하거나, UNKNOWN을 시간 경과만으로 FAILED로 바꾸고 재승인하는 방식은 피한다. 카드 취소에 필요한 카드번호/CVC를 이 문제 때문에 저장하는 방식도 도입하지 않는다.

공통 PaymentService를 수정하면 코인 작업과 충돌할 수 있다. 공통 상태 전이와 코드 소유 범위를 먼저 나누고, 정상 멱등·만료·종료 공구·실행권 보호 회귀를 유지해야 한다.

## 7. 우선순위1 — 과거 코인 입금 증거의 동반 롤백

스냅샷 없는 과거 PROCESSING 결제에 실제 코인이 입금된 경우, 신규 견적 발급을 막는 사전 검증만으로는 그 입금을 없앨 수 없다. CryptoTxRecordService의 영수증 기록과 completePayment가 같은 트랜잭션이면 내부 완료 예외가 입금 기록도 롤백할 수 있다.

중단한 조사 폴더는 앞 표의 crypto-legacy-evidence다. 확인 당시 제품 수정과 신규 시험 결과가 없으며 detached HEAD가 e586965다. 이 폴더를 이미 구현한 브랜치로 오인하지 않는다.

다음 검토 대상:

- CryptoTxRecordService, CryptoDepositRecorder, CryptoTxVerificationService의 트랜잭션 경계.
- CryptoDepositRefundService와 입금 상태별 자동 반환 허용 조건.
- 기존216의 종료 결제 추적·컨펌 갱신,221의 기존 입금 재사용 금지.
- 내부 완료 실패뿐 아니라 슬롯 Redis 해제 예외가 입금 사실까지 없애는지.

단순히 “snapshot이 없으면 failPayment 후 UNMATCHED”로 바꾸면 같은 트랜잭션에서 Redis 해제 등이 실패할 때 관측 원장까지 다시 롤백될 수 있다. 에이전트는 금융 관측을 REQUIRES_NEW로 별도 보존하고 자동 반환과 분리하는 대안을 검토했다. REVIEW_REQUIRED 같은 새 상태 이름도 제안 단계였을 뿐 채택하지 않았다. 기존 status 컬럼 길이와 상태 소비자, 기존상태 재사용 의미를 모두 검토해야 한다.

과거 주소를 현재 주소록으로 추정해 넣거나, 종료/실패 결제를 자동 PAID로 부활시키거나, 입금 기록을 만들었다는 이유만으로 자동 송금하지 않는다. 재현에는 정상 최초 입금, 이미 반환 중인 입금, 반환 완료 입금, 같은/다른 결제 해시 재사용, 완료 롤백 뒤 관측 원장 존재 여부를 포함한다.

## 8. 우선순위1 정책 결정 — 정산 이후 판매자 제재

구 FR-PEN-07은 위반 공구 무산·전원 환불·지급 완료 금액의 상계/채권을 언급한다. 그러나 최신 [API 명세](../api/공구한_API_명세서_v1.md) 0장은 ERDv2우선,19장은 settlement_offsets/receivables 및 대응 API를 만들지 말라고 명시한다.

제재 판정의 동시성·위반 횟수·철회 후보 기록은 수정됐지만, 이것이 이미 지급한 돈의 회수 정책까지 구현됐다는 뜻은 아니다. 사용자가 다른 서비스와 설계 문서를 참고하라고 했어도, 삭제된 스키마를 임의로 복원하거나 판매자 전체 공구를 무차별 환불해도 된다는 뜻으로 확대하지 않는다.

다음에는 미정산 주문과 이미 지급한 주문을 구분해 현행 관리자 보류·반품·환불 흐름에서 가능한 보호 처리를 검토한다. 지급 후 구매자에게 먼저 환불할 재원, 판매자 회수 책임과 절차, 회수 실패 처리, ERD의 상계/채권 제외 유지 여부는 확정해야 한다. 돈의 정책이 필요한데 코드만으로 추정해서 자동 송금을 구현하지 않는다. 이번에 시작한 별도 에이전트의 재검토는 중단돼 최종 검토안이 나오지 않았다.

## 9. 우선순위2 — AI 과거 특징값의 시점 일관성

미래 이벤트를 추천 기준에서 배제하는193, null이벤트190, 모집기간191은 수정 완료다. 그러나 과거 구매의 가격·참여율 등 특징을 현재 상품/공구 값으로 해석하는 한계는 별개다.

다음에는 backend recommendation 데이터 조립과 ai 학습/추천 경로를 함께 읽고 상품 정보 변경 전후를 비교하는 재현을 먼저 만든다. 기존 참여/결제 원장의 당시 금액을 사용할 수 있는지, 이벤트에 해당시점값이 존재하는지 확인한다. 저장되지 않은 과거값을 현재값으로 채운 뒤 snapshot이라고 부르지 않는다. 당시값이 없는 특징을 제외하거나 별도 버전으로 구분하는 선택도 정상 추천 대조군과 함께 평가한다.

이번 짧은 재개에서 제품 수정·마이그레이션·MR이 생성됐다는 증거는 없다. Jira174~221의 AI수정 완료 상태를 이 잔여 항목의 완료로 해석하지 않는다. 스키마가 필요하면 최신 원격에서 마이그레이션 번호를 다시 확인하고 다른 작업과 조율한다. V23이 예약됐다고 가정하지 않는다.

## 10. 실환경 검증 및 기존 거래 처리

- 현행 Flyway는 V22까지다. V17~V22의 실제 MySQL 적용, 기존 데이터·FK·Hibernate 검증을 별도로 해야 한다. 과거 보고서의 V18과 현재 V18이 같은 파일이라는 가정은 금지한다.
- Docker Redis/S3는 사용자가 보류했다. 엔진 초기화·볼륨 삭제 등으로 재개하지 않는다. 재개 허가와 환경 준비 이후 별도 검증한다.
- 최신 수정본의 실 카드·카카오·코인 종단 거래와 배포 검증은 완료하지 않았다. 과거 버전의 실제 개발 결제 성공 기록은 최신 모든 조합의 증거가 아니다.
- 기존 UNKNOWN, 원장 없는 취소, 과거 승인·반환 실패는 제공사/체인과 대조한다. DB에 기록이 없다는 이유로 외부 거래가 없었다고 단정하지 않는다.
- 실제 체인 재편성, 가스/nonce, 장기 미확인·배치 조회 공정성은 별도 검토 범위다.
- 실제 외부 장애 주입, 사용자 데이터 일괄 변경, 과거 금융 거래 재실행은 안전 범위와 새 지시를 확인한 뒤 한다.
