# 판매자 제재 판정과 프로필 변경의 동시성 보호

이슈: S15P21B205-215. 기준 커밋: DevelopV2 `8902037`. 실제 배포 DB나 금융기관은 호출하지 않았다. 이 문서는 재현 가능한 현상, 설계 판단 근거, 구현과 검증 범위를 설명한다.

## 1. 왜 이 문제를 따로 고쳤나

위반 후보는 자동으로 생성되지만 확정과 기각은 관리자의 판단이다. 확정된 위반 수가 정책 임계에 도달하면 판매자의 신규 상품 등록과 공동구매 생성을 제한한다. 따라서 중복 판정이나 횟수 유실은 단순 목록 표시 오류가 아니다. 정지되어야 할 계정이 판매를 계속하거나 서로 다른 관리자 판단이 기록에서 사라질 수 있다.

기존 PenaltyService에는 트랜잭션과 상태 검사가 있었다. 하지만 트랜잭션이 있다는 것만으로 동시에 읽은 값의 변경이 직렬화되지는 않는다. 두 요청이 같은 CANDIDATE를 읽으면 둘 다 확정/기각이 가능한 상태라고 판단한다. 서로 다른 후보를 확정해도 공통 판매자 penalty_count는 두 요청 모두 이전 값을 읽고 같은 증가 결과를 저장할 수 있다.

검토 중 판매자 자신의 프로필 수정도 같은 엔티티를 저장하는 것을 확인했다. Hibernate는 기본적으로 변경 감지 후 엔티티의 갱신 가능한 컬럼들을 UPDATE한다. 연락처만 수정하는 요청도 오래된 penalty_count와 status를 함께 저장할 수 있다. 제재 서비스에만 잠금을 추가하면 이 경로가 여전히 정지 상태를 덮어쓴다. 따라서 모든 관련 판매자 쓰기 경로를 함께 보호해야 한다.

## 2. 수정 전 실제 재현

새 테스트는 격리된 H2 데이터베이스, 실제 Spring 서비스 프록시, 실제 JPA 트랜잭션을 사용한다. 첫 요청이 엔티티를 변경하고 flush한 다음 커밋 전에 기다리게 한다. 별도 스레드의 두 번째 요청이 시작된 것을 확인하고 첫 커밋을 허용한다. 테스트 스레드마다 별도의 영속성 컨텍스트를 사용하므로 같은 Java 객체를 공유하는 가짜 경합이 아니다.

기준 코드에 테스트만 추가해 실행한 결과 6개가 모두 실패했다. 원본 조건과 결과는 `penalty-transition-before.json`에 남겼다.

| 순서 | 수정 전 관측 | 기대값 |
|---|---|---|
| 누적 1회에서 서로 다른 후보 2건 확정 | 판매자 횟수 2 | 원장과 프로필 모두 3, 판매 정지 |
| 누적 3회에서 서로 다른 확정 2건 취소 | 판매자 횟수 2 | 원장과 프로필 모두 1 |
| 같은 후보 확정 후 동시 기각 | 뒤 요청도 성공 | 기각 거절, 확정과 감사 로그 보존 |
| 같은 확정 건을 두 번 취소 | 뒤 요청도 성공 | 두 번째 상태 전이 거절 |
| 세 번째 확정 중 판매자 연락처 수정 | 횟수 2로 복귀 | 횟수 3과 정지 유지, 연락처도 저장 |
| 연락처 수정 중 세 번째 확정 | 연락처가 null로 복귀 | 연락처와 제재 모두 보존 |

두 번째 요청이 잠시 대기했다는 사실만으로 테스트가 통과하지 않는다. 기존 코드도 UPDATE 단계에서는 DB 잠금 때문에 기다린다. 문제는 기다리기 전에 이미 오래된 값을 읽었다는 것이다. 최종 커밋 후 JDBC로 다시 조회해 원장 수, 비정규화 횟수, 상태 및 연락처를 확인한다. 이 최종 단언이 수정 전 6개 오류를 잡았다.

## 3. 대안과 선택 기준

JVM synchronized는 서버가 여러 대이면 보호하지 못한다. 카운터만 `count = count + 1`로 원자 갱신하는 방법은 상태 판정 및 다른 프로필 쓰기가 별도로 남고, JPA 관리 객체와 직접 갱신 값의 동기화도 필요하다. 버전 컬럼을 이용한 낙관적 잠금도 가능하지만 충돌 응답과 관리자 재시도 계약, 마이그레이션이 추가된다.

이번에는 기존 프로젝트의 JPA 비관적 쓰기 잠금 방식을 적용했다. 제재는 대량·고빈도 쓰기가 아니라 관리자가 개별 판단하는 경로이며, 같은 판매자에 대한 짧은 DB 작업을 직렬화하는 비용을 감수할 수 있다. 외부 API 호출을 잠금 안에 추가하지 않는다. 정상 조회 API는 일반 읽기를 그대로 유지한다.

## 4. 잠금 순서와 구현

SellerPenaltyRepository.findForUpdate는 판정할 위반 행을 잠근다. confirm/dismiss/revoke는 상태를 판단하기 전 반드시 이 메서드를 사용한다. 따라서 같은 후보를 두 관리자가 열었어도 나중 요청은 먼저 커밋된 상태를 보고 원래의 INVALID_STATE_TRANSITION으로 거절된다.

confirm과 revoke는 이어서 SellerProfileRepository.findForUpdate로 판매자 행을 잠근다. 서로 다른 위반 행을 처리해도 같은 판매자를 대상으로 하면 누적 횟수 갱신을 순서대로 수행한다. 기각은 판매자 횟수를 변경하지 않으므로 위반 행만 잠근다. 프로필 updateProfile도 판매자 잠금을 사용하지만 위반 행은 요청하지 않는다. 이 변경 범위에서 잠금 순서는 위반 → 판매자이며 반대 순서의 추가 잠금을 만들지 않는다.

정책값 읽기와 confirmedCount 집계는 두 잠금 이후로 배치했다. MySQL REPEATABLE READ에서 잠금을 기다리기 전에 일반 조회로 오래된 읽기 뷰를 만들지 않기 위해서다. 현재 컨트롤러에서 서비스로 진입하는 쓰기 경로를 기준으로 하며, 상위 트랜잭션이 먼저 관리 객체나 읽기 뷰를 만든 뒤 이 서비스를 호출하도록 확장한다면 별도 재검토가 필요하다. H2 테스트만으로 MySQL 격리 수준의 모든 특성을 증명했다고 주장하지 않는다.

상태 변경, 판매자 카운터, 감사 로그는 기존과 같이 하나의 트랜잭션이다. 새 스키마나 native UPDATE SQL은 없다. JPQL 조회에 PESSIMISTIC_WRITE를 붙인 것이며 DB가 해당 잠금을 구현하는 SQL을 생성한다. 테스트 fixture와 최종 검증의 JDBC는 서비스 구현을 SQL 방식으로 바꾼 것이 아니다.

## 5. 유지한 정책과 이번에 하지 않은 일

누적 임계값과 해제 규칙은 변경하지 않았다. 판매 정지는 기존 거래의 배송·반품·정산을 중단하는 명령이 아니다. 과거에 이미 틀어진 카운터를 임의로 다시 계산하거나 배포 데이터를 수정하지 않았다. 이런 데이터는 원장과 감사 로그를 대조하는 복구 절차가 필요하다.

구 요구사항 PDF의 FR-PEN-07에는 위반 확정 후 공구 무산·전원 환불과 지급액 상계/채권이 있다. 그러나 최신 API 명세 0장은 최신 ERD v2를 우선하고, 19장은 settlement_offsets와 receivables 및 대응 API를 만들지 않는다고 명시한다. 따라서 이 동시성 수정에서 제거된 상계·채권 구조를 부활시키거나 이미 지급한 돈을 자동으로 다시 보내지 않았다. 해당 공구의 진행 상태별 환불/정산 처리 공백은 별도의 설계 결정 사항이며 이 MR로 완성됐다고 표현하지 않는다.

## 6. 성능과 검증 한계

이 작업은 정합성 수정이지 성능 최적화가 아니다. 조회 개수는 확정/취소에서 위반 1건·판매자 1건으로 동일하지만 잠금 의미가 추가된다. 기각은 위반 1건, 프로필 수정은 판매자 1건만 잠근다. 같은 판매자에 대한 요청은 기다릴 수 있으므로 더 빠르다고 주장하지 않는다. 외부 호출 수 증가는 0이며 별도의 지연시간/처리량 벤치마크는 수행하지 않았다.

기존 단위 테스트는 findById 스텁을 findForUpdate로 바꾸되 상태 전이·감사 로그·알림 단언은 유지했다. 새 통합 테스트 6개는 실제 동시 트랜잭션의 최종 상태를 검증한다. Docker 보류로 실제 MySQL 컨테이너 경합 검증은 하지 않았다. Redis/S3 환경 조건으로 제외되는 전체 회귀 항목을 통과로 계산하지 않는다.

재실행: backend에서 Java 21을 지정한 뒤 `./gradlew.bat test --tests '*Penalty*Test' --console=plain`, 이어서 `./gradlew.bat test --console=plain`을 실행한다. 학습 순서는 수정 전 실패표 → SellerPenalty의 상태 전이 → 서비스 잠금 순서 → 프로필 쓰기 경로 → 실제 두 트랜잭션 테스트 → 감사 로그 원자성 순서다.

## 7. 실행 결과

수정 전 신규 경합 테스트 6개 모두 실패했다. 수정 후 전체 백엔드 회귀에서 120개 스위트, 총 780개 중 777개 통과, 실패·오류 0, Redis 2개/S3 1개 환경 제외를 확인했다. 같은 신규 6개 모두 통과했다. 전체 실행시간 3분 21초는 개발 환경의 검증 소요시간이며 서비스 처리 성능 지표가 아니다. `git diff --check`도 통과했다. 이후 다른 MR과 합친 DevelopV2의 종합 회귀는 이 단일 브랜치 결과와 구분해 기록한다.
