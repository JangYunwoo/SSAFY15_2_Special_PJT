# C06 판매 철회 위반 후보의 필수 연결 복구

이슈: S15P21B205-214. DevelopV2 전용 수정이며 실 금융 호출, 배포 DB 변경, 자동 제재 확정은 하지 않는다.

## 먼저 확인한 설계의 우선순위

`docs/api/공구한_API_명세서_v1.md` 0장은 문서가 충돌하면 최신 ERD v2 정책·구조를 우선한다고 명시한다. GRP-10 설명은 참여자가 있는 판매 철회에 사유를 받아 공동구매 취소·전원 환불 개시·판매자 위반 후보 생성을 한 흐름으로 수행하라고 요구한다. 요구사항 PDF 13쪽 FR-PEN-02에도 일방적 판매 철회가 위반 사유이며 FR-PEN-06은 관리자가 후보를 확정 또는 기각하도록 한다. 따라서 철회 후보 생성은 선택 기능이 아니다.

반면 API 14장은 정산 등 거래 알림을 '제공할 수 있다'고 설명한다. SettlementCompletedEvent 소비자가 없다는 사실만으로 정산 알림을 필수 버그라고 정하지 않았다. ReturnNeglectEvent 역시 존재하지만 PDF 11~12쪽 반품 요구사항과 13~14쪽 제재 요구사항에서 수거 방치 그 자체를 자동 위반 후보로 만드는 명시 의무는 확인하지 못했다. 반품 거부에 대한 구매자 이의 접수는 별도의 필수 의무다. 이벤트 이름만 보고 새 제재 정책을 만들지 않으며 두 선택 사항은 이번 MR에 구현하지 않는다.

구 요구사항 FR-PEN-07은 위반 확정 시 해당 공구의 무산·전원 환불, 지급 완료분 상계·회수 채권을 기술한다. 그러나 최신 API 0장 및 19장은 상계·채권 테이블을 제거했고 `settlement_offsets`, `receivables`와 대응 API를 만들지 말라고 한다. 이 충돌은 최신 ERD 우선 규칙에 따라 다뤄야 하므로 이번 후보 연결을 핑계로 상계·채권을 부활시키지 않는다. 배송·정산까지 진행된 공구의 위반 확정 후 처리 경계는 별도의 정책/설계 검토 항목이며, 판매자 전체 진행 공구를 일괄 환불하는 동작도 추가하지 않는다.

## 기존 코드가 놓치던 지점

`GroupBuyWithdrawalService.withdraw`는 prepareWithdrawal에서 공구 취소 및 참여 REFUNDING 전이를 커밋하고, 외부 환불을 순서대로 호출한 뒤 마지막에 GroupBuyWithdrawnEvent를 발행했다. 첫째, 이 이벤트를 소비하는 penalty 리스너가 없었다. 둘째, 소비자만 추가해도 앞선 환불 호출이 예외를 던지거나 프로세스가 중단되면 이벤트에 도달하지 못한다. 취소가 확정되었는데 필수 위반 후보만 빠지는 구조다.

필수 내부 기록을 외부 서비스 성공 여부에 의존시키면 안 된다. 위반 후보는 '판매자가 철회했다'는 사건의 증거이고 '환불이 모두 성공했다'는 증거가 아니다. 따라서 금전 반환의 결과와 후보 등록을 구분해야 한다.

## 구현 및 대안 선택

prepareWithdrawal이 사유도 인자로 받고 공구를 먼저 비관적 쓰기 잠금으로 읽는다. 같은 공구의 동시 철회가 두 번 준비되지 않도록 한 번에 처리하며 소유권 검사는 그대로 수행한다. 취소·참여 전이와 환불 대상 수집이 끝난 뒤 **같은 트랜잭션 안에서** 이벤트를 발행한다. 외부 환불 반복은 여전히 트랜잭션 바깥이다.

새 `WithdrawalPenaltyListener`는 일반 동기 EventListener와 MANDATORY 트랜잭션을 사용한다. 이벤트 발행자의 트랜잭션에 반드시 참여하며, 후보 저장 실패 시 철회 준비도 롤백된다. AFTER_COMMIT 비동기 저장은 취소만 커밋하고 후보가 누락되는 간격을 남기므로 필수 원장에는 선택하지 않았다. 도메인 경계를 없애고 groupbuy 서비스가 penalty 테이블을 직접 조작하는 방식 대신 기존 이벤트 경계를 실제 소비자로 연결했다.

리스너는 동일 공구를 잠근 뒤 취소 상태와 판매자 일치를 검증한다. 같은 공구·WITHDRAWAL 사유의 기존 기록이 있으면 상태와 관계없이 새 기록을 만들지 않는다. 후보가 이미 확정·기각된 경우도 단순 재발행으로 다시 후보를 쌓아서는 안 된다. 현재 이벤트의 refundedParticipants 필드명은 기존 계약을 유지하지만 발행 시점에서 이 값은 환불 **대상 수**이지 반환 완료 증명이 아니다. 후보 메시지에는 환불 완료라고 쓰지 않는다.

위반 사유는 WITHDRAWAL, 상태는 CANDIDATE로만 저장한다. 판매 정지나 누적 횟수 변경은 관리자의 별도 확정 기능 책임이다. 원래 철회 사유를 후보 detail에 넣되 컬럼의 500자 한계를 넘지 않도록 제한한다. 사건 시각은 주입된 Clock의 instant를 UTC로 변환하여 호스트 시간대 의존을 피한다.

## 검증 설계

단위 테스트는 후보 상태·사유·시각·내용, 기존 기록의 재생 방지, 취소 전 이벤트 거부, 다른 판매자 이벤트 거부를 확인한다. 실제 트랜잭션 통합 테스트는 별도 H2 DB에서 Spring 서비스를 호출한다. 외부 환불 서비스만 mock으로 바꾸므로 실 자금이나 배포 서버에는 요청하지 않는다.

검증 시나리오는 다음과 같다.

1. 철회 준비가 커밋되면 공구 CANCELED와 위반 CANDIDATE가 함께 남고 금융 호출은 없다.
2. 외부 환불 호출이 예외를 던져도 이미 확정된 철회의 후보는 1건 남는다.
3. 준비 트랜잭션이 롤백되면 공구는 RECRUITING, 참여는 PAID로 유지되고 후보도 없다.
4. 같은 이벤트를 다시 발행해도 후보는 1건이며 긴 사유는 DB 길이 제한 안에 저장된다.
5. 두 철회 요청을 서로 다른 스레드로 실행하고 첫 트랜잭션의 커밋을 지연하면 두 번째는 기다린 뒤 거절되며 후보는 1건만 남는다.

이 테스트는 이벤트 객체의 생성 여부만 검증하지 않는다. 실제 DB를 새로 읽어 취소 상태와 후보 기록의 동시 커밋/롤백을 확인하므로 리스너 연결이 빠지거나 트랜잭션 경계가 바뀌면 실패한다. 원래 코드에는 소비자가 없어 후보 수가 0이므로 후보 1건 기대 조건을 만족하지 못한다. 실제 환불 처리의 전원 재시도 보장이나 금융 결과 대조를 이 테스트의 통과로 주장하지 않는다.

## 비용과 한계

전체 백엔드 회귀는 Java 21/H2 테스트 프로필에서 119개 스위트, 766개 중 763개 통과, 3개 스킵, 실패·오류 0개였다. 스킵은 실제 Redis/S3 환경 조건을 충족하지 못한 기존 테스트이며 통과로 계산하지 않는다. 전체 실행은 3분 18초였고 병렬 테스트와 자원을 공유한 검사 시간이다. 후보 생성 후 판매자 누적 0/ACTIVE 유지 단언과 정상 판매자 프로필 fixture를 추가한 뒤 관련 9개를 별도로 재실행하여 모두 통과했다(53초). 제품 코드는 전체 회귀 이후 변경하지 않았다. `git diff --check`도 통과했다.

정합성 수정이며 성능 최적화는 아니다. 철회 준비에 후보 존재 조회와 후보 INSERT 및 동일 공구 잠금 확인이 추가된다. 외부 금융 호출 수는 늘리지 않고 잠금 보유 중 외부 호출도 추가하지 않는다. 같은 공구의 동시 철회는 대기하도록 바뀌므로 응답속도가 빨라진다고 주장하지 않는다. 실제 MySQL 격리 수준/대기 시간 측정은 Docker 보류로 수행하지 못했다.

기존에 취소됐지만 후보가 없는 배포 데이터는 자동으로 소급 채우지 않는다. 어떤 경로로 취소되었는지와 당시 사유를 확인한 뒤 별도 복구해야 하며, 이번 변경은 신규 철회 경로를 바로잡는다. 후보 기록은 전원 환불 성공을 뜻하지 않으며 중간 환불 실패의 재처리 상태는 환불 원장과 별도로 대조해야 한다.

학습 순서: API 0장/GRP-10/19장 → withdraw와 prepareWithdrawal의 경계 → 동기 이벤트와 MANDATORY 의미 → 후보와 확정의 차이 → 통합 테스트의 커밋/롤백·경합 순서다. 재실행은 backend에서 `./gradlew.bat test --tests '*WithdrawalPenalty*Test'`, 이후 `./gradlew.bat test`로 진행한다.
