# B01: 카카오 취소·실패 콜백을 결제 상태 검증에 연결하기

## 1. 기준과 한 가지 문제의 범위

Jira는 [S15P21B205-175](https://ssafy.atlassian.net/browse/S15P21B205-175), 기준 브랜치는 B07 MR !139가 병합된 DevelopV2다. 수정 브랜치는 `fix/be/S15P21B205-175-kakao-callback-state`다. 백엔드와 프런트를 함께 수정하지만 해결하는 문제는 취소·실패 콜백의 state 검증 누락 한 건이다.

다른 폴더의 미완료 금융 경합·환불·슬롯 전환 변경은 포함하지 않았다. 프런트는 요청 인수만 바꾸므로 스타일과 레이아웃은 그대로다. DevelopV1과 배포 서버를 변경하지 않는다.

## 2. 왜 문제가 되는가

카카오 Ready를 요청할 때 서버는 결제 ID, 로그인 사용자 ID, 만료 시각, 임의 nonce를 서명하여 state를 만든다. 승인·취소·실패 복귀 URL에 이 값을 넣는다. 하지만 기존 코드에서 실제 검증은 승인 경로에만 있었다.

취소·실패 페이지는 URL에 state가 비어 있지 않은지만 확인한 뒤, paymentId만으로 POST를 호출했다. 서버의 두 컨트롤러는 본문 자체를 받지 않고 PaymentService.abortPayment로 넘어갔다. 따라서 임의의 문자열을 state로 넣어도 서버는 서명을 검사할 기회가 없었다. 기존 본인 결제 접근 검증이 있더라도, 해당 복귀가 서버가 준비한 결제 시도에서 유래했는지는 검증되지 않았다.

state는 결제가 승인되었다는 증거가 아니다. 서버가 발급한 복귀 문맥에 연결된 값이다. 실제 승인 금액·TID 검증은 기존 승인 경로의 별도 책임으로 유지한다.

## 3. 선택한 계약

기존 URL과 POST 방식을 유지하되 두 경로 모두 JSON 본문 `{ "state": "서버가 발급한 값" }`을 필수로 받는다.

- `KakaoPayFlowRequest`: 비어 있지 않은 최대 512자 state. 기존 생성 토큰을 수용하면서 무제한 입력을 받지 않는다.
- `KakaoPayController`: DTO의 기본 검증을 거친 뒤 서비스에 전달한다.
- `KakaoPayService.verifyCallback`: 기존 HMAC 검증기를 사용하고 사용자·결제 번호를 실제 요청과 비교한다.
- `KakaoPayRecordService.endCallback`: 저장된 Ready를 잠근 뒤 nonce, 사용 여부, 저장된 만료와 서명된 만료를 확인하고 결제를 종료한다.
- `KakaoPayPayment.consumeCallbackState`: 정상 종료된 복귀 값이 승인이나 다른 종료 콜백에 재사용되지 않도록 소비 시각을 남긴다. 결제 종료가 실패하면 같은 DB 트랜잭션의 소비 기록도 커밋되지 않는다.
- 프런트 `payment/api.ts`, `KakaoPayCallbackPage.tsx`: 이미 읽고 있던 state를 요청 본문으로 끝까지 전달한다. 검증 실패 시 다른 abort 경로를 자동 호출하는 우회는 추가하지 않았다.

정상 취소는 KAKAOPAY_USER_CANCELLED, 실패 복귀는 KAKAOPAY_AUTH_FAILED라는 기존 종료 사유를 유지한다.

## 4. 대안과 선택 기준

프런트에서 state 문자열의 존재만 확인하는 대안은 서명 검증이 아니다. 공격자가 직접 API를 호출하면 프런트 검사는 적용되지 않는다.

서버에서 서명만 확인하는 대안도 충분하지 않다. 동일 결제의 과거 Ready에서 발급된 state일 수 있으므로 현재 저장된 nonce와 연결해야 한다. 이미 소비된 값도 거부해야 한다.

서명·nonce를 읽기만 한 뒤 별도 트랜잭션에서 해제하면 검증과 변경 사이에 준비 정보가 바뀔 수 있다. 따라서 Ready 행 잠금 → 상태 검증 → 기존 결제 종료 → state 소비를 같은 짧은 트랜잭션으로 묶었다. 이 기준 코드의 승인 완료 경로와 같은 상세 행 → 결제 행 잠금 순서를 사용하여 반대 순서의 잠금을 새로 도입하지 않았다.

브라우저 복귀 URL의 GET 이동을 POST로 바꾸는 대안은 외부 결제사의 리다이렉트 계약을 해결하지 못한다. GET 페이지 이동은 유지하고, 그 페이지에서 실행하는 상태 변경 POST를 검증한다.

## 5. 요청 본문 오류 처리까지 바꾼 이유

본문을 새로 필수화하면 누락된 JSON과 문법 오류가 HttpMessageNotReadableException으로 발생한다. 기존 공통 예외 처리에서는 일반 Exception으로 분류되어 500과 예외 로그로 처리될 수 있다.

GlobalExceptionHandler에 이 입력 예외를 400 VALIDATION_ERROR로 처리하는 경로를 추가했다. 원래 예외 메시지나 요청 본문을 응답·로그에 복사하지 않는다. state와 같은 값이 포함될 수 있기 때문이다. 이 변경은 다른 JSON API에도 적용되므로 전용 테스트뿐 아니라 백엔드 전체 회귀 테스트를 수행한다.

## 6. 테스트 기획과 수정 전 증거

단순히 ‘정상 취소가 성공한다’만 검사하면 원래 코드도 통과한다. 따라서 잘못된 입력이 결제를 변경하지 않는 경계를 먼저 검사했다.

1. `KakaoPayCallbackBoundaryTest`: 실제 MVC 바인딩·컨트롤러·서비스·HMAC 검증을 사용하고, DB/금융 경계는 mock으로 대체한다. 본문 누락, 공백, 잘못된 JSON, 서명 없는 값, 다른 사용자, 다른 결제, 만료를 두 경로 각각 검사했다. 수정 전 14개 모두 실패했으며 컨트롤러는 200을 반환했다.
2. `kakaoCallback.test.ts`: 실제 프런트 API 함수를 호출하여 state가 POST 본문에 포함되는지 확인한다. 수정 전 취소·실패 2개 모두 실패했고 API 호출에는 본문이 없었다.
3. 추가 경계 사례로 state 필드 누락, 과도한 길이, 정상 바인딩을 검사했다. 이 6개는 수정 후 보강한 사례이므로 수정 전 14개 실패 수치에 섞지 않는다.
4. `KakaoPayCallbackIntegrationTest`: 실제 서비스·JPA·H2를 사용하고 Redis와 외부 결제사를 대체한다. 정상 종료, 오래된 nonce, 저장된 만료, Ready 부재, 중복 콜백을 검사한다. 각 테스트는 롤백하여 테스트 데이터가 남지 않는다.

통합 테스트에서 잘못된 nonce와 저장된 만료는 payment=PROCESSING, reserved_slots=1, state 미소비를 유지해야 한다. 정상 콜백은 payment=FAILED, reserved_slots=0, state 소비가 되어야 하며 외부 결제사 호출은 없어야 한다. 중복 콜백에서도 슬롯 게이트 해제는 한 번뿐이어야 한다.

## 7. 결과

전용 검증과 전체 회귀 결과는 아래와 같다. 백엔드는 최종 XML 90개 테스트 클래스의 집계를 사용했다.

성능 최적화가 아니라 입력 검증과 상태 정합성 수정이다. 테스트 실행 시간을 서비스 지연시간 개선으로 표현하지 않는다. 실서비스 TPS, p95 또는 네트워크 응답시간을 측정한 결과는 없다.

제외된 3개는 실제 Redis 환경이 필요한 GroupBuySlotGateIntegrationTest 2개와 S3ProductImageStorageIntegrationTest 1개다. 제외를 통과로 세지 않았다. 원래 미완료 변경이 있는 작업 폴더의 테스트 수와 이 독립 브랜치의 테스트 수는 서로 다르다.

## 8. 검토 결과와 남은 한계

프런트와 백엔드를 함께 배포해야 한다. 예전 프런트가 본문 없이 호출하면 이제 400으로 거절되는 것이 의도한 동작이다. 서명 값이나 키 원문을 이 문서와 테스트 데이터에 사용하지 않았고, 테스트 비밀값은 실행 전용 고정 fixture다.

승인이 이미 완료되어 state가 소비된 결제는 이 콜백으로 실패 처리하거나 환불하지 않는다. 이미 처리된 콜백을 다시 열면 검증 오류가 표시될 수 있다. 정상 종료 화면의 재방문 편의성과 보안 검증을 무조건적인 성공 응답으로 섞지 않았다.

이 수정은 외부 승인 요청을 보낸 뒤 응답을 기다리는 동안 취소와 경합하는 별도 문제, 기존 Redis 해제의 커밋 시점, 실제 결제사 승인/환불 중복 실행 방지 전체를 해결하지 않는다. 해당 금융 실행 문제들은 전용 버그/MR로 이어서 처리해야 한다. H2 검증이 배포 MySQL의 모든 경합 특성까지 증명하는 것은 아니며 실제 휴대전화 인증·배포 서버 브라우저 점검을 이번 MR에서 새로 수행하지 않았다.

## 9. 학습 및 재실행 순서

프런트 API 인수 → 컨트롤러 DTO → 서비스 서명 검증 → RecordService 잠금 및 nonce 검증 → PaymentService 종료 → state 소비 순서로 읽는다. 이후 수정 전 실패 사례를 보고 각 검사가 어느 단계에서 요청을 중단하는지 연결한다.

backend에서는 `./gradlew.bat test --tests '*KakaoPayCallback*'`, 이어서 `./gradlew.bat test`를 실행한다. frontend에서는 `npm test`, `npm run build`, `npm run lint`를 실행한다. 로컬 금융 키나 EC2 접속 권한 없이 재현 가능한 검증이다.
