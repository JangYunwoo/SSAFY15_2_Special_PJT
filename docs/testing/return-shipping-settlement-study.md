# 반품 배송비 잔액 정산과 0원 환불 학습 기록

이슈: S15P21B205-208. 대상은 DevelopV2이며 DevelopV1, EC2 DB, 실제 금융 거래는 변경하지 않았다. B12 공통 반품 환불, C04 구매확정/반품 경합, B13 영속 환불 복구, 정산 실행권 보완이 선행된 상태에서 이어지는 수정이다.

## 1. 왜 또 수정하는가

반품은 원결제 전액을 항상 되돌려주지 않는다. 구매자가 단순 변심으로 반품하면 기존 정책은 상품 분담금에서 반품배송비를 공제하고 원배송비는 돌려주지 않는다. 예를 들어 상품 10,000원, 원배송비 1,000원, 반품배송비 2,000원이면 환불은 8,000원이고 에스크로에는 3,000원이 남는다.

이전 정산 조회는 CONFIRMED이며 부분 환불 누계가 0인 참여만 선택했다. 반품 완료 참여는 REFUNDED이고 에스크로에 환불 누계가 있으므로 이 3,000원은 정상 반품이 끝나도 영구 보류됐다. 반대로 조건을 단순히 풀어 원 상품금액 10,000원을 정산하면 실제 보관금 3,000원을 초과하고 상품 수수료도 잘못 부과한다. 따라서 “남았으니 전부 상품 매출” 또는 “부분 환불이니 전부 보류” 두 극단을 피할 별도 분류가 필요했다.

또한 상품 1,000원에서 반품배송비 2,000원을 공제하면 기존 미리보기 산식은 환불액 0원이다. 그런데 공통 환불 원장은 양수만 허용했다. 화면이 제시한 반품이 정작 수거 완료 단계에서 실패하는 계약 불일치다. 0원도 정상적인 반품 종결일 수 있지만 외부 은행/PG에 0원 송금을 요청해서는 안 된다.

## 2. 참고한 타 서비스와 우리 정책의 구분

[네이버 스마트스토어 공식 도움말: 네이버페이 수수료와 쇼핑 판매 수수료](https://help.sell.smartstore.naver.com/faq/content.help?faqId=3558)는 결제 관련 수수료와 판매 수수료를 구분하며, 초기·반품·교환 배송비에 쇼핑 판매 수수료를 부과하지 않는다고 안내한다. 결제 수수료는 별도 기준이다.

이 자료가 우리 서비스의 계약을 자동으로 결정하는 것은 아니다. 사용자가 타 서비스의 방식을 참고한 정책 결정을 위임했고, 현 프로젝트에 구현된 수수료가 플랫폼 판매 수수료라는 점을 기준으로 다음을 선택했다.

- 반품 완료 후 잔액이 원배송비와 공제된 반품배송비임을 입증할 수 있으면 판매자 정산에 포함한다.
- 해당 잔액의 상품 분담금은 0원으로 분류하여 플랫폼 판매 수수료도 0원으로 계산한다.
- 프로젝트에 없는 별도 PG 수수료를 임의로 신설하거나 역산하지 않는다.
- 상품 잔액, 금액 불일치, 분쟁, 미완료 반품은 자동으로 판매자에게 넘기지 않는다.

배송비의 부가세 처리, 택배사에 직접 지급하는 방식, 정산 후 역정산 정책까지 확장한 것은 아니다. 이번 정책은 현재 프로젝트의 에스크로와 판매자 정산 경계에 한정한다.

## 3. 산식을 먼저 고정하고 데이터로 증명한다

변수는 주문 당시 스냅샷이다. 현재 상품 가격이나 현재 배송비를 다시 가져오지 않는다.

| 기호 | 의미 |
|---|---|
| P | 참여의 상품 분담금 |
| S | 참여의 원배송비 |
| R | 승인된 반품의 반품배송비 |
| T | 원결제 총액 P + S |
| F | 환불액 max(0, P - R) |
| B | 정산할 잔액 T - F = S + min(P, R) |

첫 예에서는 T=11,000, F=8,000, B=3,000이다. 둘째 예에서는 P=1,000, S=1,000, R=2,000이므로 F=0, B=2,000이다. 반품배송비가 상품대금보다 커도 이 모델은 이미 보관한 금액 이상을 청구하지 않는다. 회수 가능한 반품배송비는 상품대금 범위에서 공제되고 초과분을 자동 결제하지 않는다.

ReturnShippingSettlementRepository의 JPA 투영 쿼리는 다음 조건을 동시에 만족해야 후보를 반환한다.

1. 참여와 반품이 모두 REFUNDED이고 구매자 부담 단순변심이다.
2. 구매확정 보류가 아니며 관리자 검토 중도 아니다.
3. 배송 기준 정산 가능 시각이 존재하고 지났다.
4. 해당 반품·참여에 연결된 RETURN 환불 원장이 COMPLETED다.
5. P, S, R이 음수가 아니고 참여 총액과 에스크로 원금이 P+S다.
6. 반품 환불액이 max(0,P-R)이고 원장 환불액과 에스크로 환불 누계도 정확히 같다.
7. 에스크로는 HELD이고 잔액이 양수다.
8. 기존 정산 항목이 없으며 다른 미종결 반품도 없다.

환불 누계만으로 배송비임을 추정하지 않는 것이 핵심이다. 원장·반품 산식·에스크로가 서로 다른 숫자이면 조용히 보정하지 않고 제외한다. 후보 재조회에서 중복 증거가 나타나도 단일 후보가 아니므로 정산을 거절한다.

## 4. 구현 흐름과 책임의 위치

SettlementTargetRepository는 기존 일반 구매확정 조회와 새 배송비 후보 조회를 합친다. 일반 후보는 원 분담금/원배송비를 유지하고 반품 배송비 후보는 shareAmount=0, shippingFee=B, returnShipping=true로 만든다. 따라서 Settlement의 기존 수수료 공식 shareTotal × platformFeeRate를 바꾸지 않고도 상품 수수료가 0이 된다.

SettlementRecordService.settle은 후보의 값을 바로 지급 명세에 복사하지 않는다. 참여 행을 잠근 뒤 공구별 회차 잠금을 얻고 배송비 증거를 다시 조회한다. 재조회 결과가 처음 후보의 금액·판매자·수수료율 등과 달라졌으면 전체 회차를 롤백한다. 후보 조회 이후 이의 제기나 금액 변화가 끼어들어도 기존 후보를 강행하지 않는다.

배송비 정산은 EscrowService.releaseReturnShipping을 호출한다. 이 메서드는 반드시 이미 열린 트랜잭션 안에서 호출돼야 하며 참여가 REFUNDED이고 보류가 아니며 실제 보관잔액이 기대 금액과 같은지 다시 검사한다. 에스크로는 RELEASED로 바뀌지만 참여는 REFUNDED로 보존한다. 판매자에게 배송비를 정산했다고 구매자의 반품 이력이 SETTLED로 바뀌어 사라져서는 안 된다.

정산 항목의 참여별 유일 제약과 RELEASED 에스크로가 재정산을 막는다. 실제 판매자 계좌 송금은 이 배치가 하지 않는다. 기존 관리자 정산 실행 경로가 별도 실행권을 얻고 처리한다. 이번 시험도 지급 명세 생성과 에스크로 해제까지만 검증하며 실제 판매자 송금을 했다고 주장하지 않는다.

## 5. 0원 반품은 왜 별도 완료 메서드인가

Refund 생성자는 RETURN 사유에만 0원을 허용한다. 일반 참여 취소·모집 실패·미매칭 입금은 기존 양수 조건을 유지한다. 음수는 어떤 경우에도 허용하지 않는다.

RefundOrchestrationService는 0원 RETURN이면 외부 실행권 획득이나 계좌·지갑 조회 전에 completeWithoutTransfer를 호출한다. RefundLedgerService가 원장 행을 잠그고 PROCESSING인 0원 반품만 COMPLETED로 만든다. 이미 완료됐다면 같은 결과를 반환하므로 최초 요청과 복구 요청이 겹쳐도 외부 거래가 발생하지 않는다. 양수 환불을 이 경로로 넘기려 하면 엔티티가 거절한다.

이후 공통 반품 종결에서 반품/참여 상태를 완료하고 에스크로가 실제 HELD인지 확인한다. 누계에 0원을 더하거나 가짜 거래번호를 만들지 않는다. 0원 환불도 처리 이유와 반품 연결이 원장에 남아, “환불 작업이 없었음”과 “배송비 공제로 환불액이 0원이었음”을 구분할 수 있다.

## 6. 회차와 절상 차액을 놓치지 않는 방법

이전 규칙은 roundNo==1이면 공구의 절상 차액을 넣었다. 배송비 전용 정산을 추가하면서 이 규칙을 그대로 쓰면 상품이 하나도 없는 배송비 정산에서 차액을 지급한다. 단순히 배송비 첫 회차에서 0으로 바꾸기만 하면 다음 상품 회차는 이미 2회차여서 차액이 영구 누락된다.

현재는 상품 분담금 합계가 양수이고, 해당 공구의 기존 정산에 양수 절상 차액이 배정된 적이 없을 때만 차액을 한 번 넣는다. 배송비 전용 1회차는 0원, 최초 상품 2회차는 공구 차액, 이후 3회차는 0원이다. 이미 배정된 정산이 이체 보류/실패여도 새 회차에 다시 배정하지 않는다. 그 원래 정산이 여전히 지급 책임을 갖기 때문이다.

서로 다른 참여 두 건을 별도 배치가 동시에 처리해도 회차와 차액은 같은 공구 자원이다. 참여 잠금만으로는 이를 직렬화할 수 없어 공구 행 잠금을 추가했다. DB 유일 제약 위반을 정상 회차 할당 방식으로 사용하지 않는다.

## 7. 잠금 순서 자체를 검토한 이유

초안은 공구를 먼저 잠그고 참여를 잠갔다. 전수 검색에서 ParticipationCancelService의 기존 순서가 참여→공구임을 확인했다. 정상 업무 상태가 달라 직접 충돌 가능성이 낮다는 이유로 역순을 허용하지 않고, 정산도 참여 ID 오름차순 전체 잠금→공구 잠금 순서로 바꿨다.

여러 참여를 오름차순으로 잠그면 서로 겹치는 참여 목록을 처리하는 정산끼리 순서를 맞출 수 있다. 공구 잠금 이후에만 일반 조회와 차액/회차 집계를 시작한다. 공구 잠금을 기다리기 전에 일반 조회로 스냅샷을 만들어 이전 회차를 계속 읽는 일을 피하기 위한 순서다.

관련 경로도 읽었다. 수동/자동 구매확정은 참여를 잠근다. 반품 변경은 참여→반품 순서다. 이의 제기는 참여 잠금 뒤 공구를 일반 조회하며 공구 쓰기 잠금을 추가로 잡지 않는다. 슬롯 확정은 공구 잠금 아래 새 참여를 생성하는 경로로 기존 정산 대상 참여를 수정하지 않는다. 이 검토가 모든 미래 코드의 교착을 보장하는 것은 아니므로 새 변경에서도 잠금 순서를 유지해야 한다.

통합 시험에서 실제 Spring Data 저장소 호출 순서를 관측해 참여 잠금이 공구 잠금보다 먼저임을 확인한다. 별도로 서로 다른 참여를 동시에 정산하는 두 실제 트랜잭션을 시작하여 2·3회차가 각각 생성되고 차액 합계가 한 번분인지 확인한다. H2 검증은 실제 MySQL 격리 수준의 모든 잠금 특성을 대신하지 않으며 운영 DB 다중 인스턴스 시험은 별도다.

## 8. JPA를 쓰는데 왜 SQL이 남아 있는가

신규 배송비 증거 조회는 Spring Data JPA의 JPQL 투영으로 구현했다. 연관관계가 없는 엔티티도 다중 루트와 키 조건으로 조회할 수 있다. 따라서 “연관관계가 없어서 SQL밖에 못 쓴다”는 이전 주석은 바로잡았다.

기존 일반 정산 보고서의 SQL을 이번 MR에서 전면 교체하지 않았다. 기존 보고서 조회의 구조 변경과 돈을 배분하는 정책 변경을 동시에 묶으면 원인 추적이 어려워진다. 새 쓰기 동작은 엔티티 메서드와 JPA 트랜잭션으로 처리하며 기존 SQL은 읽기 전용이다. SQL을 사용하는 것 자체와 도메인 변경을 SQL로 우회하는 것은 구분해서 검토해야 한다.

## 9. 테스트 기획과 전후 관측

정책 변경의 성공 기준은 응답 속도가 아니라 자금 보존·중복 방지·수수료 분류다. 실제 JPA/H2 MySQL 모드의 참여, 반품, 환불, 에스크로, 정산, 정산 항목을 사용하고 은행 응답만 모킹한다.

| 시나리오 | 변경 전 코드의 판정 | 변경 후 테스트 관측 |
|---|---|---|
| 상품 10,000/원배송 1,000/반품배송 2,000 | REFUNDED/부분환불이라 정산 후보 제외 | 환불 8,000, 배송비 정산 3,000, 플랫폼 수수료 0 |
| 상품 1,000/원배송 1,000/반품배송 2,000 | 0원 환불 원장 생성 예외 | 환불 0 완료, 외부 호출 0, 배송비 정산 2,000 |
| 판매자 귀책 전액 환불 | 에스크로 전액 환불 | 전액 환불 유지, 배송비 후보 0 |
| 환불/누계 불일치·판매자 부담·검토/보류 | 부분 환불 제외 | 각각 배송비 후보 0, HELD 유지 |
| 조회 후 이의 보류 발생 | 기존 C04 재검증 원칙 | 반품 배송비도 정산 항목 0, HELD 유지 |
| 배송비 첫 회차 이후 상품 정산 | 해당 배송비 회차 자체가 없었음 | 차액 0 → 7 → 0원 |
| 일반 상품과 배송비 잔액 혼합 | 배송비 잔액 누락 | 상품 10,000+배송비 4,000, 수수료 500, 지급명세 13,500 |
| 같은 공구의 서로 다른 참여 동시 처리 | 공구별 별도 직렬화 없음 | 서로 다른 회차 2·3, 차액 합계 7원 |

변경 전 열은 이전 코드의 조건을 읽은 판정이며 같은 성능 부하 시험을 측정한 수치가 아니다. 변경 후 금액/횟수는 자동화 테스트의 실제 단언이다. 서로 다른 환경이나 테스트 총 실행시간으로 성능 개선율을 만들지 않는다. 이번 변경은 정확성 수정이며, 후보용 조회 1회와 정산 직전 후보별 검증 조회·공구 잠금 비용을 추가한다. 대량 공구에서 처리량이 개선됐다는 주장은 하지 않는다.

신규 ReturnShippingSettlementIntegrationTest는 매개변수 경우를 포함한 13건이다. RefundTest에는 0원 정상 종결과 잘못된 금액/경로 거절 2건을 추가했다. 최종 전체 회귀 결과는 아래 검증 기록에 기재한다.

## 10. 검증 기록과 적용 전 한계

최신 origin/DevelopV2 b365dda의 B13 환불 선점 및 정산 이체 실행권을 통합했다. 충돌한 공통 환불 execute에서는 원격의 실행권 선점을 보존하면서 0원 내부 종결만 그 앞에 두었다. SettlementRepository는 기존 정산 이체 잠금 조회와 신규 차액 배정 확인을 모두 유지했다.

전체 회귀 실행: backend에서 Java 21로 `./gradlew.bat test --console=plain`. 116개 테스트 클래스, 748개 중 745개 통과, 실패/오류 0개, 환경 제외 3개(Redis 2/S3 1). 신규 배송비 통합 시험 13개도 모두 통과했다. 전체 실행 4분 26초, 신규 통합 시험 클래스 실행 6.614초는 이 로컬 병렬 작업 환경의 검증 소요시간이며 서버 처리 지연이나 처리량 지표가 아니다. 테스트한 기능 소스는 b365dda 통합 후 4e6e166이며 이후 변경은 설명 주석과 본 문서뿐이다.

이 작업은 외부 은행 성공 응답을 모킹한 로컬 시험이다. 실제 SSAFY 송금/카카오 취소/체인 환불을 재실행하지 않았다. Redis와 S3는 사용자 요청대로 환경 점검을 보류한 별도 항목이다. 신규 마이그레이션은 필요하지 않으며 기존 반품·원장·에스크로 스냅샷을 사용한다. 기존에 일치하지 않는 누계를 가진 데이터는 자동 보정하거나 지급하지 않는다. 배포 전 후보를 조회하고 정책과 맞는 명세인지 확인해야 한다.
