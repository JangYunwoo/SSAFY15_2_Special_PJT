# DevelopV2 수정 통합 점검과 학습 안내

관련 이슈 S15P21B205-220. 이 문서는 개별 버그의 상세 학습 문서를 대신하지 않고, 무엇이 수정됐는지와 어떤 증거까지 확보했는지를 연결하는 최신 색인이다. 테스트 개수를 기능 완성률로 환산하지 않는다.

## 1. 이번 작업의 기준

2026-09-21 사용자 요청으로 작업을 중단했고 9월 22일 재개했다. 재개 직후 원격 DevelopV2는 `301eef91c031775d47d27f5f3fff62ffc933d9ce`였다. 원본 작업 폴더에는 기존 사용자 변경과 이전 미완료 초안이 있으므로 덮어쓰지 않았다. 독립 worktree에서 최신 원격을 통합하고 버그마다 별도 MR을 사용한다.

DevelopV1은 배포 기준이며 이번 수정의 대상이 아니다. 로컬 테스트 성공, DevelopV2 병합, 실제 EC2 배포, 과거 거래의 금전 대조와 복구는 서로 다른 완료 조건이다. 이 문서의 병합 완료가 배포 완료를 뜻하지 않는다. GitLab에 실제 파이프라인이 없는 MR은 CI 통과라고 부르지 않는다.

## 2. 왜 여러 종류의 시험을 나누는가

단위 시험은 입력·상태 조건과 외부 어댑터 호출 횟수를 빠르게 확인한다. 그러나 Java 객체에 상태를 바꾸는 것만으로 DB 트랜잭션, 잠금, 유일성 제약, rollback 후 영속 기록의 존재를 증명할 수는 없다. 따라서 결제·환불·정산·제재 경계에는 실제 Spring/JPA/H2 통합 시험을 추가했다.

동시성 시험은 두 작업을 다른 스레드와 트랜잭션에서 실행한다. 첫 작업을 외부 응답 대기 또는 커밋 전 상태에서 잠시 멈춘 뒤 두 번째 작업을 시작하고, 최종 DB 상태와 외부 호출 횟수를 함께 검사한다. 잠시 기다렸다는 사실만으로 안전하다고 판단하지 않는다. 기다리기 전에 오래된 객체를 읽었다면 커밋 순서가 정해져도 나중 UPDATE가 앞선 상태를 덮을 수 있기 때문이다.

외부 금융망, PG, 체인 RPC는 이 회귀에서 대체 응답을 사용한다. 성공·명확한 거절·응답 불명·내부 저장 실패를 제어할 수 있어 같은 오류를 반복 재현할 수 있다. 이 방식은 실 가스비, 실제 송금, 제공사 장애 분포, 체인 재편성 전체를 검증하는 시험이 아니다.

각 개별 문서의 수정 전 실패는 보존한다. 최종 코드에서 녹색이 된 결과로 이전 실패 파일을 덮어쓰지 않는다. 테스트 fixture 오류나 외부 환경 미구성 실패도 제품 결함 재현과 구분한다.

## 3. 수정 내용을 학습할 때의 순서

### 결제 준비부터 승인까지

먼저 [슬롯 수명주기](payment-slot-lifecycle-study.md)를 읽는다. 결제수단 선택 이후에 준비하고 수단 변경 시 기존 해제를 기다리는 이유, 오래된 응답의 슬롯을 정리하는 이유, 새 시도와 같은 요청 재전송의 키를 구분하는 이유를 다룬다. [멱등 요청 검증](payment-idempotency-study.md)은 서버가 소유자·공구·수단·주소·코인 자산을 비교해야 하는 이유를 설명한다. UI에서 버튼을 막아도 API 자체 검증이 필요한 별도 경계다.

다음 [공통 결제 전이](payment-transition-study.md), [카드 승인 실행권](card-approval-claim-study.md), [배송지 스냅샷](payment-shipping-snapshot-study.md)을 읽는다. DB 잠금과 외부 호출을 한 트랜잭션으로 길게 묶지 않고 짧은 실행권을 먼저 기록하는 이유, 결과 불명을 단순 실패로 보고 재승인하면 안 되는 이유, 수정 가능한 주소록 ID와 거래 당시 배송 정보가 다른 이유를 연결할 수 있다.

[모집 시각 검사](payment-recruitment-window-study.md)는 새 결제 준비 가능 기간과 이미 부여한 유효 슬롯을 구분한다. [만료 슬롯 해제](expired-slot-release-study.md)와 [종료 공구 슬롯 정리](terminal-slot-release-study.md)는 결제 종료와 공구 카운터 초기화가 서로 다른 순서로 일어나도 결제의 정리가 끝나야 한다는 점을 다룬다. [종료 공구 승인 진입 차단](payment-terminal-boundary-study.md)은 TTL이 남았다는 이유만으로 취소된 공구의 외부 결제를 시작해서는 안 된다는 별도 경계다. 이미 PAID인 결제의 완료 응답 재조회까지 차단하지는 않는다. 외부 승인 성공 후 내부 완료가 실패한 거래의 자동 복구까지 보장하는 변경은 아니다.

### 취소·반품·환불·정산

[참여 취소 원자성](B11-cancel-transaction-study.md) → [반품 환불](return-refund-lifecycle-study.md) → [모집 실패 복구](recruit-failure-refund-recovery-study.md) → [정산 실행권](settlement-transfer-claim-study.md) 순서로 읽는다. 각 요청의 성공 여부보다 중요한 것은 원장 생성, 실행권, 외부 결과, 내부 종결이 어느 단계까지 완료됐는지다.

[확정·반품·정산 경합](confirm-return-settlement-lock-study.md)과 [배송·분쟁 경합](delivery-dispute-lock-study.md)은 같은 참여 행을 여러 도메인이 수정할 때 잠금 규칙을 공유해야 하는 이유를 보여 준다. [부분 반품 잔여 배송비](return-shipping-settlement-study.md)는 금액이 0인 환불 처리와 실제로 남아 있는 배송비의 정산을 구분한다. 근거 원장과 금액식이 맞는 경우만 허용하고 정책을 추정해 잔액을 지급하지 않는다.

[판매 철회 환불 예약과 복구](withdrawal-refund-recovery-study.md)는 취소 후 환불을 차례로 시작하다 서버가 중단되는 문제를 다룬다. 대상 전원의 원장을 취소와 함께 커밋해야 뒤 구매자의 반환 의무를 잃지 않는다. 개인 취소와 잠금 순서를 통일하고, 도중 새 구매자가 확정되면 새로운 트랜잭션으로 명단을 재조회하는 선택도 설명한다. [참여 시각 UTC](participation-clock-study.md)는 시간대 해석과 과거 데이터 보정이 별개임을 다룬다.

### 코인 결제

[지갑 증명](crypto-wallet-proof-study.md) → [준비 자산 일치](crypto-asset-binding-study.md) → [입금 반환 실행권](crypto-deposit-refund-execution-study.md)을 읽는다. 로그인 사용자, 서명 지갑, 준비 자산, 견적, 실제 거래가 연결되어야 하며 각 검증이 서로 대체 관계는 아니다. 입금 확인수는 자금 확정 정책이고 실행권은 중복 반환 방어다.

이어서 [실패 슬롯 게이트 반환](crypto-failure-slot-study.md), [종료 결제의 늦은 입금 추적](crypto-terminal-deposit-study.md), [반환 대상 입금 재사용 차단](crypto-deposit-reuse-study.md)을 읽는다. 마지막 문서는 이번 재개 후 추가로 재현해 Jira221로 분리한 결함이다. 입금 행의 UNIQUE와 유효한 지갑 서명이 있어도 이미 반환할 돈을 새로운 구매 자금으로 쓸 수 있는 오류는 막히지 않았다. 기존 행을 발견했을 때 삽입을 생략하는 코드가 그 행의 상태·소유권까지 보장하지는 않기 때문이다.

### 판매자 제재와 화면·AI

[철회 후보](withdrawal-penalty-study.md)와 [제재 판정 잠금](penalty-transition-lock-study.md)은 위반 후보의 자동 생성과 관리자의 확정을 구분한다. 연락처 수정 같은 다른 쓰기 경로도 판매 정지 상태를 덮어쓸 수 있어 전체 행의 변경자를 확인해야 한다.

## 4. 설계 문서가 충돌할 때 적용한 기준

구 요구사항의 FR-PEN-07에는 위반 확정 시 해당 공동구매 무산·전원 환불, 이미 지급한 금액의 상계/채권이 있다. 반면 [최신 API 명세](../api/공구한_API_명세서_v1.md) 0장은 최신 ERD v2 우선, 19장은 settlement_offsets/receivables와 대응 API를 만들지 않도록 명시한다. 제거된 구조를 버그 수정이라는 이유로 다시 만들지 않았다. 이미 지급된 거래의 제재 후 처리 공백은 별도 정책 검토가 필요하다. 판매자 전체 공구를 무차별 취소하는 것으로 해석하지 않는다.

부분 반품 후 배송비에는 공식 SmartStore의 판매수수료와 배송비를 구분하는 정책을 참고했다. 프로젝트에는 PG 수수료 원장이 없으므로 외부 서비스의 모든 비용 구조를 그대로 복사하지 않았다. 적용 조건, 금액식, 제외한 대안은 개별 문서에 상세하게 남겼다. 외부 사례는 참고 근거이고 최신 프로젝트 설계를 대체하지 않는다.

정책 결정이 필요한 질문은 구체적이다. 이미 판매자에게 지급한 위반 공구의 구매자를 어떤 재원으로 먼저 환불할지, 판매자 회수와 손실 처리를 누가 어떤 절차로 수행할지, 최신 ERD의 상계/채권 제외를 유지할지부터 정해야 한다. 기술적으로 가능한 송금 API를 호출하는 것과 이 책임·회계 정책을 확정하는 것은 다르다. 이 문서는 해당 정책이 정해졌다고 가정하지 않는다.

## 5. 시험 수치와 성능 지표를 구별한다

이번 묶음은 주로 오류·중복 지급·상태 유실을 막는 정합성 수정이다. 관측 지표는 외부 승인/반환 호출 횟수, 원장 수, 원장과 비정규화 카운터의 일치, 종료 후 참여 생성 0건 등이다. 테스트 실행에 걸린 시간과 프런트 빌드 시간은 개발 검증 소요시간이지 API 지연시간 개선율이 아니다.

조회 횟수 변화는 코드 경로 분석으로 설명할 수 있다. 예를 들어 신규 결제 완료의 주소록 재조회는 스냅샷으로 제거되지만 준비 시 저장할 컬럼과 검증 경계는 늘어난다. 비관적 잠금은 동시 상태 손상을 막지만 같은 행 요청을 기다리게 한다. 실제 동일 환경 부하 시험의 TPS/p95/p99 없이 “빨라졌다”는 결론을 만들지 않는다.

## 6. 아직 별도 확인이 필요한 범위

1. 실제 MySQL에서 현행 V17~V22 Flyway 적용과 스키마 검증. H2는 Hibernate DDL을 사용하므로 MySQL 마이그레이션 문법·기존 FK·기존 데이터 제약까지 증명하지 않는다. 과거 초안 V18과 현재 V18의 내용이 다를 수 있으므로 파일 이름만으로 적용됐다고 판단하지 않는다.
2. 실제 Redis/S3. 사용자가 Docker 작업을 보류했으며 기존 실환경 시험 3개는 제외 상태다. 로컬 대체 게이트는 실제 Redis 원자 스크립트·다중 서버·장애 조치를 대신하지 않는다.
3. 과거 UNKNOWN 및 원장 없는 취소의 제공사/체인 대조. DB 상태나 시간 경과만으로 송금 여부를 추정하거나 실행권을 해제하지 않는다. 읽기 목록과 실제 복구 승인은 구분한다.
4. 외부 승인 진행 중에 공구가 철회되는 경합의 사후 거래 처리. 새 진입 차단과 이미 외부로 나간 요청의 결과 대조는 별개다. 이미 승인됐는데 내부 완료가 실패하면 자동 재승인으로 해결하지 않는다.
5. 스냅샷 없는 과거 PROCESSING 코인에 이미 입금된 경우. 현재 주소를 당시 주소라고 만들어 넣지 않는다. 신규 견적/증명은 사전 스냅샷을 보장하지만 레거시 입금 증거와 완료 복구는 별도 대조가 필요하다. 최초 영수증 기록과 내부 결제 완료가 같은 트랜잭션이면 완료 예외가 입금 기록도 함께 롤백할 수 있으므로 DB에 없다는 사실만으로 실제 입금이 없다고 판단하면 안 된다.
6. 실제 체인 재편성·가스·nonce·장기 미확인 거래, 추천 품질 평가, 최신 버전의 실제 브라우저 및 금융 종단 검증. 추천 구매 이벤트의 과거 가격·모집률 등 특징값을 당시 스냅샷으로 보존하지 않은 한계도 미래 이벤트 차단과 별개다. 기존 과거의 실거래 성공 증거가 현재 모든 조합의 검증을 대신하지 않는다.
7. 시험 인프라의 공통 H2 데이터베이스 격리 확대. 아래에서 실제 오염이 드러난 판매자 공구 시험은 전용 DB로 분리했지만 모든 기존 시험의 공유 구조를 바꾼 것은 아니다. 기본 메모리 설정의 무조건 성공이나 작은 캐시에서도 시험이 독립적이라는 보장은 하지 않는다. CI에 적용할 때는 실행 명령과 메모리 자원 조건을 같이 반영하거나 클래스별 DB 격리/프로세스 분리를 별도 검증해야 한다.

### 전체 회귀의 메모리 조건

판매 철회 MR의 중간 전체 실행은 866개 중 847개 통과, 16개 실패, 3개 제외였다. 실패한 접근제어 클래스의 첫 원인은 Spring 컨텍스트 생성 중 OutOfMemoryError였고 나머지는 같은 컨텍스트 초기화 실패였다. 분리 실행에서는 해당 16개와 철회 관련 시험까지 37개가 통과했지만, 분리 성공으로 전체 실행 실패를 지우지 않았다.

최종 통합 실행에는 [선택형 테스트 실행 설정](full-regression-runtime.gradle)을 사용한다. Gradle Test JVM의 최대 힙을 2GiB로 명시하고 Spring 시험 컨텍스트 캐시를 64개로 설정한다. 애플리케이션 운영 JVM이나 기본 build.gradle을 바꾸는 설정이 아니며, 이 init script를 지정한 시험 실행에만 적용한다. 이것은 제품 속도 최적화가 아니라 테스트 실행 자원 조정이다.

처음에는 캐시를 8개로 줄여 메모리를 회수하려 했으나, 판매 철회 기준의 전체 887개 실행에서 20개가 실패했다(반품 저장소 8개, 정산 배치 12개). OOM이 아닌 `Table users not found`, `settlement_items` 테이블 없음이 원인이었다. 일부 서로 다른 Spring 컨텍스트가 공통 H2 데이터베이스와 `create-drop`을 공유해, 캐시에서 한 컨텍스트가 닫힐 때 다른 컨텍스트가 쓰던 스키마까지 사라지는 시험 환경 문제다. 따라서 8개 설정을 최종 설정으로 채택하지 않았다. 현재 시험 묶음의 컨텍스트를 유지하도록 64개로 늘리고 힙도 함께 확보한다. 장기적으로 클래스별 DB 격리나 별도 JVM 분리가 필요할 수 있으며, 이 임시 실행값이 시험 수 증가에도 영구적으로 충분하다고 가정하지 않는다. 이 실패도 실제 금융 기능의 실패나 테스트 성공으로 바꿔 적지 않는다.

실제 MySQL로 바꾼 것이 아니고 환경 제외 시험을 활성화하지도 않는다. 프로세스의 정상 종료, XML의 전체 건수·실패·오류·제외를 함께 확인해 성공 여부를 결정한다. 실제 경합 재현과 외부 호출 횟수 검사는 그대로 실행하며 실패 테스트를 제외하는 필터를 쓰지 않는다.

### 공유 DB의 잔존 데이터와 시험 격리

64개 캐시와 2GiB 힙에서는 OOM·테이블 유실 대신 판매자 공구 통합 시험 2개가 실패했다. 철회 기준 실행은 887개 중 882개 통과·2개 실패·3개 제외, 입금 재사용 기준 실행도 같은 2개가 실패했다. 공구 생성 API 자체는 201로 성공했지만 `groupBuyRepository.findAll()`은 기대한 1개 대신 2개를 반환했다. 다른 시험에서는 새로 생성된 920005/920006 대신 첫 행인 ID 1로 판매자 상세 조회를 요청해 404를 받았다. 같은 실행 설정으로 해당 클래스만 실행하면 2개 모두 통과했다.

이 클래스는 자신이 만든 상품과 판매자, 공구만 존재하는 독립 DB를 전제로 작성됐지만 기본 `mem:gongguhan`을 다른 컨텍스트와 공유했다. 기존 정산 배치 시험에는 ID 1·판매자 201의 공구 INSERT가 있고 테스트 뒤 삭제/롤백이 없어 잔존 데이터의 직접적인 후보다. 실패 실행 당시 ID 1의 모든 열을 별도로 채집하지 않았으므로 특정 시험이 남긴 행이라고 확정하지는 않는다. 생성 성공, 전체 조회에 추가 행 존재, 잘못 선택한 ID로 인한 조회 실패, 단독 통과는 실제 관측한 사실이다.

이번 Jira220에서는 `SellerGroupBuyIntegrationTest`의 datasource URL만 클래스 전용 `mem:sellergroupbuy`로 바꿨다. 정원·금액·HTTP 상태·소유권 검증이나 assertion을 완화하지 않고, 이 클래스가 전제로 하는 시험 데이터 범위를 분리한 것이다. 제품 코드, 실제 데이터베이스 설정, 실제 판매자의 데이터는 바꾸지 않았다. 단순히 예상 행 수를 2로 바꾸거나 404를 허용하는 대안은 오류를 숨기므로 제외했다. 캐시 축출로 우연히 이전 데이터가 지워지는 동작에 의존하는 대안도 제외했다.

두 금융 수정 브랜치와 이 시험 환경 보강을 독립 통합 worktree에 먼저 결합해 전체를 실행했다. 통과 뒤 금융 MR !182와 !186을 각각 DevelopV2에 병합하고 그 원격을 worktree에 다시 통합했다. 테스트한 소스와 현재 backend/frontend/ai 파일 차이가 없음을 확인했다. 나머지 시험 환경·기록 4개 파일만 Jira220의 별도 MR !187로 전달한다. 모든 금융 버그를 하나의 MR로 묶지 않았다.
