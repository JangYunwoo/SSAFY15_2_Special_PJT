# 종료된 코인 결제의 입금 추적과 반환 확인수 — S15P21B205-216

## 1. 이 문제를 결제 실패로만 끝내면 안 되는 이유

공동구매 참여 자리는 일정 시간만 유지된다. 반면 구매자가 이미 제출한 블록체인 거래는 서버의 슬롯 만료와 무관하게 나중에 블록에 포함될 수 있다. 따라서 `payments.status=EXPIRED/FAILED`는 참여를 더 이상 만들 수 없다는 뜻이지, 입금이 존재하지 않는다는 뜻이 아니다. 자리를 되살리지 않는 안전성과 실제로 받은 금액을 장부에서 잃지 않는 안전성을 동시에 지켜야 한다.

기존 폴링 조회는 PROCESSING 결제만 선택했다. 영수증이 아직 없는 상태에서 만료되면 이후 입금 사실을 읽지 않았고, 이미 영수증을 읽었어도 충분한 확인수에 도달하기 전에 만료되면 입금 반환 후보 분류가 중단됐다. 또한 미달·초과 입금 원장에는 확인수를 갱신하는 독립 경로가 없었으며, 관리자 반환은 확인수가 충분한지 검사하지 않았다.

이번 수정은 새로운 만료 결제 견적·서명 제출을 허용하는 변경이 아니다. 이미 서버에 저장된 거래 해시와 미매칭 입금만 계속 추적한다. 자동 반환도 추가하지 않는다. 관리자가 확인하고 실행하는 기존 권한 경계는 유지한다.

## 2. 수정 전 재현과 시험 설계

기준 커밋은 `8902037`이다. H2의 MySQL 호환 모드에서 실제 Spring 트랜잭션, JPA 저장소, 엔티티를 사용했다. 세 개의 실패를 먼저 확인하고 `crypto-terminal-deposit-before.json`에 별도로 보존했다.

1. 거래 해시는 저장됐지만 영수증이 없는 결제를 EXPIRED로 만든 뒤 대기 목록을 조회했다. 해당 결제가 없어 실패했다.
2. 같은 종료 결제에 성공 영수증을 전달했다. 서비스가 결제 상태만 보고 반환하여 입금 원장이 0건이어서 실패했다.
3. 성공 영수증은 이미 받았고 확인수는 1인 결제를 만료시켰다. 추가 확인수 조회 대상에서 빠져 실패했다.

만료 자체를 만드는 일부 시험은 SQL fixture로 상태를 설정한다. 이는 만료 배치 전체의 검증이라고 주장하지 않기 위해 명시한다. 별도로 슬롯 시간이 지났지만 아직 PROCESSING인 실제 서비스 경로도 시험해 FAILED 전환과 DB 예약수의 한 번 감소를 확인한다. Redis 슬롯 게이트는 mock이므로 Redis Lua나 네트워크 장애의 검증은 아니다. 첫 확장 시험에서 게이트를 대체하지 않아 Redis 연결 오류 1건이 발생했고, 외부 의존성을 명시적으로 격리한 뒤 다시 실행했다. 기능 실패를 통과로 숨긴 것이 아니라 시험 환경 의존성을 수정한 것이다.

## 3. 선택한 해결과 제외한 대안

### 3.1 종료 결제도 기존 거래는 추적한다

`CryptoPaymentRepository.findAwaitingReceipt`와 `findPendingConfirmation`은 PROCESSING뿐 아니라 EXPIRED/FAILED를 읽는다. PAID는 정상 결제 완료 경로로 유지한다. `applyLateReceipt`와 `refreshConfirmations`은 Payment를 먼저 잠근 다음 CryptoPayment를 읽는다. 반대 순서로 읽으면 잠금을 기다리기 전의 오래된 거래 상태로 판단할 수 있기 때문이다.

늦은 성공 영수증이 종료 결제에 도착하면 로그를 검증하고 입금 원장을 저장한 뒤 MATCHED를 UNMATCHED로 바꾼다. 참여·에스크로를 만들거나 슬롯을 재확보하지 않는다. 아직 PROCESSING이지만 시간이 지났다면 공통 `failPayment`로 종료시킨다. 이미 종료된 결제는 다시 실패시키지 않으므로 슬롯 반환을 반복하지 않는다. 영수증이 revert라면 반환할 토큰 자체가 없으므로 입금 원장을 만들지 않는다.

만료 뒤 결제를 성공으로 바꾸는 대안은 제외했다. 자리는 이미 다른 구매자에게 넘어갔을 수 있으므로 그 방식은 모집 인원 초과를 일으킨다. 종료 결제를 무시하는 기존 방식도 받은 자금의 추적을 잃으므로 제외했다.

### 3.2 과거 영수증의 블록 번호만으로 반환을 허용하지 않는다

기존 정상 결제 확인수 계산은 저장된 블록 번호와 최신 블록 높이를 사용한다. 그러나 반환 후보가 된 입금까지 이 값만 신뢰하면 이후 영수증이 사라지거나 다른 블록으로 이동한 사실을 읽지 못할 수 있다.

따라서 기존 MATCHED 입금을 종료 경로에서 재분류할 때, 이번 호출이 새 영수증을 직접 대조한 경우가 아니면 입금의 반환용 확인수를 0으로 되돌린다. 다음 독립 입금 폴링에서 새 영수증을 읽어 로그 인덱스·토큰 계약·송신자·수신자·원시 수량을 모두 원장과 비교한다. 성공 영수증과 정확히 일치할 때만 현재 영수증의 블록 번호와 최신 높이로 다시 계산한다. 영수증 없음, revert, 송신자 변경, 수량 변경은 확인수를 올리지 않는다.

`CryptoDepositRepository.findUnconfirmedRefundCandidates`는 설정된 체인에서 UNMATCHED/UNDERPAID/OVERPAID이며 자산별 필요 확인수 미만인 입금을 고른다. 결제 상세 트랜잭션이 롤백됐어도 별도 저장된 미달·초과 입금은 이 목록으로 진행한다. 조회는 JPA JPQL이다. 엔티티 사이 FK 연관관계가 없어도 두 엔티티의 체인·토큰 조건을 결합할 수 있으므로 SQL을 추가할 필요가 없었다.

### 3.3 확인수와 반환 실행권은 서로 다른 방어선이다

`CryptoDepositRefundService`는 반환 원장을 새로 열거나 송신 실행권을 잡기 전에 입금 확인수가 자산의 필요 확인수 이상인지 검사한다. 필요 확인수 설정이 0 이하인 경우도 안전하게 거절한다. 확인수가 충분하다는 것은 입금 확정 정책을 통과했다는 뜻이다. 중복 송금 방지는 별개로 선행 S15P21B205-213의 공통 원장 실행권이 맡는다. 결과 불명 원장을 자동 재송금하는 우회는 없다.

이미 COMPLETED인 반환 원장의 입금 종결 기록 복구는 이 확인수 검사보다 먼저 수행한다. 이미 나간 돈을 다시 보내는 작업이 아니므로, 환율 서비스나 확인수 변화 때문에 종결 복구까지 막아서는 안 된다. 폴링의 입금 수정과 `markDepositRefunded`에는 같은 입금 행 잠금을 사용하여 오래된 폴링 저장이 REFUNDED를 덮어쓰지 않게 했다. 금융 RPC는 DB 트랜잭션 밖에서 실행하는 구조를 유지한다.

## 4. 코드 흐름을 따라 읽는 순서

먼저 `CryptoPaymentRepository`의 두 조회를 읽고, 스케줄러가 어느 결제를 고르는지 확인한다. 다음 `CryptoTxRecordService.applyLateReceipt`에서 Payment 잠금, 영수증 검증, 입금 저장, 종료 분류 순서를 읽는다. `refreshConfirmations`는 이미 영수증이 있던 경우의 대응 경로다. 두 경로의 공통 정책은 `classifyTerminalDeposits`에 있다.

그다음 `CryptoConfirmationScheduler.pollConfirmations`의 독립 입금 목록과 `refreshDepositConfirmations`를 읽는다. 스케줄러는 한 주기 최신 블록 높이를 한 번만 조회하고 개별 영수증을 조회한다. 각 항목 오류는 해당 항목에 격리한다. 목록은 주기 시작에 읽으므로 방금 MATCHED에서 UNMATCHED로 바뀐 입금은 다음 주기에 새 영수증을 대조할 수 있다. 그 사이 확인수를 0으로 두므로 성급한 반환은 막힌다.

마지막으로 `CryptoDepositRefundService.refund`에서 기존 완료 원장 복구 → 반환 상태 → 필요 확인수 → 원장 생성/재사용 → 실행권 → 송신 순서를 읽으면 된다. 이번 변경은 상태 표시만 바꾼 것이 아니라 조회·분류·검증·반환 경계에 동일한 정책을 연결한 것이다.

## 6. 한계와 운영 확인 항목

이번 시험은 Java 21, Spring/JPA, H2 MySQL 호환 모드이며 체인 조회·송신·환율과 Redis 게이트를 대체했다. 실제 MySQL 잠금/실행 계획, Redis, RPC 장애 분포, 가스비, 지갑 nonce, 실제 체인 재편성까지 검증한 것은 아니다. 배포나 실제 과거 입금 재처리도 하지 않았다.

필요 확인수는 위험을 줄이는 정책이지 수학적으로 절대적인 확정 보장은 아니다. 임계값 도달 이후의 깊은 체인 재편성 감시, 과거 미등록 해시를 찾는 지갑 전체 스캐너, 등록된 해시가 영원히 발견되지 않을 때의 운영 보존 정책은 이번 수정 밖이다. 배치가 오래된 ID부터 읽는 구조이므로 장기 미확인 건이 대량으로 쌓일 때 공정한 순환 조회 정책도 별도 고려가 필요하다.

주소 스냅샷이 없는 레거시 PROCESSING 거래는 최신 공통 결제 정책에 따라 임의의 현재 주소를 끼워 넣지 않는다. 확정 시 예외가 발생하는 경우 거래 증거의 별도 보존·운영 대조가 필요하며 이번 종료 결제 경로가 과거 레거시 데이터를 자동 복원한다고 해석하면 안 된다. 미달·초과·반환된 기존 입금의 다른 결제 재사용 가능성은 원래 FR-PAY-26 범위의 별도 격리 재현 대상으로 분리한다.
