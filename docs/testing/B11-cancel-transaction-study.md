# B11: 입력 오류가 참여 취소를 먼저 확정하지 않도록 경계 맞추기

## 1. 기준과 범위

Jira: [S15P21B205-177](https://ssafy.atlassian.net/browse/S15P21B205-177). 브랜치: `fix/be/S15P21B205-177-cancel-transaction-boundary`. 기준은 B27 MR !141까지 병합된 DevelopV2 `d3eaa50c1ef994bece20b377093492f51d899ec5`다.

이번 MR은 참여 취소의 입력 검증·상태 변경·환불 의도 저장 경계를 수정한다. 다른 결제 승인 경합, 관리자 환불 재처리 실행권, 카드 반품 환불 경로 등 원래 작업 폴더의 미완료 변경을 가져오지 않았다. HTTP 요청 모양이나 프런트 스타일을 변경하지 않는다.

병합 직전 팀원의 개인화 추천 기능이 DevelopV2에 추가되어 최종 기준을 `e6ae9a11a3b900795caca508b52277761596e5e7`로 갱신했다. 충돌 없이 재배치한 뒤 전체 테스트를 다시 실행했으며 동일하게 583개 중 580개 통과, 3개 제외, 실패/오류 0을 확인했다. 팀원 변경은 이 MR의 수정 목록에 포함하지 않는다.

## 2. 기존 흐름과 사용자가 겪는 오류

기존 cancel은 먼저 prepareCancel의 트랜잭션을 호출했다. 여기에서 참여를 PAID에서 REFUNDING으로 바꾸고 공동구매 참여 인원을 줄였다. 이 트랜잭션이 커밋된 다음에야 카드번호와 CVC가 있는지 확인했다.

카드 정보가 없으면 사용자는 400 오류를 받지만 DB에는 이미 취소 준비가 확정되어 있었다. 입력을 고쳐 다시 요청해도 PAID가 아니라는 이유로 거절됐다. 환불 원장 생성은 더 뒤에서 수행되므로 환불 원장 없이 REFUNDING만 남을 수 있었다.

원장 저장에 실패하는 경우도 같은 문제다. 원장이 없는 취소 의도는 복구할 대상을 추적하기 어렵다. 그래서 이 문제를 단순히 카드 입력 if문 위치만 옮겨 해결했다고 판단하지 않았다.

## 3. 반드시 함께 유지해야 하는 조건

| 단계 | 보장할 상태 | 외부 금융 호출 |
|---|---|---|
| 입력·소유권·상태 검증 실패 | 참여 PAID, 인원 유지, 새 환불 없음 | 없음 |
| 취소 의도 저장 성공 | 참여 REFUNDING, 인원 감소, 환불 PROCESSING 원장 존재 | 아직 없음 |
| 외부 환불 성공 | 기존 종결 서비스가 참여·에스크로·환불을 완료 | 한 요청이 실행 |

입력 오류와 DB 저장 오류는 취소 의도까지 롤백해야 한다. 외부 금융망을 호출한 뒤의 오류는 이미 기관에서 처리되었을 수 있으므로 같은 방식으로 무조건 되돌리거나 재호출할 수 없다. 이번 변경은 두 종류의 실패를 구분하는 출발점이다.

## 4. 구현과 선택 기준

### 4.1 상태 변경 전에 입력을 검증한다

ParticipationCancelService.prepareCancel은 참여 행을 잠그고 소유권과 PAID 상태를 확인한다. 원 결제수단이 CARD인 경우 카드번호는 숫자 16자리, CVC는 숫자 3자리인지 검사한다. 잘못되면 공구 인원이나 참여 상태를 변경하기 전에 오류를 반환한다. 카드 원문을 로그나 DB에 저장하지 않는다.

다른 수단에는 카드 입력을 강요하지 않는다. 앞서 수정한 카카오 일반 취소도 동일한 공통 취소 흐름을 계속 사용할 수 있어야 한다.

### 4.2 같은 참여와 같은 공구의 경쟁을 직렬화한다

기존 findById 대신 이미 존재하는 JPA 비관적 잠금 조회를 사용한다. 참여 행을 먼저 잠그므로 같은 참여를 동시에 취소하는 요청은 앞선 상태 변경을 확인한 뒤 하나만 진행한다. 공구 행도 잠가 다른 참여의 취소와 인원 변경이 겹쳤을 때 갱신 유실을 막는다.

이 작업은 모든 업무의 교차 잠금 문제를 해결한 것은 아니다. 반품·구매확정·정산이 같은 기준을 사용하는지는 별도의 경합 점검 항목이다.

### 4.3 상태·인원·환불 원장을 한 트랜잭션으로 묶는다

환불 오케스트레이션에 reserveParticipationCancellation을 추가했다. 이 메서드는 결제수단에 맞는 환불 방법을 정하고 원장만 연다. 실제 외부 호출은 하지 않는다. 카드 참여 취소는 CARD_CANCEL, 다른 수단은 기존 환불 방법 선택을 사용한다.

이 메서드에는 MANDATORY를 적용했다. 호출자의 취소 트랜잭션이 없으면 실행하지 않는다는 뜻이다. 원장 저장의 기존 REQUIRED 트랜잭션은 취소 트랜잭션에 합류한다. 따라서 원장 저장 실패 시 참여 상태와 공구 인원도 함께 롤백된다. 이미 진행/완료된 원장이 반환되면 새 취소로 취급하지 않고 예외로 전체 변경을 되돌린다.

외부 호출까지 하나의 트랜잭션으로 감싸는 대안은 선택하지 않았다. DB 롤백으로 외부 결제사에서 이미 수행한 취소를 되돌릴 수 없으며, 기관 응답을 기다리는 동안 DB 잠금과 커넥션을 오래 점유하게 된다.

### 4.4 DB 커밋 이후에 캐시와 금융 처리를 진행한다

Redis 슬롯 게이트 해제는 afterCommit으로 옮겼다. 원장 저장이 실패해 DB 취소가 롤백되었는데 Redis만 먼저 줄어드는 상황을 줄이기 위해서다.

이미 DB가 커밋된 뒤 Redis 해제가 실패하면 이를 재대조가 필요한 오류로 기록하되, 이미 예약된 환불 실행까지 건너뛰지 않는다. 예외 로그에는 카드 입력을 넣지 않는다. Redis 자동 복구가 완성됐다는 의미는 아니며, 캐시·DB 재대조는 별도 운영 과제로 남는다.

executeParticipationCancellation은 새 원장을 만든 요청만 실행하고 기존 종결 서비스를 호출한다. NEVER를 적용하여 열린 DB 트랜잭션 안에서 금융 호출을 시작하는 잘못된 사용을 거절한다. 정상 경로는 prepareCancel이 반환되며 커밋을 마친 다음 이 메서드에 도달한다.

## 5. 수정 전 재현과 테스트 설계

최신 원격 기준에 먼저 ParticipationCancelSafetyIntegrationTest 8개를 넣어 실행했다. 결과는 6 실패/2 통과였다.

- 카드 정보 누락: 예외는 나지만 PAID와 인원이 보존되지 않아 실패.
- 카드 형식 오류: 기존 코드는 비어 있는지만 확인하여 올바르게 거절하지 못해 실패.
- 원장 저장 실패: 참여 상태가 먼저 커밋되어 롤백 조건 실패.
- 올바른 입력으로 재시도: 앞 요청에서 REFUNDING으로 바뀌어 재시도 실패.
- 동시 취소: 하나의 명확한 업무 거절 대신 낙관적 갱신 충돌이 노출되어 실패.
- Redis 장애: 기존 코드에서는 환불 실행까지 도달하지 못하여 실패.
- 외부 호출의 트랜잭션 외부 실행·원장 존재, 다른 사용자 거절: 기존 코드에서도 통과.

테스트는 실제 Spring 서비스·JPA·H2 트랜잭션과 공통 환불 원장을 사용한다. 카드 기관과 Redis 경계만 대체하며, 스케줄러는 끈다. 단순히 메서드 호출 순서만 보는 대신 DB에 커밋된 참여 상태·인원·원장 수를 재조회한다. 외부 카드 호출 내부에서도 활성 트랜잭션이 없고 환불 원장이 이미 보이는지 검사한다.

동시 취소 테스트는 별도 두 스레드의 시작을 맞춰 요청을 보낸다. 수정 후 성공 하나/업무 거절 하나, 기관 호출 한 번, 게이트 해제 한 번, 인원 0을 요구한다. H2가 배포 MySQL의 모든 잠금 특성을 대신 증명하지는 않는다.

추가로 원장 예약을 트랜잭션 밖에서 호출하면 거부되는지, 외부 실행을 트랜잭션 안에서 호출하면 기관 호출 전에 거부되는지 두 사례를 보강했다. 이 두 사례는 수정 후 추가한 것으로 수정 전 8개 결과에 섞지 않는다.

## 6. 회귀와 남은 한계

수정 후 최초 8개 시나리오와 앞서 병합한 카카오 일반 참여 취소 환불 통합 3개가 함께 통과했다. 트랜잭션 전파 경계 2개를 보강한 후 전체 백엔드를 다시 실행했다.

| 검증 | 전체 | 통과 | 실패/오류 | 제외 |
|---|---:|---:|---:|---:|
| 수정 전 B11 재현 | 8 | 2 | 6 | 0 |
| 수정 후 B11 (추가 경계 2개 포함) | 10 | 10 | 0 | 0 |
| 최종 백엔드 전체 회귀 (92개 클래스) | 583 | 580 | 0 | 3 |

최종 Gradle 결과는 BUILD SUCCESSFUL이며 XML 결과를 합산했다. 제외 3개는 실제 Redis 게이트 2개와 S3 관련 1개이므로 해당 외부 환경까지 통과했다고 해석하지 않는다. 프런트 변경은 없으며 이번 MR에서 프런트 테스트를 재실행한 것으로 기록하지 않는다. GitLab CI 성공이 아니라 로컬 JDK 21 테스트 결과다. 수치는 `B11-cancel-transaction-results.json`에도 저장했다.

이 구현은 트랜잭션 커밋 직후 프로세스가 종료되는 간격 자체를 없애지 않는다. 환불 의도는 원장에 남지만 이를 안전하게 다시 실행하려면 실제 금융 호출 여부를 대조하는 실행권/복구 체계가 필요하다. 단순히 PROCESSING/FAILED 원장을 전부 재전송하는 자동 반복을 추가하지 않았다. 기존 실패 거래를 실제로 재처리하지도 않았다.

외부 기관 timeout의 성공 여부 판정, 관리자 환불 재처리 경합, 카드 반품 자동 환불, 모집 실패 자동 환불은 다른 버그로 남는다. 현재 원장을 남겼다는 이유만으로 금융 처리 전체가 exactly-once라고 주장하지 않는다.

이 변경은 성능 최적화가 아닌 정합성 수정이다. 기관 호출 횟수는 중복 방지의 기능 지표이며 TPS나 지연시간 향상률이 아니다. 외부 호출 중 DB 트랜잭션을 열지 않는 설계 선택은 테스트로 확인했지만, 실제 운영 부하의 수치 개선을 측정한 것은 아니다.

## 7. 재실행과 읽는 순서

ParticipationCancelService.cancel → prepareCancel의 검증과 잠금 → reserveParticipationCancellation과 RefundLedgerService.openForParticipation → afterCommit → executeParticipationCancellation → 기존 환불 종결 순서로 읽는다. 입력 검증 실패와 기관 응답 불명 실패가 왜 같은 롤백으로 해결되지 않는지 비교한다.

backend에서 `./gradlew.bat test --tests '*ParticipationCancelSafetyIntegrationTest' --tests '*KakaoPayParticipationRefundIntegrationTest'`, 이어서 `./gradlew.bat test`를 실행한다. 실제 카드·금융망 키 없이 실행 가능하다.
