# B27: 카카오 일반 참여 취소 환불이 반품 번호 때문에 실패한 이유

## 1. 기준과 범위

Jira: [S15P21B205-176](https://ssafy.atlassian.net/browse/S15P21B205-176). 브랜치: `fix/be/S15P21B205-176-kakao-participation-refund`. 기준은 B01 MR !140이 병합된 DevelopV2 `94b16ac2ba28561bfb34001eb962536e2766e116`이다.

이전 로컬 작업에 같은 원인의 수정 초안이 있었지만, 다른 미완료 금융 변경과 함께 병합하지 않았다. 원격 기준의 독립 작업 폴더에 B27 테스트를 먼저 옮겨 다시 실패를 확인한 다음 이 버그의 수정만 적용했다.

## 2. 증상과 호출 흐름

카카오페이 결제 후 모집 중 참여 취소를 요청하면 참여 상태는 환불 진행으로 바뀌지만 카카오 외부 취소 호출 전에 환불이 실패했다. 원인은 제공사의 API 키나 전화 인증이 아니라 우리 어댑터의 입력 계약이었다.

일반 참여 취소는 ParticipationCancelService에서 취소 가능 여부와 참여 상태를 처리하고, RefundOrchestrationService.refundParticipation으로 환불을 위임한다. 이 서비스는 공통 refunds 원장을 생성하고 카카오 어댑터에 RefundCommand를 전달한다. 일반 참여 취소이므로 반품 신청을 뜻하는 returnId는 null이다.

그런데 KakaoPayCancellationRecordService.validate는 returnId가 null이면 요청을 거절했다. 반품 환불에서는 항상 들어오던 값을 모든 환불에 필요한 식별자로 잘못 취급한 것이다. 결과적으로 외부 취소가 호출되지 않고 공통 환불 원장에 실패가 남았다.

## 3. 구현 선택과 유지한 방어

validate에서 `command.returnId() == null` 조건만 제거했다. RefundPort.RefundCommand의 문서에는 returnId가 반품 추적 정보이며 일반 참여 취소·모집 실패 환불에서는 null임을 명시했다.

환불 대상을 식별하는 필수 값은 원결제 paymentId와 그 결제에 저장된 승인 TID다. 원결제의 승인 결과 AID, 요청 금액, 요청 키도 계속 검사한다. 다음 조건은 완화하지 않았다.

- 결제수단은 KAKAOPAY이며 paymentId가 있어야 한다.
- 금액은 양수이고 원 승인 금액을 넘을 수 없다.
- 요청 키는 비어 있지 않고 64자 이하여야 한다.
- 원 결제에 승인 AID와 TID가 있어야 한다.
- 같은 요청 키는 같은 결제·금액을 가리켜야 한다.
- 성공한 취소는 캐시된 결과를 사용하고, 처리 중/결과 불명인 취소는 외부 호출을 다시 보내지 않는다.

가짜 returnId를 만들어 넣는 대안은 실제 반품이 없는데 반품 이력이 있는 것처럼 보여 추적 정보를 오염시킨다. 일반 취소마다 반품 신청을 생성하는 대안도 도메인 의미가 다르므로 선택하지 않았다. 카카오 취소 API를 우회하여 계좌이체로 바꾸는 것은 원결제 취소라는 요구와 다른 기능이다.

## 4. 테스트 기획과 수정 전 결과

단위 테스트만으로는 어댑터에 도달한 명령이 허용되는지만 알 수 있다. 사용자가 실제로 보는 참여 상태, 에스크로, 모집 인원, 환불 원장이 함께 정리되는지는 별도 통합 검증이 필요하다.

먼저 기존 단위 테스트 4개에 returnId 없는 정상 취소와 과다 금액의 정확한 거절 사유 확인 2개를 추가했다. 다음 3개의 통합 테스트도 추가하여 수정 전 실행했다.

1. 실제 로컬 결제 확정으로 참여·에스크로를 만든 뒤 일반 참여 취소를 실행한다. refund가 COMPLETED, 참여와 에스크로가 REFUNDED, 공구 참여 인원이 0이어야 한다. 두 번째 취소는 거절하고 제공사 취소 호출은 한 번만 있어야 한다.
2. 외부 호출 전에 기존 B27 검증 오류로 실패한 원장을 테스트 DB에 재현한다. 재처리 성공 후 같은 상태로 종결되며, 이미 줄인 공구 인원을 다시 줄이지 않아야 한다. 이 시나리오는 제공사 응답을 잃어 결과가 불명확한 실패와 구분한다.
3. 실제 반품 번호가 있는 800원 부분 환불은 returnId·금액을 보존한다. 이 경로의 반품 상태 종결 책임을 일반 참여 취소의 종결 로직이 대신 수행하면 안 되므로 에스크로는 반품 도메인이 처리하기 전 HELD를 유지한다.

수정 전 9개 중 4개 실패, 5개 통과였다. 일반 취소와 이전 실패의 재처리 통합 2개가 실패했고, 단위 2개도 실패했다. 과다 금액 테스트의 실패는 ‘과다 금액을 허용했다’는 뜻이 아니라, 금액 검증에 도달하기 전에 반품 번호 누락으로 잘못 거절했다는 뜻이다.

## 5. 실행 환경과 격리

통합 테스트는 실제 Spring 서비스·JPA·H2 트랜잭션과 공통 원장·카카오 어댑터를 사용한다. 외부 카카오 Gateway와 Redis 슬롯 게이트만 대체한다. 별도 이름의 메모리 DB와 테스트 전용 ID를 사용하고 스케줄러를 끈다. 운영 DB나 실제 환불을 호출하지 않는다.

원래 미완료 로컬 작업 폴더와 달리, 이 브랜치에는 B27에 필요 없는 카드 취소 검증·정산 경합·환불 실행 가드 초안이 없다. 따라서 이 브랜치의 전체 테스트 집계를 원래 폴더의 과거 수치와 단순 비교해서 기능이 줄었다고 해석하면 안 된다.

## 6. 검토와 검증 한계

수정 후에는 필수 입력 누락·잘못된 수단·0/음수 금액·너무 긴 키를 계속 거절하는 추가 단위 테스트와 미승인 결제를 거절하는 테스트를 넣었다. 운영 코드 변경은 검증 조건 1개 제거와 계약 설명뿐이며 DB 마이그레이션·프런트·스타일 변경이 없다.

이 변경을 병합했다고 운영에서 이미 실패한 환불을 자동 재시도하지 않는다. 특히 실제 외부 취소의 성공 여부를 모르는 거래는 먼저 제공사 상태와 원장을 대조해야 한다. 이번 통합 재시도는 ‘외부 호출 전 입력 검증 실패’임이 확실한 테스트 데이터에 한정한다.

별도 문제인 환불 실행권 경합, 카드 반품 환불 경로, 모집 실패 자동 환불 이벤트 소비, 반품·정산 교차 경합을 이 수정으로 해결했다고 주장하지 않는다. 실제 교육망·카카오 신규 승인/환불을 이 MR에서 다시 실행하지 않았으며 실제 배포 검증은 별도다.

성능 최적화가 아니므로 처리속도 향상률을 기록하지 않는다. 외부 호출이 빠졌던 버그를 고쳤기 때문에 정상 경로에서 기관 호출이 발생하는 것이 의도한 기능 회복이다.

## 7. 학습과 재실행

최종 XML 집계는 백엔드 91개 테스트 클래스, 총 573개 중 570 통과·실패/오류 0·환경 의존 3 제외다. 카카오 취소 단위 8개와 참여 환불 통합 3개는 모두 통과했다. 제외는 Redis 슬롯 게이트 2개와 S3 1개로, 이들을 통과로 표시하지 않았다. 최초 전용 9개는 수정 전 4 실패/5 통과에서 수정 후 9 통과로 바뀌었고, 이후 추가한 입력 방어 2개도 통과했다.

RefundCommand의 returnId 의미를 먼저 읽고, RefundOrchestrationService가 일반 참여 취소와 반품 환불을 어떻게 다르게 여는지 비교한다. 다음으로 카카오 recordService의 필수 검증을 읽고, 통합 테스트에서 참여·에스크로·원장이 각각 어떤 상태가 되는지 따라간다.

backend에서 `./gradlew.bat test --tests '*KakaoPayParticipationRefundIntegrationTest' --tests '*KakaoPayCancellationRecordServiceTest'`, 이어서 `./gradlew.bat test`를 실행한다. 테스트에는 실제 비밀키가 필요하지 않다.
