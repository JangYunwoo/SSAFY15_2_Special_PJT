# 추천 세션 최초 생성 경합과 원자적 소유권 확인

이슈 S15P21B205-186. 기준 DevelopV2 ce43a8e. 작성일 2026-09-21.

## 1. 실패 시나리오

RecommendationService.recordEvents는 sessionId의 소유자를 조회해서 현재 사용자와 다르면 거절한다. 이미 존재하는 세션에 순서대로 접근할 때는 충분해 보인다. 하지만 신규 sessionId에 A와 B가 동시에 요청하면 두 트랜잭션 모두 처음 SELECT에서 행이 없다고 볼 수 있다. 이후 둘 다 saveEvents에 들어간다.

기존 저장 코드는 session_id 기본키로 INSERT ON DUPLICATE KEY UPDATE를 실행한다. 먼저 온 A가 세션을 만들고 뒤의 B는 같은 행의 마지막 활동 시각과 종료 여부만 바꾼다. user_id는 A로 남아 있지만 B의 이벤트는 자신의 user_id로 삽입된다. 이벤트 테이블은 session_id와 user_id를 각각 참조할 뿐 두 컬럼 조합이 세션 소유자와 같아야 한다는 제약은 없다. 확인 시점과 사용 시점 사이 상태가 달라지는 TOCTOU 문제다.

무작위 UUID 추측 확률이 낮다는 것은 정확성 보장이 아니다. 프런트 재사용 버그, 비정상 클라이언트, 같은 ID를 전달하는 동시 요청에서도 서버가 원칙을 지켜야 한다. 이전 MR의 프런트 계정 분리와 이 MR의 서버 정합성 검사는 서로를 대체하지 않는다.

## 2. 해결 방법의 비교

사전 SELECT에 잠금만 추가하면 아직 존재하지 않는 행의 생성 순서 및 갭 잠금·교착 문제를 별도로 다뤄야 한다. JVM synchronized는 서버가 여러 대일 때 효력이 없다. 세션과 이벤트의 복합 외래키를 새로 추가하는 방법은 기존 혼합 데이터 정리와 DB 마이그레이션이 필요하다.

현재 upsert가 같은 기본키의 세션 행을 확보하는 지점을 이용했다. 해당 행의 소유자를 같은 트랜잭션에서 FOR UPDATE로 읽고 현재 사용자와 비교한다. 다르면 BusinessException(RESOURCE_ACCESS_DENIED)을 던져 이벤트 삽입 전에 중단한다. upsert로 잠시 변경한 last_event_at·ended_at·end_reason도 함께 롤백된다.

일반 SELECT를 다시 호출하는 대신 잠금 읽기를 선택한 것은 일관 읽기의 이전 스냅샷에 의존하지 않기 위해서다. MySQL 공식 문서는 FOR UPDATE가 최신 사용 가능한 데이터를 읽고 해당 행을 잠근다고 설명한다. [MySQL 8.4 Locking Reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html).

## 3. 트랜잭션 경계

서비스의 기존 @Transactional은 유지한다. 저장소 saveEvents에는 Propagation.MANDATORY를 추가해 Spring을 통해 트랜잭션 없이 호출하는 실수를 막는다. 잠금 읽기는 트랜잭션이 끝나기 전에 보호 대상의 이벤트 삽입까지 수행해야 의미가 있기 때문이다. 이 메서드 안에서 REQUIRES_NEW로 분리하거나 예외를 삼킨 채 커밋하면 롤백 보장이 깨진다.

변경은 추천 저장소 한 곳에 한정하고 결제·정산·사용자 기본정보를 건드리지 않는다. 사용자 소유권 사전 검사는 기존에 존재하는 잘못된 소유자의 요청을 빠르게 거절하는 용도로 남겨 두되 최종 권한 판단은 저장 직전의 잠금 검사로 보완한다.

## 4. 재현 테스트 설계

Docker를 재시도하지 않고 애플리케이션 테스트 의존성인 H2의 MySQL 모드를 사용했다. 테스트마다 UUID 이름의 별도 메모리 DB를 만들고 테스트가 끝나면 해당 DB만 종료한다. 배포·로컬 실제 DB와 연결하지 않는다. 실제 JDBC INSERT, SELECT FOR UPDATE, 배치 INSERT와 트랜잭션 롤백을 사용하며 저장소 메서드를 mock하지 않는다.

두 스레드에 서로 다른 사용자 ID와 같은 신규 sessionId를 준다. CountDownLatch로 두 트랜잭션 모두 사전 조회에서 소유자가 없음을 확인한 다음 동시에 저장으로 진행시킨다. 우연히 경쟁이 일어나기를 기다리지 않고 취약한 순서를 고정한 것이다. 한 요청은 SAVED, 다른 요청은 정확히 RESOURCE_ACCESS_DENIED여야 하며 최종 이벤트는 1개, 세션 소유자와 이벤트 사용자 불일치는 0개여야 한다. 이 시나리오를 독립 DB로 5회 반복한다.

별도 테스트는 같은 소유자의 연속 저장이 정상적으로 두 이벤트를 남기는지, 다른 소유자 요청이 이미 닫힌 세션을 재개하지 못하고 종료 사유가 유지되는지 검사한다. 오류가 나기만 하면 통과하는 것이 아니라 최종 저장 결과도 확인한다.

## 5. 수정 전·후 결과와 한계

수정 전 7개 테스트 중 6개가 실패했다. 5번의 동시 생성 시험 모두 두 요청이 저장되어 실패했고, 다른 소유자의 직접 저장도 거절되지 않았다. 같은 사용자의 연속 저장만 통과했다. 수정 후 위 7개를 포함한 전체 백엔드 회귀가 통과했다. 최종 XML 집계는 별도 확인한 총 636개 중 633개 통과, Redis/S3 환경 3개 제외, 실패·오류 0이다.

H2 MySQL 모드는 MySQL/InnoDB와 동일한 엔진이 아니다. 이번 결과는 잠금 이후 검사·예외 전파·롤백 및 동시 소유자 분리의 구현을 검증하지만 실제 InnoDB의 REPEATABLE READ, 갭 잠금, 교착 재시도까지 실측했다고 주장하지 않는다. Docker가 가능해지면 같은 동시 생성 시나리오를 MySQL로 재실행해야 한다. 경합과 함께 다른 다중 행 갱신이 추가된다면 교착 처리 정책도 점검해야 한다.

성능 최적화가 아닌 권한·정합성 수정이다. 저장 요청에 잠금 SELECT가 하나 추가되므로 더 빠르다고 주장하지 않는다. 해당 비용을 수치로 비교하는 벤치마크는 이번에 수행하지 않았다. 학습 데이터 오염을 방지하는 정확성이 선택의 우선 기준이다.

## 6. 학습 및 재실행

서비스 recordEvents의 사전 검사 → 저장소 saveEvents의 upsert → 잠금 읽기 → 이벤트 배치 저장 순서로 읽는다. 테스트의 barrier가 어느 순서를 강제하는지 읽은 뒤 수정 전에는 두 요청이 왜 모두 성공하는지 설명해 보면 된다.

backend에서 Java 21로 `gradlew.bat test --tests '*RecommendationOwnershipIntegrationTest' --console=plain`을 실행한다. 전체 회귀는 `gradlew.bat test --console=plain`이다. 기존 테스트 보고서를 보고 수정 전 실패를 수정 후 실패로 혼동하지 않도록 프로세스 완료 이후 XML을 집계한다.

DevelopV2에 독립 MR로 병합하고 Jira에는 구현 완료와 실환경 검증 한계를 함께 남긴다. DevelopV1·배포 서버·실제 금융 거래는 변경하지 않는다.
