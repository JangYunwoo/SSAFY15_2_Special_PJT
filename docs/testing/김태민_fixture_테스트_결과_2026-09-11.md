# 김태민 담당 fixture 기반 테스트 결과

## 1. 결론

고정 fixture를 넣어 실제 MySQL·Spring Boot·프론트를 연결한 결과, 김태민 담당 범위의 조회·권한·금액 계산·상태 변경 API는 대부분 정상 동작했다.

- fixture 조회·권한 회귀: 구현 시나리오 15개 통과
- 알려진 누락 확인: GRP-10은 예상대로 HTTP 404
- 상태 변경: 상품 수정·삭제, 공동구매 생성·수정·취소, 반품 신청·승인·거절·이의제기 통과
- 전체 백엔드 회귀: 350개 중 348개 통과, 실제 Redis가 있어야 하는 2개는 조건부 건너뜀
- 프론트: typecheck·lint·build 통과, 홈에서 모집 중 fixture 2건 렌더링 확인

이번 수정으로 S3가 없는 로컬에서도 상품 이미지 등록·조회·삭제가 가능해졌고, Redis가 없는 단일 인스턴스 로컬 실행에서도 결제 슬롯을 원자적으로 제한할 수 있다. 식별자 JSON 타입과 프론트 빈 배열 검증 오탐도 수정했다. 김태민 범위를 완전한 종단 MVP로 판정하지 못하게 하는 남은 기능 결함은 GRP-10 공통 환불 의존성이며, AI 성공 경로와 실제 Redis Lua 경로는 해당 외부 환경에서 추가 확인해야 한다.

## 2. 재현 파일

- DB fixture: `backend/src/test/resources/fixtures/kim_taemin_manual_test_dump.sql`
- API 회귀 실행기: `backend/scripts/test-kim-taemin-api.ps1`
- 실제 결과 JSON: `docs/testing/results/김태민_fixture_API_결과_2026-09-11.json`
- 수동 시나리오: `docs/testing/김태민_담당_수동_점검_시나리오.md`

fixture는 사용자·상품·공동구매·참여·결제·에스크로·배송·반품을 `910000`번대 이상의 ID로만 만든다. 일반 데이터는 삭제하지 않는다. 여러 차례 다시 적용해도 사용자 3명, 상품 4개, 공동구매 3개, 참여 2개, 반품 1개로 되돌아오는 것을 확인했다.

## 3. 정상 확인 항목

### 3.1 상품·카테고리

- CAT-01은 기획 순서의 카테고리 20개를 반환했다.
- 판매자 상품 목록에서 fixture 상품 4개와 이미지·연결 공동구매 상태가 정상 조회됐다.
- 구매자 토큰으로 판매자 상품 API를 호출하면 `ROLE_ACCESS_DENIED`, HTTP 403이 반환됐다.
- 연결되지 않은 상품은 이미지 교체 없이 수정할 수 있었다.
- 생성한 공동구매를 취소한 후 상품 삭제가 정상 처리됐다.

### 3.2 공동구매

- 공개 목록에서 모집 중 fixture 2건을 반환했다.
- 100,000원, 목표 4명, 배송비 3,000원의 미리보기 결과는 분담금 25,000원, 수수료 5,000원, 예상 정산액 107,000원이었다.
- 신규 생성 시 81,000원과 목표 3명에서 분담금 27,000원으로 올림됐다.
- 참여자 없는 모집 조건 수정과 취소가 정상 처리됐다.
- 배송 완료 fixture에서는 참여자 2명, 에스크로 보유액 126,000원, 반품 1건이 조회됐다.

### 3.3 반품

- 판매자 귀책 `DEFECT` 미리보기에서 최초 배송비 포함 63,000원 전액 환불, 반품 배송비 판매자 부담으로 계산됐다.
- 반품 신청 후 판매자 거절, 구매자 이의제기 상태 전이가 정상 동작했다.
- 별도 fixture의 판매자 승인도 `REQUESTED → APPROVED`로 정상 전환됐다.
- 반품 상세에는 상태 이력과 수거 주소가 함께 반환됐다.

상태 변경 테스트가 끝난 뒤 동적으로 생성한 반품과 공동구매만 명시적으로 제거하고 fixture를 다시 적용했다. 현재 DB는 사용자가 직접 조작하기 좋은 초기 상태다.

## 4. 발견된 문제

### P0 — GRP-10 판매자 귀책 판매 철회 미구현

`POST /sellers/group-buys/930003/withdrawal`은 HTTP 404와 `RESOURCE_NOT_FOUND`를 반환했다. Controller 경로 자체가 없다.

이 기능은 공동구매 취소뿐 아니라 참여자 전원 환불, 정산 제외, 판매자 제재 후보 생성을 요구한다. 김태민 코드에서 카드·코인 환불 구현을 직접 참조하면 도메인 결합이 커지므로 공통 `RefundPort`와 결제수단별 어댑터가 선행되어야 한다.

### 해결 — S3 미설정 로컬에서도 PRD-01 상품 등록 가능

수정 전 실제 이미지 multipart 등록 결과는 HTTP 500이었다.

```json
{
  "success": false,
  "error": {
    "code": "INTERNAL_SERVER_ERROR",
    "message": "S3 버킷이 설정되지 않았습니다."
  }
}
```

`local` 프로필 전용 `LocalProductImageStorage`와 조회 Controller를 추가했다. 같은 `ProductImageStorage` 포트를 구현하므로 상품 서비스는 저장 방식이 로컬인지 S3인지 알 필요가 없다. 운영·테스트 프로필은 기존 S3 구현을 유지한다.

실제 PNG multipart 등록 결과 상품 생성 HTTP 201, 반환 이미지 URL GET HTTP 200과 `Content-Type: image/png`, 검증 후 상품 삭제 HTTP 200을 확인했다. 파일명은 서버가 UUID로 생성하고, 정규화한 경로가 설정 루트 밖으로 나가지 못하게 검사한다.

### 해결 — 로컬 실행과 실제 Redis 통합 테스트의 책임 분리

수정 전 다음 두 테스트는 Redis 연결 거부 때문에 업무 코드 실패처럼 빨갛게 표시됐다.

- `GroupBuySlotGateIntegrationTest.concurrentHydrationOnlyAppliesDbTruthOnce`
- `GroupBuySlotGateIntegrationTest.onlyTargetParticipantsGrantsSucceedUnderConcurrency`

로컬 프로필은 `ConcurrentHashMap.compute` 기반 단일 인스턴스 원자 게이트를 사용하도록 분리했다. 정원 확인·초기 DB 값 hydration·증가가 한 연산 안에서 이뤄져 같은 프로세스의 동시 요청이 정원을 넘지 않는다. 배포 환경은 설정 기본값이 `false`라 기존 Redis Lua를 그대로 사용한다.

DB 동시성 테스트는 로컬 원자 게이트로 실행해 외부 환경과 분리했고, Redis Lua 자체 통합 테스트는 Redis가 실제로 응답할 때만 실행한다. 전체 백엔드 회귀 결과는 350개 중 실패 0, 통과 348, Redis 조건부 건너뜀 2다. 실제 분산 인스턴스 원자성의 최종 증명에는 여전히 CI Redis 또는 Testcontainers가 필요하다.

### 해결 — 공동구매·반품 식별자를 JSON string으로 통일

수정 전 API 명세 1.5의 식별자 문자열 규칙과 상품 DTO의 문자열 응답과 달리 공동구매 `id`, `productId`, 참여 `participationId`, 반품 `id`가 JSON number로 반환됐다.

프론트 런타임 검증에서도 다음 오류가 실제로 기록됐다.

```text
id: expected string, received number
productId: expected string, received number
```

공동구매 공개·판매자 응답의 `id`, `productId`, `categoryId`, 참여자 응답의 `participationId`, 반품 목록·상세의 `id`, `participationId`, `groupBuyId`를 문자열로 변환했다. 실제 API JSON에서 모두 따옴표가 있는 문자열로 반환되고 프론트 Zod 계약과 일치함을 확인했다.

### 해결 — 빈 목록에서 프론트 계약 검증 오탐 제거

수정 전 `unwrapPage`가 항상 `data[0]`을 Zod 스키마로 검사했다. 빈 목록이면 `undefined`를 검사해 정상 HTTP 200 응답에도 `expected object, received undefined`를 출력했다.

검사 대상을 `data.length > 0`일 때의 첫 항목으로 제한했다. 비어 있지 않은 응답은 기존처럼 첫 항목의 계약 오류를 잡고, 빈 배열은 정상 목록으로 처리한다. 프론트 typecheck·lint·production build를 모두 통과했다.

### P1 — AI 성공 경로는 검증되지 않음

AI 서버가 실행되지 않은 상태에서 AI-01은 의도한 실패 격리 결과를 반환했다.

```json
{
  "success": true,
  "data": {
    "status": "FAILED",
    "warnings": ["AI 분석을 완료하지 못했습니다. 직접 입력해 주세요."]
  }
}
```

서비스 전체가 500으로 종료되지 않고 판매자 직접 입력으로 전환되는 것은 정상이다. 하지만 모델 서버 성공 응답과 실제 이미지 필드 매핑은 별도 AI 서버 없이는 완료 판정할 수 없다.
