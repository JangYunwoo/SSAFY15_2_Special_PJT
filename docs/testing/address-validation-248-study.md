# 배송지 전화번호 검증 수정 학습 기록 — S15P21B205-248

## 재현한 현상과 영향

2026-09-23 실서비스 QA에서 배송지 등록 API에 `recipientPhone: "abc"`를 보내면 HTTP 201이었고, 실제 내 정보 화면에도 영문 전화번호가 나타났다. 전화번호가 빠지지는 않았지만 연락처로 쓸 수 없는 값이 저장된 것이다. 잘못된 QA 배송지는 점검 종료 때 삭제했다.

새로운 격리 테스트에서는 등록뿐 아니라 수정도 재현했다. 등록 전 기본 배송지를 만들어 두고, 잘못된 번호와 `isDefault: true`를 함께 보내면 검증 없이 새 기본 배송지가 만들어질 수 있었다. 수정에서는 잘못된 번호와 수취인 이름 변경을 동시에 보냈을 때 전체 요청을 거절해야 한다. 단순히 오류 문구만 바뀌고 일부 필드가 저장되면 해결된 것이 아니다.

## 원인과 동일한 저장 경계

`AddressCreateRequest.recipientPhone`은 `@NotBlank @Size(max=20)`만 적용되어 있었다. `abc`는 비어 있지 않고 길이도 짧기 때문에 유효하다. `AddressUpdateRequest`에는 최대 길이만 검사하므로 빈 문자열도 가능했다. 회원가입 시 기본 배송지에 사용되는 `SignupRequest.AddressRequest`도 별도 입력 경로여서 함께 확인했다.

`AddressController`의 등록·수정 메서드에는 이미 `@Valid`가 있다. 회원가입은 중첩 주소에 `@Valid`가 있다. 이 경계를 활용해 형식 검사를 추가하면 서비스의 기본 배송지 해제나 저장이 실행되기 전에 요청을 거절할 수 있다.

## 구현과 선택 기준

S15P21B205-247에서 추가한 `AccountInputPatterns.PHONE_DIGITS`와 오류 문구를 재사용한다. 전화번호는 기존 FE와 API의 계약처럼 숫자 전용이며 0으로 시작하는 ASCII 9~11자리다. 02 일반전화, 지역 전화, 휴대전화·070 형식을 함께 허용한다. 하이픈 원문을 수용하려고 영문까지 무조건 삭제하는 변환은 사용하지 않는다. `abc010...`를 정상 번호로 바꿔 받아 버리는 문제를 피하기 위해서다.

등록과 회원가입 기본 주소에서는 `@NotBlank`를 유지한다. 전화번호 필드가 없거나 null이면 등록할 수 없다. 반면 PATCH는 필드 생략이나 null을 기존 값 유지로 취급하므로 `@NotBlank`를 추가하지 않는다. null을 허용하는 `@Pattern`만 추가해, 전달한 빈 문자열·공백·잘못된 형식은 거절하고 미전달은 유지한다.

같은 PATCH DTO에는 배송 요청사항에 대한 특별한 규칙이 있다. `deliveryRequest` 생략은 유지이고 명시적 null은 삭제다. 전화번호를 검증하면서 기존 presence flag와 setter를 건드리지 않으며, 요청사항 null 삭제가 여전히 동작하는지 통합 테스트로 확인한다.

변경 파일은 AddressCreateRequest, AddressUpdateRequest, SignupRequest의 중첩 AddressRequest다. 기존 데이터 치환, DB 마이그레이션, 프런트 수정, 결제 금액·환불 로직 변경은 포함하지 않는다. 번호가 실제 개통되어 있는지 또는 수취인의 소유 번호인지 검사하는 기능도 아니다.

## 테스트 설계와 수정 전 증거

`AddressInputValidationTest`는 등록·수정·회원가입 기본 배송지의 규칙을 함께 검사한다. 영문, 잘못된 길이, 0이 아닌 시작 숫자, 하이픈, 전각 숫자를 거절한다. PATCH에서 빈 문자열·공백·탭은 거절하지만 null은 허용하는지, 등록의 null은 계속 거절하는지 구분한다.

`AddressValidationIntegrationTest`는 실제 Spring 컨트롤러와 JWT 필터, 서비스, JPA, 격리된 H2 DB를 사용한다. 잘못된 등록은 배송지 행 수를 늘리지 않고 기존 기본 배송지를 유지해야 한다. 잘못된 수정은 전화번호·이름·기본 여부 어느 것도 일부 변경하지 않아야 한다. 정상 번호는 등록·수정 후 DB를 다시 조회해 확인한다. 필드 생략, 명시적 null, 기존 배송 요청사항 삭제 계약도 포함한다.

수정 전 25개 테스트 중 15개가 실패했다. 검증 거절을 기대했는데 허용되거나 400 대신 200/201이 반환되는 실패였다. 정상 형식과 null/부분 수정 계약을 확인하는 10개는 원래 통과한다. 수정 전 XML은 로컬 `output/input-validation-20260923/address-*-before.xml`에 보관했다. 수정 후 실행 결과는 별도로 기록한다.

## 수정 후 결과와 검토

2026-09-23 Java 21 로컬 실행에서 새 배송지 테스트 25개가 모두 통과했다. 수정 전에 실패한 15개가 통과로 바뀌었고, 원래 정상 입력과 PATCH 계약을 확인하던 10개도 유지됐다. 프로필 수정(S15P21B205-247)을 포함한 전체 백엔드 회귀는 총 1,006개 중 1,003개 통과, 실패 0개, 오류 0개, 환경 미구성으로 생략 3개(Redis 2개, S3 1개)다. bootJar 빌드도 성공했다. 이 숫자는 로컬 결과이며 Jenkins 결과나 운영 배포 완료를 의미하지 않는다.

코드 검토에서는 세 입력 경로가 같은 정규식을 사용하는지, 컨트롤러의 @Valid와 회원가입 중첩 검증이 유지되는지, PATCH null의 기존 의미를 바꾸지 않는지, 잘못된 요청이 기본 배송지 교체 전에 거절되는지 확인했다. 서비스·엔티티·DB 스키마·프런트에는 변경이 없다. 별도 전용 계정으로 배포 후 HTTP 검증을 수행하고 해당 계정과 배송지는 점검 뒤 제거한다. 병합·CI·운영 검증 결과는 Jira S15P21B205-248에 별도로 남긴다.

## 재실행

Java 21에서 backend의 `gradlew --init-script ../docs/testing/full-regression-runtime.gradle test --tests '*AddressInputValidationTest' --tests '*AddressValidationIntegrationTest' --tests '*AddressRequestClearTest'`를 사용한다. 전체 회귀는 같은 init-script에 `test bootJar`로 수행한다. init-script는 테스트 프로세스에 2GB 힙과 Spring 컨텍스트 캐시 설정을 적용하며 애플리케이션 런타임 설정을 바꾸지 않는다.

로컬에서 Redis·S3 통합 테스트가 환경 부족으로 생략되면 통과로 셈하지 않는다. Jenkins의 별도 임시 Redis·MinIO 환경에서 이 테스트까지 실행한 결과와 배포 커밋을 분리해 확인한다. 운영 DB나 외부 금융망을 단위·통합 테스트에 연결하지 않는다.

## 한계와 검토 포인트

서버 검증은 신규 HTTP 입력을 막는다. 이미 저장되어 있는 실제 사용자 데이터를 임의로 정상 번호로 추정해 고치지 않는다. 과거 주문의 배송지 스냅샷도 수정하지 않는다. 주소록 수정과 과거 주문 주소는 서로 다른 책임이다.

이번 전화번호 규칙은 서비스 입력 형식의 최소 검증이다. 국제 번호·대표 번호 지원 등 요구사항이 늘어나면 정책과 FE 계약을 함께 논의해야 한다. 응답은 기존 HTTP 400, `VALIDATION_ERROR`, fieldErrors 형식을 유지하므로 화면 디자인을 바꿀 필요가 없다.

성능 최적화가 아닌 데이터 정합성 수정이다. 테스트 실행 시간을 전후 성능 개선율로 표시하지 않는다. 어떤 오류가 저장 전에 차단되었는지와 정상 입력·부분 수정이 유지되는지가 검증 기준이다.
