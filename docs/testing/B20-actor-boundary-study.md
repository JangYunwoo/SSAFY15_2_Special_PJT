# B20: 관리자 ID를 구매자 ID로 해석하지 않도록 인증 주체를 분리하기

## 1. 범위와 추적

Jira: [S15P21B205-178](https://ssafy.atlassian.net/browse/S15P21B205-178). 수정 브랜치는 `fix/be/S15P21B205-178-actor-boundary`, 병합 대상은 DevelopV2다. 수정 전 재현 기준은 개인화 추천이 병합된 `e6ae9a1`이며, 수정 후에는 참여 취소 MR !143까지 포함한 `3101c92fd9455034b4c2710c5ae1506da9337c98`를 사용한다.

이 문서는 B20의 권한 경계만 다룬다. 리프레시 토큰의 동시 재사용(B19), 잘못된 HTTP 메서드의 500 응답(B21), 결제 실행권 등은 별도 버그로 분리했다. 실제 배포 계정이나 배포 DB는 변경하지 않는다.

## 2. 증상: 숫자가 같아도 같은 사람은 아니다

프로젝트는 구매자·판매자를 users에, 관리자를 admins에 저장한다. 각 테이블의 PK가 독립적으로 증가하므로 users의 1번과 admins의 1번은 서로 다른 사람일 수 있다. JWT subject에도 두 경우 모두 숫자만 들어가고, ADMIN 또는 USER 역할이 별도 claim으로 붙는다.

기존 JWT 필터는 역할에 따라 인증을 만들지만, SecurityConfig의 나머지 경로 규칙은 authenticated였다. 이는 로그인했는지만 확인한다. 따라서 정상적으로 서명된 관리자 JWT도 구매자 API에 들어갈 수 있었다. 컨트롤러가 principal Long을 userId로 사용하면 관리자 번호를 구매자 번호로 조회한다.

격리 DB에 같은 숫자 ID의 서로 다른 구매자와 관리자를 만들고 실제 서명 JWT를 발급하여 재현했다. 수정 전에는 관리자 요청으로 구매자 프로필 조회·수정과 알림 조회에 접근했다. 결제 조회도 권한 단계에서 차단되지 않고 업무 조회에 도달했다. 테스트에서 이 요청은 403이어야 하지만 기존 구현은 그렇지 않아 실패했다.

서명 검증만으로 관리자 인증을 만드는 문제도 있었다. JWT는 발급 뒤 계정이 비활성화되거나 삭제됐는지 알려주지 않는다. 기존 코드는 admins를 다시 확인하지 않으므로 그런 토큰도 관리자 조회에 성공했다.

## 3. 선택한 해결과 배제한 대안

### 역할에 따라 해석 가능한 경로를 제한한다

SecurityConfig는 공개 API, 관리자 API, 판매자 API 순서의 기존 규칙을 유지하고, 나머지 업무 경로는 USER 역할을 요구한다. 관리자 API는 ADMIN, 판매자 API는 SELLER가 있어야 한다. 판매자는 users의 한 종류이므로 필터가 USER와 SELLER를 함께 부여하며 구매자 기능도 유지한다.

로그아웃은 두 계정 종류의 공통 인증 동작이다. POST /auth/logout에 authenticated 예외를 먼저 두어 관리자도 로그아웃할 수 있게 했다. 이 컨트롤러는 principal을 구매자 PK로 사용하지 않고 전달된 refresh token을 폐기하는 서비스로 위임한다. 공개 카테고리·공구 조회 규칙은 그대로 두었다. 공구 공개 컨트롤러는 principal을 구매자 ID로 사용하지 않는 것도 코드에서 확인했다.

각 구매자 컨트롤러마다 ADMIN 거절문을 넣는 방식은 제외했다. 새 API에서 누락하기 쉽고 동일한 보안 정책이 여러 도메인에 흩어진다. 관리자를 자동으로 같은 번호의 구매자로 바꾸거나 DB ID 대역만 다르게 하는 방식도 제외했다. 두 ID의 우연한 불일치에 보안을 의존해서는 안 된다.

장기적으로 principal을 ActorId(role, id) 같은 타입으로 만드는 방법은 더 명시적이다. 그러나 이번 패치는 모든 컨트롤러와 인증 주입 계약을 동시에 바꾸지 않고 중앙 경로 인가와 필터를 통해 노출을 차단한다. 이후 관리자 공통 API를 추가할 때도 subject의 테이블 의미를 먼저 결정해야 한다.

### 서명 검증 뒤 현재 계정을 확인한다

JwtAuthenticationFilter의 ADMIN 분기에서는 AdminRepository로 현재 계정을 조회하고 ACTIVE인 경우에만 인증을 만든다. USER 분기의 기존 활성 사용자 확인은 유지한다. 알 수 없는 역할은 USER로 추정하지 않으며 인증을 만들지 않는다.

유효한 ADMIN 인증으로 구매자 경로에 들어오면 403, 삭제·비활성 계정 등 인증 자체를 만들 수 없으면 401이다. 이 구별을 응답 테스트로 확인한다. 관리자 요청마다 DB 조회가 추가되는 비용이 있지만, 비활성 상태를 즉시 확인하려면 필요한 비용으로 판단했다. 상태 캐싱은 권한 회수 지연을 만들 수 있어 이번에는 추가하지 않았다. DB 장애가 나면 서명만 믿고 접근을 허용하는 우회도 추가하지 않았다.

## 4. 수정 전후를 확인하는 테스트 설계

ActorBoundaryIntegrationTest는 실제 SecurityFilterChain, JWT 서명·파싱, 컨트롤러, JPA 저장소와 H2를 사용한다. MockMvc로 로컬 요청을 보내되 토큰을 출력하지 않는다. MockUser로 역할만 주입하면 문제가 있는 JWT 필터를 건너뛰므로 사용하지 않았다. 스케줄러와 관리자 시드는 비활성화하고 매 테스트마다 UUID 이메일을 사용한다.

최초 12개를 수정 전에 실행한 결과 6개 실패/6개 통과였다. 실패한 것은 관리자→구매자 프로필 조회·수정, 알림 조회, 결제 조회 차단과 비활성·삭제 관리자 거절이다. 정상 관리자 환불 조회, 구매자의 관리자 접근 거절, 구매자 프로필, 공개 카테고리, 판매자 겸 구매자 조회, 관리자 로그아웃은 기존에도 통과했다. 정상 기능을 잃지 않는지 같은 테스트로 계속 검증한다.

수정 후 추가한 4개는 알 수 없는 역할 거절, 익명 사용자 보호, 비활성 구매자 거절, 같은 번호의 구매자가 판매자여도 관리자에게 SELLER 권한이 생기지 않는지다. 이 4개는 수정 전 12개 통계에 포함하지 않는다.

특히 프로필 변경 거절은 HTTP 상태만 확인하지 않고 실제 구매자의 nickname이 그대로인지도 확인한다. 조회 차단과 데이터 변경 차단이 모두 필요하기 때문이다. 판매자 권한은 JWT isSeller를 그대로 믿는 대신 현재 DB의 판매자 여부를 사용하는 기존 동작을 유지한다.

## 5. 결과와 한계

최초 12개는 수정 후 모두 통과했고, 추가 4개를 포함한 권한 통합 테스트 16개도 모두 통과했다. 전체 백엔드는 93개 클래스, 599개 테스트 중 596 통과, 실패/오류 0, 제외 3개다. 제외는 실제 Redis 게이트 2개와 S3 1개이며 외부 환경까지 검증됐다는 뜻은 아니다. 결과는 `B20-actor-boundary-results.json`에도 저장했다. Gradle BUILD SUCCESSFUL과 XML 집계를 확인한 로컬 검증이며 GitLab CI 성공으로 표현하지 않는다. 외부 결제사·배포 환경을 호출한 시험은 아니다.

관리자 화면은 별도 AdminLayout을 사용한다. 구매자 공통 SiteHeader는 로그인 여부로 구매자 메뉴·알림을 표시하는 부분이 있으므로 관리자가 구매자 페이지로 이동했을 때 403을 보일 수 있다. 이것은 관리자에게 구매자 데이터를 다시 허용할 근거가 아니다. 필요 시 별도 프런트 기능 버그로 역할별 메뉴를 정리한다. 이번 MR은 스타일을 변경하지 않고 프런트 테스트를 실행했다고 주장하지 않는다.

이 테스트는 대표 경로와 중앙 기본 규칙의 회귀 검증이지 모든 컨트롤러의 행 단위 소유권 검사를 완료했다는 의미가 아니다. 관리자 토큰 탈취, 비밀키 회전, 모든 JWT 형식 오류 처리, 동시 토큰 갱신은 별도 범위다. H2 시험을 배포 MySQL·Redis·브라우저 통합 검증으로 표현하지 않는다.

성능 최적화가 아니라 권한 정합성 수정이다. 처리량 개선 수치를 만들지 않았으며 전체 테스트 소요 시간을 응답속도 개선으로 간주하지 않는다. 관리자 DB 조회 증가에 대한 실측 부하 테스트는 수행하지 않았다.

## 6. 학습과 재실행 순서

먼저 admins와 users의 분리 구조, JwtTokenProvider의 subject/role 생성, JwtAuthenticationFilter의 역할별 계정 조회, SecurityConfig의 위에서 아래로 적용되는 경로 규칙, UserController의 Long principal 사용을 차례로 읽는다. 핵심은 인증(누구인가)과 인가(이 경로를 사용할 수 있는가)가 서로 다른 조건이라는 점이다.

backend에서 `./gradlew.bat test --tests '*ActorBoundaryIntegrationTest'`로 권한 경계를 확인하고, `./gradlew.bat test`로 전체 회귀를 실행한다. 토큰 원문·실제 계정 비밀번호·외부 API 키를 보고서에 붙일 필요가 없다.
